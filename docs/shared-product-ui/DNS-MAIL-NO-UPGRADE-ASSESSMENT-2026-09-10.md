仍须确认 sales 邮箱存在、正确配置收发认证并实测双向邮件。网站询价落库与通知邮件
是两条链路，DNS 升级不会自动打开通知功能。

本轮发布期间再次只读核对：Google 公共 DoH 返回 MX 为 `5 mxbiz1.qq.com`、
`10 mxbiz2.qq.com`，根域名 CNAME 为 `supplychainsai.com.tcbaccess.tencentcloudbase.com`。

本轮只补充评估；没有购买套餐、勾选自动续费、添加 PTR 或更改解析。

### 为什么需要处理

官网和企业邮箱都使用 `supplychainsai.com`。DNS 可以理解为这个域名的
“地址簿”：浏览网站时指向网站服务器，发邮件时指向邮件服务器。现在根域名
的网站别名记录（CNAME）与邮箱记录（MX/TXT）共存，部分解析器处理不一致。
这不是网站和邮箱不能共用一个域名，也不是要重新买域名，而是需要处理解析兼容性。
腾讯将 CNAME 展平列为解决这一类兼容问题的功能。
[功能与限制说明](https://cloud.tencent.com/document/product/302/115536)

### 我们的建议

**如果客户愿意承担当前约 ¥1,800/年的费用，优先评估留在 DNSPod 升级企业版；
如果不接受这笔持续费用，再选择 Cloudflare 免费 DNS。** 这是基于现有系统集中在
腾讯、客户希望后续好维护的工程判断，不是声称 DNSPod 技术上绝对优于 Cloudflare。

Cloudflare 是可行的免费候选，不是“免费就应该迁”。本项目使用它的主要收益
确实是免掉为展平而购买的 DNS 套餐费；只使用 DNS，不应把 Cloudflare 的网页
加速、WAF 或托管 SSL 当成本方案的收益。网站请求仍直接去 TCB。
[DNS-only 的含义](https://developers.cloudflare.com/dns/proxy-status/)

### 两个方案的真实取舍

| 比较项 | 留在 DNSPod 升级 | 迁到 Cloudflare 免费 DNS |
| --- | --- | --- |
| 日常管理 | 延续腾讯账号和现有解析记录，交接相对集中 | 新增 Cloudflare 账号、成员权限、双重验证和恢复资料 |
| 变更范围 | 原解析记录保留；按升级结果核对并更新套餐要求的 DNS 服务器 | 全量迁移地址簿、在注册商修改 NS，需要逐项防遗漏 |
| 排障 | DNS、TCB、腾讯证书集中在同一服务商体系，但仍是不同产品 | DNS 找 Cloudflare，网站/证书找腾讯，排障可能跨双方 |
| 持续支出 | 每年续费；忘记续费会失去付费功能，需安排责任人 | 无本次 DNS 套餐年费，但维护人员的时间不是免费 |
| 主要风险 | 展平本身也有超时回退及服务检测兼容限制 | 整个域名及子域名迁移风险，证书验证流程可能更分散 |

DNSPod 官方说明升级保留原记录，但付费套餐启用涉及 DNS 服务器更新；
**不能把升级说成只付款、永远不用改 NS**。先读控制台给出的服务器地址再操作。
[升级步骤](https://cloud.tencent.com/document/product/302/7805)、
[升级常见问题](https://cloud.tencent.com/document/product/302/105693)

Cloudflare 的主要缺点展开如下：

1. **新增的是长期依赖，不只是一次搬家。** 切换后 DNSPod 的记录不再是生效来源。
   以后加子域名、改邮箱验证、加证书验证记录，要到 Cloudflare 操作；维护人员若仍
   修改 DNSPod，可能出现“后台改好了但没有效果”。客户应持有账号，至少指定主备管理员。
2. **免费技术支持有限。** Free 的常规 DNS 技术问题主要依靠文档和社区；标准工单
   仅覆盖账单、账号和注册商问题，不能当成有人工响应时限的付费运维服务。
   [Cloudflare 支持政策](https://developers.cloudflare.com/support/contacting-cloudflare-support/)
3. **不只影响官网。** 切换的是整个域名的解析权威服务，必须保留已查到的 11 条记录，
   包括邮箱、验证记录及 `kb`、`marketagents`；自动扫描不能代替清单核对。
4. **证书与平台检查要验证。** 迁到第三方 DNS 后，腾讯证书验证可能需要在另一后台
   加 TXT。TCB 是否接受根域名展平后的结果仍待确认；不能承诺迁完自动续期无影响。
5. **回退不即时。** NS 和递归缓存需要传播，故障时不是点击撤销就能让所有用户马上恢复。
   需要维护窗口、新旧记录保持一致及回退清单，不能边迁边补遗漏。

这些是维护复杂度和风险，不代表 Cloudflare 必然不稳定，也不能因为它是境外服务商
就断言大陆用户一定打不开。实际目标地区的解析表现需要测试。本方案不启用网页代理。

**付费也不是免验收。** 腾讯明确指出 CNAME 展平无法承诺 SLA，递归超过 1600ms
会回退返回 CNAME；部分平台还可能提示未配置 CNAME。因此两个方案都要先验证
TCB 的兼容性，再验收网站 HTTPS 和邮箱双向收发，不能把买套餐等同于问题已解决。
[腾讯展平限制](https://cloud.tencent.com/document/product/302/115536)

## 不升级方案的技术评估

在“不购买 DNSPod 付费套餐”的约束下，候选是把 **权威 DNS 托管**迁到 Cloudflare Free，使用根域名自动
CNAME 展平；**网站仍在 TCB、企业邮箱仍在腾讯、域名注册商不迁移**。
这不是已经执行的迁移，也不能在下面的预检通过前承诺零中断。

Cloudflare 官方说明所有套餐默认支持根域名 CNAME 展平，因此无需购买
DNSPod 展平套餐。[官方说明](https://developers.cloudflare.com/dns/cname-flattening/set-up-cname-flattening/)
Free 使用完整权威 DNS 接入，需要更换注册商处的 NS，不是仅添加一条
CNAME 就能使用。[接入方式](https://developers.cloudflare.com/dns/zone-setups/full-setup/setup/)

## 迁移中保留什么

| 用途 | 迁移规则 |
| --- | --- |
| 官网 @ | 保留当前 TCB CNAME 目标；DNS-only，根记录自动展平 |
| 官网 www | 保留当前 TCB CNAME 目标；DNS-only，不增加代理/CDN 层 |
| 收件 MX | 完整保留 `5 mxbiz1.qq.com`、`10 mxbiz2.qq.com` |
| SPF | 保留现有单条 SPF；不要新建第二条冲突 SPF |
| 邮箱验证 | 保留 `qqmail4261b488` CNAME，DNS-only，不展平此验证记录 |
| DMARC | 先原样保留，报告地址更正另行确认 |
| 两条域名验证 TXT | 从原 DNS 导出逐条保留，用于现有服务/证书验证 |
| kb、marketagents | 原值保留，防止其他站点随 NS 迁移失效 |

只使用 Cloudflare DNS，不开启橙云代理、Email Routing、Workers 或更换
腾讯 MX。DNS-only 不把网页流量代理到 Cloudflare，避免把 HTTPS、回源、
缓存、跨境访问的变化混入本次修复。[代理状态说明](https://developers.cloudflare.com/dns/proxy-status/)
自动扫描并不保证发现所有记录，必须对照 DNSPod 导出清单核对，而非照单接受扫描结果。

## 执行前必须通过的门槛

1. 确认域名注册商/NS 修改权限、客户持有的 Cloudflare 账号和维护窗口。
   此次评估没有创建 zone、授权新应用或更改 NS。
2. 导出 DNSPod 全量记录及 TTL/线路/启用状态；重新核对迁移时是否仍为 11 条。
   保留原 DNSPod zone，不删除任何记录。冻结迁移窗口内的并行 DNS 修改。
3. 核查父区 DS/DNSSEC；如已启用，按双方文档处理签名切换，不能只换 NS
   留下旧 DS 导致验证失败。本次 Google 和 Cloudflare DoH 的 DS 查询均为成功空答案，未发现
   已发布 DS；实际切换前仍需与注册商配置及父区状态再次核对。
4. **核查 TCB 的根域名验证与证书续期能否接受展平返回的 A/AAAA。**
   TCB 文档以 CNAME 为常规验证方式；Cloudflare 根展平不会直接返回该 CNAME。
   这是兼容性预检，不应因为 HTTPS 此刻能打开就假定后续续期一定正常。
   保留既有绑定和验证 TXT，必要时由腾讯支持确认，不删除重建线上域名。
   [TCB 自定义域名](https://docs.cloudbase.net/service/custom-domain)
   腾讯 SSL 的自动 DNS 验证依赖腾讯解析托管，第三方 DNS 可能需要手动添加
   验证记录。迁移前需确认当前 TCB 证书采用哪种托管/验证方式；不要将普通
   SSL 产品的续期规则直接假定为本环境的自动证书规则。
   [腾讯自动 DNS 验证](https://cloud.tencent.com/document/product/400/54502)
5. 候选 zone 准备好后，直接查询分配的新权威 NS，核对 @ 的 A/AAAA、MX、TXT，
   www、邮箱验证记录和其余子域名。新旧记录逐项一致才允许切换。
6. 再次取得明确迁移批准后，仅修改 NS。该操作与网站 CI/CD 分开记录。

## 验收与回退

- 使用多家递归解析器和新权威 NS 检查 @/www、MX/SPF/DMARC/验证记录。
- 验证根域名和 www 的 HTTPS、证书、首页、Admin 登录、公开商品和 API。
- 核对 kb、marketagents，不只测试主站。
- 用已确认存在的 sales 邮箱与独立外部邮箱互相收发，查看完整邮件头中的
  SPF/DKIM/DMARC 结果；没有真实收发，不声称邮件修好。
- 不把上述邮件测试顺手扩展成开启网站询价通知或向客户群发测试邮件。
- 若出现记录遗漏、证书/解析异常，先修正候选 zone；严重问题按记录恢复原 NS。
  NS/递归缓存的生效与回退都不是即时的，因此需保留双方一致记录与观察窗口。
  当前 NS 为 `purple.dnspod.net` / `tipsy.dnspod.net`；本次查询显示 NS TTL
  为 21600 秒，不能用网页记录较短的 TTL 推断 NS 切换或回退也能立即完成。

## 不采用的捷径

- 不把当前 CDN 解析 IP 写死为根域名 A：IP 不是 TCB 承诺的固定入口。
- 不删除网站 CNAME 给邮箱“腾位置”，也不把根域名改到 mail.qq.com。
- 只保留 www 可以绕开部分根域名冲突，但根网址还需要可靠 HTTPS 重定向服务；
  这会引入新入口及 URL 行为变化，不能作为免费的无成本替代直接执行。
