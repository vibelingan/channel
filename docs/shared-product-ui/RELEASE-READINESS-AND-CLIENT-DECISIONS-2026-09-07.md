## 2. 两个错误究竟是什么

两项都是本地异常数据回归发现的问题，不是已经确认发生于线上真实商品的事故。

### 2.1 坏小标题导致旧详情 404

结构化说明同时保留纯文本 `notes` 和带类型的 `noteBlocks`。二者文本及顺序必须一致。
测试构造 `notes = ['Approved note']`，而小标题写成 `Different note`：单个字段看似合法，
但完整发布快照的跨字段校验应当拒绝。不是缺少一个可选小标题就应该 404。

旧本地批准流程先清空旧 `catalogDetailPublication`、写 SKU，再验证新快照。
因此新数据校验失败时，旧批准快照已经被清空；公开详情没有有效快照，安全地返回 404。
原始数据和产品记录并未删除，真正错误在于批准失败破坏了原先可用的公开版本。

修复：先构造并完整校验共享批准计划、检查媒体，再开始写入。
本轮回归确认错误输入被拒绝，旧版本仍可读，不能把“返回错误”作为唯一通过标准。

### 2.2 SKU 身份错绑没有在批准前拒绝

假设 A 商品的 SKU 数据库行 ID 是 `a`，B 商品的是 `b`。
如果 A 行里嵌套的候选数据错误地声明自己的 ID 为 `b`，旧逻辑没有交叉核对身份，
便可能按嵌套 ID 把 A 的批准内容写到 B 的 SKU 行。这不是正常的同名/同款 SKU 合并。

修复：批准前核对商品归属、来源归属、候选 ID 与数据库行 ID、重复 ID 等约束；
任一不一致立即拒绝，不能靠前端筛选保证安全。
本轮回归确认 A 的旧详情与 B 的 SKU/详情均不被这种输入改写。

两项修复见 [09A](CUI-09A-APPROVAL-PREFLIGHT-2026-09-07.md)。
**仍有边界：写前校验不等于事务。** 多记录写入期间断进程、并发同步或另一个管理员批准，
仍需要下一步正式持久化的版本检查、原子切换及失败恢复；本地 CLI 不能直接变成线上 action。

## 3. 生产 E2E 是否需要批准真实商品

需要覆盖真正的公开路径，但必须在正式接线及 CI/CD 发布完成后。
后台私有预览不能证明匿名买家路径正确；当前公开访问还要求 published 和有效批准快照，
仅有来源同步数据并不足够。生产 E2E 的公开样本会真实对外可见，不能把“test”当安全沙箱。

建议发布验收顺序：

1. 本地用隔离数据完整覆盖正式路由及真实 handler/adapter 边界，不读写用户现有样本记录。
2. 同 SHA 完成 CI/CD；先保持新功能关闭，回归旧列表、详情、媒体、Admin 和 OEM。
3. 私有云端验收：同步/候选数据、批准校验、存储资源和权限。资源隔离环境如需新建须另行授权。
4. 用户明确授权具体商品 ID、公开内容/价格/图片后，开放 2–3 个代表性样本，邮件仍关闭。
5. 无 preview 参数、匿名买家走列表 → 详情 → SKU/数量 → RFQ；Admin 查看 → 跟进 → 完成 → 重读验证。
6. 检查持久化记录和提交时快照，而非只看成功提示；回归后才逐步扩大开放范围。

公开正例宜有：多 SKU 阶梯价耳机、不同规格/图片的另一商品；无可用价格的询价商品可作为第三类。
未批准/未发布必须另作负例。还需覆盖过期 revision、重复提交/响应丢失、跨商品 SKU、
两管理员并发、权限拒绝、私有媒体不泄露、历史询价不随商品更新漂移。
这些不要求每种都用真实公开商品；破坏性和对抗测试应尽量在隔离数据完成。

本轮不执行真实批准、发布、询价或邮件发送，也不删除已产生的用户询价记录。

## 4. 分类问题：三个不同概念

| 字段 / 概念 | 含义 | 决策边界 |
| --- | --- | --- |
| 网站 productFamily | Headphones / AI Gadgets / Toys / Other Electronics & Toys 对应导航 | 客户定义经营范围与归类 |
| 旧 products.category | wired / office / bluetooth，原耳机筛选枚举 | 不是 Alibaba API 类目；连接方式和使用场景可能重叠 |
| Alibaba category_id | 来源平台类目 ID，名称/路径仅在有来源依据时采用 | 需要映射，不能仅凭名称猜测网站 family |

9 月 4 日历史审计记录：1,074 个 Alibaba 草稿中 716 个已映射 Headphones，358 个未分配网站 family，
包括钟、风扇、灯、马达等。这是历史样本统计，本轮没有重查当前线上数量。
这些商品已 materialize，不是 API 漏同步；其他标签空不能推出来源只卖耳机。
来源类目证据仍保留；补充网站映射通常不需要重新 OAuth 或整批拉取商品。
缺失的来源类目名称/路径如需补齐，则是单独的元数据获取问题，不能编造。

遵守现阶段暂停分类调整的决定：未映射数据保留后台草稿；不一律塞进 misc、不猜 AI、不自动创建公开分类。
分类确认不阻塞已确认耳机的正式接线，但阻塞这些未归类商品的规模化公开。

### 9 月 7 日进一步澄清：不是 Alibaba 缺少主分类配置

“旧页面有 wired/office/bluetooth”表述过宽：本轮确认的是仓库里的旧字段、
`packages/shared/src/catalog-product.ts` 的枚举，以及 `apps/site/src/i18n/content/catalog/en-US.md`
的前台筛选配置；未证明用户当时访问的线上页面正在展示三个筛选。Admin 四个 family 标签不是这三个值。

实际 `apps/functions/alibaba-catalog-sync/src/linking.ts::mappedCategory` 的规则：

1. 查 `sourceCategoryMappings`，键为 `provider=alibaba + sourceTaxonomy=alibaba:icbu + sourceCategoryId`，
   取我们配置的 `productFamily` 和可选 `channelCategory`。
2. 未得到公共 family 时兼容旧 `alibabaCategoryMappings`；如果有旧 `channelCategory`，
   代码显式补 `productFamily='headphones'`。这不是 Alibaba 直接返回官网 Headphones 主类。
3. 没有可用映射就不填网站 family，但仍创建未发布商品并保留来源类目 ID。

因此“358 个没有分类”应精确说“358 个没有官网 family 映射的草稿”；本轮已重新只读确认此数量。
来源有 category ID、不带完整名称路径，不能推断商家未配置主类或只配置子类。

上游变化的当前代码行为：同一来源 ID 改名不改变按 ID 的映射；商品换成另一来源 ID 时需要新映射判断。
`reconcileLinkedDraft` 只给系统生成、未发布、待审核、且 family 尚未填写的草稿补值；
它不会覆盖已有非空 family。所以已有网站分类**不会自动跟着换**，也可能在源类目变化后变旧。
需要补来源类目/映射版本差异提示和受控重新归类；当前不宣称该整套 taxonomy 变更流程已经实现。
运营者修改映射表同样不是一次自动批量重分类。分类已恢复推进：CAT-01 待分类队列本地完成，CAT-02..04 负责规则预览、例外与受控批量应用，业务映射仍须确认。
