## Recovery Work Implemented

### Server: retain results when a later row is uncertain

**What / why:** a guard, mutation or readback exception after an earlier successful
write could discard the page's confirmed results; lease-release failure could mask
them too. The server now retains confirmed rows, marks the uncertain row `error`,
stops later writes with `write-unconfirmed`, and preserves results while appending
`lease-release-unconfirmed` when release cannot be confirmed. Private error text is
not returned.

**Tests written / validation:** injected failures before/after commit, during
readback/lease renewal, combined write/release failure, and thrown/false release;
assert retained outcomes, no later writes and no private error leakage. The server
regression suite's 50 passing tests are reported above. **Result:** implemented,
included in the active release, not live-repair exercised. **Engineering rationale:** a page is not an atomic all-or-nothing
write; preserve confirmed evidence without counting a possibly committed row as
verified or attempting an unsafe rollback.

### CLI: retain attempts before validation and prohibit replay

**What / why:** the CLI previously validated a response and public readback before
saving the response, losing partial evidence on failure. It now persists a pending
attempt before the request and the received response before validation. Failures
retain the checkpoint, mark the attempt `unconfirmed` and manifest
`reconciliation-required`, and reject reuse of that manifest.

## Required Recovery Procedure

1. On partial/ambiguous apply, stop. Retain the original private manifest, page plan,
   hashes, `page.attempt`, any response and last confirmed `nextApplyIndex` with
   restricted local permissions (0600). A lost response is not proof of no write.
   Do not edit status/hashes, advance the cursor or rerun the old manifest.
2. Reconcile **every originally planned eligible product**, not only acknowledged
   `repaired` rows. Include the uncertain row that may have committed and later
   untouched rows, across attempted pages and the unattempted remainder. Read each
   current full product through authorized access; match its own product/link/source
   identity, its own planned proposed price (currency, amount and tiers), and its
   retained `protectedHash` using the repair's canonical hashing rules. Only the
   allowlisted internal revision/timestamp differences are exempt from preservation.
3. Record each row privately as confirmed applied, unchanged/not applied, or
   conflicting/unresolved. An unchanged price is not a successful repair; an equal
   price is insufficient if protected fields differ. Investigate mismatches and
   concurrent edits without overwriting them. Missing reads remain unresolved.
4. For published records, verify the public API against the current effective price;
   for confirmed repairs it must match that product's proposed price. Include
   uncertain-but-committed rows even when the server never marked them `repaired`.
   Verify protected approved detail/receipt state separately. Preserve private
   readback/preview evidence for drafts. Do not treat a fresh `valid-source` label
   as a substitute for these checks.
5. Resolve every uncertainty and failed public/preservation check, and confirm the
   primary sync lease (exclusive permission to write source-linked products) is
   idle/released through its normal fenced ownership rules. Do not force-release a
   lease, change scheduler configuration, bypass a hash or auto-rollback products.
6. **Only after reconciliation**, create a new full audit under a new manifest name
   against current records and the verified API origin. Never replay the old
   manifest. Review the new eligible/deferred outcomes before bounded apply, retain
   both evidence sets, then repeat private/public verification and the full audit.
