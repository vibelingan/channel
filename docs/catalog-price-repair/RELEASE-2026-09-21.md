## Release Failure and Approval-Guard Fix

existing approval step. Both PR CI `35528796338` and Deploy Test `35529373564`
returned the exact error `Review and approve current product details before publishing`

the last verified public health reads still showed `fd6c1b4` for all three services.
These are the earlier failed attempts, not the status of the now-successful PR CI
or the latest test release cancelled on the job time limit.

**What / why:** the root approval guard was too broad: it required current-detail
approval even for a non-price save that did not request publication or change
pricing. The five-file fix makes handler/database `requireDetailApproval` apply
to publication or pricing changes. Inside the transaction, pricing changes are
determined against the existing row using all five editable price inputs:
`catalogPricingMode`, `manualCatalogPricing`, `unitPrice`, `wholesalePrice` and
`moq`. Explicit publish still requires the full detail fingerprint check.
Non-price saves retain the existing publication state and approved snapshot.

**Tests written / validation:** a valid real approved product reproduced the
failure before the fix (RED); 160 tests passed afterward. Independent review
found no blocker. The first post-fix browser run passed public 41, catalog 87 and
formal 6, then failed taxonomy on a hidden link. An unchanged complete rerun
passed public 41, catalog 87, formal 6 and taxonomy 1. No tests were relaxed and
no menu code was changed. The rerun establishes a passing local run, not a proven
race diagnosis. Subsequent full root tests completed with zero failures and the

**Result:** locally verified and independently reviewed; code `8dfd51b` and docs

**Engineering rationale:** compare submitted prices with the existing row within

## Recovery Work Implemented

### Server: retain results when a later row is uncertain

**What / why:** a guard, mutation or readback exception after an earlier successful
write could discard the page's confirmed results; lease-release failure could mask
them too. The server now retains confirmed rows, marks the uncertain row `error`,
stops later writes with `write-unconfirmed`, and preserves results while appending
`lease-release-unconfirmed` when release cannot be confirmed. Private error text is
not returned.

**Tests written / validation:** injected failures before/after commit, during
readback/lease renewal, combined write/release failure, and thrown/false release;
assert retained outcomes, no later writes and no private error leakage. The server
regression suite's 50 passing tests are reported above. **Result:** implemented,
not deployed. **Engineering rationale:** a page is not an atomic all-or-nothing
write; preserve confirmed evidence without counting a possibly committed row as
verified or attempting an unsafe rollback.

### CLI: retain attempts before validation and prohibit replay

**What / why:** the CLI previously validated a response and public readback before
saving the response, losing partial evidence on failure. It now persists a pending
attempt before the request and the received response before validation. Failures
retain the checkpoint, mark the attempt `unconfirmed` and manifest
`reconciliation-required`, and reject reuse of that manifest.

**Tests written / validation:** transport loss, partial acknowledgement and failed
public readback prove durable attempt/response storage, no checkpoint advance and
no replay. CLI suite: 6 passed. **Result:** implemented, not live-exercised.
**Engineering rationale:** a failed request can still have committed writes; a new
audit alone could classify them as already valid and omit their preservation checks.
Earlier coverage did not prove retained multi-row results and durable failed-attempt
evidence together; these regressions exercise those failure paths explicitly.
