# 官网客服与企微任务控制：交互设计补充

2026-10-28。本轮由用户要求补齐设计；本文件是待确认的建议，不表示企微控制已经实现或上线。官网 UI 原型不改产品代码。后台只推进不依赖控制交互的 SG2.3 成果归档切片。

## 建议采用的方式

企微保留一个主要工作入口。正常运行默认静默，待人处理或遇到异常才发标准任务消息。销售通过任务卡片上的按钮，或引用带任务短号的通知，提出操作；系统明确回复这条任务是否操作成功。详细日志留在 Hermes，讨论某条询盘可转入与同一机器人的私聊，不要求销售另开群或记住技术 ID。

这些任务属于客户的 Hermes Sales 流程。Channel 保存询盘、产品等业务事实，不新增一套 Agent 控制中心。Resend 展示邮件、草稿和附件；Hermes 记录任务、控制命令和成果版本。官网买家的对话又是一层独立交互：停止当前回答不暂停已提交的销售任务。

## 当前实际有什么

本轮读了销售分支 `f3937ea` 的 Hermes 源码，并核对相关文件与 GitHub main 的 blob 身份；最终审计保存在交付目录 `wecom-source-audit.md`。这是源码结论，未登录服务器核对实际部署配置。

- 当前网关有同一聊天会话忙时中断、排队和引导当前回答的机制。新消息可能中断一次模型回答；它不是面向独立 task 的暂停、接管协议。单独新建通知机器人也不会自动改变此机制。
- 当前 WeCom adapter 保留引用文字，但 `reply_to_message_id` 写的是 `quote:本次入站消息ID`，不是被引用的原消息 ID。因此不能凭这个字段精确定位任务。
- 当前 Sales 有事件接收、运行受理和读取授权查询，没有面向销售人员的暂停、恢复、接管或审批接口。SG2.4 证明的是“任务状态已在库里改变之后，读取门禁会拒绝”，不是“暂停按钮已经交付”。
- 现有门户并不等于客户实名审批系统。客户级访问凭据不能替代每位销售人员的身份和角色。
- 当前官方智能机器人 SDK 有模板卡片、按钮事件和卡片更新能力；现有适配器还未完整接入这些事件。具体限制与正式来源以审计文件为准，不能拿群 webhook 通知能力冒充双向控制。

## 为什么不建议每个阶段都播报

以用户举的 50 条询盘为例，假设每条有 6 个内部阶段，逐阶段播报就是 300 条消息；即使压成每条 3 条，仍有 150 条。新建一个“状态群”只是把消息搬过去，不能解决信息量。

建议默认策略：

| 事件 | 群里默认显示 | 私聊与主动查询 |
| --- | --- | --- |
| 已接收、排队、查资料、生成中 | 不逐条发 | 问“我的待办/进度”时返回当前任务列表 |
| 草稿可审阅、资料需补充 | 按负责人合并待办；通知频率可调 | 有权限且具备私聊送达条件时定向通知 |
| 生成 token、内部工具日志、普通重试 | 不发 | 运维日志或任务详情按需查 |
| 权限异常、长时间阻塞、发送结果不明 | 通知负责人；严重或超时再升级群提醒 | 显示处理建议，不自动继续外发 |
| 人发起的暂停、改稿、接管、恢复 | 必须有简短回执 | 原入口回复，带任务短号和实际结果 |
| 已发送、完成 | 合并进结果摘要；主动发送时给回执 | 可查看邮件与执行记录 |

通知数字是设计估算，不是接口限额或实测吞吐。举例：50 个待审任务若按每 10 个合成 1 条待办摘要，就是 5 条摘要，而不是 50 条完成通知；任务仍有 50 次人工审核，不能靠摘要假装省掉审核。发送结果不明不参加静默合并，要即时处理。负责人私聊是否能主动送达需在接入时验收；不能私聊时就在已获准的群按负责人合并摘要，不丢通知。

## 三种界面安排与选择

| 安排 | 适用情况 | 代价与结论 |
| --- | --- | --- |
| 一个工作群，关键待办与控制共用入口 | 第一阶段；现有团队已在群里工作 | 建议默认。先用合并通知和按需查询控制噪音 |
| 增加一个“销售待办”群 | 主工作群还在讨论内容、任务较多 | 可选。新群只放任务摘要、操作与回执；详细日志仍不上群 |
| 每任务一个群或强制到网页操作 | 极少数需长期多人讨论的案件 | 不作为默认。50 个任务会制造 50 个空间或大量页面切换 |

“告警机器人”作为程序通知服务值得保留，但第一期不必因此多一个可见机器人账号。通知程序可使用同一授权机器人身份发标准消息，模型不负责推断状态，也不用为播报状态调用大模型。若为了运维告警分开机器人，双向任务控制仍需智能机器人或有身份的应用入口；单向 webhook 不能接收销售的回复并执行控制。

## 一条可操作的任务消息

示例数据，不是真实客户：

> Q-1042 · ACME · 官网询盘 · 500 份耳机礼品  
> 待审阅：跟进邮件 v3，附件 2 个；尚未发送。负责人：李销售。  
> 建议按钮：查看邮件 / 改稿 / 暂停 / 更多。  
> 更多：人工接管 / 查询状态。具体发送须明确针对当前邮件版本。

人可以引用它说“暂停这条”或“改成先问目的地，不写交期”。回执例如：

> Q-1042 已暂停。不会发起新的工具操作或发送。已保存 v3。  
> 可选择“继续准备”或“由我接管”；继续不会自动发送或恢复旧批准。

如果后台尚未确认停止点，先回复“Q-1042 暂停请求已受理，正在停止当前步骤”，不能先说已经完全停下。如果已有外部请求提交，则回复“Q-1042 已禁止后续动作，正在核对此前发送结果；暂勿重复发送”。系统不能承诺撤回已发邮件。

## 如何保证控制的是那一条

1. 通知服务从已提交的任务事实生成卡片，保存客户、任务、群、消息引用、显示版本和通知事件的关联。卡片里的短号帮助人看懂，不承担授权作用。
2. 优先用卡片按钮携带服务器绑定的 task 引用。当前 quote 回调没有可依赖的原消息 ID，引用路线需从引用正文中读出服务端签发的不透明短引用，再查持久映射。引用卡片可能不带正文，必须提供文本短号备选；不能保证时引导选择，不猜。
3. 验证回调来自官方通道，再根据实际 userid、企业、客户绑定及角色检查操作权限。知道短号、复制别人的通知或加入群，都不增加权限。引用是定位依据，不是授权凭据。
4. “停一下”“继续”“把它发掉”没有可用任务引用时，先返回有权限的候选列表。即使当前看起来只有一条任务，发送、接管等重要动作也要求确认对象；禁止按聊天最近的一条、模型记忆或群名猜任务。
5. 命令用入站事件和动作生成幂等 ID，持久保存操作人、目标、结果；重复回调返回原回执。模型只把普通话转成候选动作与修改意见，最终对象、角色、版本和状态由服务验证。
6. 暂停/接管针对定位到的当前任务；旧通知也可以请求暂停。批准发送则绑定最新的收件人、发件人、正文、附件和版本，旧 v2 的批准不能发送 v3。已完成或已取消的任务返回事实，不悄悄新建任务。

这套控制必须放在任务级后端，不能只在 prompt 写“请找对任务”。

## 讨论细节：不要模拟不存在的群线程

企微群里的引用不等于独立线程。短操作在群里完成并给回执；长篇改稿、业务讨论建议私聊同一机器人。私聊顶部/首条信息显示“正在讨论 Q-1042 · ACME · 跟进稿 v3”，每次产生控制命令时仍带明确任务引用。切换任务必须选择或引用，不靠长期保持一个隐含的“当前任务”。

如果没有已验证的私聊送达能力，不宣称系统能自动开侧边会话。可以让用户主动进入机器人私聊，并带任务短号；或留在群里进行少量有任务标识的问答。群里只同步“改稿已受理、v4 已准备、仍待审批”这种结果，不复制私聊全文。

被动保持群清爽也不能表现成不理人：每条被受理的操作都须回复已定位的任务、实际状态与下一步；不能识别就明确说明并列候选。无权操作返回不泄露其他客户细节的拒绝。

## 暂停、停止、接管、恢复分别意味着什么

| 操作 | 对哪一层生效 | 可见结果与后续 |
| --- | --- | --- |
| 官网 Stop generation | 当前买家的这一次回答 | 保留已生成内容和问题，可继续提问；不撤销已提交询盘 |
| 暂停销售任务 | 已定位的 Hermes 任务 | 先阻止新动作、撤旧批准，再记录停止点；人另行恢复 |
| 停止此任务 | 取消已定位的业务任务 | 需要确认；终态保留证据，不能用一句“继续”偷偷复活 |
| 人工接管 | 同一任务的执行和发送归属 | 先撤销代发权限；若在途结果不明先对账，再交人工 |
| 继续准备 | 已暂停任务 | 重新核对最新需求/来源并创建获准运行；旧批准仍失效 |
| 交回 Agent | 人工任务 | 明确交回，读取人工修改后的事实，生成新审核版本 |

当前每任务只有一个 run 的存储与入口尚有限制。恢复/交回所需的新 run 与上下文切换还需后续实施；本轮设计不宣称这些入口已经存在。

“暂停”和“取消”不是同一个按钮；群里的“停止”含义不清时，先让人选择“暂停，可恢复”或“取消本任务”。紧急全局停发是单独的高权限操作，不能从“停一下”推断成停止全部客户任务。

## 完整邮件在哪里看

正文、HTML 版式和附件仍需要一个完整审阅表面。Resend 原有工作台优先复用；如果直达草稿或私有预览体验不足，再用 Hermes 现有产品门户增加单条任务的成果预览，不复制 Channel 任务中心。

日常查询、暂停、改稿意见和接管不应强制跳网页。真正需要看 HTML/附件时允许在企微内打开预览，尽量用已有账号或企微授权保持登录；这是设计目标，不是声称当前已接好免登录。预览链接不授予权限。多入口审批可共用同一后端，只有具体个人身份和角色确认后才开放网页批准。

审批回执应写明“Q-1042、收件人、跟进邮件 v3、附件 2 个”，重要字段不能只回复“好的，已发”。“内容不错”“可以了”仍需要结合明确目标和发送意图；不含发送意图时只保存审阅意见。

## 官网 UI 的设计覆盖

独立原型、状态清单及入口/退出规则见 `output/design/2026-10-28-assistant-controls/assistant-ui.html`、`screens.json`、`assistant-ui-spec.md`。沿用真实网站组件与视觉，不在销售分支实现另一份官网助手。设计覆盖接待、输入后等待、检索/工具、回答、产品与比较、澄清、能力边界、失败恢复、停止、历史、询盘确认/提交/成功和人工入口。

每个输入应最终有答案、澄清、明确拒绝或可恢复失败；不得空白等待。产品工具和完整卡片是未来设计，不能因为原型能点就说模型已经支持。关闭面板、停止回答、发出询盘是不同动作；提交成功不意味着销售邮件已经发送。

## 后续实施顺序与验收

1. 先修官网可用性、等待与恢复，复用已有 Phase 2 部分工作；不把本轮静态原型合进线上组件。
2. 完成来源核验/授权签发和成果归档，再接 Sales 生成闭环。SG2.3 本轮实施只覆盖经验证的归档范围。
3. 实施 SG5.1 任务控制、个人身份和精确命令；不沿用通用聊天中断作业务暂停。
4. 实施最小企微任务卡片、引用备选、通知合并及回执，受控演练；SG5.2 只按需要补完整预览。
5. 最后才接审批和真实外发，覆盖并发/重复/旧版本/发送结果不明/人工原生发送竞争。

必须验证：100 个任务中精确暂停一条；新 @ 消息不取消其他任务；引用错客户/伪造短号拒绝；同人并行聊两条任务不串线；重复点击只执行一次；旧卡片暂停当前任务有效、旧批准不能发送新稿；暂停后迟到成果不发布；已提交发送不假报撤回；无私聊权限有可见退路；批量待办只发摘要；聊天噪音量与人工操作回执分别计数。

未定的业务输入仍是审批人员、承诺范围与告警升级负责人。通知间隔、每批条数先作为可调工程默认，不再让客户决定协议或事务细节。
