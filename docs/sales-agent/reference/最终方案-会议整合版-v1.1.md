# AI 获客、询盘跟进与客户维护：会议整合版 v1.1

2026-10-14。整合 Brian 的 v1.0、我们的 v0.4、今天短会及最新 comments。供同事复核和客户确认方向，尚未实施。原稿与旧版保持不变，本版额外提供图文 PDF。

## 方向与范围

先打通一套能减少客户工作量的流程：官网和主动获客带来需求，现有 Agent 团队帮助查资料、准备邮件，客户确认后联系；各渠道联系人统一进入客户自己的 Resend。主动获客、询盘跟进和客户维护分别配置业务流程，共用 HermesInfra、企微、同步服务和邮件工具。

今天会议确认三类主要入口：官网表单、官网 AI 悬浮助手、Apollo 主动获客。官网内部的首页 OEM、单品表单、智能客服确认提交，仍统一形成正式询盘。阿里国际站、环球资源、展会等作为已有联系人来源接入统一管理。

## 系统与人员分工

| 部分 | 负责什么 |
|---|---|
| 官网与 Channel | 智能客服接待、引导并确认需求；保存正式询盘与产品快照，提供授权业务资料和必要回执 |
| HermesInfra / 定海 | 复用现有 Agent 中枢，协调和分派获客、销售准备、内容与发布任务 |
| Sales 能力 / 内容创作 | 查询产品、理解需求、生成建议、邮件正文和附件；是否复用内容工厂或另设岗位，在实施时确定 |
| 发布助手 / 邮件执行 | 按批准内容执行发送并留下结果；管理发布侧的联系人同步服务 |
| 独立同步服务 | 定期或按事件汇总各渠道联系人，保留来源、业务和联系资格；作为程序服务运行，不让模型负责记住轮询 |
| 企微 | 日常 Agent 入口，通知、查询、改稿、确认、暂停和接管；网页也可以调用同一审批能力 |
| Resend | 客户自有的联系人与邮件工作台，保存联系人、当前草稿、会话及收发结果，客户可人工操作 |
| Apollo | 主动寻找潜客并按获批活动开展冷外联；有回复后按意图处理和交接 |
| 客户负责人员 | 判断商务承诺，核对邮件与附件，批准实质发送，跟进回信或接管 |

Channel 第一阶段不增加通用 Agent 任务管理页。询盘和产品事实继续留在 Channel；邮件操作集中 Resend，Agent 日常操作延续企微。平台、同步服务与官网业务解耦，方便以后复用；当前先验证这一客户的流程，不承诺已经成为可直接打包销售的标准产品。

## 官网询盘流程

![官网询盘与邮件跟进](client-images/02-website-flow.png)

1. 首页 OEM、单品表单或智能客服确认提交，Channel 保存询盘与相应产品资料。只聊天、未提交不算正式询盘。
2. 保存成功自动触发销售准备，销售不用再下“开始处理”的指令。固定确认信经 Resend 自动发一次，模板提前批准。
3. 定海将工作分派到现有 Agent 体系的 Sales 能力。Agent 查询授权需求和产品资料，生成产品建议、HTML 正文及所需附件；缺价格、交期等真实依据时请人补充。
4. 邮件草稿保存在 Resend，企微通知负责销售并提供完整查看入口。销售核对收件人、正文、图片和实际附件，可以反复要求 Agent 修改。
5. 销售通过企微或网页批准确定的任务、收件人和正文附件版本，发布助手按批准内容调用 Resend 发送。两个入口共用一个批准状态，重复确认不重复发送。
6. 买家回信后，关联原询盘/会话并通知负责人。第一期由人跟进，必要时让 Agent 继续分析和拟稿；不把每轮回信自动创作、自主回复或自动定时追信作为当期必需功能。

这里的“Agent 不自动发邮件”，指它不能自行决定实质对外发送。人批准之后由系统执行发送，仍然可以自动化；固定确认信采用预批准模板自动发送。Apollo 开发活动和 Resend 维护活动，按已批准的受众、内容与范围执行，变更后重新确认。

人工在 Resend 编辑或发送前进入接管模式，Agent 停止覆盖和后续外发。新来信、改稿、收件人/附件变化、暂停或接管都会使相关旧批准失效。无法准确确认对象或当前稿时，保留人工发送兜底。

## 联系人统一入库，判断与发送分别处理

![联系人同步与回复分流](client-images/03-contact-intent.png)

无需在 Apollo 和 Resend 之间再加一个独立 AI 系统。同步服务做固定的数据汇总，联系人可以先进入 Resend 并标记来源和待判断状态；现有 Sales/协作 Agent 辅助理解回复意图，明确规则先处理，不明确时通知负责人。

| 情况 | 处理规则 |
|---|---|
| 明确采购需求 | 交销售准备或负责人跟进，调用该业务允许的产品和资料 |
| 明确同意相应营销联系 | 进入对应维护分组，活动仍由人确认 |
| 拒绝、退订 | 停止相关联系，保留禁止联系记录，避免再次导入后重新发送 |
| 休假等自动回复 | 按暂停规则处理，不当成采购或营销同意 |
| 一般咨询、模糊回复或无法判断 | 保留记录并通知人确认，不自动升级为营销对象 |

Apollo 收到回复后先暂停或停止适用的开发活动，再分类处理。联系人同步不表示原邮件会话已经搬到 Resend，也不表示客户已同意新品营销。具体采购交接与后续会话由实施方案衔接。

同一联系人可以来自多个渠道，也可能参与多个业务。来源说明从哪里来；业务范围决定能使用哪些产品、价格、附件和发件身份。共享名单不会自动生成官网询盘或套用 Channel 报价。

## 给人和 Agent 共用的使用规则

人需要规则来决定联系谁、批准什么；Agent 也需要规则来分类、推荐人群和拟稿。即使最后由人确认，错误的分组或建议仍可能造成误联系，所以规则同时进入人员操作说明和 Agent 岗位指引。

第一期保留几条明确规则即可：入库不等于营销许可；拒绝和退订停止联系；不明意图交人确认；产品与报价按业务授权；没有商务依据不自行承诺；实质发送必须有适当批准。执行工具也要遵守禁止联系与批准要求，不只依赖模型自觉。

## 邮箱与记录

业务邮件统一规划经 Resend，保留官网公开地址。腾讯企业邮可继续收信并转入 Resend，表单与直接采购来信不必拆两个地址。原企业邮和 Resend 的已发送、已读和人员分派不自动同步；一期不额外建设完整邮箱同步。

官网当前旧邮件路径先保留。本轮没有改代码或邮箱；正式启用统一确认路径前停旧询盘确认动作，避免双发。确认信、Sales 任务和联系人同步各自触发，联系人同步失败不阻塞确认和销售准备。

Resend 保存当前草稿、联系人和邮件会话；Hermes 持久保留任务、成果版本、最终附件及批准/执行记录；Channel 保存询盘、产品资料和必要的业务关联。群聊和机器人临时文件不作为唯一档案。

## 能力判断与实施边界

基本方向有官方能力支持：Apollo 提供潜客搜索、邮件和 sequence 相关 API/MCP；Resend 提供联系人/分组、邮件草稿、发送、收件与事件接口。我们需要完成 Agent、官网和这些服务之间的整合。

本版不再讨论接口字段、锁、重试或页面路由。原生预览、审批操作、会话交接、渠道接入和异常处理由实施团队按以上业务原则设计并验收。Resend 按用户既定的全功能可用条件规划；不把能力开通重新变成业务会议的问题。

这轮未登录客户账号或进行联调，所以“具备基本实现能力”不等于“已完成客户环境验收”。具体渠道获取方式和账户服务授权按实际接入落实，不承诺所有渠道已实时同步，也不增加未经确认的名单所有权、客户数量或开发周期承诺。

## 仍需客户确认的业务事项

1. 每类询盘由谁负责，谁可批准价格、交期和附件，负责人不在时谁接替？
2. 产品、价格、MOQ、交期和附件以什么资料为准，由谁维护；确认信是否保留“24 小时回复”？
3. 第一批接哪些渠道和业务，哪些人群允许进入维护活动，归属不明邮件交给谁？
4. 人工接管时的日常操作如何分工，谁继续跟进，何时交回 Agent？
5. 哪些最终内容与记录需要留存，保存多久、谁可看；Channel 当期需要显示哪些结果？

预览与审批的技术衔接由我们给出方案，不再请业务方决定技术路线。客户确认方向和上述事项后进入实施，先小规模验证，再根据效果优化与复用。

## 第一轮应验收的业务结果

- 三种正式官网提交均自动开始准备正文和附件，未提交咨询不触发；确认信只有一封。
- 所看、所批准和实际发送属于同一任务、收件人及版本；重复确认不双发。
- 改稿、新来信、暂停或接管能阻止有关旧稿；人工处理不与 Agent 竞争。
- 回信通知负责人，并能按需获得 Agent 拟稿帮助；第一期无需依赖全自动回信循环。
- 多渠道联系人保留正确来源和业务；拒绝、自动回复、采购意向与营销许可分别处理。
- 错误业务联系人不会收到 Channel 报价；同步或留档失败不会导致重复发信。

核心验证是减少人工找资料、整理需求和写初稿的工作量；实际节省步骤与转化效果在试点中观察，不预设未测得的比例。
