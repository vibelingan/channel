# 官网助手：会话生命周期、防护、隐私、可复用内核与 Backlog（2026-11-02，11-03 两次更新）

本文件记录本轮之外的规划和调研：
- 聊天什么时候过期、记录保存多久；
- 怎样挡住无意义和不安全的提问；
- 隐私说明放在哪里；
- 助手怎么做成能给下一个客户复用的产品；
- 按“现在／全链路跑通后／以后”排好的 backlog。

本轮正在实施的内容仍以 [ROUND2-DESIGN.md](ROUND2-DESIGN.md) 为准，这里的条目不改变它的顺序。负责人 2026-11-03 的决定见 §8。

## 1. 模型是怎么“记住”上一句的

我们用的是 DeepSeek 的 chat-completions 接口，它是**无状态**的：模型服务那边没有 session，也不保存我们的对话。每次访客提一个新问题，worker 从我们自己的 PostgreSQL 取最近的消息，连同系统规则和检索到的资料，作为一次全新的请求发过去。取消息的规则是查 30 条、送最近 20 条，见 `packages/ai-store/src/store.ts` 和 `packages/ai-policy/src/index.ts` 的 `maxContextTurns`。模型“记得”前文，只是因为我们每次都把前文重发了一遍。

所以：

- **会话 ID 是我们的，不是模型的。** `conversationId` 是我们库里的主键，用来找回这段对话的消息、运行状态和询盘，模型服务从来看不到它。
- **每个新问题都会调用一次或几次模型。** 新问题需要新回答，这是必须的。
- **刷新页面不是新问题。** 刷新前问题已经发出，模型已经在生成。刷新后用原来的 idempotencyKey 接上同一个 run 的事件流，读的是正在生成或已经生成好的结果，不会再调用模型（MIU 17）。
- **缓存不是记忆。** DeepSeek 会自动把请求的公共前缀缓存在磁盘上，下次请求前缀完全相同时，这部分输入按缓存价计费，明显更便宜，也不需要改代码。但它按内容前缀命中，与会话 ID 无关，是尽力而为，过一段时间会自动清掉。[DeepSeek context caching](https://deepseek.com/en/news/context-caching/)。OpenAI 的 prompt caching 同理，默认保留几分钟到 24 小时不等，取决于模型和设置。[OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching.md)。
  - 让缓存多命中的顺序是：系统规则放最前且保持不变，历史按顺序追加，每次不同的检索资料放最后。当前 engine 已经是这个顺序。
- **有状态的接口也有，但不省钱。** OpenAI 的 Responses API 可以用 `previous_response_id` 或 Conversations 对象把历史存在 OpenAI 那边，response 默认保存 30 天。但整条链上的历史输入仍按输入 token 计费，只是少传数据，而且对话会绑在一家厂商上。[OpenAI conversation state](https://developers.openai.com/api/docs/guides/conversation-state)。我们以自己的库为准，换模型也不丢历史，这也是常见做法。

## 2. 会话什么时候过期，聊天记录保存多久

### 2.1 现在的行为（MIU 17 之后）

| 层 | 保存什么 | 多久 |
| --- | --- | --- |
| 浏览器标签页（sessionStorage） | 会话凭据、未完成的问题、未提交的询盘 | 关掉标签页就清除；刷新和同标签页跳转保留；新开标签页是新对话 |
| 会话凭据 | 证明“这个浏览器可以读这段对话” | 创建后 24 小时（`AI_CREDENTIAL_TTL_SECONDS`），固定期限，不随使用延长；过期后页面显示“开始新对话” |
| 服务端 PostgreSQL | 全部消息、事件、运行记录 | 目前没有删除机制，一直保留 |
| 模型服务 | 无 | 每次请求结束即结束（缓存除外，见上） |

### 2.2 保存按价值分，不按天数一刀切（负责人决定，2026-11-03）

**同一次访问内要连续。** 刷新、来回切换页面都不能丢上下文。MIU 17 已经做到；MIU 18 让产品页也挂上助手，切到产品页再回来也接得上。这就是本阶段的要求，跨天回访不做（§3）。

**有价值的聊天长期保存，只删无效的：**

| 类别 | 判定方法（用已有的运行记录，不另调模型） | 保存多久 |
| --- | --- | --- |
| 询盘 | 访客确认提交了询盘 | 随 Sales 记录长期保存；聊天原文一起留着，作为这条线索的来龙去脉 |
| 有业务内容 | 问过产品、公司或 OEM：出现过产品查找、资料引用、追问或询盘建议 | 作为业务记录长期保存；访客要求时删除 |
| 无效 | 只有问候、超出范围、被防护层拦下，或者是空会话 | 30 天后删除，只保留统计数（天数可调） |

- **存储不是问题。** 一段文字聊天通常只有几 KB，十万段也只是几百 MB。
- **符合隐私规则的常见写法。** GDPR 的“存储限制”原则要求保存时间与目的相符，并在隐私说明里写清楚。“作为业务记录保存，访客要求时删除”是常见写法。
- **Sales agent 不会看到无效聊天。** Sales 只收到访客自己点了确认、勾了同意的询盘，单纯聊天不会进 Sales（MIU 12、16 的规则）。万一有人乱填询盘，应由 Sales agent 标成“不是有效线索”，不起草回复。这条记入 Hermes 侧 backlog（N9）。
- **实现（N1）：**
  - 每个 run 记下 planner 选的动作类型，按它给会话打价值标记，比按文字去猜可靠。
  - 每天一次的清理任务只删“无效”类，删除前后的计数写日志。
  - 隐私说明同步（§6）。

**凭据期限：** 24 小时从创建算起，聊到第 23 小时 59 分会被打断。可以改成“最后一次提问后 24 小时、最长 7 天”。但关掉标签页本来就会清除凭据，这个改动收益小，列为低优先（N3）。

### 2.3 业界怎么做

- **Intercom：**
  - 没登录的访客，对话靠浏览器 cookie 保存：访客识别 cookie 保留 9 个月，会话 cookie 保留 1 周。
  - 官方也提醒：共用电脑时，下一个人能看到上一个人的对话，退出时要主动清掉。
  - 资料：[Intercom 安装说明](https://developers.intercom.com/installing-intercom/web/installation.md)、[Intercom 隐私说明](https://www.intercom.com/legal/product-privacy-notice)。
- **Zendesk：** 默认跨访问保留匿名访客的对话。对共用浏览器提供 “Forget history” 选项，开启后每次都从新对话开始，效果和我们按标签页保存一样。[Zendesk 说明](https://support.zendesk.com/hc/en-us/articles/4531075858458)。

## 3. 回访访客：本阶段不做跨天记忆（负责人决定，2026-11-03）

本阶段只要求同一次访问内不丢上下文（§2.2）。

“同一设备记住 N 天”不做，因为成本比收益大：
- 要单独做一个单元：localStorage、凭据期限、“继续／新对话／忘记”三个入口；
- 要处理共用电脑的风险；
- 要写进隐私说明。

以后需要时可选的做法：

| 方式 | 能做到 | 代价 |
| --- | --- | --- |
| 同一设备、同一浏览器（localStorage 或第一方 cookie） | 几天后回来，显示“继续上次的对话” | 共用电脑会被下一个人看到；清浏览器数据、换浏览器或用无痕窗口就没了 |
| 邮件链接（访客提交询盘时留了邮箱） | 换设备也能回到同一段对话 | 要发邮件（真实发信目前关闭），还要防止链接被转发后泄露 |
| 登录账号 | 完整历史 | 匿名 B2B 访客基本不会为了问问题去注册 |

对真正有意向的买家，提交询盘后由 Sales 用邮件跟进，已经覆盖了回访的主要价值。

## 4. 做成可复用的 AI 客服产品

### 4.1 业界的共同做法

几家主流平台说法不同，结构基本一致：

- **一个助手就是一份配置：** 角色和规则、知识来源、启用哪些动作、安全限制、上线渠道。
  - Salesforce Agentforce 的结构是 agent → topic → action。topic 是一类业务，带“什么时候用”的说明和规则；action 是具体操作，可以是流程、代码或提示词模板。topic 和 action 可以在多个 agent 之间复用。
  - 资料：[Agentforce 组件概览](https://www.asagarwal.com/?p=31668)、[Agentforce 标准动作](https://developer.salesforce.com/agentforce-workshop/employee-agents/3-standard-actions)。
- **动作就是有类型的工具：** 一个名字、一段给模型看的说明、一份 JSON Schema 输入、一个服务端处理程序，外加权限和确认规则。OpenAI function calling、GPT Actions（OpenAPI）、MCP tools 都是这个形状。
- **动作的界面按名字注册：** 服务端产生动作结果，前端按动作名找到对应组件来渲染。
  - assistant-ui 的 tool UI 按工具名注册 React 组件，执行逻辑在别处登记。[assistant-ui tool UI](https://www.assistant-ui.com/docs/guides/tool-ui)
  - OpenAI ChatKit 用 widget 在聊天里显示卡片和表单，用 action 让界面不经过用户消息就触发后端操作。[ChatKit 进阶集成](https://developers.openai.com/api/docs/guides/custom-chatkit)
  - MCP Apps 让 MCP 服务器返回在沙箱 iframe 里运行的界面，Claude、ChatGPT、VS Code 等宿主都支持；不支持的宿主退回显示文字结果。[MCP Apps 概览](https://rits.shanghai.nyu.edu/ai/mcp-apps-interactive-uis-become-an-official-part-of-mcp)
- **模型可以替换：** 会话、记忆、安全规则都在自己这边，模型只是其中一个可替换的环节。

### 4.2 我们已经有的通用部分

| 已有 | 位置 | 换一个行业还能用吗 |
| --- | --- | --- |
| 模型接口（engine port，可替换 DeepSeek、AnythingLLM 等） | `packages/ai-engine`、LLD-002 | 能 |
| 会话库：幂等提问、事件流续读、运行状态、人工接管 | `packages/ai-store`、LLD-001 | 能 |
| 安全策略（只说公开事实、不编价格、联系方式不进模型） | `packages/ai-policy` | 结构能用，内容要按行业换 |
| 前后端合同 | `packages/ai-contracts` | 能 |
| 页面的会话层：发送、停止、续读、刷新恢复 | `apps/site/src/islands/ai/assistant` 的 session、adapter、persistence | 能 |
| 业务专用：销售提示词、产品查找与产品卡、询盘表单与 Sales 落盘 | engine 提示词、`catalog-*`、`InquiryCard`、`apps/functions/sales-integration` | 不能，属于“外贸销售”业务插件 |

现在的问题是：业务专用部分和通用部分写在同一批文件里，还没有一条“业务插件”的边界。

### 4.3 做法（负责人同意，2026-11-03）

只有一个客户时就做通用引擎，很容易猜错抽象：第二个行业的需求往往和想象的不一样。业界常用的经验是“第三次再抽象”。

负责人的要求：
- 方向要一直记着，逐步演进。
- 不过度架构，也不为“通用”去重构已经能用的部分。
- 先保证上线，上线后在不影响线上功能的前提下逐步重构。

分三步：

- **现在（本轮）：** 新写的代码沿边界放，业务专用的放业务一侧，不额外写通用框架。MIU 16 的询盘卡已是消息流里的一种消息类型，由“消息类型 → 组件”渲染；以后它就是“外贸销售”插件里的一个动作组件。
- **全链路跑通后，与 Hermes H3 一起：** 写一份 ADR，定义两份合同，并把现有销售业务改成第一个使用它们的插件。
  - `AssistantProfile`：id、角色与规则、语言、知识来源、启用的动作、安全策略、防护规则（§5）、上下文预算、会话与保存期限（§2）。
  - `ActionDefinition`：名字、给模型看的说明、输入 JSON Schema、确认规则（模型只能建议，还是必须由人确认）、服务端处理程序、幂等规则、结果 schema、前端组件名。
- **第二个行业来时：** 用这两份合同接入，比如法律咨询的利益冲突初筛、预约、材料清单，并按需要修正合同。到时再决定是否用 MCP 承载服务端动作。
  - 对我们自己的聊天窗口，类型化的组件注册表比 MCP Apps 的 iframe 简单。
  - MCP Apps 适合以后要把助手接进 ChatGPT、Claude 这类外部宿主的场景。

不变的原则：
- 模型只能建议。确认、同意、提交这类业务动作由人来点。
- 动作的权限由服务器按配置决定，不信任模型的输出。

### 4.4 要逐步补齐的产品能力

这些是“快速交付给下一个客户”需要的能力，按 backlog 编号排在后面，不影响本轮上线：

| 能力 | 对应 |
| --- | --- |
| 一份配置定义一个助手（规则、知识、动作、防护、期限） | N4 |
| 按价值保存与清理 | N1 |
| 防护层：重复、刷屏、无关、不安全的提问不调用模型 | N7、以后的 L1 |
| 用量与成本：按会话、按客户看模型费用 | N6 |
| 新行业的动作和组件按名字注册 | N4 之后，第二个行业 |
| 多模态、长期客户记忆 | 以后 |

## 5. 防护层（调研，2026-11-03）

### 5.1 现在已有的防护

- **频率限制：** BFF 对每个 IP 每分钟 60 次、全站每分钟 600 次，由 `AI_IP_REQUESTS_PER_MINUTE` 和 `AI_GLOBAL_REQUESTS_PER_MINUTE` 设置。超过返回 429，页面按 Retry-After 等待。IP 只存 HMAC 散列。
- **长度限制：** 单条消息最长 8000 字符（`packages/ai-contracts`）。
- **模型规则：**
  - 资料、历史、产品数据都按“不可信数据”处理。
  - 不透露提示词、凭据和内部文档。
  - 超出范围的请求走 `help/unsupported`，由应用回固定文字，不让模型自由发挥。
- **出口检查：** 没有公开来源支撑的事实回答不发布；价格、MOQ、交期不编。
- **联系方式：** 发给模型前会被替换掉。

### 5.2 缺口

- **每条消息都要先调用一次模型来判断。** 不管是不是废话，planner 都要调用一次模型才能决定怎么处理。重复发 20 遍 “hello” 就是 20 次模型调用，单个 IP 每分钟最多 60 次。
- **没有按会话的提问上限。**
- **没有内容安全分类。** 违法、暴力、色情、自伤一类内容，目前只靠模型自己拒绝。

### 5.3 分两层，第一层不调用模型

**L0 规则层：已实现（2026-11-03，负责人：Go）。** 下表是当初的建议；实际做法和取舍见 §5.6。

| 规则 | 做法 | 访客看到的 |
| --- | --- | --- |
| 重复 | 10 分钟内与本会话最近 3 条问题相同（忽略大小写、空格、标点） | 固定回复：上面已经回答过，可以换个问法或补充需求 |
| 问候 | 纯问候（hello、hi、你好……）直接用固定问候回答；重复问候同样处理 | 固定问候，不调用模型 |
| 无内容 | 没有字母、数字、汉字，或者是乱码 | 固定提示：请描述你要找的产品或服务 |
| 太长 | 问题上限从 8000 降到 2000 字符；询盘需求字段另算 | 提示精简 |
| 频率 | 每个会话每分钟 6 个问题、每天 60 个；每个 IP 每天 200 个需要模型的问题；现有每分钟限制保留 | 告知等多久，并给出“把需求发给团队”的表单入口 |
| 冷却 | 10 分钟内被拦 5 次，冷却 10 分钟，自动解除 | 同上；永不永久封禁 |

- 被拦下的消息不发给模型。只记类别、时间、长度和散列，保存 30 天用于统计，不存原文。
- 冷却之外，每条消息单独判断：之前被拦过，不影响之后的正常提问。
- 数字都是起点，看 N6 的用量数据再调。

**L1 内容安全分类**等日志里真的看到滥用再加。**负责人已选腾讯云文本内容安全（TMS）**，到时候给负责人开通链接（§5.7）。当时比较过的方案：

| 方案 | 形态 | 成本 | 适合 |
| --- | --- | --- | --- |
| 腾讯云文本内容安全（TMS） | 同一朵云上的 API，按调用计费；首次开通有 1 万条试用 | 按量计费，价格以官方定价页为准 | 不想运维；中国境内服务的合规审核 |
| Qwen3Guard-Gen-0.6B（Apache-2.0） | 自己部署成一个只在 VPC 内可访问的 CloudBase Run 服务，和 worker 一样 | 一个常驻实例。按已公布价格，2 核 4 GiB 约每月 170 元（只算计算）；CPU 上的延迟需要实测 | 想用开源、可自托管、多语言的方案；输出安全／有争议／不安全三级 |
| 继续靠现有 planner 调用 | 现状（`help/unsupported`） | 每条消息一次短调用 | 现状 |

现在不采用的：
- **NeMo Guardrails、LLM Guard：** 都是 Python 框架。主要价值（话题限制、越狱检测）和我们已有的规则重叠，还要多维护一套运行时。另外有资料称 LLM Guard 已归档，需要核实。
- **`@openai/guardrails`：** 虽然是 TypeScript，但它包装的是 OpenAI 客户端，用 OpenAI 的接口做判断，和 DeepSeek 不搭配。
- **Guardrails AI：** 偏输出结构校验，不是我们缺的部分。

资料：[guardrails 工具对比](https://dev.to/agdex_ai/best-ai-agent-security-guardrails-tools-in-2026-llm-guard-vs-nemo-vs-guardrails-ai-5e5d)、[2026 guardrails 评述](https://wz-it.com/en/knowledge/ki/ai-guardrails/)、[@openai/guardrails](https://openai.github.io/openai-guardrails-js/quickstart)、[Qwen3Guard](https://docs.api7.ai/ai-gateway/traffic-controls/guardrails/qwen3guard)、[腾讯云内容安全 API](https://cloud.tencent.com/document/product/1124/51860)。

### 5.4 放在哪里

- **L0 不单独起服务。** 它要读本会话最近几条消息和计数，库就在旁边。单独起服务多一跳网络，反而更慢、更贵。实现时按数据所在拆成两处，见 §5.6。
- **L1 如果自托管模型，单独部署成 VPC 内部服务。** CloudBase Run 一个服务只监听一个端口，所以“另开一个端口”在这里的做法是：在同一环境、同一 VPC 里再部署一个服务，和现在的 worker 一样不对公网开放。

### 5.5 误判怎么控制

- 固定回复要客气，说明能帮什么，并给出表单入口。
- 冷却时间短，自动解除。
- 每周看一次被拦统计和抽样（只看类别和计数），规则随时可调。
- L1 只拦“不安全”。“有争议”的放行并记录，避免误伤正常业务词。

### 5.6 L0 实际做法（2026-11-03）

两处都在模型调用之前，都不调用模型：

| 位置 | 规则 | 访客看到的 |
| --- | --- | --- |
| BFF，接收新问题之前（`apps/ai-bff/src/server.ts` 的 `questionWait`） | 每个会话每分钟 6 个、每天 60 个新问题；每个 IP 每天 200 个；重试同一条提交不计数 | 429 和 Retry-After；页面显示要等多久（秒、分钟或小时），并提示仍可用 Prepare inquiry 把需求发给团队 |
| 同上 | 被拒 5 次后冷却，到 10 分钟窗口结束自动解除 | 同上 |
| 同上 | 问题超过 2000 字符直接拒收，不截断；输入框本身也限 2000 | 输入框打不进更多字 |
| 同上 | 连续 5 个“空转回答”（固定寒暄回复或超出范围的拒答）之后，后面的问题每 10 分钟最多 3 个；任何一个正常回答都会结束这个状态 | 同上，显示要等几分钟（最多 10 分钟） |
| worker，调用模型之前（`apps/ai-worker/src/screen.ts`） | 只有寒暄：问候和“在吗”、问好（how are you）、问身份（你是谁、是机器人吗）、问能做什么（help、你能做什么）、感谢、道别；助手上一句没在提问时的“ok／好的” | 固定回复，见下面的“寒暄的边界” |
| 同上 | 没有字母、数字、汉字，或一个键按住不放、整排乱敲 | 固定提示：没看明白，请说明要找的产品或服务，并给出三个开始选项 |
| 同上 | 同一个问题连续问第三次，前两次都已有回答 | 固定回复：上面已经回答过，可以换个问法或补充细节 |

**寒暄的边界（负责人意见后修订，2026-11-03）：** 很多访客习惯先打招呼，所以寒暄一定要回，而且要把人引到产品咨询和询盘上；同时不能让反复寒暄消耗模型。做法：

- **只要整条消息只是寒暄，就由规则回答，任何次数都不调用模型。** 消息里带了问题（“Hi, do you make earbuds?”“Can I talk to a real person?”）就交给模型，不会被挡。
- **回复随连续次数变化：** 第一次是完整的欢迎，说明能查产品、讲 OEM／ODM 定制、整理询盘，并附三个开始选项（看看产品／OEM 定制／提交需求）；第二次换一句更短的话，选项还在；第三次起固定一句“我在这里帮你查产品、了解 OEM 定制和整理询盘”，选项一直保留，所以任何时候点一下就能开始。感谢、道别、“ok”第一次不附选项，连续三次以上才附。
- **问身份时如实说是 AI 助手**，需要人工的事情由销售团队在询盘后跟进。
- **“到次数”之后：** 寒暄本来就不调用模型，所以没有“到次数后模型不回”这一步；真正的上限是 BFF：连续 5 个空转回答后，每 10 分钟只能再发 3 个问题，加上原有的每分钟 6 个、每天 60 个、每个 IP 每天 200 个。等待最长 10 分钟，不按小时封：时间拉长拦不住真正想刷的人，只会把回来问真问题的访客挡走（负责人，2026-11-03）。正常访客只要问一个真问题，空转状态就结束，不受影响。
- **对模型上下文的影响：** 寒暄和它的固定回复不放进之后的模型请求（MIU 19），所以混着寒暄的长对话也不会多花 token。

为什么固定回复放在 worker 而不是 BFF：
- **顺序：** 前一个回答还在生成时，后一条寒暄要排在它后面回答；worker 本来就按顺序处理，BFF 直接回答会插队。
- **只有一处写回答：** 刷新、跨页恢复、快照读到的回答都来自同一条存储路径，BFF 不必另写一套“直接完成回答”的逻辑。
- **要看上下文：** 判断“ok”是不是在回答助手的提问、第几次寒暄、是不是第三次重复，都要读最近的对话，worker 已经读了。
- **成本一样：** 两处都不调用模型。worker 每 250 毫秒取一次任务，固定回复大约半秒内出现。

限额和长度在 BFF：超额的问题根本不进库、不建 run。

和最初建议的差别：
- **重复：** 不按“10 分钟内”算，而是按“连续第三次，且前两次都有回答”。第二次照常回答，因为可能是重试或想要新回答；没答完（停止、失败）的那次不算。
- **符号：** 如果助手上一句是在提问，“👍”“？”这类回复交给模型理解，不当作无内容。
- **问候里带了问题**（“Hi, do you make earbuds?”）照常交给模型。
- **记录：** 被拒的问题不入库，只在日志里记规则和长度；被固定回复的消息是对话的一部分，照常保存，日志只记类别。
- **冷却：** 用固定窗口，所以最长 10 分钟，可能更短。
- **环境变量：** 全部可调，见 `.env.ai-runtime.example`（含 `AI_IDLE_REPLIES_BEFORE_SLOWDOWN`、`AI_IDLE_QUESTIONS_PER_WINDOW`、`AI_IDLE_WINDOW_SECONDS`）。本机联调和测试不设限额。
