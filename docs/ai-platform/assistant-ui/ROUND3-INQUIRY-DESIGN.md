# 第三轮设计：助手自己整理询盘，表单作最后手段

2026-11-03，草案；同日按负责人答复定稿（§6）。负责人要求先设计、拆 MIU；第二轮在线上跑通、给客户演示之后再实现。现有询盘卡保留，只是第二轮上线前先去掉了同意勾选框（§4.1）。

## 1. 要达到的效果（负责人原意）

- 聊天是为了让询盘更省事。访客在对话里说过的数量、产品、用途，不再让他在表单里重填一遍。
- 大多数情况（目标 80% 以上）由助手自己整理并落盘：“信息齐了，剩下的交给我们团队”。
- 访客在对话里留了邮箱、却没点提交，也要落盘，交给 Sales agent 在合适的时候跟进。很多访客不认识这家公司，第一反应就是不提交表单；客服要尽责，把潜在机会转出去。
- 表单是最后手段：访客一上来就说“我要询盘”、前面什么都没聊，这时在聊天里给一个简短表单是可以的，至少不用跳回首页。
- 首页、OEM 页和聊天里的表单，提交的数据结构一样；组件能复用就复用，聊天里的可以更简单。
- 问了好几个产品，也只是一条询盘记录，里面列多个产品；不拆成几条，避免给同一个人发几封邮件。

## 2. 现状

| 入口 | 访客要做什么 | 落到哪里 |
| --- | --- | --- |
| 首页／OEM 页 `ProjectForm.astro` | 自己填全部字段 | public-api → `saveFinalizedOemInCloud` → `oemProjects` |
| 聊天询盘卡 `InquiryCard` | 点“核对询盘”，填邮箱、姓名、公司，确认（同意勾选框已去掉，和首页表单一样只有隐私说明链接） | BFF → sales-integration 的 assistant intake → 同一个 `saveFinalizedOemInCloud` → `oemProjects`（带 `assistantSubmission`） |

已有的基础：
- MIU 19 的需求摘要记下了产品、数量、用途、目的地、预算、定制、必要功能和已选产品，并标出哪些是访客原话。这就是助手整理询盘的原料。
- 联系方式从不进模型输入，也写不进需求摘要。这一点继续保持。

缺口：
- 只有访客点确认才落盘，留了邮箱不提交的人会流失。
- 一条询盘只有一个 `productId`。
- 两处表单的字段定义各写一份。

## 3. 一次对话的三种结局

| 情况 | 助手怎么做 | 落盘内容 |
| --- | --- | --- |
| A. 需求够了，对话里也留了联系方式 | 回一段很短的总结：“我会把这些交给团队：700 副耳机，印 logo，发德国；回复会发到 m***@weber-audio.de”，附 [没问题] [改一下] 两个按钮 | 一条询盘，内含多个产品。访客点了就是“已确认”；没点就离开，按“未确认”落盘，Sales 能看出区别 |
| B. 有需求，没有联系方式 | 正常回答。在有价值的时候（问报价、起订量、交期时）自然地问一次邮箱，不拿回答当条件 | 一条不含个人信息的“匿名机会”，供 Sales agent 分析需求趋势。之后访客留了邮箱，就升级为 A |
| C. 一上来就要询盘，或者访客说“我自己填” | 在聊天里给一个简短表单：邮箱必填，已知的产品和数量预先填好 | 和 A 是同一种询盘记录 |

只有 C 会出现表单。A 和 B 都不让访客填表。

## 4. 关键设计

### 4.1 访客在聊天里留下的联系方式，由我们的服务器摘出来存好

这里的“识别”和发邮件无关（发邮件仍是 Resend，属于后续邮件模块）。意思是：访客在聊天里打了一句“my email is mia@weber-audio.de”，我们的服务器（BFF）用固定规则把邮箱、电话、WhatsApp 从这句话里摘出来，单独存好；转给 AI 模型的那份文字里，联系方式照旧换成占位符。这样做是为了联系方式不经过模型服务商，模型也不可能把它写错、编造或者发给别人。

- 存进 `conversation_contacts`，按会话关联。
- 识别到之后，助手当场回一句：“谢谢，我们的销售团队会通过 m***@weber-audio.de 回复你这个需求。”邮箱打码显示，访客能发现打错了并直接改。旁边只有隐私说明链接。
- 没有同意勾选框，也没有“不要联系我”按钮（负责人 2026-11-03 决定）：访客留了联系方式，就是为了询盘。首页、OEM 页和聊天里的表单都一样，按“提交”即表示请我们就这个询盘联系他。
- 依据记为 `contactBasis: 'provided_in_chat' | 'form'`，带上当时显示的提示文案版本号。

访客在对话里说了“先别联系我”“只是看看”之类的话，也照样记录、照样跟进：
- 记录上加一个提醒 `visitorNote: 'asked_not_to_contact'`（以及原话摘录），不改变状态。
- Sales agent 照常起草跟进，但按这个情况调整写法（例如更短、不催单、只给资料），并在草稿顶部标出来，让审核的人看到。
- 发不发、怎么发，由审核的人决定。所有跟进都是草稿，不会自动发出。

### 4.2 “够了没有”由服务器判定，模型只提议

- 就绪规则只看访客原话里的事实：有联系方式；有产品或已选产品；数量、定制、目的地至少有一项。
- 模型可以在计划里提议 `handoff: true`。服务器按规则复核，模型不能直接写记录。
- 缺的关键信息在回答里顺带问，一次只问一项，整个对话最多问两次，避免变成盘问。

### 4.3 一条询盘，多个产品

- 需求摘要增加 `items[]`，每项是 `{productId?, name, quantity?, customization[], notes}`。访客选中的卡片或明确说出的产品各成一项；目的地、用途、预算放在整条询盘上。
- 询盘合同升级到 v2：`items[]`（1–10 项）、`summary`（助手写、访客能看到的总结）、`source: chat | chat_form | site_form`、`status: confirmed | unconfirmed`、`contactBasis`、可选的 `visitorNote`。v1 照旧接收。
- 每个会话最多一条 `oemProjects` 记录，按 `conversationId` 去重。后面补充的信息更新这条记录并留下版本，不新建，所以 Sales 只跟进一个线程。

### 4.4 什么时候落盘

- 已确认：访客点击时。
- 未确认：会话空闲 30 分钟后（浏览器关闭无法可靠得知，所以用空闲时间），如果就绪规则满足，由 worker 落盘。
- 匿名机会：同一个空闲触发。有产品、没有联系方式时记一条，不含 IP 和原文，保留 90 天。

### 4.5 表单共用一套字段

- 在 shared 包里定义一份询盘字段（字段名、必填、校验）。首页／OEM 的 `ProjectForm` 和聊天表单都从它渲染，提交同一个合同。
- 聊天表单只显示最小的一组：邮箱必填；需求和产品从对话预填，可改；姓名、公司选填。没有勾选框。
- 组合方式：同一批字段组件，按入口挑不同的字段，不复制一份新表单。

### 4.6 Sales 侧（Hermes）

- 投递内容增加产品清单、确认状态、联系依据、助手总结，并标出哪些是访客原话。
- 未确认线索：Sales agent 起草首次跟进，进“待审核”，人工批准后才发（真实发信仍是后续邮件模块）。带 `visitorNote` 的线索同样起草，草稿顶部标出访客说过的话。
- 匿名机会：按周汇总成需求趋势，不跟进个人。
- 第 N9 项（乱填询盘标为“不是有效线索”）同样适用。

### 4.7 滥用和出错

| 风险 | 做法 |
| --- | --- |
| 填了别人的邮箱 | 所有跟进先过人工审核；同一 IP 每天的线索数有上限 |
| 邮箱打错 | 打码回显，访客可以直接改 |
| 重复落盘 | 每个会话只有一条记录，靠更新补充 |
| 访客说过不要联系 | 照样记录和起草，草稿顶部标出原话，由审核的人决定 |
| 模型编造需求 | 总结只用访客原话里的事实；推测项单独标出，不进“访客要求”栏 |

### 4.8 怎么衡量

- 不经表单落盘的询盘占比（目标 80% 以上）、已确认和未确认的比例，以及 Sales 跟进后得到回复的比例。

## 6. 负责人决定（2026-11-03）

1. 没有同意勾选框，也没有“不要联系我”选项。访客留了联系方式就是询盘，要跟进；访客说过不要联系，只作为提醒标给审核的人。第二轮的聊天询盘卡已先去掉勾选框。
2. 会话空闲 30 分钟后，未确认线索落盘。
3. 匿名机会保留，90 天。
4. 一条询盘多个产品，不拆分。
5. 电话、WhatsApp 都算联系方式，邮箱优先。
