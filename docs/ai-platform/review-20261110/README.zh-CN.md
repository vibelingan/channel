## 1. 先区分两条业务

**被动询盘：** 买家在 Channel 官网提问、提交需求。官网保存询盘后，通知 Hermes 的 Sales Agent；Agent 读取这一条需求及相关产品，准备回复，在 Resend 保存未发送草稿，等待人审核。

**主动获客：** Channel 的销售人员提出“找美国中小型耳机品牌或进口分销商”等目标。Hermes 的 Sales Agent 使用公司介绍、客户画像与产品能力，向 Apollo 查询并研究潜在买家，保存候选、证据、建议和待审文案。找到了公司不等于找到了采购意向，更不等于已经建立合作。

两条业务复用客户身份、任务权限、资料读取、文案版本和审批规则；来源、授权联系依据、发送渠道分开。**不能把 Apollo 陌生买家直接送入官网询盘的 Resend 发送链路。** Resend 官方规则禁止未经请求的冷开发邮件，包括购买名单和抓取联系人。该限制涉及发送资格；本轮不发送邮件，也不把仅创建草稿说成获准发送。[Resend 官方规则](https://resend.com/legal/acceptable-use)

## 2. 哪些程序是什么，在哪里

读下面的流程前，先固定名称。原来的“Channel Sales”容易被理解成第二个 AI Agent，今后面向业务称为 **Channel 询盘与资料接口**。代码目录 `apps/functions/sales-integration` 保留，避免为改名称改动运行协议。

| 名称 | 所属与位置 | 实际工作、模型和数据 | 本轮读到的状态 |
|---|---|---|---|
| 官网聊天界面 | Channel，访客浏览器 | 展示对话和表单；不保存服务端密钥、不决定客户权限 | 线上旧版有拒答后隐藏输入框缺陷；新版交互和署名已汇入评审分支，未发布 |
| 官网 AI 接收服务（BFF） | Channel 的上海 CloudBase，容器 `ai-bff` | 接收访客问题、验证会话、保存事件并推给浏览器；不在这个进程直接运行销售模型 | 已部署；本轮未更新 |
| 官网 AI 问答执行程序（Worker） | 同一 Channel 云环境，容器 `ai-worker` | 调用 DeepSeek、公开知识库与产品接口，检查回答并保存；聊天进度在 Channel PostgreSQL | 现用 `vibekb@1.0.0`、`deepseek/deepseek-v4-pro`，公开工作区 2／文档 12；不是 AnythingLLM 引擎 |

| Channel 专属销售执行服务 | HermesInfra，现有 Hub 主机 `marketagents.supplychainsai.com` | **Python Web 服务**，systemd 管理，绑定 `127.0.0.1:19011`；任务分派和消费者是另外两个进程。模型选择产品／款式，当前询盘邮件正文仍有固定模板 | 运行代码 `b356d437`；serve 运行，dispatch／consume 停止。不是新购服务器，不是腾讯 Serverless，也不是 Node 服务 |

Channel 的 PostgreSQL `ai_assistant` 保存**网站聊天**；Channel 云数据库保存**询盘和公开产品**。Hub 的 `sales_channel_website` 保存**这个客户的 Sales 任务、结果和草稿编号**。它是共享 MySQL 服务里的独立逻辑库，有限库账号；不是独立物理服务器，也不是所有 Agent 随便读同一组表。当前专属 Sales 任务没有统一塞进旧 Hub 的共享任务库。

## 3. 一条官网询盘到底怎样处理

以买家咨询耳机并确认留下需求为例，以下是**要验收的目标顺序**，不是宣称正式网站已全部跑完：

1. 买家在浏览器确认需求。浏览器携带自己的会话凭据，把确认结果交给官网 BFF；买家不接触腾讯云管理密钥。
2. 官网后台请求 Channel 询盘与资料接口。接口核对固定业务来源、确认内容和重复提交编号，保存询盘及待交接记录；未确认的聊天不擅自变成询盘。
3. Channel 的普通投递程序向 Hermes 任务接收接口发送“有一条新询盘”的事件。只带客户连接标识、来源编号、版本及必要证明，不把整个产品库和所有附件发过去。
4. Hermes 核对发送方凭据和服务器登记的客户范围，**先将任务写入自己的库**，再回应已受理；重复事件返回同一任务，不再生成一份任务。
5. Hermes 发送第一条企微通知：“询盘已受理，正在准备跟进内容”。不是在接收一个未保存的网络包时就通知成功。
6. 消费者领取任务，Sales Agent 通过受限工具读取**这一条**询盘、所需的公开产品和该询盘所列附件。没有附件就不调用附件接口；一次可以批取同一任务所需的少量产品。
7. Agent 使用公司已批准的说法与本次需求生成内容。生成完后在真正提交边界检查任务仍有效、资料版本未发生影响本稿的变化。不是每个小函数都重新查远端权限。
8. 将确定版本保存为 Resend 未发送草稿，读回收件人、标题和正文，关联任务。随后发送第二条企微通知：“草稿已准备，请审核”。两条通知有各自的去重键与失败重试；不会因通知失败重新生成或发送邮件。
9. 后续审批和真实发送是另一项工作。客户回复后的来信关联、生成第二封跟进也单独登记，不能把首封草稿成功当成回复闭环完成。

[按时间展开的流程图](../../sales-agent/diagrams/inquiry-sequence-20261109.html)把两次通知分开。跨服务读取仍有往返，因为原始业务资料归 Channel，任务执行归 Hermes；这是受控按需读取，不是两个 Agent 在互相聊天。

## 4. 为什么保留 HTTP 接口，怎样承受更多客户

**HTTP 接口与队列不冲突。** 推荐外部客户通过 HTTPS 交任务，Hermes 很快完成认证、去重和持久化，然后返回任务编号。耗时的模型、Apollo 查询和草稿操作由队列后面的执行程序完成，不让客户的一条 HTTP 请求等几分钟。

现有代码有 `ThreadingHTTPServer`、持久任务记录、消费者认领及任务锁，但不能凭这几样宣称已有无限并发或完整跨客户调度。现有专属服务适合早期隔离接入；每加一个客户复制一整套源码和人工端口配置，不适合作为长期平台模式。

建议分两步，均待评审后实施：

- **现在复用：** 同一版代码、配置化客户实例。入口限制请求体、速率和在途请求；每客户默认同时处理 1 个任务，全机另设有界总并发。任务必须先认领成功，才调用外部模型。额度／模型拥堵影响该客户队列，不让它占满所有执行者。
- **多客户真正增长后：** 共用薄接收层，以服务器认证得到的客户编号路由到其任务库／sandbox；按客户公平领取任务、设置配额和熔断。客户适配器与业务 Agent 分开，不能用请求正文里一个可改的 `client_id` 直接决定读哪个库。

暂不增加云端 Pub/Sub 产品。已有数据库队列足以覆盖本期的一对一交接；补强持久化、去重、失败补投，比再加一个消息系统更有直接收益。当实际测到接收峰值超过入口容量、需要多个独立订阅者、积压持续超标或跨区域广播时，再把内部投递替换为消息总线。即使采用 Pub/Sub，客户身份、去重和业务状态仍要验证，队列不会自动解决隔离。

**拟定调用预算：** 普通无附件任务、模型一次批查产品、无重试时，目标为 1 次新询盘通知＋1 次来源授权＋2 次必要资料读取（询盘、批量产品）＋最多 1 次生成后版本／许可复核＋最多 1 次受限许可回查，合计 **不超过 6 次 Channel↔Hermes HTTP 请求**。Resend、模型和企微另计。若首次读取可合理合并，预算可以继续下降，不为凑 6 次制造请求。

授权检查保留在每次独立请求进入及真正提交边界，同一请求内复用核验结果。跨请求的受限许可只有在明确约定有效期、资源范围、撤权时效后才缓存；建议先以最长 60 秒的只读许可评审，最终草稿提交必须重新核对当前任务状态。不能用“会话可信”省掉跨客户／跨任务检查，也不能每秒刷新一个本可持续几十秒的许可。

HTTP/2 可以在同一连接并行传请求，服务端同样能受益；它不会让 14 次不必要的授权变必要，也不会自动证明 6 个请求属于同一客户。先减少重复查询、批取产品、复用连接，再按实际代理与服务支持决定是否用 HTTP/2；不为了协议名重写全套服务。法兰克福 Hub 与上海 Channel 的跨区延迟另列性能待办，不擅自挪动现有需境外模型访问的服务。

## 5. 三种身份分别保护什么，怎样复用

这里讨论的是 **Hermes 服务器向 Channel 资料接口请求数据**，不是买家登录。

- **网络传输：** HTTPS 加密流量、核对服务端证书；它本身不证明是哪个客户。
- **调用程序身份：** 拟用腾讯云支持的函数网址签名认证，限制 Hermes 这份机器凭据只能调用指定 `sales-integration` 函数。标准 `Authorization` 头留给 TC3 云签名。另一客户若不使用腾讯云，就由其适配器使用该系统提供的 OAuth、签名或 mTLS，Hermes 不强迫它上腾讯云。
- **客户与任务权限：** Channel 接口收到请求以后，根据服务器保存的连接登记核对客户、安装、业务线、环境、任务、动作、资源范围、有效期和撤权版本。现有应用凭据计划通过 `X-Sales-Authorization` 携带；它不是第二份腾讯签名。请求通过云检查，也不能读另一个客户或另一个任务的资料。
- **Channel 程序自身查库身份：** 接口内的数据库 SDK 使用 Channel 配置给函数的运行角色。腾讯平台可以提供短期凭据；这是函数查库的身份，不是 Hermes 的机器身份，更不是访客身份。

例如，Channel 任务 123 只允许查询询盘123和它引用的产品／附件。Hermes 凭据有权调用函数，任务标识换成客户 B 的456，业务检查仍拒绝。模型只能说“我要这条任务所需产品”，不能选择数据库、集合名、密钥或放宽任务范围。

[请求与检查发生在哪里](../../sales-agent/diagrams/request-auth-20261109.html)是拟实施方案。**当前不能报告 CAM／TC3 接线已完成。** 本轮仅确认函数为 HTTP、角色已绑定；没有取得“正式签名入口成功＋函数使用真实短期身份查库”的新证据。SDK 的本地测试曾替换 `Request.prototype.send`，证明业务组装而非真实凭据。这是测试覆盖缺口，不是证明线上无凭据也能读库。

接下来的验收顺序固定为：核实平台文档和已安装 SDK → 尝试原有 SDK 自动取凭据的最小真实只读请求 → 能用就复用；不能用才在入口读取**可信平台传入**的短期凭据，建立本请求专用 SDK 实例，传给现有资料读取器。不能从任意公网请求头信任凭据，也不能把它写进进程全局变量导致并发请求串身份。HTTP 函数在 Node 中监听9000，由腾讯转发网络请求；已有 admin／public-api 的事件函数则接收腾讯整理的 `event/context`。保留 Sales 的 HTTP 接法，不因补认证就迁移全部 Event 处理器。

**可复用模块的边界：** 不另建一个 SDK 仓库，先在现有两个仓库中组织清楚，并复用官方 SDK：

1. Channel 的 `packages/sales-contracts` 继续保存两种语言一致的客户／任务／来源格式与错误码；不放客户密钥或特定云账号。
2. Channel 的平台接线模块负责可信运行身份、HTTP 头适配、固定环境的 SDK 创建；业务资料模块负责公开产品字段、询盘与附件归属。它们不调用模型。
3. Hermes 的 Channel 连接适配器负责固定服务网址、腾讯请求签名和受限凭据；通用任务权限模块不依赖腾讯。其他云新增适配器，不能复制整套 Sales Agent。
拟定代码位置：Channel先在已有资料接口内设 `platform-auth.ts`，负责函数入口的云／应用头适配；SDK请求级创建放在现有db包的小模块中，接口只接收已核验参数，不保存全局密钥。Hermes复用 `channel_reader.py` 和 `source_grant_client.py`，把重复的固定URL／签名发送收进 `channel_transport.py`；客户／任务校验仍由原Boundary／合同模块负责。这些是待评审的文件组织，不是本轮已新建的代码。

4. 同一种模块在第二个真实客户用例中证明接口稳定后，再提为独立可版本化包。TypeScript 和 Python 各自调用本语言官方 SDK，共用协议和一致性样例，不为“统一”写一个跨语言万能 SDK。

## 6. 公司资料从哪里来，怎样形成获客标准

**建议由 Sales Agent 负责销售资料整合，内容助手提供它已经维护的知识访问能力。** 这样没有两个 Agent 争夺策略最终版本。知识库适合相对稳定的公司介绍、制造能力、客户类型、已批准案例和禁用说法；实时产品接口适合产品发布状态、类别、型号与最新事实。

目标流程：

1. 为 Channel 配置一份有版本的“已批准销售资料包”，包括公司简介、服务市场、目标买家、排除条件、产品能力、允许承诺、待确认信息及每条事实的来源／更新时间。存入 **Hermes 的该客户专库及成果目录**，不是写到 Apollo 的共享账号上下文。
2. Sales 通过已有可授权的知识工具取得材料。若内容助手已有稳定的只读“资料检索”工具，优先复用其工具；不为每次搜索都额外启动一轮内容助手聊天。需要语义整理、冲突确认等具体工作时才通过已鉴权的 Hub A2A 任务请内容助手协作。A2A 指两个 Agent 交接具体任务，不是免费且自动正确的知识库代理。
3. 对官网公开产品按类别取少量代表型号，保存产品编号、类别、修改时间和来源；产品事实仍以实时接口为准，不全量复制到知识库。每次写具体型号卖点前，按需要读回对应产品。
4. 默认**每周检查一次版本变化**，无变化不重跑模型。已有产品同步／发布记录可作为“需要检查”的信号；同步成功不等于新增公开产品，更不等于销售策略自动改变。新类别如 AI 玩具只产生策略候选变更，交业务负责人确认后才用于找新买家。
5. 企业介绍和公开知识可由内容助手或客户维护；证据冲突时记录并暂停相应断言，不由 Sales 默默替客户改公司定位。旧任务继续绑定原批准版本，决定是否刷新时有记录。

这份销售资料包是“有来源的结构化摘要”，并非整个公司知识库，更不是只有3个产品就代表全公司。知识库给稳定能力，产品接口给当前可售事实，Sales 把它们组合成可执行的获客条件。

## 7. Apollo 现在能做什么，报告是谁写的

现有两份候选文案／结果页由 **Hermes 的规则和模型生成**。Apollo 提供了结构化公司记录和分页；不能把 Hermes 的匹配理由、推断和邮件当成 Apollo 已核实的调研报告。现有样本25家公司没有 `short_description`；这说明当次返回字段有限，不代表 Apollo 只有网址。

官方的公司补全接口可返回行业、营收、规模、融资、地点、组织关系等字段；AI Research 可按自定义问题研究公司，部分模式可联网并保存研究字段。MCP 也提供公司研究能力。因此推荐先验收它的研究结果，再决定补多少网页抓取，不从零爬全站。[公司补全](https://docs.apollo.io/reference/organization-enrichment) · [AI Research](https://knowledge.apollo.io/hc/en-us/articles/29193277882125-AI-Research-Overview)

### OAuth／Assistant 具体评估计划

OAuth 是由用户在 Apollo 页面授权一个工具使用账号的连接方式，不是再找一把API Key。MCP只是工具协议，Assistant才是可能自行选择多种动作的Agent；连接MCP不等于必须使用Assistant。

下一阶段：确认使用Channel专属Apollo账号、外部AI工具训练设置关闭 → 发起标准OAuth → 只申请需要的 `read_user_profile`／`organizations_search`／`organizations_enrich` 等只读范围，不申请context读写、联系人写入或邮件发送 → 检查授权页的权限、主体与有效期 → 在确认具体权限后才同意 → 只取工具清单和输入格式 → 允许名单中分别验证公司搜索、补全、研究。记录每项返回、来源、成本和是否会写账号记录；禁止直接暴露保存联系人、入序列、发送邮件等工具。OAuth授权扩大账号访问时需当场确认；本轮没有创建这种新访问。

Assistant先用单客户专属账号，输入公开的销售画像和一家公司官网，要求返回业务角色、相关产品、来源链接及未知项；记录接受、等待、完成的全过程，按服务返回的等待间隔查询，不每秒轮询。开始前明确额度上限和可执行动作；不能仅在提示词写“只读”，却把可写账号的全部能力交给它。若服务没有可强制执行的动作／额度限制，就不把它放入共享账号的自动主链路。[任务协议](https://docs.apollo.io/reference/run-an-assistant-task) · [MCP连接说明](https://docs.apollo.io/docs/apollo-mcp) · [适用计划](https://www.apollo.io/product/mcp)

## 8. 从一次查询到持续获客，不是凑够5家就结束

历史事实是：**一次请求 `page=1, per_page=25`**；Apollo返回25家，报告总匹配348家、共14页。剩余323家是尚未取回，不是我们排除了323家。Hermes粗筛分18家方向相关、1家不适合、6家待核实；后来只选3家作模型样例，最终写了2份文案，不是18家已经逐一核实后只剩2家。

25是首批大小，可按额度与时延改为20或50；首期默认25，避免换参数又浪费试用查询。**5家是给老板首屏优先看的建议数量，不是获客总量或永久停止条件。** 每次运行保存筛选版本、排序、游标、已研究／未研究／已联系状态及额度账本。首批已足够展示时可以先交一页报告，未研究的候选仍保留；后续由人工“继续研究／下一批”或已批准的周期任务继续，不静默无限翻页，也不把其余公司当作不存在。

尽量由Apollo做地区、员工规模、行业、业务关键词等原生筛选。关键词“任意命中”并不保证“既做耳机又是分销商”；需要按其实际支持的逻辑，拆成几种明确买家类型，分别查询／研究并去重。API只支持结构条件的路径由Hermes转成合法参数；Assistant可接收自然语言，但它的可用性、安全和成本要另验收，不能把普通REST请求说成Apollo自动理解整家公司。

### 判断方式与证据冲突

保留已讨论的三种结果：

- **建议联系：** 官方产品／业务角色等有依据，方向符合，无明确冲突；未发现采购公告也可试探合作，标明“未确认当前采购需求”。
- **待核实：** 有相关性但缺资料、角色不清或来源冲突。信息不全不是直接否决，也不能包装成已确认。
- **明确不适合：** 有具体证据表明无关、重复／已拒绝，或触犯该客户的明确硬条件。记录来源及理由，不因为一个模型猜测就永久拉黑。

Rio Branco原来先由关键词规则放行、后由模型按名称和字段推断是纸业，预览却同时显示“通过”和“排除”。**当前合适状态是待核实，不是已查证排除。** 下一实现应保留 `initial_screen`、`evidence_review`、`final_recommendation` 的分阶段记录，老板只看到明确解释后的最终建议；页面不能上面排除、下面又通过。

Sentry和Sakar目前是文案样例公司，不是已确定合作商。Sentry提供私标业务，只证明它具备该业务，不证明它正在寻找Channel这样的上游供应商。Apollo数据库也不是由所有自愿接受开发信的注册买家组成；官方说明包含公开网页、贡献网络和第三方来源，进入数据库不等于向Channel同意收邮件。[Apollo数据来源](https://knowledge.apollo.io/hc/en-us/articles/45824429846669-Apollo-Data-Overview)

## 9. 给老板看的公司报告：先复用Apollo，再补必要证据

每家公司一份简明资料页，老板不用再自己从主页逐页探索。首屏回答“这是谁、为什么值得谈、我们能卖什么、有什么不确定”；展开后再看证据和图片。它不是原始API JSON，也不是模型一段无出处的总结。

建议内容：公司名称／官网／地点／规模与核对日期；产品和销售渠道；与Channel能力匹配的2–3个具体理由；官网相关产品或案例的截图／图片；原网页链接和资料时间；明显冲突及未确认项；建议下一步与待审开场白。营收等估计值明确标Apollo估算；“有厂房照片”不证明自有工厂；成功案例只在有原始证据时展示。

资料来源按需使用：

1. Apollo公司查询／补全提供基础记录；有权使用AI Research时，先让它研究产品、渠道、角色和来源。不假设所有研究模式都能返回引用或图片，按实际返回验收。
2. 对缺失或冲突的关键结论，访问该公司公开官网的About、相关产品、渠道／案例页面。默认每家最多3个相关页面，最多扩到5个；命中预算后保留待核实，不全站遍历。未获预算不自动调用昂贵研究。
3. 图片从已核实页面选择1–3张，保留网址与说明；不把抓到的广告图、合作方Logo或图库图当成对方工厂。页面不可访问时如实写缺口，不让模型补图冒充实景。
4. 每条结论保存来源、抓取时间、来源类型、内容摘要和内容指纹；报告区分“网页记载”“Apollo记录”“我们的判断”“未知”。Apollo原始记录和客户成果按客户、活动、任务分别留存，不混入共享全局知识库。
5. 文案基于已批准的Channel资料包和候选已核实事实。只有通过人工选定的公司才解锁必要联系人或写文案，不为25家公司都消费邮箱额度。

是否额外Web搜索由证据缺口决定，不是每家公司机械查十遍。Apollo字段完整、官网证实业务的普通样本无需重复多源调查；身份混淆、行业冲突、失效域名等才要求独立证据。目标是降低错推荐，又保留可能值得谈但资料不全的真实公司。

## 10. 发信能力与人工审核

Apollo可以连接发送邮箱、使用单封邮件或Sequences，并支持按公司／产品上下文生成个性化邮件。付费功能是否包含在当前账号、可发多少、哪条API能操作，仍要核对，不把“有credits”当成所有发送功能已开放。[Sequences](https://knowledge.apollo.io/hc/en-us/articles/4409237165837-Sequences-Overview) · [AI文案](https://knowledge.apollo.io/hc/en-us/articles/15396174946445-Use-the-Writing-Assistant-to-Compose-Emails)

它不等于对方在Apollo注册了“愿意被联系”的商家邮箱；通过Apollo发送也仍受己方邮箱、域名声誉和接收方过滤影响，不能保证进收件箱。

本期推荐先保存Hermes待审文案。将来选Apollo发送时，先确认正确客户的独立账号和邮箱、只创建人工邮件任务或不激活的草稿，核对正文与发送状态。**不入自动发送序列，不自动发第一封。** 审核绑定客户、候选／收件人、正文版本、资料包版本和发送通道；修改正文或通道使旧批准失效。共享其他客户Apollo额度时禁止接入其邮箱、序列、联系人库或AI公司上下文。

## 11. 共享Apollo额度时，哪些边界必须守住

Hermes客户工作区与Apollo账号不是一回事。前者绑定客户身份、数据库、规则和任务；后者是外部服务的账单／账号边界。两个客户暂时共享额度，Hermes必须仍分别保存和授权。原来的真实MySQL双库测试使用了假的Apollo／模型响应，不能改口说两个真实客户共享真实Key的生产接入已验收。

现有实现：入口固定客户配置；模型不能选择客户、Key、数据库；每客户独立逻辑库和私有目录；连库核对归属标记；任务按完整客户范围读取，提交前检查绑定版本／撤权。后续sandbox是运行进程和文件的隔离层，不能替代这些业务权限。逻辑 `runtime_id` 应与容器实例编号分开，才能换sandbox而不改旧任务身份。已核对可见远端，尚未找到能明确对应“每客户sandbox”的并行后端分支；`feat/react-router-scaffold`是前端分支。最终要用具体重构提交再核对可信入口、目录、凭据、网络出口和历史任务兼容，不能先保证零重构冲突。[隔离图](../../sales-agent/diagrams/apollo-isolation-20261109.html)

**临时共享方案的强限制：**

- 只允许经批准的公共公司条件查询，两个客户分别绑定连接与额度账本；优先独立限定Key，便于分别撤销。Key不同仍不等于Apollo账号内数据不可见。
- 客户私密知识、询盘、联系人、报价、附件、策略文档，不传到共享Apollo Assistant、AI Context Center、Lists或Contacts。原生Assistant可读账号共享上下文，单独task_id不能建立客户秘密隔离。
- 禁止使用账号的其他客户已有列表／研究／联系人来补结果。返回记录只在发起客户的任务库中使用，不做跨客户候选缓存或共享文案记忆。
- Apollo账号管理员仍可能看见平台侧查询／用量／保存内容。Hermes隔离无法隐藏服务商或同账号管理员已经能看到的数据。若查询条件本身保密，就不共享该账号，改独立账号；不能承诺绝对保密后仍上传秘密。
- 切换到另一个客户的付费账号前，要由账号拥有方授权使用范围／额度；不沿用原账号的Assistant任务、OAuth、邮箱或上下文。执行新的连接身份验证、双客户同请求编号、错库／错目录、撤权、重放和费用归属验收后才启用。未决选择留给评审，不在本轮切账号。

## 12. 超时调查不能用“后来成功了”替代

已有记录至少两次模型阶段失败：整个任务约158.726秒、恢复任务90.156秒，后来约13秒成功。首次搜索页已保存，失败位置在后续模型阶段；恢复没有重复Apollo查询。这证明恢复可节省查询，不证明“DeepSeek默认思考”就是根因。

当时同时减候选、缩标签／文案、关闭思考；日志又没有保留供应商请求号、首字时间和各阶段配置，因此目前不能将某个参数变化与改善建立因果关系。下一实现应把排队、连接、首响应、生成、解析、校验和数据库提交分别计时，保存请求号、模型参数指纹、输入／输出用量、HTTP状态和取消原因，不存密钥或完整客户提示词。

重试策略：429按返回窗口退避，短暂网络故障有限重试；权限错误直接解释，不重试；生成超时可由保存页恢复一次有界尝试，仍失败就明确终止／待处理。不能每次重新查询Apollo，也不能无限重试掩盖供应商或本程序问题。正常单例成功不等于延迟分位数已经达标。

## 13. 下一轮评审需要确认什么

建议评审顺序：先确认公开知识范围及拒答恢复方案；再确认公司资料包、候选研究／报告及共享账号边界；随后看HTTP接收＋持久任务、云身份接线与调用预算；最后决定联系人和发送通道的试点。

实施前必须有代表性验收：普通公司问答＋同义追问且输入框保留；真实平台签名入口＋真实运行身份查库；合法客户／错误客户／错误任务；并发重复询盘只产生一个任务／草稿；Apollo页落盘与游标续查；冲突候选保持待核实；共享账号的秘密不进入外部上下文；模型超时恢复不重复查询；老板报告中每项事实可追到来源。后续流式正文继续排在业务稳定之后，不借本轮规整提前实现。

本轮没有启用自动派发、变更云权限、扩大Key、购买套餐、更新知识公开清单或发送买家邮件。客服咨询与只读调查按授权执行；小署名及既有实现只推评审分支，线上保持原版本。
