# 官网助手连续输出：设计与后续实施范围

2026-11-09。状态：设计待评审，未实施。统一待办编号 AI-STREAM-01，优先级在 Resend、Apollo 的业务稳定验收之后；当前答复丢失、挂起、保存失败仍属立即修复的故障，不因本设计后置而推迟。

## 这次要改善什么

访客发送“你们能提供什么耳机？”后，应立即看到 Thinking… 和简短说明。真正开始查产品或公司资料时，页面显示对应阶段；开始形成可公开的答案后，同一条回答持续增加内容，不等整篇结束才出现。

“查资料阶段”和“正文连续输出”是两件事。前者只发状态；后者要让模型服务、执行程序、内容检查、事件库和网页都能连续传递正文。这不是单改 CSS 或 BFF 的开关。

## 哪个程序在哪里，负责什么

所有程序仍属于 Channel 的官网助手，不是 HermesInfra 的 Sales 任务：

| 程序 | 位置与责任 | 当前状态 |
|---|---|---|
| 官网聊天组件 | 访客浏览器；即时反馈、卡片、同一气泡追加正文 | 新前端可接收片段，浏览器验收使用模拟 IO |
| AI BFF | Channel 的 AI 后台入口；验证访客会话，接收提问，读取事件库，用 SSE 发给网页 | 已有事件流；旧接口跳过查询阶段事件，V2保留 |
| AI Worker | Channel AI 后台的任务执行程序；调用模型／公开产品／VibeKB，检查并保存结果 | 会等整份回答通过检查才发布正文 |
| VibeKB 引擎适配包 | Worker 内的库 `packages/ai-engine-vibekb`；编排模型与 MCP 检索 | 模型请求 stream:false，完整 JSON 返回后解析 |
| VibeKB MCP | 现有知识库服务；仅查询明确获准的公开资料范围 | 已有检索接线，不回退到旧 AnythingLLM 路线 |
| PostgreSQL | Channel 聊天库；会话、运行、带序号事件、恢复位置 | 可复用现有事件与运行控制；不因连续输出新建任务系统 |

SSE 是服务器在一条保持打开的 HTTP 响应中连续发送事件的方式。网页已能读取，缺的是上游持续产生合格正文事件。模型到 Worker 的流、BFF 到网页的流，是两段连接。

## 当前为什么等整份答案

现有 VibeKB 模型调用明确使用 `stream:false` 和 JSON 输出；同一份 JSON 可能是查知识、搜产品、准备询盘或回答。部分 JSON 不是可展示正文，不能把原始片段直接发给访客。

Worker 还保留了旧知识引擎的整篇检查：来源不明确时先不公开文本，最后检查后再发出一段正文。旧设计的保护意图是合理的，但 VibeKB 已可先取到获准资料，后续应为它单独设计逐块发布条件，不能直接删除全篇保护让所有引擎一起裸流。

具体代码依据：VibeKB `src/index.ts` 的 call/streamRun；Worker 的 rawEvent token/citation 分支及 approvedEvents；BFF 的 streamEvents；前端 http-adapter 的 frames 和事件合并逻辑。

## 推荐方案：先取证据，正文按可检查的块发布

1. 浏览器发送后立即显示 Thinking…，不等网络响应。它表示请求正在处理中，不展示模型内部推理。
2. 继续复用现有内部 JSON 计划，确定要查询什么；内部计划不发给访客。
3. 实际调用产品接口／VibeKB 前，Worker 保存真实的阶段事件。查询成功、失败均由真实结果决定，不靠计时器切换。
4. 查询结果先检查归属、公开范围和字段，固定这次回答可用的资料与来源。
5. 最终文字生成请求启用流式；只让这一步生成访客可读文字。产品卡、询盘操作和需求更新仍按完整结构检查后发布，不流式拼装可点击按钮，也不执行半份 JSON。
6. Worker 将收到的字符暂存在内存中，凑成一个完整、可检查的句子／段落，再检查并保存。已有 token 事件可以承载正文块，不需要每个字写一次数据库。
7. BFF 复用现有事件序号和 SSE，将新增块传给网页；网页只给同一 messageId/runId 追加，不重复创建气泡。旧接口是否补阶段事件由兼容测试决定，不能把 V2 的支持误报成旧版也支持。
8. 最后一条事件明确完成、停止或失败。正文块已经显示但生成失败时，保留已发布内容并标明未完成，不伪造成功。

[执行先后图](diagrams/streaming-target-20261109.html)。图省略了内部短计划调用和 BFF 不断读事件库的重复过程；真实阶段也经同一事件通道及时到达网页，不是等正文结束才显示。

本方案是“生成未结束时已有正文可见”，不要求每个 token 都立即出现。不会把等整篇完成后再切成小段的动画称为真实连续输出。

## 发布边界与部分答案

- 只能使用已核验的公开资料。来源名称、私有链接和内部计划也不能提前泄露。
- 段落检查不能证明模型每句话都正确。报价、认证、交期等高风险承诺继续由现有明确规则控制；不能满足安全发布条件的回答保留完整检查，不为流式牺牲保护。
- 段落检查必须考虑相邻文本：禁止语句或敏感串可能跨网络片段，不能逐个 chunk 单独检查后拼接。
- 第一次正文发布后，后面的错误不能撤回已送出的字节。因此当前全篇检查需要逐条分类：哪些可在取资料时完成，哪些可逐块完成，哪些必须保持整篇检查。这是实施前的必要设计验收，不能仅靠 stream:true 算完成。
- 断线只重放同一运行已保存的事件，不重新问模型。若 Worker 崩溃且模型生成无法恢复，记录未完成；新的生成属于新尝试，不能把不同尝试的正文无提示拼成一份。
- 保留现有停止、运行版本与写入门禁；停止后晚到的片段不得写入当前回答。

## 改动大小与复用范围

这是中等范围的后端贯通改动，现有前端和 BFF 事件流可以复用，不是重建聊天系统。

| 模块 | 计划改动 |
|---|---|
| ai-engine-vibekb | 保留私有结构化计划；最终回答流式读取、使用量与终止原因；处理破碎 SSE 帧与 UTF-8 |
| ai-engine 的统一接口 | 明确已获准证据与可流式正文的能力／事件规则；其他引擎仍按原有完整检查运行 |
| ai-policy + ai-worker | 将资料公开检查前置；定义可逐块检查的内容与必须整篇检查的内容；有界缓冲、按序持久化 |
| ai-contracts + ai-bff | 复用事件身份、序号与重放；确保各客户端理解真实阶段和中断状态 |
| ai-store | 先复用现有 token/final/error 及事务；只有核对实际事件约束确实不足时才提出最小迁移 |
| 官网组件 | 复用已有追加逻辑；验证部分答案、中途失败、停止及减少动态效果；不重做整套 UI |

不预设必须升级模型 SDK：当前用 fetch，浏览器已有流读取器，旧引擎也有 SSE 解析经验可复用。先核对现有依赖与供应商协议，再决定是否抽取小型共用解析器；不为了连续输出先引入完整新 AI 框架。

## 调用和写入预算

- 问候等固定回答仍不调用模型。询盘／卡片等短结构结果可以完整返回，不强求一切流式化。
- 典型“短计划 → 一次知识／产品查询 → 最终答案”保持原有模型调用数量；不能先让模型生成一份完整答案，再多调用一次仅为制造流式体验。
- 只有拿到可检查正文块时才写入，网络碎片不等于数据库事件；单次回答的字节与事件总量有明确上限，达到上限应合并缓冲或停止，不静默丢字。
- 不新增每个片段的远端授权回查。复用当前运行身份与受保护写入机制，在真正写入／停止／完成边界检查。
- 第一块文字时间受检索与模型实际速度影响。记录受理、检索、首块正文、完成时间及事件数，不承诺没有实测依据的固定响应秒数。

## 后续实施顺序与验收

先完成 Resend／Apollo 当前业务验收；本待办回到设计评审时，按四个可验证步骤推进，不另造 A/B/C 模块编号：

1. 冻结内部计划与公开正文的分界、内容检查分类和兼容规则；用代表性片段验证输出协议。
2. 接一条真实模型＋VibeKB 的完整问答，保留既有任务／事件库与新旧接口；不新增额外模型回合。
3. 接真实网页，证明在模型生成完成前，同一条回答至少发生多次可见增长；同时记录查询阶段先于对应结果，不能只用模拟 IO 证明。
4. 做针对性的异常和上线验收：流在任意字符处切开、中途失败、停止竞态、事件重放、错误来源、产品结构结果、手机与减少动态效果。线上代理不缓冲要在真实官网观察，不拿本地替代。

关键缺陷注入：改回 stream:false、让 Worker 重新攒完整份、让 BFF 丢弃阶段事件、关掉事件去重、允许停止后晚到片段写入。对应断言必须失败。只覆盖因果相关风险，不穷举所有内部函数组合。
