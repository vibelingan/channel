# P7a5：减少已验证图片证明阶段的重复分轮

## 运行问题

真实生产构建组合两次在20件、每件9张共享图片时超过原90秒验收限。保留的阶段时序和失败DB确认：所有已完成件都需要5次准备worker，像素已验证9/9后还要分三轮证明；最后4件90秒时尚在证明。没有分类错误或图片invalid/retry。单件准备12.64–19.42秒，四并发按整个工作流持槽，五组累积超过门槛。证据前缀 batch-progress-diag-r1。

当前 catalog-preparation-worker.ts 把来源下载、像素检查、已保护像素证明三种循环都用 maxImages=4 限制。9张图先4/4/1检查，然后4/4/1证明；最后一个像素检查步可开始证明，所以共5步。证明阶段是逐张原事务读取已持有的、已验证的像素记录，没有外部对象下载；用相同4条上限迫使每轮再次完整读候选、租约/绑定和HTTP交接。

## 数据与约束

- 原jobId、inputDigest、contentGeneration、leaseVersion、计划摘要、每张imageId及hold/像素证明均保留。
- 原命令 attest-media-image 仍逐张执行，每次由原事务重新校验当前租约、计划、图片、hold、保护证明。没有新的批量事务，不改98操作余量或平台SDK。
- 来源下载和像素检查仍最多4张/次、顺序执行；证明阶段单步上限改为16，仍逐张检查原20秒预算减8秒收尾余量。达到时间预算立即留下原精确游标。
- 最终当前候选复查、seal和ready提交保持原样。缺分类仍保留缺分类；ready不等于允许发布。
- 线上仍为原Node20.19 Event Functions；本变更不改runtime、权限、超时、内存、环境变量、路由或存储合约。

## 修复选择

仅把证明上限与字节检查上限分开。9张应在3个像素步内完成全部证明；27张应在7个像素步加1个证明步内完成。16仍是有界工作量，大计划继续分轮；实际慢事务可能先耗完时间，绝不为了满足16而忽略预算。保留每张renew和原权限/CAS检查，本 MIU 不靠减少校验取得速度。

不采用增加发布并发、延长浏览器/测试时限、跳过像素或证明、把准备Ready当作已发布，也不合并跨图片事务。Context7本会话无工具；未新增SDK调用或改变已验证wire合约，复用原签名命令和已通过的SDK gate，修改后再次运行契约检查。
