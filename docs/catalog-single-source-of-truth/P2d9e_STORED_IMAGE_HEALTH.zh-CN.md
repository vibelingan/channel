# P2d9e：当前存储图片的联合检查

新增 readStoredCatalogImageHealth，组合实际存储字节、像素解码和最终记录读回。它不写商品、图片、来源、分类或发布状态，也不产生准备封印或发布许可。正式准备 producer、列表准入和持久操作还未接线，fullDeliveryReady=false。

## 执行顺序和结果

复用原字节检查的同一读取骨架：先核对记录与修改锁，下载一次并严格检查base64、长度、SHA及MIME签名；将已经验证的同一私有Buffer交给像素检查；等检查实际完成后，再读当前图片记录，核对存储输入digest、记录形态、锁和引用计数。成功结果仅包含imageId、digest、长度/SHA和画布/帧数，实际图片、签名地址及原生异常均不返回。

原字节接口继续只返回字节证据，新接口才返回stored-image-health-v1。新共享inspect函数只接收后端受信回调，没有HTTP入口。正常路径仍为两次记录读取、一次对象读取，不重复下载或base64解码。第三方解码证据的SHA必须与本次已校验字节相同。无主分类与这里的图片健康无关，不修改商品分类。

像素timeout/unavailable保持retry，异常也归为可重试且不泄露内容。解码期间图片被替换/删除会返回changed；新锁返回busy；坏计数器返回record。共享图片引用从0增到2不改变内容digest，也不撤销有效像素证据。最终目标变化优先于旧对象的成功、无效或重试结果。

这只是当前读取证据，不能单独长期缓存为ready。准备producer还必须绑定商品/来源/链接/策略版本及当前存储身份；可能继续被写入的目标需要完成相应版本或不可变性保护。这里没有宣称存储对象之后不会被修改。

## 实际资源反例与恢复

在自有临时Event函数中使用合成输入，代码仍为当前默认像素解码器，原生2秒和总5秒预算保持不变。记录了全部失败：

| --- | --- | --- |
| 256MiB，6000×6000 PNG，488517字节 | 通过 | 733ms |
| 256MiB，1000×1000、64帧GIF，56283字节 | 通过 | 1150ms |
| 256MiB，四次36MP PNG并发，重复输入 | 四件通过 | 526ms |
| 256MiB，16383×16383最大画布PNG | 通过 | 1673ms |
| 256MiB，四张不同最大画布并发 | 两件通过、两件timeout | 4124ms |
| 256MiB，原两张超时图片串行重试 | 两件仍timeout | 10309ms |
| 512MiB，同两张原图串行重试 | 两件通过，逐件SHA匹配 | 1353ms |
| 512MiB，四张不同最大画布并发 | 四件通过，逐件SHA匹配 | 2091ms |

最大画布为268402689像素，四图各约3.56MB，都在10MiB字节合约内。首次GIF生成曾被编码器合为32帧；显式保帧后确认实际64帧才用于云测。256MiB四不同图峰值约194MiB，512MiB约200MiB。两张失败文件在本机Node20也可正常解码，不能把云端超时归成坏内容。

只改了自有探针的MemorySize，已读回512/Active；正式应用配置没有修改。现有alibaba-catalog-sync实际为512MiB/900s/Nodejs20.19，提供后续后台准备的资源依据。该对照说明256MiB交互函数不能承担最坏图片准备，单纯限流也不足；正式准备需在后台worker的512MiB预算下执行并保留可恢复任务。它不是完整应用的P95、硬内存上界或所有图片的性能保证，P6仍需完成真实应用组合基准。
