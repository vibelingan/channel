# P2d6 完整配置图片准备

这个单元修复 worker 把 UI 选择器的 200 项上限误用为全部配置图片上限。保留来源完整数据、URL 安全策略、四并发复制、逐来源持久失败记录、手动重试固定 cutoff 和商品最后一次 CAS。不是属性筛选或正文存储拆分，也不自动分类。

完整观察中的配置 URL 逐条使用同一单 URL 策略，按原顺序去重，不受 UI 集合 cap 影响。网页选择器仍有自己的 200 上限。已经复制的图片继续通过 source-link 复用，不重复下载；时间预算在波次间判断，未完成时游标仍停在原商品，图库、描述图和可见性不做部分保存。

配置完成标记改为固定大小的 schemaVersion、完整规范化 URL 列表 SHA-256、sourceCount、unusableCount。它只表示该来源集合完成一次复制尝试，不授予发布或媒体封存权。完整来源 URL 仍在 observation，逐图失败仍在现有 catalogSourceLinks，product 不再复制整串配置 URL。摘要比较同时核对计数；格式错误或来源变化重新检查，不能当完成。旧 sources/imageIds/unusable/missing 配置标记保留读取；旧200标记遇更大的实际集合会继续准备，最后写新摘要。图库和描述图的旧标记/所有权语义不变。

| 输入或交错 | 必须结果 |
| --- | --- |
| 205+唯一配置图、HTTP/HTTPS重复 | 全部规范化去重处理，末图不漏；界面 cap 保持 |
| 旧200完成标记、实际205 | 复用已成功200张，只下载后5张，写完整摘要 |
| 波次预算耗尽/响应丢失后续跑 | 商品照片和可见性不部分保存，成功源图不重复下载 |
| 末图临时失败/永久失败 | 临时等待；永久记录数量并给检查模块编辑回退，不能假装 ready |
| 手动重试失败图 | 固定cutoff，仅失败项重新下载；成功项保留 |
| 来源、人工编辑、批准/发布/归档在复制中发生 | 原商品版本/身份/未批准draft CAS拒绝旧保存，不覆盖新状态 |
| 长URL/大量配置 | 完成标记固定大小；不因复制全部URL到product超限 |
| 完成标记损坏或来源集合变化 | 不复用错误完成状态；没有强制类型转换或静默截断 |

发布前旧 writer 必须 drain；旧 worker 不认识新摘要会重新用旧200规则写标记，不能与新 writer 混跑。P7读端先行和900秒 drain门槛保留。

现有续跑仍会扫描已复制前缀的元数据，预算是软边界，不能承诺严格12秒墙钟。该成本须在持久操作/服务协议和实际CloudBase性能验证中解决；不能通过不核对已删除的缓存图片来跳过前缀。合法超过98事务操作的发布仍由P3协议解决；本单元不以205源图复制通过冒充205独立媒体审批通过。


实现复核补充：明确重试会核对全部配置绑定，因此即使摘要没有失败也能补回已删除缓存；成功项不重下载。版本化摘要损坏不能退回旧 sources 标记伪装完成。来源缺失、损坏、停用或属于其他 sourceKey 时返回未知，不写零配置摘要；只有有效观察的空集合才清理旧配置完成状态。来源失败统计只计符合条件的草稿。

本地验收：159focused、2692全量（0失败/0skip）、51/3两个故障注入baseline及26个检出缺陷、六套类型、实际Biome/SDK、最终构建浏览器151及owned库清理。原生JSON后端另验证205个独立媒体全部检查；205个来源共享对象的另一案例覆盖末图永久失败→人工替代→审批→五页公开读回→下架/计数恢复。两项证明范围不同，不把共享对象发布当成205个独立媒体的大事务发布通过。目标云文件及真实20件验收仍待P6/P7。
