# P2d8a 上传前记录永久文件目标

状态：上传基础层已实现；导入状态机、坏数据修复、test 部署和真实商品验收仍待后续 MIU。原目录与原分支保持不变。

## 复现与边界

真实 JsonFileAdapter 和 LocalDiskMediaStorage 的隔离复现：普通 PNG 导入通过；数据库提交图片行后丢失回执，旧补偿逻辑删除了文件，留下 active 行；URL 大小写、默认端口和 fragment 会产生与网站映射不同的绑定键；已导入 URL 再次请求供应商，503 使重试失败。证据在 `output/pricing-clock-repair-2026-10-13/p2d8/import-protocol-red.log`，1 个对照通过、3 个业务反例失败。最初脚本路径错误属于测试工具错误，不计业务复现。

本 MIU 先提供上传前的持久化检查点，供后续导入协议保存永久 ID。单凭新增此接口，不能认定上述三个导入问题已修复。

## 实现

`putObject(input, { beforeWrite })` 先取得固定永久目标，等待回调完成，再写字节。回调拒绝时不写字节。数据库回执不明时，调用方必须读回确认同一操作的检查点，不能凭内存状态继续。上传失败或回执不明后，调用方保留 pending 目标用于恢复，不能立即补偿删除可能已生效的 active 文件。这个协议的调用方在后续 MIU 接入。

本地适配器先回调再创建或写文件。云适配器使用现有 node-sdk minter，只 mint 一次，将同一 ID 交给回调，再按安装的 SDK sender 发送原始 PUT 字节和五个凭据头。生产使用 Node HTTPS，拒绝 HTTP、URL 用户信息、fragment 和重定向；只有空响应体的 HTTP 200 才确认成功，整个字节请求与响应默认限时 60 秒。回调本身由数据库操作的超时和恢复协议约束。

没有检查点且输入是 Buffer 或 fs.ReadStream 时，保留原生 SDK 路径。Uint8Array 先转 Buffer；普通可读流走同一个受限 PUT sender。安装的 node-sdk 实际只接受 Buffer/fs.ReadStream，原手写接口的宽类型不符合运行时，已收紧。现有真实调用方使用 Buffer；没有修改浏览器凭据结构或上传容量。

SDK 文档查询与安装包互相核对：Context7 当前不可用；已读取 CloudBase 官方 Node 存储文档、安装包 types/index.d.ts 及 src/dist storage sender。COS 官方 PUT Object 说明成功返回 200 且响应体为空：<https://cloud.tencent.com/document/product/436/7749>。没有发送 x-cos-return-body，不接入其另外的响应格式。真实安装 SDK 的无网络探针确认 Uint8Array 在 metadata 请求前被拒绝。

## 检查与反例

- 存储测试最终 45 项，无失败、无跳过。新增测试使用独占临时目录和监听 127.0.0.1 的 HTTP 服务，检查方法、五个头、原始字节、检查点完成顺序和失败后的目标保留。测试注入的 request 仅把该独占 HTTPS 测试地址转换到本地 HTTP；生产默认 HTTPS sender 未降级。
- 11 次运行代码故障注入全部检出；每次都有通过的对照测试，且原文件逐字恢复。移除回调、漏 await、错误动词、漏头、错误字节、接受 503/204/错误响应体、移除总时限、Uint8Array 不转换均有对应失败。
- 10 次 SDK 门禁故障全部检出，基线 98 检查。覆盖真实 sender 与 minter 协议、状态/响应体/时限、回调位置、SDK 输入类型及新增发送方；保留无关正确关键字的干扰项也不能使检查通过。发送方清单从实际 fetch/request 语句扫描，排除凭据返回对象和测试断言，当前为 3 个；Git 路径使用 NUL 分隔以保留非 ASCII 和换行文件名。
- 存储、admin、public-api、alibaba-catalog-sync、local-server 共 5 个类型检查通过；三个云函数构建通过。完整回归2815项/0失败/0跳过，耗时119.48秒。

第一次“缺少回调”注入让测试等待回调而挂起，已给测试自身加有界检查，挂起不计有效故障结果。第一次 503 注入仍被响应体检查挡住，随后补上空响应体 503 才分别证明两个检查。响应体注入保留 data listener 消费流，只移除拒绝和 destroy，避免用正常请求挂起冒充错误体保护的验证。
