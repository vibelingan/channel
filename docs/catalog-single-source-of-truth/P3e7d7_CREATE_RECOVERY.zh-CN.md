# P3e7d7 创建草稿的原回执恢复

状态：创建草稿的本地单元完成，未部署。创建后发布及其他编辑入口的统一接线继续实施。

## 实际问题与边界

`createRecord` 的 create 已提交但回复丢失时，表单重试再次进入 `createCatalogProductRecord(values, undefined, ...)`，重新生成 UUID。真实 Admin/JWT/JSON 组合已复现两个草稿；不是实际商品数据异常。此前底层发布操作的 operationId 不能证明创建结果。

原分类、价格、图片、唯一 SKU/slug、贡献者 OWN-1 和非商品创建继续使用既有写入规则。新增创建协议只创建未发布商品，保留既有新建时的归档选项；不批准、不发布、不导入来源。发布意图在确认创建后单独处理。客户端恢复记录只存账号、端点、尝试 ID 与摘要，不存 JWT 或商品正文。

## 数据与流程

一次尝试为 `{attemptId:uuid, values:完整冻结的草稿输入}`。服务端以 actorId + attemptId 推导固定 productId，以实际 JSON 请求 values 的 SHA256 绑定输入。在既有原子 create 中同时保存私有 `catalogCreateReceipt:{schemaVersion,actorId,attemptId,inputDigest}`，不增加新集合、SDK方法或额外事务写入。

新 `catalogProductCreate` 的 start/get 严格分开。start 先检查原回执，再调用既有 createAction；并发 create 的 exists 只在原回执完全匹配时恢复。get 只读且检查 actor/attempt/digest。相同尝试改变输入必须拒绝，不能覆盖已创建商品。旧服务端不认识新 action，会明确拒绝，不能默默忽略新参数后重复创建。回执从普通 Admin 产品响应移除，公开响应仍由既有 allowlist 投影。

客户端写前保留尝试，丢回复先查同一尝试。已知 BUSY 仅重试相同输入，未知结果先只读恢复；用户显式重试且原查询为 NOT_FOUND 时，仅能用相同冻结输入和同一尝试再调用幂等 create，禁止生成第二个 ID。普通成功与读回成功都检查结果绑定。创建后的商品若已被编辑、归档或发布，恢复只能打开当前记录，不能将旧发布意图施加到它。不同账号/端点不能继续原尝试。

## 取舍

不以名称/SKU搜索推断成功：名称不唯一，合法用户可创建相似商品。不在浏览器按内容全局去重：同样内容可代表两次不同意图。不把新建伪装为已有商品 update：会越过原子身份索引、图片保护和创建权限。复用既有原子 create 和产品内私有回执，避免两次事务之间出现“有回执无商品”或相反状态。
