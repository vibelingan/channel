# P7a10：缓存检查与物理图片检查分开限量

## 运行问题与边界

P7a9缓存命中已只需reserve/advance原事务、零对象I/O，但循环仍n<4，9张已经有效保护的共享图仍强制3次worker。每次完整来源候选、claim、bind、checkpoint/release和HTTP往返都重复。此处应保持物理检查最多4张，同时允许有界的已保护元数据推进。

值：physicalChecks为本worker实际进入原prepareStoredCatalogImage或注入checkImage的图片数量（每张内部恢复逻辑保持），最多4；cached命中必须是本次reserve事务已验证的protectedHealth，否则必须计入physicalChecks。总处理仍最多16张（与证明元数据上限相同），原20秒/8秒收尾预算每轮前检查。达到4次物理工作就立即停，不额外预留第5张；全部缓存9张可一轮完成检查与9张证明，27张需16/11的检查与16/11证明，3次有界worker。

## 选择

将原maxAttestations命名为maxProtectedImages=16，既用于证明也限制单步总图片元数据工作。增加physicalChecks，loop同时受total<=16和physical<4约束；只有cache miss/诊断进入原检查前增加physicalChecks。源下载仍原maxImages=4，任何缓存证明都不能直接跳过advance、当前租约、候选/计划、hold或最终seal。像素/来源无缓存时仍原4/4/1和105张原分轮，不靠增加字节并发或时限。

## RED与风险

真实9/27张先按原物理4张完成保护，再生成合法9gallery+18description的共享未发布商品：零对象I/O，9张1次ready，27张恰3次并第一步只16张。原实现9张只4，27张3次只12，应失败。4缓存+5原始图片的第一轮只能完成4缓存+4物理，总8张，不能碰第5张物理图；旧循环只4。推进一个缓存后耗尽时间预算应只保存精确1张，下一轮零对象I/O继续。第5张缓存前编辑/取消必须拒绝旧ready，而非因为放宽元数据上限跳过guard。所有测试核对未发布、分类、图片集和引用计数零；原冷9/27/105图、诊断checkImage、来源上限、ACK和回滚组合随后跑Node20，再跑原20件90秒与formal全组合。


## 小流程、回归与review

6条新增RED全部按预期失败：缓存9/27张不能在1/3步完成、混合只能推进4而非8、预算后恢复仍只有4、旧循环未到第5张取消/编辑。实现后与P7a9组合19/19；补充原缓存故障回退及明确拒绝/预算后定向25/25、Node20.19相关完整组合579/579、0跳过。实际覆盖冷9张3步、冷27张8步、105张原33步，零缓存时4张物理上限未变；缓存9张1步、27张3步，第一步16张；4缓存+4物理恰8，未尝试第5张物理；缓存耗时边界只持久化1张，下一轮零对象I/O完成。并发取消/编辑在第5张缓存前仍拒绝，分类、原图片与未发布/计数状态保持。

Standards：实际审查worker物理/缓存/来源/证明循环、reserve的私有opt-in和legacy回退、advance/attest的当前数据重读、kernel/private facade、既有cache故障注入及新增小流程。每步最多16张元数据且最多4张进入原物理路径；4张达限立即停，不给第5张留hold；每轮原预算前置判断保留。cache proof只用于少一次重复保护读取，所有实际进度和ready仍由原事务完成。SDK contract gate再次通过；无SDK方法、存储/迁移/类别/价格/权限/环境变化。
