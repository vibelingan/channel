> 当前实施候选已整合为 [Catalog 发布可靠性整合方案](PUBLISH_RELIABILITY_PLAN.zh-CN.md)。本文件保留历史提案/审查记录，不再单独作为实施依据。

## 当前结论

原提案方向合理，但不能直接称为已确认可实施，更不能称为绝对不会失败。
目前没有证据说明三件时钟必须通过新增内容存储修复。应先收敛设计、明确
各阶段验证证据及退出条件，再由用户确认进入实施。

### 必须修改或补齐的设计项

1. **将 R3 从必经依赖改为条件分支。** 三件时钟的真实失败字段尚未确认；
   不能据合成超限样本引入 v4、内容分页、新集合和清理机制。先复用现有
   存储与审批协议。只有真实合法内容超出预算、且现有表达无法完整承载时，
   才单独评估分页方案，明确缺页、版本混读、重试和清理的失败语义。
2. **把 R2 的一致性规则落实到写入边界。** 不能仅写“指纹失效 + CAS”。
   需要逐入口列出来源同步、管理员编辑、图片绑定、分类及分类表变化时，
   哪个事务撤销哪一份检查结果，哪个版本条件阻止旧检查覆盖新输入。
   并举出来源更新与发布交错的完整时序，证明正式审批仍验证实际生效数据。
   当前代码的 ingest 先更新 observation，后续才协调产品；新增 readiness
   若沿用异步标记会产生旧 ready 放行窗口。设计必须消除或在正式预检中拦住。
3. **收窄 R4 的交付范围。** 本次实际验收是 20 件；现有每批上限 20、
   并发 4。50/100 件持久化发布作业是独立扩展，不能成为本次修复的必经
   实现。先证明 20 件在现有审批、共享图片引用计数、BUSY 重试与读回规则下
   可行。分类保存和正式发布仍需分别报告；有问题的单件不能拖垮其他结果。
4. **明确列表准入与历史数据启用的顺序。** 缺 readiness 字段必须定义为
   未检查。先有可查看/可修复的问题入口，再完成影子检查和数量核对，最后
   开启新准入条件。无主分类应保持无分类；Misc 无子分类是合法状态。
   新来源有问题不能替换或下架已有批准版本。回滚开关只恢复列表行为，不能
   回滚公开内容或图片计数。
5. **将验收拆为可检查的门槛。** 每个 MIU 明确红测、实现、review、本地
   测试/类型检查/lint/SDK 门槛/构建及隔离浏览器流程；这些完成后才进入
   test 部署。最后定向 resync 坏数据，逐件验证 Preview/Edit，再通过
   Assign category → Save and publish 验证 20 件，核对公开详情并恢复未发布。
   本地 20 件测试必须检查共享图库和 SKU 图片的引用计数、一次 BUSY、部分
   失败/重试剩余、版本变化，以及回退后的访问状态；现场验收不得以本地
   fixture 或 HTTP 200 代替。
