## Current-release frontend design

Retain the existing shared assignment schema and Admin function. Classifying a product never directly changes `published` unless it was already public, in which case same-family child changes may be visible immediately. Save and publish is an explicit client sequence: send the existing classification command with saved revisions requested, require every assignment to be confirmed, then issue one existing revision-checked product publish request at a time. Report each result and stop when an outcome is unknown; do not compensate, parallelize or auto-retry a possibly committed write.

## Current-release call flow

1. Preview: 1–20 selected products, saved public/draft flags, taxonomy revision and per-product `updatedAt` determine eligibility. Save and publish is unavailable for already-public or mixed selections; Save classification warns that same-family public edits can change storefront filters immediately. A published product moving to another main family remains blocked by server rules.
2. Confirm: construct the existing assignment request. Save only omits `includeSavedRevision`; Save and publish requests it. The UI does not send either command until a second intent-named confirmation.
3. Assign: one existing `catalogCategories` assignment call returns a result per product. Only complete `saved` statuses with known revisions may enter automatic publication; a transport error may follow a committed write, so unknown outcomes require a status read, not a retry.
4. Publish: the existing `publishConfirmedClassification` helper validates results, then `batchUpdateRecords('products', ids, {published:true}, savedRevisions)` makes sequential revision-checked `update` calls. Show a single delayed waiting state, not per-product live progress. At the end, distinguish confirmed successes, rejections, unknown and not-attempted items. A later unconfirmed result stops further requests; confirmed successes are never rolled back.
5. Readback: after the writes, invalidate active product/taxonomy queries and *observe errors explicitly*. Keep confirmed receipts through `refreshing`; a failed readback gets `Refresh statuses`, not `Publication failed`. Only a current successful list response can complete Done/selection clearing; a partial or unknown result retains context for inspection.

The modal never fabricates a percentage or claims a single atomic batch. When a publish response is held, it shows waiting without item numbers or enabling duplicate writes. The separate bulk Publish/Disable commands remain independent visibility operations; do not silently route them through the classification dialog.

## Trade-offs, performance and delivery

- **Verified batch semantics (2026-09-29):** `CatalogClassificationAssignmentRequestSchema.products` and the current product client publish helper cap at 20. Admin `batchUpdateSchema` accepts up to 500 IDs for *other collections* but explicitly rejects products. The repository DB facade's `batchUpdate()` loops `db().update(id)`; it is not a set-based, transactional DB command. Installed `@cloudbase/node-sdk@3.17.2` / database 1.4.3 sends multi-document `Query.update()` **without** the surrounding `transactionId` (captured by a no-network runtime probe). Latest 3.x still pins 1.4.3. Node SDK 4.1.0 / JS SDK 3.10.1 embeds database 1.5.1 and **does** send the ID for a transactional multi-update (also probed without network); official NoSQL OpenAPI documents transaction-bound `runCommands`. Context7 exposes CloudBase docs, but neither docs nor fake-transport probes prove deployed rollback, 20-item size/time limits, per-item guards or image-counter consistency. See [SDK-PROBE.md](SDK-PROBE.md).
- **Current-release path:** bounded sequential publication preserves the existing per-product approval/revision checks. It is not atomic across products; image visibility counters currently update after each product commit. Report partial outcomes honestly and do not promise faster DB writes.
- **Rejected G3 candidate A:** one dedicated bounded product-publication HTTP request carrying each product's `id` and `expectedUpdatedAt`. A server loop with per-item responses would reduce browser round trips but not DB work or guarantee a whole-batch outcome. The user explicitly rejected this approach for the current <=20 selection.
- **Deferred true set-based update:** batch-read selected products, validate their individual business eligibility in memory, then use write-time revision/approval predicates for an atomic multi-document update with an exact match count. Include image refcount changes and a durable operation receipt in the same transaction. New SDK client wiring is proven locally, but cloud acceptance, cross-collection rollback and limits require a **separate NoSQL test environment**, because the EnvId previously labeled `test` actually hosts production domains. This is a later feature, not a current-release gate or a license for blind writes.
- **150-item example (out of scope):** the existing classification dialog cannot submit 150; 100+50 was a hypothetical example, not a validated CloudBase limit. This release keeps the existing <=20 selection and sequential publication.
- **Current progress UI:** preserve G2 layout/colors. Disable repeat submit immediately; if the sequential publication settles quickly, show confirmed/partial results directly. If still pending after 250 ms, show `Publishing selected products…` without live item counters. A lost response after a possible commit needs explicit status readback before the UI claims that product's outcome. This threshold is a display delay, not a measured production latency.
- **Rejected:** directly enabling `batchUpdate` for products or issuing one blind database `published:true` update; the current server explicitly rejects products and its DB `batchUpdate` already loops `db().update` without per-product revisions or publication guards. Also reject optimistic success, automatic write retry and compensating rollback. Whether durable operation state is necessary for lost-response recovery is part of G3 proof, not an excluded feature.
- **Unverified:** customer's particular live error and dominant production request time. Local browser measurement identified table paint overflow as the document-wide blank-space source and confirmed table-local scrolling after containment. Visual feedback does not reduce the underlying network duration.
- **Build/runtime:** the UI-only release requires a site bundle rebuild, with no Admin function, database, SDK or schema change. The owned local runner built and tested the site at six exact CSS viewport widths; 720px reflow was used as a 200%-zoom-width proxy, not native browser zoom. The user confirmed `test` serves production traffic and authorized deployment and controlled Admin-page acceptance; use the UI-only fixture/restore gates in [G4-TEST-PLAN.md](G4-TEST-PLAN.md), not direct database or API writes. The deferred batch would require a separately approved server/function contract and isolated test environment.
