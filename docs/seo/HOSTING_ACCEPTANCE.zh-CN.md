## 已查明的线上行为

对 `https://supplychainsai.com` 做了匿名 GET，分别使用普通请求和 `Cache-Control: no-cache` 请求。没有添加随机 query。

| 检查 | 实测 |
| --- | --- |
| 首页、`/headphones/` | HTTP 200，正确页面 |
| 根目录不存在的路径 | HTTP 404，但正文与首页完全一致 |
| 不存在的商品路径 | HTTP 404，但正文与首页完全一致 |
| 上述 HTML 的缓存头 | `public, max-age=300, s-maxage=600` |
| 网站错误文档 | 云配置仍为 `index.html` |
| 域名接入 | HTTPService / DIRECT，静态上游 `STATIC_STORE`；当前返回没有边缘 Cache 扩展配置 |

因此目前不能说“缺失路径返回首页 200”。实际问题是错误正文，以及缓存允许未经校验复用。`s-maxage` 表示响应允许共享缓存保留，不证明当前已启用 CDN 或命中过边缘缓存。原始响应和检查报告在 `output/hosting-2026-10-20/`。

再次用不跟随重定向的 GET 确认：未知 URL 返回 `HTTP/1.1 404 Not Found`，没有 `Location`，正文 SHA-256 与首页完全相同。这是托管内部拿 `index.html` 作为错误正文，浏览器没有被 301/302 跳到首页。需要的全局页面兜底是“未知页面 → 404 状态 + 专用 404 正文”；接口仍保留 JSON 错误，服务故障也不能统一伪装成 404。

新的严格检查在现有站点得到 0/8：这些是新发布要求未满足，不代表网站不可访问。首页/分类失败于缓存规则，缺失路径失败于错误正文。线上尚未交付本分支的新商品标准页，本轮不把不存在的新页面算作旧网站故障。

## 本轮实现

- 专用 `404.html` 使用现有组件、noindex,follow，排除 sitemap。部署脚本预先检查产物，下次部署才设置错误文档为这个文件。

- 任何云端写入前先检查现有域名的缓存策略。当前线上策略会阻止部署脚本继续更新函数或上传文件，先修复配置再发布。后置完整检查继续是必需步骤，不能设置 continue-on-error。
- CI/CD 显式采集快照，构建只读保存的 JSON。上传前保存完整站点与公开快照，artifact 名带代码 SHA/run ID，保留 14 天；保留后置检查报告。
- 公共请求层只完成[设计](REQUEST_LAYER_DESIGN.zh-CN.md)，尚未接入商品页。没有 Tunnel。

## 缓存配置如何落地

目标是可变 HTML/XML/manifest 复用前必须向服务器校验。带内容 hash 的资源可以长期缓存；公开详情 API 保持 no-store。浏览器已有的旧缓存需要单独验收，更新配置不能主动删除所有浏览器缓存。

已核对官方 `ModifyHTTPServiceRoute` 与 `HTTPServiceExtension.HeadersHandler.ResponseHeadersToAdd`：支持对现有路由覆盖响应头，Action 可设 `OVERWRITE_IF_EXISTS_OR_ADD`。这条路径不要求为了设置响应头迁移到 EO，也不应调用旧 hosting CDN 域名配置去修改当前 DIRECT 域名。[修改接口](https://cloud.tencent.com/document/api/876/129797)、[数据结构](https://cloud.tencent.com/document/product/876/34822)。

已从本次真实配置生成 `cache-change-plan.json`：只对 `/`、`/*` 两条 STATIC_STORE 路由覆盖 `Cache-Control: no-cache`，保留已有扩展/其他头部；不传 AccessType、证书、上游、路径重写，也不修改其他 API 路由。代码会在 DIRECT 接入、静态路由归属或头部配置变化时拒绝沿用计划。此临时策略会让带 hash 的静态资源也重新校验，存在额外请求成本；精细长期缓存需后续核对规则能力。

该文件同时保存恢复旧响应策略 `public, max-age=300, s-maxage=600` 的反向参数。这里的 backout 只恢复之前观测到的 HTTP 行为，会留下显式头部覆盖，不能称为逐字段恢复原配置。没有假定空数组能清除配置，也没有调用修改接口。正式执行必须先重新读回比对计划中的配置 hash，再持有共享部署锁，核对变更/反向操作的真实效果。

官方字段存在只证明有配置入口。本轮没有调用修改接口，不能据此声称响应头已生效或恢复已验证。需要验证旧浏览器缓存到期后的普通刷新、ETag/304、新旧 context、API 与 HTML 分开刷新，以及失败时不会服务过期正文。

## 恢复能力的实际边界

当前安装的部署 CLI 为 3.5.9。其 hosting uploadFiles 仍逐文件增量上传；对安装代码的检查没有找到新在线文档所述的 safe/prune/备份实现。因此不能直接添加这些旗标并承诺平台会自动恢复。

保存新的构建产物也不等于保存当前线上版本。本次已另外完成实际线上备份；后续每次发布也将先保存备份。失败发布不能把自己登记为 last-successful。站点文件备份不包含云函数、数据库或对象级缓存元数据，不能当成全站基础设施快照。

应先做一个网站静态产物恢复入口：输入指定的已验证 release，不安装、不采集、不构建；先恢复兼容资源，再恢复页面和发现文件，只按已拥有的 manifest 处理精确路径差异。恢复还要经过当前撤回清单，防止旧产物复活已撤回商品。恢复配置、普通 URL hash 和缓存校验都成功后，才标记恢复完成。函数/数据库不随静态页面回滚。

目前仍不能承诺原子切换或恢复耗时。真实上传中断、回退、缓存收敛和撤回后回退，需要在现有目标上受控演练并计时；本地测试不能替代这一步。

## 发布与验证顺序

1. 实际线上备份已核验，锁内自动备份步骤已接入分支代码；上线前需让真实 workflow 执行并成功保存 artifact。
2. 将恢复执行接入现有共享锁及可信发布状态；执行前重新捕获目标当前状态，避免用本轮旧计划覆盖后来的发布。
3. 在共享锁内落地最小缓存补丁、读回普通/重新校验/条件请求，并演练反向配置；再交付本分支的 404/商品产物。发布代码需先完成与目标分支的整合，不能直接用旧 SEO 后端覆盖 pricing 后端。
4. 在同一真实目标核对正常页、真实/未知商品 URL、404、sitemap、manifest、旧缓存、刷新、图库/变体/询盘与恢复。线上写入演练使用约定的测试记录和通知去向；读取验收不创建客户询盘。

现有 workflow 名叫 Deploy Test，但没有另一个隔离环境。本轮只读线上检查可以独立执行；写配置与发布必须走同一环境的协调锁，不能在 pricing 的交付/验收中途另用 MCP 改站点。
