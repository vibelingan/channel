# 商品更新后，怎样生成新网页并安全恢复

更新于 2026-10-30。沿用原 SEO 分支。代码、本地测试、云端部署和实际验收分别记录，不能相互代替。

## 要完成的事

商品资料保存后，浏览器调用 API 能拿到新资料；网址最先返回的 HTML 也要更新，首次访问和搜索抓取才能直接看到新正文。这条链路负责重新生成和交付商品网页。普通访客与搜索引擎访问同一份 HTML。

Blog 由文章服务器读取当前公开版本，发布文章不用等待商品构建。恢复商品网页程序也不会撤回文章、恢复数据库或改价格。

| 部分 | 实际做什么 | 完成标准 |
| --- | --- | --- |
| 保存固定网页程序 | 从确定的 Git 提交取源码，连同锁文件、Node/pnpm 版本及文件校验值，存进现有私有云存储 | 下载后逐项核对，再用这份源码实际运行 Astro |
| 保存恢复材料 | 保存已接受网页包和候选包，包括快照、清单及配置；私有数据库记录其位置和校验值 | Actions 附件过期后仍可从私有存储读回，并通过原有来源和内容检查 |
| 自动通知 GitHub | 私有 CloudBase 定时函数每分钟检查待办，有变化才通知已有工作流 | 无待办不构建；重复通知合并；仍排队使用原部署锁 |
| 登记已有商品 | 将当前公开网址和上次已接受的网址登记为待检查项 | 不改商品，保留较新的待办；覆盖登记前已撤回的旧网址 |
| 生成和交付 | 用已批准的网页程序读取当前商品资料，差异上传，检查真实网址 | HTML、API、canonical、sitemap、图片、404 和缓存均通过 |
| 恢复旧程序 | 指定已保存的旧程序，重新读取当前商品资料再生成网页 | A 程序 → B 程序 → A 程序，客户内容仍为当前版本 |

## 归档放在哪里，为什么这样放

程序与网页包放在当前环境的普通 CloudBase 存储桶，路径为 `seo-recovery/objects/<SHA-256>.bin`。这个桶与静态网站托管桶不同，已只读核对为私有。上传前检查权限及生命周期规则；若该路径会自动过期或转入不能直接读取的归档存储，停止，不擅自改桶规则。

路径由完整内容的 SHA-256 决定。同一内容重试使用同一路径，不同内容使用不同路径。小对象每段限时 60 秒，大于 8 MiB 的归档每段最多 300 秒；两者都记录脱敏耗时及结果。上传后完整下载，检查长度和 SHA-256；上传回应丢失时，也必须读回完全一致的内容才能继续。工具不设置自动删除，不公开桶、不输出签名地址，不把云密钥交给网页程序。

最初考虑 GitHub Release，核对官方权限说明后放弃：包含工作流变化的提交可能需要额外的 Workflows 写权限，普通工作流令牌不能取得这项权限。尚未向 GitHub 写入 Release。最终复用现有私有存储，不扩大 GitHub 权限。Actions 附件继续用于查看日志和本次回执，长期恢复不依赖它的 90 天期限。

## 开通顺序

1. `catalog-prepare`：核对已有 6 个私有集合，补 2 个私有集合及 3 条读取索引；不改业务行、不删除旧索引。完整目录读取失败时停止，不能把查询超时当成“表不存在”。
2. `renderer-archive`：保存固定提交的程序并完整下载核对。归档本身不修改网站。
3. `catalog-clock-stage`：安装独立函数 `catalog-seo-clock`，保持关闭，不加定时器或 HTTP 路由；检查真正运行的程序提交与云端包 hash。
4. 部署全部实际商品写入程序，并核对配置一致：`admin` 和 `alibaba-catalog-sync` 都记录变化，`public-api` 与构建端使用同一批准详情模式。仅在 GitHub 填开关不算完成。
5. `catalog-bootstrap`：登记已有网址，首次生成带跟踪版本的 HTML，验收并记录接受版本。已有较新待办、客户内容均保留。
6. 完成网页程序 A→B→A 的真实交付及恢复验收，确认商品页就绪查询已开启，再按[授权说明](07-github-app-setup.zh-CN.md)开通仓库专用 GitHub App，最后开启定时通知。

准备入口沿用 `.github/workflows/seo-static-canary.yml` 和原 `test` 目标、原共享部署队列。不增加另一个日常网站发布流程，不改 main/test 的代码来抢先注册调度器。

## 写入前的范围、恢复和停止条件

资源准备仅增加本模块声明的私有集合和索引；程序归档只写本模块存储前缀及私有登记。定时函数只管理 `catalog-seo-clock`，同名但不属于本模块时停止。上述准备失败，现有网站继续运行；保留回执，先查实际结果，不重复创建或删除重建。

正式网页交付前确认当前已接受版本可下载、可校验，且网站配置与预期一致。每批上传前重新核对商品版本。明确的失败且没有未决云调用时，使用已批准程序配当前内容恢复；上传结果不明时保留锁和记录，先读回，禁止另一个任务覆盖。

权限不符、源码 CI 未通过、归档内容不符、两条商品写入入口未接通、构建期间商品或网站配置发生变化、云写入结果不明，以及 HTTP/浏览器检查失败，均不能接受发布。恢复不会还原客户数据库，不会改变 Blog 的发布状态。

## 自动通知的权限

CloudBase 使用只安装到 `vibelingan/channel` 的专用 GitHub App，申请 Actions 读写、Contents 读取和 Metadata 读取。它没有源码写入或仓库管理权限。GitHub 的 Actions 权限本身覆盖该仓库的工作流；本项目的调用代码进一步固定工作流、分支和输入，不能把平台权限说成只允许启动一个工作流。

App 私钥仅用于换取短期安装令牌，不放仓库、日志或下载包。不使用个人 CLI 登录令牌或范围未知的 `GH_PAT`。SSH 密钥不能代替这次 GitHub API 授权。按用户安排，先完成代码和可独立执行的验收，再进行这次授权。

## 怎样判断速度与结果

分别记录排队、读取商品、下载程序、安装依赖、生成 HTML、归档、上传和验收时间。八分钟是完整交付目标，不是只看 Astro 命令的时间。其他任务占队列时单列等待时间；未实测前不承诺已达标。

本地已从提交 `394fe872` 的归档还原源码，用锁文件安装依赖，读取修改后的两件合成商品，真实 Astro 构建 8.12 秒，19 份 HTML 通过 SEO 规则。这只能证明该程序能读新资料，不能代表真实 528 件商品的全站耗时。

本轮新增索引分别对应批准变体 `productId/catalogDetailRevision/_id`、旧变体 `productId/_id`、商品 `productFamily/_id` 的实际翻页查询。原索引保留。云端是否已创建，以实际回执为准。

SDK 已核对 manager-node 5.9.1、node-sdk 3.17.2、COS 2.15.4 的实际实现。归档传输现接官方 COS uploadFile/downloadFile：1 MiB 分片、最多 3 个分片并行、单次文件传输有总时限；上传保留 CloudBase 文件元数据，下载前后检查大小和 ETag，再由外层验证完整 SHA-256。普通网站图片仍用原来的受限上传/读取，不改业务媒体流程。当前是 SCF Event、Nodejs20.19 环境，定时器采用七字段表达式。Context7 当前不可用，使用官方文档、安装包源码和此前真实回执交叉核对；不添加虚构 SDK 方法。

实际进度见[总表](README.zh-CN.md)及[工作记录](WORKLOG.zh-CN.md)。[完整时序图](diagrams/renderer-delivery.html)展示设计机制，不能代替云端验收结果。


核对依据：[GitHub 创建 Release 的工作流权限限制](https://docs.github.com/en/rest/releases/releases#create-a-release)、[腾讯云 COS 生命周期读取接口](https://cloud.tencent.com/document/product/436/8278)、[Node.js SDK 生命周期示例](https://cloud.tencent.com/document/product/436/43806)。后两项都是读取配置；本实现不设置或删除生命周期规则。


本轮审查补充：只有网页交付和商品页面状态都验收完，才能更新自动通知读取的程序记录，并完整读回该记录。人工完整构建未纳入商品跟踪时，明确记为 `catalogTracked:false`。开启定时通知前还检查全部实际商品写入方、已有页面登记及公开 API 的就绪查询；仅有一份可访问的网页包不足以开启自动通知。


### 真实传输检查与方案修正

第一次 GitHub 上传约 46.7 MB 单请求在 60 秒未完成；第二次先上传 556 字节说明文件，写入和完整读取分别约 0.96、1.22 秒成功，大包单请求到 300 秒仍未完成，补读也未发现完整对象。两个失败运行均未批准程序或改网站。这个结果证明当前单请求方案无法满足交付要求；不能仅靠增加时限认定解决。

本机官方工具对照上传同一固定提交的本机归档约 32 秒、下载约 38 秒，完整 hash 相同，返回的是分片 ETag。位置与传输实现均不同，因此不能从该对照单独认定 GitHub 网络的根因。已选择官方支持的分片上传与并发下载，保留权限、生命周期、整体时限、长度和完整 hash 检查。真实运行 40994923963 仍在大包上传时到五分钟上限；没有批准程序或改网站。下一轮记录具体 SDK 阶段和已发送字节，不能把本地通过当作云端修复。只取消本模块尚在运行的旧传输测试，不取消其他部署。

本机和 GitHub 对归档压缩字节的校验值分别记录，不能拿本机包替代 CI 包的批准记录。恢复只取私有登记中实际上传并完整验证的包。

官方接口：[Node.js 分片上传](https://cloud.tencent.com/document/product/436/64980)、[Node.js 并发下载](https://cloud.tencent.com/document/product/436/64981)。下载取消采用文档和安装包实际存在的任务接口；没有补写不存在的 SDK 方法。
