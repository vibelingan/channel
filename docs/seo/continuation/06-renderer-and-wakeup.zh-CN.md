# 固定网页程序、自动更新和恢复

状态：2026-10-30 开始实现。原 SEO 分支；不改 main/test，不改其他应用。

## 本次交付要解决什么

商品保存以后，浏览器接口能立即读到新资料，但最先返回的 HTML 仍是上一次生成的。此次补齐从保存记录到重新生成、交付、验收的整条路。Blog 仍由文章服务读取当前公开版本，不参加商品构建。

| 部分 | 谁做什么 | 验收方式 |
| --- | --- | --- |
| 网页程序归档 | GitHub 从固定提交打包源码、锁文件、Node/pnpm 版本，保存校验值和长期 Release 附件 | 同一提交两次归档字节相同；篡改、错误提交、不兼容输入拒绝；真实 Astro 构建 |
| 自动唤醒 | CloudBase 每分钟查看商品待办；有变化才通知 GitHub；GitHub 仍使用现有网站部署队列 | 空队列不启动构建；重复触发不重复交付；丢失回应可查询，故障后的积压仍能处理 |
| 当前内容配旧程序 | 运行已批准的旧网页程序，但输入重新读取的当前商品资料 | A 程序 → B 程序 → A 程序，当前内容不倒退；不恢复数据库或文章 |
| 网页交付 | 沿用现有差异上传、版本检查、共享锁、HTTP 和浏览器验收 | 正文、canonical、地图、图片、404、缓存及浏览器 API 刷新；有未知云调用先查清 |
| 搜索平台 | 读取真实 Google/Bing 报告，修技术阻碍，必要时请求重抓 | 分别记录可抓取、允许收录、地图发现和已收录，不能用提交成功冒充收录成功 |

## 凭证和权限

CloudBase 只使用专门用于此仓库的 GitHub App，申请 Actions 写权限和元数据读取；不使用个人 CLI 登录令牌或未知范围的 GH_PAT。App 私钥不进仓库、日志或下载包。安装只选择 vibelingan/channel。安装令牌短期生成，过期自动重取。需要账号持有人完成这一次授权，代码和测试可以先完成。

归档程序的工作流单独申请 contents:write，只用于创建固定提交的 Release；日常生成和上传只读归档。归档附件与私有数据库里的校验值一起核对，下载到不同内容时停止。是否启用 GitHub 自身的不可修改 Release 设置另行读回，不把普通 Release 描述成平台保证不可修改。

## 写入范围、恢复和停止条件

先做独立测试资源，不修改客户商品、文章、询盘和价格。正式写入前读回线上函数版本、记录开关、当前接受版本、网站配置及索引。只更新本模块负责的函数及配置，保留未管理的配置；不删除现有索引。

正式 HTML 使用当前公开商品资料。写入前保存接受版本和候选包；失败时优先查明是否真的写入。明确没有未决请求才能用已批准程序重新生成当前内容；结果不明时保留锁和记录，禁止另一个任务覆盖。关闭自动唤醒不会关闭正常网站。客户正在写入的数据不恢复。

权限不符、源代码未通过 CI、归档校验不符、商品资料在交付中变化、网站配置变化、云写入结果不明、HTTP/浏览器检查失败时停止。不得跳过测试强行接受。

## 时间怎么计算

分别记录等待队列、读取变化、下载/安装程序、生成 HTML、归档、上传和验收；八分钟是端到端目标，不能只报告构建命令的耗时。其他部署占用队列时单独记录排队时间。每分钟检查属于尽快启动和补漏机制，不承诺严格实时。

## 当前落地文件和验收记录

- 程序归档：`scripts/release/catalog-renderer.mjs`、`catalog-renderer-source.mjs`、`extract-renderer.py` 和 `scripts/archive-catalog-renderer.ts`。归档只读 Git 对象，校验源码提交、锁文件、文件清单和下载字节；不读取本地未提交内容。
- 自动通知：`tools/catalog-seo-clock/index.mjs`、`scripts/release/catalog-wakeup.mjs`、`catalog-github-app.mjs`。仅有待办才通知；没有已验收程序或当前代码未通过 CI 就不启动。源码分支前进后先核对新提交的 CI，页面仍使用已验收的固定程序。
- 定时函数安装、停用和开启：`scripts/run-catalog-clock.ts`、`scripts/release/catalog-clock-deploy.mjs`。只管理新函数 `catalog-seo-clock`；同名但归属不符立即拒绝；不会修改 admin、public-api 或助手服务器。安装先保持关闭，读回真正运行程序的提交和云端包 hash。
- 真实页面交付仍走 `scripts/run-site-delivery.ts`；`renderer_sha` 选择已批准程序，`restore + refresh + renderer_sha` 用旧程序重新读取当前内容。不能取旧 HTML 顺带恢复业务内容。
- 正常 test 部署在记录开关开启后，先执行同一提交的程序归档，再继续原部署。记录开关关闭时该步骤跳过，原 CI 全部仍须通过；取消工作流后不继续部署。

本地证据：已从提交 `394fe872` 的归档中还原源码并用锁文件安装依赖，再读取修改后的两件假商品快照，真实 Astro 构建 8.12 秒，19 份 HTML 通过现有 SEO 规则。这个数字只是本地小数据构建，不能用来证明真实 528 商品交付达到八分钟。

本轮新增三个读索引，匹配消费者实际按 `_id` 翻页的查询：批准变体的 `productId/revision/_id`、旧变体的 `productId/_id`、产品的 `productFamily/_id`。原有排序索引全部保留；现场创建和读回另记，不把声明写好当成云端已创建。

SDK 核对：本机 manager-node 5.9.1 的类型和运行代码存在 `createFunctionTriggers`、`updateFunctionConfig`、`getFunctionDownloadUrl`；官方定时器为七字段表达式。当前环境的 admin 实际为 SCF Event、Nodejs20.19，不套用不支持 timer 的 CBF 环境。原生调用结果依照前轮真实回执读取顶层 `RetMsg/RequestId`，不是凭直觉使用 `Result.RetMsg`。Context7 当前没有可用工具；已用官方文档、安装包源码和既有真实回执交叉核对。`verify:cloudbase-sdk` 已通过。

**尚需解决的长期保存边界：**旧交付包仍主要保存在 90 天 Actions artifact，不能保证半年后原样下载。程序长期归档已经实现；接受版本和快照的长期保存也要补齐，未补齐前不宣称自动交付已可长期无人值守。此项并入本模块，不另开分支。
