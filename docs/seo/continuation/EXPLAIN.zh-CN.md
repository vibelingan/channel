# 商品页面为什么还需要更新：先看这份说明

2026-10-29。本文解释现有网站与本轮四个模块。沿用已验收的 Astro、React、API 和 Blog 服务，不引入另一套客户页面。

[看图：浏览器 API 与服务器 HTML 怎样各自更新](diagrams/html-and-api.html)。图中自动接线明确标为待实现，已有网页与接口仍继续使用。

## 同一个商品网址，分两步显示

第一步，服务器把已经保存的 HTML 发给访问者。这份文件里有商品正文，是上一次生成页面时的数据。第二步，React 在浏览器里运行，调用公开 API，再把页面更新成当前数据。正常访客和搜索引擎访问的是同一个网址、同一份初始 HTML；不存在单独给 Google 看的一套商品内容。

分类页里普通点击商品，会沿用原有的页内展开交互，直接通过API取详情；新窗口或直接打开`/products/p-…/`独立地址，才会收到该商品的初始HTML。搜索引擎索引的标准地址也是这个独立地址。两种打开方式继续保留，不能把页内API交互和独立网址混为一个加载过程。

SSG不会因为有人点菜单、打开商品或Google访问就重新执行。正常访问直接取已经生成的文件，随后浏览器才调用API。“自动更新”发生在后台内容变更之后，也不等于每个访客都要等构建。

| 网站中的部分 | 现在怎样返回内容 | 内容改变后怎样更新 |
| --- | --- | --- |
| 商品首次收到的HTML | Astro构建时生成，托管/CDN保存文件 | 需要重新生成并交付文件；自动触发仍待接通 |
| 浏览器里的商品交互 | React运行后请求公开API | 请求时读取当前公开内容；不改写托管文件 |
| Blog列表与文章 | Astro服务器按请求读取公开文章，直接返回HTML | 管理员发布后从当前公开版本读取，日常不跑GitHub构建 |

例如上午生成 HTML 时商品说明是 A，下午后台改成 B。接口此时会返回 B；打开页面的人先收到 A，随后浏览器显示 B。但是这个接口响应不会写回托管服务器，服务器保存的文件仍是 A。刷新页面会再经历一次这个过程。新商品如果没有生成文件，甚至还没有可直接打开的独立 HTML；撤回商品的旧文件也不能一直保留成 200。

这里说接口“读当前数据”，指每次实际发起请求时读取。已经打开的页面不会仅因后台改了商品就自动收到推送；现有详情会在挂载、换商品或重试时请求。接口请求若失败，也不能因此把服务器上原有的可读正文说成已经更新。

所谓“自动更新 SSG”，就是在公开商品改变后，自动生成并交付新的初始 HTML。数据库变一次不等于页面文件也变一次，这正是需要补的连接。它还同时更新标题、规范网址、内链、地图和撤回状态。只变内部字段或未公开草稿时不重建；连续改几次可以合成最新一版。

当前代码里还有一个实际区别：独立商品页的浏览器标签标题、description 和 Product 结构化数据，由 `productPageDescriptor` 在构建时写进 `BaseLayout`。详情接口刷新的是 React 商品区域，不会同步改写这些页面头部数据。因此即使Google执行接口看到了B正文，也可能仍遇到A的标题和商品描述。新增商品的独立地址、撤回后的真实404，也需要服务器处理，不能靠当前浏览器显示变了就算完成。

这是网站内容交付的一部分。代码部署确定用哪个经过测试的程序生成页面；商品内容更新复用这个程序，输入最新公开数据，不需要把每次改说明都当一次完整软件发布。具体取包、版本核对与失败恢复属于模块03。

## 把“公开变更、唤醒、合并”换成实际动作

这条自动流程仍是下一阶段要接通的工作，不是现有接口已经具备的能力：

| 步骤 | 谁做什么 | 为什么要有这一步 |
| --- | --- | --- |
| 商品公开内容生效 | 后台把允许访客看到的内容改为B，API能读到B | 私有草稿和内部同步状态不算公开变化 |
| 记下版本和待办 | 同一次数据库提交记下“这件商品现在是第几版，需要更新页面” | 避免商品已保存，更新通知却丢了 |
| 唤醒并合并 | 后台启动更新工作；同一商品连续改三次，就取最后一版 | 客户不用跑命令，也不用为每次输入都重建 |
| 更新快照和HTML | 快照是本次渲染用的公开数据JSON；Astro用它生成页面文件 | API不会替我们改服务器文件 |
| 交付并验收 | 上传变化文件，核对正文、标题、图片、地图和撤回404 | 构建通过不等于正式网址已更新 |
| 等待搜索抓取 | 搜索引擎从链接或地图发现地址，再来网站读取 | 提醒抓取不等于直接写入搜索索引 |

已有商品修改期间，浏览器可能先收到旧HTML，再从接口显示B；自动更新的目标是缩短这段时间。新增商品在独立HTML准备好前，不能给买家一个打不开的链接；撤回也要区分API已撤回和静态文件已清理。模块03补了这些过渡期的明确要求，实施时会单独验收，不能只证明旧商品修改的顺利路径。

## Google 会不会调用接口

Google具备运行JavaScript并请求API的能力，不能把“Google不会调用接口”当成它的技术限制。不过，本站目前的robots规则是禁止抓取`/api/`，只放行`/api/images/`公开图片；商品详情实际请求`/api/products/{id}/detail`，仍在禁止范围。因此在当前设置下，不能指望Google靠这个接口获取最新商品。普通买家的浏览器不受robots约束，仍正常请求接口。

Google先抓取页面，再安排渲染，最终决定是否索引；这些阶段不保证同时完成。其他抓取工具还可能不会运行JavaScript。现有商品初始HTML已提供公开正文，我们需要保持这份正文和页面标题等信息正确。

所以浏览器接口继续保留，初始 HTML 也应保持正确。这样用户更早看见当前内容，搜索和分享工具不必依赖后续脚本来纠正旧正文。我们采用 SSG 是当前商品托管方式的选择，并非 SEO 强制所有网站构建静态文件；换成每次请求生成 HTML 的 SSR 也能满足要求，但会扩大商品服务与运维改动，本轮不迁移。

[Google JavaScript 官方说明](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)。

## 页面怎样进入搜索结果

我们先把正确页面放到自己的网站。sitemap 相当于公开网址清单，canonical 表示本页认可的标准网址，noindex 表示明确要求不要收录。页面和清单准备好后，搜索引擎自行抓取；站长平台的重新抓取请求或支持的变化通知只是在提醒它，不能把 HTML 直接推入它的索引。

“允许抓取”“具备收录条件”“已经收录”“获得商品增强展示”“排名或流量提高”是不同结果。我们应交付全部应公开页面的发现入口、正文、正确状态与收录许可，并实际跟进平台排除原因；无法承诺搜索引擎选择收录每一个网址或固定时间内完成。已发现、已提交不能写成已收录。

商品增强展示还需要适用的真实报价或评价数据。缺这类数据不等于普通商品页不能收录。沿用真实公开报价，不能为了消除提示填虚假金额、评分或评论。

## 为什么 Blog 不用这样重建

Blog 已经采用请求时生成 HTML：管理员发布后，服务读取当前公开文章，为读者返回正文；列表、图片和地图也读取公开状态。因此日常发文章不用等 GitHub 构建，更不用等五分钟定时器。本轮已完成正式网站的收录开关调整与实际验收；现有后台、配图、草稿及人工发布功能继续使用。

用户已确认现有两篇公开文章可以保留并允许收录。本轮读过正文：样品检查文章为完整清单；采购准备文章较短但有实际内容，没有发现虚构公司能力、报价或认证。短文可保留，之后有客户内容再扩充，不为了 SEO 凑字数。这个内容检查不代表 Google 必然收录。

## 四份模块分别解决什么

| 模块 | 为什么需要 | 实际要做什么 | 对客户的影响 |
| --- | --- | --- | --- |
| 01 页面规则与 Blog 开放 | 有正文仍可能被 noindex 或图片规则挡住 | 把状态、HTTP头、正文、地图和图片一起检查；正式域名开放，临时地址和私有内容继续排除 | 正常发布的文章具备收录条件，编辑和审核流程不变 |
| 02 商品公开变更记录 | API保存成功后，需要有人可靠地记住该更新页面 | 商品与更新待办一起提交；失败重试、合并连续修改、覆盖所有实际写入方 | 客户照常保存商品，不需要自己跑构建 |
| 03 商品 SSG 自动交付 | 服务器文件不会被浏览器 API 响应改写 | 更新变化商品的快照与HTML，处理新增、撤回和旧任务；复用已有发布与恢复 | 下次打开先看到正确正文，现有图库、变体和询盘继续用实时接口 |
| 04 搜索平台跟进 | 页面做好与搜索引擎实际收录有时间差 | 核对 Google/Bing、处理排除原因，只通知已上线变化 | 可以知道哪些是技术问题、哪些还在等待抓取，不把地图成功当成收录完成 |

## 纠正以前的进度说法

商品独立网址、初始正文、浏览器实时读取，Blog 后台、文章服务器、图片与助手草稿链路已经分别实现并做过验收。上一轮没有同时完成商品变化自动刷新文件、正式开放Blog收录和平台跟进。此前把前面几项的完成概括成“SEO整个好了”是不准确的，造成客户预期过高。本轮已补Blog正式开放、公开图片规则和实际平台跟进；商品自动更新仍待02、03模块实现。以后按具体功能和实际部署结果报告，不用一个完成标记覆盖所有SEO工作。

历史设计里的任务编号也不能当成已实现。当前实现与验收状态统一看[模块总表](README.zh-CN.md)，每次交付分别列代码、本地测试、远端检查、部署与线上结果。
