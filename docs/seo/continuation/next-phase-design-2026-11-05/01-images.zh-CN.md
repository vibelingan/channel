# 01 图片可靠交付

> 2026-11-12评审后修订。三张已核验商品图的网站地址仍400；本轮只更新设计，没有修图或上线。先完成当前性能与搜索记录，再按只读盘点确定实际修复范围。

## 目标与现状

先让已发布图片稳定显示，再减少下载等待。三张Alibaba原图正常，网站通过事件型云函数返回Base64时超过6MB响应限制。[来源对照](IMAGE-SOURCE-CHECK.zh-CN.md)。上传上限10MiB与响应上限是两回事，不能只修三张历史图而继续让新图产生同样故障。

保留原图，生成适合网页的较小版本。商品、Blog继续用现有公开引用决定可见性；私有预览仍经登录接口读取字节，以浏览器Blob显示并及时释放。浏览器不拿云管理凭据，也不直接读私有存储地址。全部程序属于Channel，运行在既有后端或受控Node命令中，不调用模型、不新增常驻服务。

## 首轮流程：盘点、生成、切换

1. **先只读盘点。** 分页读取图片记录的实际大小及公开引用，分别列确定超限、临界范围、大小未知与未公开对象。约4.4MB只用于筛查，不能当平台准确阈值；Base64长度为 `4 * ceil(bytes / 3)`，还须加完整响应封装。元数据不够时，对必要对象补源站元数据读取，不先下载全库。保留三张已知样例，不能把它们当全站总数。
2. **固定本次范围。** 输出图片ID、来源摘要、字节数、受影响商品/文章及原因。首段从三张已知图开始，盘点出的其他故障图分批修复。只有列明写入对象和恢复办法后才执行；本次没有做全库盘点，数量仍待实测。
3. **每张先生成一个可用版本。** 沿用 `packages/media-storage` 的存储封装、像素验证与Sharp 0.35.5。现有生成器限制宽度最多1280像素，只缩小、不放大；它不是“最长边1280”的实现。照片优先WebP，透明图保留透明，文字图检查清晰度，必要时PNG。动画/SVG沿用现有安全分支，不静默丢动画。
4. **读回后登记。** 完整读回、解码、校验宽高和SHA-256，重新核对来源仍相同，才条件登记就绪版本。若原图已替换，拒绝旧结果。原图、人工alt、裁图和文章位置均不改。
5. **切换旧入口。** `/api/images/{id}` 保持身份与引用检查，改读可交付版本。已知超限图不得回退到仍会400的原件。缺产物时给明确失败反馈，不能把占位图当修复通过。

首轮命令只登记经过验证的ready结果，失败写操作回执；不先建完整任务调度、持久占用与超时接手系统。条件登记仍保留，因为其他业务可能同时换原图。多种真实生产入口接入时再在IMG-3补并发协调。

## 字段、尺寸与传输约束

11月16日首段采用现有 `images` 记录内的 `catalogWebImage` 字段，未新增 `imageRenditions` 表。原图身份、网页对象路径、尺寸、类型、字节数和摘要在同一事务中校验；沿用当前来源与权限。这是对早期独立表方案的精简。当前v1用 `sourceDigest` 绑定原件记录，对象路径由图片身份、原件SHA和产物SHA确定；记录内尚无独立 `policyVersion` 字段。只保存来源、就绪版本、宽高、MIME、字节数、SHA-256及私有存储身份，不向公开接口展开整条数据库记录。对象路径按不可变身份生成，不接受任意路径或远程URL。原件读取不经过会超限的公网图片入口。

首轮生成一个宽度不超过1280、且不放大的版本，真正的160/640/1280选择及 `srcset` 后置到IMG-4；160用于约76px缩略图的高密度屏幕副本，不能用1280压缩版冒充该尺寸已经完成。首屏目标500KiB是性能预算；首段实现的网页图硬上限为3,000,000字节，Base64正文约4,000,000字节，加上少量响应包装仍留有平台6MB限制的余量。实际19张最大384,134字节，已通过真实公网交付验收。质量达不到时停止切换，不能无限压低画质；确需更大图，再单独核对原生HTTP字节入口及成本，不未经验证挂到Blog服务。

既有小图可沿用可工作的交付；新响应MIME取实际产物，保留nosniff及SVG安全策略。快照目前只接受无参数图片路径，所以首轮保留旧URL；IMG-4若采用宽度参数，必须同段实现严格的 `w=160|640|1280` 白名单、快照解码和页面选择，不能只新增一半。当前公开图片接口不解析这些尺寸参数。

## 文章副本与商品减重：实现和部署分开验收

11月16日商品减重首轮实际结果：从美国 Before 中三页代表商品的 9 张去重图片里，选出 7 张超过 100 KiB 的图；原件合计 2,865,518 字节，网页副本 270,248 字节，减少 90.57%。原件和副本实际均为 800×800，沿用最大宽度1280且不放大的策略；这不是160px缩略图或多尺寸适配。7次独立官网 GET 均返回200/WebP，完整下载后的 SHA、大小和像素均与候选相符。提交事务保留原图字段、引用计数和其他记录，只增加 `catalogWebImage`；没有商品、文章、函数或权限写入。美国After已完成；具体LCP、FCP和未改善项见模块06，不用字节减少率冒充LCP收益。

商品HTML自动更新入口、兼容后端和两张文章副本均已完成真实验收；文章展示已启用并完成关闭/恢复检验。选定7张商品目标图也已按上方清单完成交付，没有批量重写全库或修改商品/文章正文。新图片自动准备仍未实施。完整性能采样和步骤见[模块06](06-page-performance.zh-CN.md)。

### 商品：先用现有单版本减重，再单独实现真实尺寸

先用现有 `createCatalogWebImage`、存储封装和 `registerCatalogWebImage`，为明确列出的804e图库图片及ffc8等目标准备网页副本。仍由 `/api/images/{id}` 交付，保留原图、`catalogWebImage` v1和图库中的原始图片身份；不改商品快照格式。已有有效v1时复用，不为追求更小字节偷偷覆盖它；需要改变既有v1产物时另列版本切换范围及恢复来源。这一步可以减少下载字节，但应报告“单个网页版本减重”，不能写“76px缩略图已适配”。

随后才实现160/640/1280的真实尺寸。只在已读回验证并登记ready后，展示层才可声明相应的 `srcset` 宽度。尺寸副本、选图描述、快照校验和浏览器接口须一起兼容；未知/重复尺寸参数拒绝，不允许任意裁图或远程URL。图库选择、变体绑定和询盘继续使用原图片身份，不能因请求了160版就被当成另一张商品图。未准备对应尺寸时，HTML继续选择现有可工作的默认地址，而不是把大原图冒充160像素。已发出的尺寸地址必须纳入旧渲染程序恢复兼容检查。

### Blog：独立登记，保留已发布原件事实

`ArticleMediaRecordSchema` 与已发布文章的 `media` 都是严格格式；公开读取还逐项核对原件SHA、MIME、字节数和宽高。不能直接把这些值换成WebP，也不能往 `articleMedia` 塞一个旧后台不认识的字段。后台的登录预览仍读取原件字节，经Blob显示并释放，不改为公开存储链接。

新增私有集合 `articleWebMedia`，每篇文章一个文档，主键为 `articleId`，避免渲染每张图都查一份登记记录。初版仅记录已验证ready的条目；失败保留执行回执，不先建设任务调度器。以下是拟实现的应用格式，不是CloudBase自带的类型：

| 对象 | 必需字段与严格约束 |
|---|---|
| 文档 | `schemaVersion=1`、`articleId`、`media`；每层都拒绝未知字段。`media`最多20项，键沿用当前文章媒体ID格式且与条目归属一致；所有计数/尺寸均为安全整数 |
| 每个条目 | `status=ready`、`policyVersion=article-web-v1`、`sourceDigest`、`source`、`web`；不接受客户端指定存储地址 |
| `source` | `mediaId`、`articleId`、`checksumSha256`、`mimeType`、`byteSize`、`width`、`height`、`storageFileId`、`storagePath`；均与当前active原件一致。原件沿用现有3MiB、格式及像素上限 |
| `sourceDigest` | 对上述原件身份和存储事实作固定顺序SHA-256摘要，限制为64位小写十六进制；不把人工alt、正文或无关更新时间纳入，以免合法编辑被误判为换原图 |
| `web` | `storageProvider`（现有CloudBase/local-disk提供方）、`storageFileId`、`storagePath`、`mimeType`、`byteSize`、`width`、`height`、`checksumSha256`。首段要求 `mimeType=image/webp`、字节1至3,000,000、宽1至1280、高1至16383，摘要同为64位小写十六进制；实际解码结果须逐项相符 |

准备命令先按明确媒体清单读取并验证原件，再生成、上传和完整读回副本；解码、字节数、尺寸和SHA均通过，才在事务内重读原件并合并登记。原件被替换、记录归属不符或已有不同版本时拒绝覆盖；相同ready结果复用。合并必须保留同篇文章其他条目，不能以旧映射整条覆盖并发登记。登记ready本身不授予公开权限。

对象继续用现有 `articles` 命名空间，逻辑身份由文章ID、媒体ID、原件SHA和处理版本计算，文件名含产物SHA；保存后按仓库路径封装重算并校验，不假设已有 `article-web` 命名空间。原件对象不得成为写入目标。

### 一次文章请求，同时给出正文和展示描述

新增显式读取模式：`GET /api/articles/slug/{slug}?view=render-web-v1`。无 `view` 的旧GET继续原样返回 `PublishedArticle`，不增加字段、不改旧调用方解析；新后端对未知或重复 `view` 返回明确参数错误。新模式的 `data` 使用严格格式：`{ schemaVersion: 1, article: PublishedArticle, presentation: { media: Record<mediaId, descriptor> } }`；这份格式是拟增加的Channel接口。

`article`仍按现有严格格式校验。`descriptor`仅含 `sourceSha256`、`url`、`mimeType`、`width`、`height`、`byteSize`、`sha256`，不包含私有文件ID、源站地址或凭据。摘要/尺寸/类型沿用上表约束，URL必须是本网站的媒体ID/产物SHA路径。映射可以只覆盖已就绪的部分图片，但每个键必须属于当前文章，`sourceSha256`及来源事实必须与当前已发布 `article.media` 一致。未知字段、跨文章媒体或错误来源一律拒绝。渲染只替换展示描述，正文JSON、发布revision、`contentHash`、发布时间和人工排版均不改。

`blog-pages`一次请求此模式即可取得文章和展示映射，不为每张图片再请求一次描述。新后端复用本次已读取的公开文章，额外最多读取一份 `articleWebMedia` 文档，不读取图字节、不重新扫描正文关联的原件，也不重新获取同一文章；HTML选择时核对已发布原件事实，实际文件身份在图片GET时再授权。不存在ready副本的图片不加入 `presentation.media`，渲染层沿用 `article.media` 构造原件地址；不能把PNG原件塞成WebP描述。缺表、无读取权限或登记格式错误属于部署/数据故障，不能伪装成“没有副本”；启用前必须验证。同一次请求若收到合法旧版 `PublishedArticle`，新服务器可以严格校验后按原图渲染，标记为旧格式回退；不能因新格式损坏而再请求一次或伪称副本已生效。

图片仍经现有公开文章媒体链路返回。新副本公开地址使用 `/media/articles/{id}/web-v1-{产物SHA}.webp`；`web-v1-` 区分原件本来就是相同SHA的WebP时的两种请求，不能混用。私有存储文件名仍按现有路径封装生成 `{SHA}.webp`，不把公开URL当作存储路径。原件地址及字节身份不变。服务端在读图前按当前已发布引用、原件身份和ready登记核对；读完后验证产物字节，再重新核对当前引用、文章内容版本和登记身份。原件变更、文章撤回或登记改变时不得继续返回旧字节；猜到SHA不代表获准读取。撤回后的HTTP读取应拒绝，已下载副本和既有浏览器缓存的边界另列，本段不延长缓存。

原件回退发生在生成HTML选择地址时。一个已经指向产物SHA的地址若读取失败，应明确返回503或404，不能在同一地址下偷偷返回原件字节。这样保留文件名摘要与实际内容的一致性，也便于恢复排查。

### 部署、停用与实现边界

1. 先合入当前主线并核对运行来源，部署保留旧GET的 `public-api` 读取兼容层和新媒体读取能力；不以旧SEO源码覆盖其他业务。验证旧请求与旧服务器仍可用。
2. 按仓库规则核对SDK，再建立旁表并对指定原件执行准备、读回和条件登记。没有ready副本时网站仍用原件；不因此撤回文章或更改草稿。
3. 再部署新 `blog-pages`，先关闭展示开关，确认旧模式不变；之后启用 `render-web-v1`，核对真实HTML、图片请求、后台预览和两种屏幕截图。实例数量、云账号权限、域名路由和其他app配置不在本段变更范围。
4. 性能回退优先关闭展示开关或恢复 `blog-pages` 渲染程序，保留当前文章、原件、旁表及副本。已经交付的新图片地址仍须能读取；不能同时回滚掉其读取能力。若旧 `public-api` 不认识这些地址，它不是这一阶段可直接使用的恢复来源，须保留兼容读取或前滚修复；不能靠撤文消除程序不兼容。

代码归属：复用 `packages/media-storage/src/web-image.ts`；商品沿用 `packages/db/src/catalog-web-image.ts` 和受控准备命令。Blog新增旁表读写模块及受控准备命令，接入 `packages/articles/src/public-read.ts`、`packages/db/src/article-public-reader.ts`、`apps/functions/public-api/src/http-adapter.ts`、`apps/site/src/lib/blog/server-client.ts`、文章路由/`BlogView`、`lib/blog/page.ts` 和 `packages/articles/src/render.ts`。不修改原件媒体和已发布文章格式；后台Blob预览只做回归验收。真正尺寸选择再改 `ProductMedia`、`Gallery`、快照及媒体URL解析，不混入单尺寸减重提交。

存储的 `putObject` / `getObjectAsBase64`、事务的 `ArticleStore.read/write` 是本仓库封装，不是凭名称推断的腾讯SDK方法。设计没有假设 `readMany`、原生图像转换、原子条件更新或“上传完成即激活”等平台能力。实施前按[SDK契约门禁](../../../CLOUDBASE_SDK_CONTRACT_VERIFICATION.md)核对官方接口、实际安装包、提供方和事务行为；运行 `pnpm verify:cloudbase-sdk`，再用隔离对象验证真实读写。不得为通过类型检查给运行时不存在的方法补声明。本轮无Context7工具，已通过CloudBase官方知识库读取storage/sdk，并核对安装的Node SDK 3.17.2、wx-server-sdk 4.0.2、现有存储封装和完整SDK门禁；代码和离线真实SDK测试通过，尚未执行本段新的真实存储写入验收。

## 新图临时保护：推荐与取舍

IMG-2必须同时阻止新增同类故障，不能等IMG-3接完生产者才处理。推荐暂时拒绝把无法安全交付、又没有ready网页版本的新图激活为可公开图片，复用现有验证失败与重试反馈，保留原件及当前可用版本。它不等于把整次商品同步偷偷判成功；实现前核对上传、同步和草稿调用方怎样呈现局部失败。直接把所有上传上限改小会影响原件保存，不作为默认选择。

另一方案是允许保留大图并显示“待准备网页版本”。它还需要持久状态、后台展示、重试入口及所有发布者共同遵守，成本更高；仅加标签而仍公开原件无法解决400。两种行为对业务有影响，实施前请负责人确认。无论选哪种，都不能激活不可读的新图、覆盖人工修改或改商品报价结构。

## 缓存：建议五分钟，撤回窗口须确认

当前公开入口为 `public, max-age=3600`。原设计改为一律 `no-store`，会让每次回访都重新经过函数和图片读取，不适合默认公开图。本轮改为建议 `public, max-age=300, must-revalidate`，配ETag；尚未部署，需确认可接受五分钟撤回窗口。网关若支持共享缓存，其有效期不得超过同一上限，不加延长窗口的 `stale-while-revalidate` / `stale-if-error`。

- 新鲜缓存可以直接显示，不调用函数；过期后才向图片入口核对。ETag取实际选定产物摘要。同一内容且**当前仍允许公开**时可返回304，节省图片字节；不能跳过引用检查先返回304。
- 撤回后，已经缓存的副本可能显示至本次有效期结束。到期请求通过当前引用检查，已无任何有效公开引用则404；其他已发布商品或文章仍引用时继续可读。304重新确认后的有效期也只能是300秒。
- 私有预览、未发布内容和拒绝响应保留 `no-store`。版本号、摘要或签名地址不能代替公开权限。浏览器已下载副本无法远程抹除；上线前已有一小时缓存也不会因改头立刻消失，需单列过渡期及平台可用的精确失效操作。

若业务要求撤回后每次联网读取都立即拒绝，则用 `no-store` 并接受回访成本，另测性能；不能同时承诺完全不请求服务器又立即撤权。[缓存语义](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)。
