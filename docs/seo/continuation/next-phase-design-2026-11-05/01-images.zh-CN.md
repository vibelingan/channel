# 01 图片可靠交付

## 目标与现状

先让已发布商品的图片稳定显示，再减少不必要的下载。三张大图的 Alibaba 来源正常、字节与存储记录一致，但网站通过事件型云函数返回 Base64 时遭遇 6MB 响应限制。[实际对照](IMAGE-SOURCE-CHECK.zh-CN.md)。这不是 robots 或建立文章分类能解决的问题。

## 推荐结构

`原图 → 校验与生成网页版本 → 产物记录 → 现有发布引用检查 → 公开图片入口 → HTML / React / 搜索图片字段`。

原图保持原样。新增网页用途的版本：商品卡片、详情大图、文章正文与封面。产物记录原图摘要、生成规则版本、实际格式、宽高、字节数与产物摘要；同一原图、同一规则重试复用产物。人工 alt、裁图与文章插图位置仍由现有内容记录管理，不让生成任务覆盖。

默认修复沿用现有图片身份和公开引用判断。旧 `/api/images/{id}` 返回可交付的网页版本并给准确 MIME；不能让旧地址永久留着 400。新 HTML 按用途选择版本、输出宽高和 `srcset`。首屏主图优先，下方图片按需加载；是否 preload 由实际时序决定。

上传原图大小与响应大小分别校验。事件型函数只交付有充分余量的小版本，实施时同时测试最终序列化包体，不能只看压缩前图片大小。若高质量版本无法适合该入口，改用受相同发布检查保护的原生 HTTP 字节服务；先核对真实路由与部署成本，不未经验证把商品交付挂到 Blog 服务。质量不够时报告失败，不靠无上限降低画质强行通过。

## 与其他模块的约定

- 商品和 Blog 共用产物描述，继续使用各自的发布、引用和私有预览规则。私有图片通过已登录接口返回字节，再以浏览器 Blob 显示；不公开桶、不把签名地址写进正文。
- 已发布图片仍受当前引用检查保护。首期不加跨请求共享长缓存；版本号只解决内容混淆，不能代替撤回授权。离线保存或已经下载的图片无法从访客设备抹除，这不属于 CDN 能保证的范围。
- 商品或文章公开前准备好必要版本，生成失败保留当前可工作的公开版本；不将草稿半成品加入 sitemap。历史三张失败图逐张补产物，之后分批处理现有图库，避免瞬间全库重编码。
- 公开价格、商品审批和跨文章共享图片引用继续使用现有规则；不改 pricing 的数据格式或同步逻辑。

## 分段交付及验收

| 段 | 交付结果 | 检查 |
|---|---|---|
| 1A | 原图与网页产物记录、受限生成 | 畸形文件、超大像素、透明图、文字信息图、相同任务重试；实际解码与摘要正确 |
| 1B | 三个失败地址可显示，旧地址兼容 | 正常 GET/HEAD、MIME、宽高、完整解码；旧地址不再返回平台错误；私有和撤回不能读取 |
| 1C | 商品与文章选择适合尺寸 | 桌面/手机截图，图库、放大、正文和预览；人工 alt 与位置不变；首屏字节和 LCP 对照 |

真实交付还覆盖共享引用、待确认引用、计数损坏、撤回、旧任务晚到、生成失败和恢复。先做隔离资源，再在明确范围内交付三张现有图；不改客户文字，不重新建文。

## 恢复与完成标准

切换产物前保存原映射和可工作的程序版本；原图不删除。失败回到已验证可显示的版本；原先 400 的地址本身不是可用恢复方案。程序恢复不撤销后来发布的文章或人工图片修改。

完成标准是三个样例实际可显示、受保护资源没有泄露、交互和图片质量通过；性能改善另报真实数值。涉及 CloudBase SDK 时执行仓库契约核对与 `pnpm verify:cloudbase-sdk`，依据已安装运行时，不自行补不存在的方法。[官方限制摘要](evidence/cloudbase-response-limit.md)。
