继续使用现有 Astro、React 和 CloudBase。商品先返回已经生成的 HTML，浏览器随后通过 API 读取当前公开数据；公开商品变化后，已启用的自动交付更新 HTML。Blog 继续由文章服务器直接返回当前公开文章，后台发文不等 GitHub 构建。两条链路分别保留，不迁移整站技术栈。

## 两项补查改变了什么判断

1. **三张 Alibaba 原图正常，网站交付失败。** 三个原始地址都返回 200，完整下载的 SHA-256 与网站保存记录一致；网站对应地址均返回 400，正文明确写函数响应超过 6MB。当前应修我们的传输及网页图片版本，不要求客户重新生成或重新同步商品。[商品 ID、完整名称与原图](IMAGE-SOURCE-CHECK.zh-CN.md)。
2. **撤回“Blog 分类请求 400 是已确认页面故障”的结论。** `/api/catalog-taxonomy` 是导航栏的商品分类接口，不是文章分类。漏传 `family` 人工请求返回 400；合法大类没有子分类时返回 200、空列表。旧本机报告保存网址时去掉查询参数，不能据此断言页面漏参；54 份美国报告保留完整网址，其中 222 次此接口请求全部 200。本机 Blog 样本也没有记录失败请求。不需要为此建立 Blog 分类；重复调用是否有浪费另按模块 02 核对。

## 整体如何工作

- 商品公开内容、报价权限、分类和已发布图片引用仍由现有业务数据决定。新的图片版本和分类 HTML 都读取这些规则，不新增一份商品业务事实。
- 商品变化继续走已启用的自动交付。新补的分类分页与对应商品使用同一份快照；图片产物准备并校验好后，HTML 才引用它。
- Blog 的文章、图片和 sitemap 继续根据当前公开版本返回。保存草稿不会公开；撤回文章不会因为恢复旧程序而重新上线。
- React 的交互保留。Google 能运行 JavaScript；初始 HTML 和真实链接是减少抓取依赖，也让普通访客更早看到内容，不是做一份专供搜索引擎的网页。
- 代码恢复只换程序及可重建产物。当前商品、文章、发布状态、人工修改和图片原件保留；旧程序不认识新内容格式时拒绝恢复，或用当前可工作的兼容程序，不静默丢字段。

## 各段共用的验收办法

| 核对层 | 要证明什么 | 不代表什么 |
|---|---|---|
| 局部测试 | 新规则、异常和重试正确；用隔离假数据 | 不等于线上平台配置正确 |
| 实际页面 | 原始 HTML、浏览器 API、图片和操作都正常 | 不等于 Google 已抓取 |
| 部署与恢复 | 精确版本、资源、配置可读回；当前内容不倒退 | 不等于所有历史版本都兼容 |
| 搜索实时检查 | Google/Bing 当前能够访问、允许索引 | 不等于已入索引或一定展示增强信息 |
| 结果观察 | 带日期的索引、展示、点击及业务结果 | 少量增长不能归因于某次代码改动 |

局部提交运行关联规则和小范围浏览器检查；不为每份文档或图片修改重跑全部后台批量发布流程。跨模块交付时再做整合检查。线上写入前逐段列实际环境、对象、共享锁、可恢复来源和停止条件；超出这些范围就停止，不临时扩大部署。

保留以下最低边界用例：大图响应、私有图片不泄露、撤回与共享引用、迟到请求、分类分页缩减、价格权限、代码恢复保留当前内容。它们是容易静默出错的边界，不能只以首页 happy path 代替。

## 需要审阅的选择与外部条件

本方案采用网页图片派生版本、可抓取分类分页、真实报价规则及视频独立观看页。文章分类目前没有明确业务需求，不因那次400新建后台功能。海外静态子域仍是延后方案。

无需客户决定代码细节。后续确实需要外部配合的是视频素材事实与授权、公开报价是否准确，以及主域HTTP 301若现有平台不支持时的入口选择。CDN及其费用/域名权限随延后模块另审。实施时先查账号现有能力，准备具体可审阅范围后再请求必要授权，不让客户提供共用密码。
