## 手机文章为什么曾要 17 秒

旧文章的首屏大图是 2,209,843 字节 PNG，浏览器把它当作按需加载图。新版保留原件，访客收到 91,902 字节 WebP，网页首次发送的 HTML 就标明立即加载、优先请求。第二张图缩到 67,836 字节，仍滚到附近再下载。两张公开图从 2,924,634 降到 159,738 字节。这项改动直接减少用户要下载的内容，并提前开始下载。

| 同一篇文章的 Chrome 请求阶段 | 原版 | 改版 |
|---|---:|---:|
| 网页首字节 | 1,452 ms | 1,649 ms |
| HTML 到达至发起首图 | 588 ms | 61 ms |
| 首图发起至收完 | 4,206 ms | 2,163 ms |
| 图收完至绘制 | 20 ms | 22 ms |

17.31→4.54 秒是美国 Lighthouse 手机慢网模拟中位数。每版三次，旧版 17.345 / 17.306 / 17.073 秒，改后 4.539 / 4.487 / 4.871 秒。美国出口从 Chicago ORD 换到 Minneapolis MSP；网络对全部差额的影响无法从历史两轮分离。表中四段是 Chrome 原始观测，和 Lighthouse 模拟值分别读。随后用同一个 Chrome、手机参数与限速交替做四组，每组三次。旧 PNG 按需 11.640 秒，旧图立刻请求 11.556 秒，小 WebP 按需 0.896 秒，小图立刻请求 0.836 秒。这个控制实验确认主要收益来自小图，运行时没有文章后台和其余外部资源。[旧版](https://github.com/vibelingan/channel/actions/runs/43741817103) · [改版](https://github.com/vibelingan/channel/actions/runs/43779782125) · [四组原始结果和没有采用的实验](06-page-performance.zh-CN.md)

### 继续从 4 秒往下查

Chrome Performance 看页面绘制、脚本和交互，Network 瀑布图记录请求什么时候发、网页或图片有多少字节及何时收完，Lighthouse 用固定慢网参数比对首屏和页面跳动。在这次已用的三个入口之外，CloudBase 请求编号还能把同一次浏览器等待和服务日志对应，分出应用、数据库、存储分别耗时。几十 KB 的图仍慢时先这样查；只有火焰图指向长脚本才考虑拆包，只有服务阶段证实重复读取才考虑复用。为不同类型页面选择首页、分类、代表商品、Blog 列表、带图文章、OEM、案例、视频页的主要用户动作，保持手机和桌面的比较口径。小效果、可能变慢或关系上线时需要更多配对复测。留每次数据、失败、出口、真实版本和缓存状态，避免只挑好的一轮。

真实访客的目标是手机、桌面各自至少 75% 的访问达到 LCP ≤2.5 秒、INP ≤200 毫秒、CLS ≤0.1。LCP 看最大内容何时出现，INP 看用户交互到画面响应的时间，CLS 看布局跳动。首绘、首段内容出现、等待网页头和脚本阻塞也继续记录，用来解释瓶颈。现有 Search Console 样本不足，实验室的脚本阻塞时间不能替代真实用户交互；如果持续缺数据，第一方匿名采集先审查指标、版本、路由分类、成本和保留期。[Google LCP 四段](https://web.dev/articles/optimize-lcp) · [Chrome Performance](https://developer.chrome.com/docs/devtools/performance/reference/) · [Web Vitals](https://web.dev/articles/vitals)

### 这轮跟进的耳机分类小图

在同一日本网络出口的手机慢网条件下，发布前录四次官网 /headphones/。每次都用请求编号把 Chrome 和腾讯网关的八条记录对应。分类首图是 63,062 字节的 JPEG。四次首图请求从发完至收到响应头为 1,393 / 692 / 748 / 705 毫秒，同一四次中腾讯存储读取约 685 / 120 / 162 / 173 毫秒。最慢一趟存储占了一段明显的时间；浏览器、网关、程序和存储各有各的计时边界，不能拿两层中位数直接相减，认定某个网络节点有故障。

现有方案在每次确认商品仍公开引用这张图后，让同一云函数实例短时间复用校验过的小图。此前已支持生成好的网页副本，此次把符合旧记录条件的小原图也纳入。图片需要有可核对的大小和摘要。错字节不进缓存，商品下架或图片引用撤掉后仍检查当前状态。首次读图及落到其它实例的请求仍可能读存储。这只减少重复读图的时间。
