# 09 发布提速：后置专项，保留完整能力

## 范围与现状

已有静态网页、文章服务、测试函数恢复及当前内容保留的验收记录。11 月 4 日实际自动交付工作流仍用 18 分 47 秒，八分钟目标未达到。这个模块优化交付等待，不把恢复功能重新设计一遍，也不与访客打开页面的耗时混为一谈。

用户允许本期先把网页及搜索方案做清楚，CI 速度单独后置。本文件提供高层方向，不立即调整线上工作流或抢占其他工作流的发布队列。

## 推荐交付链路

`范围判断 → 关联检查 → 固定输入构建 → 候选产物与恢复来源校验 → 持共享锁按差异交付 → 真实验收 → 接受登记与清理`。

按改变的内容决定需要哪种构建：

| 变化 | 应执行 | 不应误触发 |
|---|---|---|
| 仅设计文档 | 链接、格式及相关产物验证 | 全站后台批量发布、云部署 |
| 商品公开内容 | 当前内容快照、受影响商品/分类与地图，必要页面验收 | 每次重新安装全部工具、反复下载历史视频 |
| Blog 人工发文 | 当前公开版本与实时文章服务 | GitHub 整站构建 |
| 网站或渲染程序 | 关联代码检查、固定源码/锁文件构建与目标验收 | 重建不相关后端包 |
| 需要恢复 | 候选恢复版本兼容性、当前内容及依赖核对 | 正常每次部署重跑全部历史版本兼容测试 |

代码与内容任务继续共用现有锁。准备可并行，实际写入顺序固定；旧任务不能覆盖新内容。源码/锁文件/工具链参与缓存键，私密运行配置不进入公共缓存。缓存不命中仍可正常完整构建，不能让缓存成为正确性条件。

## 提速重点

先按阶段计时，区分排队、机器准备、安装、快照、构建、归档、上传、源站验收及最终登记。复用已经接受且摘要一致的产物和私有备份；只传变化文件，并验证实际云端结果。没有可证明的恢复来源时仍需完整备份，不能为速度跳过。

分段 CI 采用同一候选包跨阶段传递：无云权限的检查/构建与有权限的受控交付分开；不在多个 job 重复构建“看起来相同”的包。受影响检查之后，跨模块正式交付保留必要整合验收；避免每次小提交重跑全部历史业务。

## 时间目标和验收

目标是常规受控交付总耗时不超过八分钟，明确记录是否含排队，不能通过换计时起点隐藏慢步骤。首次完整备份、数据格式变化或应急恢复另列真实耗时，不用它们替代日常目标。预算在各阶段实测后分配，不先承诺每段能省多少。

验收需要同一候选内容的新旧链路对照，保留正确的备份、差异清单、完整读回及恢复结果。故障注入优先用隔离 dummy：上传部分失败、未知写入、接受登记失败、旧任务迟到；功能或权限异常就停止，速度更快也不能通过。

保留已验收的原入口作为实施期间的恢复路径；试验只作用于当前 SEO 受控入口，不改变 pricing、sales 或其他部署工作流。完成后更新入口说明和模块状态，避免两套长期并行、互相覆盖的网站交付方式。
