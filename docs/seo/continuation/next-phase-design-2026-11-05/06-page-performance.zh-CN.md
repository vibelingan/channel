## 优化架构与范围

沿用 Astro 初始 HTML 和 React 交互；不为了性能把商品功能删掉、换站点框架或重构其他业务。按资源发现、下载、服务响应、主线程处理四段分别定位：

| 分段 | 方案 | 验收关注 |
|---|---|---|
| 6A 首屏图片 | 使用模块 01 的合适版本、准确宽高和 `sizes`；真正的首屏图优先 | 字节、请求发起时间、完成时间、LCP 元素；文字图和透明图质量 |
| 6B 脚本与样式 | 找出公开页面引入的非必要后台/同步逻辑，按边界拆包；核对 GET 实际压缩 | 真实压缩字节、执行与长任务、完整变体/询盘交互；不能只看文件名 |
| 6C 字体与布局 | trace 证实字体延迟后，再选择授权允许的自托管、必要字重及加载策略 | FCP、字体切换、CLS；桌面手机截图不突变 |
| 6D Blog 响应 | 分开常驻服务响应、文章 API、数据库与渲染耗时 | 首次/连续/空闲后读取；不把所有慢响应归咎冷启动 |
| 6E 真实交互 | 对导航、筛选、商品图库/变体、询盘做点击与输入 trace | 事件等待、处理与绘制耗时；保留反馈和键盘操作 |

这些段有各自前后数据，实施按诊断优先级推进。不要盲目给所有图片 preload、给全部组件 memo，或添加 service worker、全站预渲染来掩盖实际瓶颈。

## 指标与采集约定

真实用户目标按第 75 百分位分别看手机与桌面：LCP ≤2.5 秒、INP ≤200ms、CLS ≤0.1。实验室同时保留 FP/FCP、LCP、CLS、TBT、Speed Index、TTFB、传输字节、请求数、LCP 元素及失败；FCP 1.8 秒、TTFB 800ms 只作诊断参考，不冒充三项 CWV。

优化后使用同一工具版本、页面状态、设备、CPU/网络与冷缓存条件，每页各三次，给中位数和范围。记录运行版本、出口地域、实际入口、资源版本及失败。主域 DNS 或公开内容已经变化时补一个同条件当日对照，不把所有差异都归给代码。

现有 9 页保留可比性；补按图片量和变体量分层的商品、空分类和视频页，不需测 500 多页。后台私有编辑作为功能验收，不与公开页面的 SEO 分数混报。美国测试必须验证网络出口；改浏览器定位不能模拟跨境线路。

真实用户采集如需新增，复用或引入有维护的 `web-vitals`，仅记路由类别、版本、设备、粗粒度地域和指标，不收询盘内容、token、全文 URL。先确认现有统计和隐私要求；不能擅自上线第三方跟踪。样本不足就报告不足，不用三次实验宣称真实用户达标。

## 发布与恢复

先评审本设计，实施时每段小范围验收，UI 变化先给截图。前后表不填预测收益；任何交互、权限或内容缺失都不能因跑分快被放行。回退对应程序/资源版本，保留当前商品和文章；真实用户指标随后单独观察。

本设计应用 core-web-vitals、performance、既有 React 性能审查原则；具体修改仍须由 trace 支持。[Google 指标定义](https://web.dev/articles/vitals)。

## 底层设计：先把测量条件固定

扩展现有 `scripts/performance/`，保留9个已有URL便于比较，再补实际图片较多/变体较多商品及空分类、视频页。每份样本记录源码或部署版本、页面内容revision、测试工具与浏览器版本、CPU/网络条件、缓存、出口country、请求/最终URL、错误和LCP元素。分类网址仅保留允许的family/page等参数；诊断时不能再次删除参数后误判400。

载入测试使用现有美国运行入口，各类手机/桌面各三次；地区、网络、页面版本变化时单列，不硬拼前后平均值。历史11月4日共54次美国样本不重写。新的优化前与优化后共用清单和参数，输出逐页中位数、范围、失败次数、FP/FCP/LCP、TBT、CLS、Speed Index、TTFB及字节与请求数。失败保留，不以增加重跑次数挑出好看的三个值。

另加真实交互旅程：打开商品→切图→选变体→填写并打开询盘；分类筛选→翻页→前进后退；Blog列表→文章。保留事件等待、处理及绘制分段和长任务归因。实验得到的是这些操作的响应时延；用web-vitals收集到一次会话INP时也只标实验室会话，不宣称达到真实访客p75。

## 底层设计：按因果逐段改

| 位置 | 具体方案 | 不允许的取巧 |
|---|---|---|
| 商品/文章图片 | 复用IMG-4的尺寸描述；renderArticle和ProductMedia显式选择宽度；LCP图在初始HTML可发现 | 把所有图片高优先级，或压到字看不清 |
| 公开React依赖 | 用Vite产物及import链定位后台/同步逻辑如何进入公开包，再拆到明确的纯类型/展示入口；大交互模块按真实操作加载 | 删除变体、询盘或助手功能来压体积；套用Next专用API到Astro |
| CSS/字体 | 对GET核对br/gzip及实际传输大小；trace证实字体延迟后只保留必需字重或授权允许的本地字库 | 仅看HEAD就断言没压缩；为了分数重做品牌字体 |
| 页面布局 | 图片/视频占位与异步模块保留尺寸；现有reveal无JS默认可见的规则不变 | 用opacity隐藏LCP或正文来改测量 |
| Blog服务器 | 在一次公开请求内分开记录文章读取、渲染与总耗时，复用已读取数据；不引入共享私有内容缓存 | 冷启动万能解释、每层重新查同一文章、缓存草稿 |
| 交互 | 只对trace指出的长任务拆分处理；稳定props、订阅范围和必要列表渲染 | 全站无依据memo；用假百分比替代真实状态 |

公开源码修改先核对当前main中的网站助手改动。主站助手属于其他工作流，本模块只给出资源和时间归因；确需它配合拆包时留下具体接口建议，由其工作流实施，不擅自改它的UI、模型或后端。

## 调用预算、门槛与数据保存

测量页面只读，不提交真实询盘或后台批量操作。加载基准不产生模型调用；若现有助手启动本身发请求，分别计入并标明，不自动打开聊天触发回答。每个变更只跑受影响代表页的三次对照，整合交付再跑一次完整清单。没有改动/新假设不反复全量回归。

最小验收包含：主要商品和图文LCP有可复核改善、CLS无明显退化、真实业务操作正常、没有新增失败请求，实际目标仍为LCP≤2.5秒、INP≤200ms、CLS≤0.1的真实用户p75。某类尚未达标就报告剩余资源与耗时，不能以总分提高宣称CWV全过。

首期采用CrUX/GSC加可复现的实验，不另开RUM数据库和第三方服务。若访问样本持续不足，再提交基于web-vitals的第一方采集：路由类别、发布版本、设备类型、指标值，去掉用户输入和token；采样率、保留期和请求费用另审。没有这些现场数据就把真实用户INP标为未知。
