## 11 月 19 日补验，Blog 更新时怎样避免页面丢样式

网站更新文章页面程序时，浏览器先取正文，再按正文里的地址取样式和脚本。两个请求可能分别到达新旧程序。两份真实部署包的五个脚本摘要完全一致，样式表则从 `404.CqKyFG8Y.css` 变为 `404.BzUXLb2V.css`。用这两份原包、本机真实 Chrome 和同一份已公开文章数据，主动交换两类请求的接收方。两次交叉都得到正文 200、样式 404，标题变成浏览器默认的 32px。原来同版请求是 200、200、30px。线上部署时也观察到两次新样式 404，当时的回执不足以确定每一次请求落到了哪台实例。

发布工具先从官网读到运行版本，再核对 GitHub 保存的两份已验收程序和资源摘要。若新版增加了样式或脚本地址，第一轮只把新文件加到当前程序，让它继续返回原来的网页。下一轮在官网确认新旧资源均可完整读回后，再提交新程序，新程序也保留旧资源。如果资源地址都已就绪，一轮即可提交新程序。每轮只提交一次，保留写入前的云端镜像。第二轮保存的上一版就是携带两套资源的旧程序，可以用于回退。样式和脚本仍走原来的网址和缓存。

### 文章图片直达接口与耗时记录（11月17日上线验收）

这一步只改变图片怎样送到读者浏览器。文章服务器照常先返回文章HTML；浏览器随后直接向网站的公开图片接口取图，文章服务器不再代转图片。图片是否已发布、是否已撤回，仍由同一个接口检查。

正文接口的 `getRender` 依次读取文章地址登记、已发布正文和网页图片登记，共三条文档读取，旧 `get` 为前两条。它们在同一个CloudBase事务内。仓库[同事务真实并发对照](../../../catalog-single-source-of-truth/P7a1_NATIVE_TRANSACTION_READS.zh-CN.md)已有并发读2/3次出现 `TransactionBusy`、串行读通过的记录，所以不能直接把后两条改为 `Promise.all`。事务外并行又会改变共同快照和撤回检查，需要另做一致性设计，当前不采用。

当前代码给文章服务器增加两项 `Server-Timing`：`article-read` 是文章API往返、正文读取和解析的合计；`blog-handler` 是中间件等待页面处理器产生响应的时间。两者重叠，不能相加，也不等于全部HTML流传输时间；尚未分别测量API内部三条数据库读取。数字之外不输出数据库名、凭据或用户资料。[响应头说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Server-Timing)。11月17日切换前，浏览器先请求 `/blog/media/articles/...`，文章服务再调用 `/api/articles/media/...`；后者负责核对公开引用、读取存储并返回字节。新程序在 `BLOG_MEDIA_DELIVERY=api` 时，HTML和结构化数据统一使用同域现有API地址，应用HTTP层数由两层降到一层；未设置时仍走 `proxy`，无须立即切换。正常成功、无事务冲突重试时，每图仍是6条文档读取、2次事务、1次临时下载地址查询和1次对象GET，不能宣称减少了授权检查或所有数据库调用。

直达前须精确放行 robots 的 `/api/articles/media/`，保留其他私有/JSON接口的屏蔽；旧 `/blog/media/...` 持续兼容，公开/撤回/换源核对不减少。完成同一篇文章、相同美国条件下三次对照后，再决定是否处理正文读取。26项定向测试和两种地址的实际打包服务器联测已通过，其中直达模式还运行真实浏览器旅程；另通过Astro检查、测试类型检查和CloudBase SDK门禁。上述本地检查、三项远端工作流以及本次真实部署和新旧方式切换分别通过；实际数据见本页11月17日记录。数据库并发方式没有改动。

本次已执行的顺序：保留当前公开文章与配置 → 美国手机/桌面各三次Before → 更新文章程序但保持proxy → 正常部署robots的精确Allow → 读回确认 → 切换api → 新旧图片地址和内容摘要验收 → 切回proxy验收 → 再启用api测After → 因未证明收益，切回proxy做一次对照并保留。美国结果见本页最新记录。恢复时把模式切回proxy，保留新兼容程序、正文和图片；若程序本身异常则用已归档的上一镜像恢复。公开图片非200、摘要不同、文章内容/日期变化或其他环境变量变化时立即停止后续切换并恢复。既有部署工具不改，CDN与发布提速继续后置。

后端先提供兼容读取，再准备副本，最后部署并启用新文章渲染；旧GET和旧图片地址须一直工作。正常文章HTML请求仍只有一次文章API往返，最多额外读取一份每篇文章的旁表，不在渲染过程中读图片字节或为每张图发请求。图片GET复用当前引用检查，副本读取前后各核对一次登记；这些额外数据库读取单独计数，不声称整条调用只有一次读库。图片转换只在受控准备中发生，不在读者请求内执行Sharp。

| 交互 | 只对trace指出的长任务拆分处理；稳定props、订阅范围和必要列表渲染 | 全站无依据memo；用假百分比替代真实状态 |

公开源码修改先核对当前main中的网站助手改动。主站助手属于其他工作流，本模块只给出资源和时间归因；确需它配合拆包时留下具体接口建议，由其工作流实施，不擅自改它的UI、模型或后端。

## 调用预算、门槛与数据保存

测量页面只读，不提交真实询盘或后台批量操作。加载基准不产生模型调用；若现有助手启动本身发请求，分别计入并标明，不自动打开聊天触发回答。每个变更只跑受影响代表页的三次对照，整合交付再跑一次完整清单。没有改动/新假设不反复全量回归。

最小验收包含：主要商品和图文LCP有可复核改善、CLS无明显退化、真实业务操作正常、没有新增失败请求，实际目标仍为LCP≤2.5秒、INP≤200ms、CLS≤0.1的真实用户p75。某类尚未达标就报告剩余资源与耗时，不能以总分提高宣称CWV全过。

首期采用CrUX/GSC加可复现的实验，不另开RUM数据库和第三方服务。若访问样本持续不足，再提交基于web-vitals的第一方采集：路由类别、发布版本、设备类型、指标值，去掉用户输入和token；采样率、保留期和请求费用另审。没有这些现场数据就把真实用户INP标为未知。
