# 06 页面性能：先看基准，再逐段优化

## 优化架构与范围

沿用 Astro 初始 HTML 和 React 交互；不为了性能把商品功能删掉、换站点框架或重构其他业务。按资源发现、下载、服务响应、主线程处理四段分别定位：

| 分段 | 方案 | 验收关注 |
|---|---|---|
| 6A 首屏图片 | 使用模块 01 的合适版本、准确宽高和 `sizes`；真正的首屏图优先 | 字节、请求发起时间、完成时间、LCP 元素；文字图和透明图质量 |
| 6B 脚本与样式 | 找出公开页面引入的非必要后台/同步逻辑，按边界拆包；核对 GET 实际压缩 | 真实压缩字节、执行与长任务、完整变体/询盘交互；不能只看文件名 |
| 6C 字体与布局 | trace 证实字体延迟后，再选择授权允许的自托管、必要字重及加载策略 | FCP、字体切换、CLS；桌面手机截图不突变 |
| 6D Blog 响应 | 分开常驻服务响应、文章 API、数据库与渲染耗时 | 首次/连续/空闲后读取；不把所有慢响应归咎冷启动 |
| 6E 真实交互 | 对导航、筛选、商品图库/变体、询盘做点击与输入 trace | 事件等待、处理与绘制耗时；保留反馈和键盘操作 |

这些段有各自前后数据，实施按诊断优先级推进。不要盲目给所有图片 preload、给全部组件 memo，或添加 service worker、全站预渲染来掩盖实际瓶颈。

## 指标与采集约定

真实用户目标按第 75 百分位分别看手机与桌面：LCP ≤2.5 秒、INP ≤200ms、CLS ≤0.1。实验室同时保留 FP/FCP、LCP、CLS、TBT、Speed Index、TTFB、传输字节、请求数、LCP 元素及失败；FCP 1.8 秒、TTFB 800ms 只作诊断参考，不冒充三项 CWV。

优化后使用同一工具版本、页面状态、设备、CPU/网络与冷缓存条件，每页各三次，给中位数和范围。记录运行版本、出口地域、实际入口、资源版本及失败。主域 DNS 或公开内容已经变化时补一个同条件当日对照，不把所有差异都归给代码。

现有 9 页保留可比性；补按图片量和变体量分层的商品、空分类和视频页，不需测 500 多页。后台私有编辑作为功能验收，不与公开页面的 SEO 分数混报。美国测试必须验证网络出口；改浏览器定位不能模拟跨境线路。

真实用户采集如需新增，复用或引入有维护的 `web-vitals`，仅记路由类别、版本、设备、粗粒度地域和指标，不收询盘内容、token、全文 URL。先确认现有统计和隐私要求；不能擅自上线第三方跟踪。样本不足就报告不足，不用三次实验宣称真实用户达标。

## 发布与恢复

先评审本设计，实施时每段小范围验收，UI 变化先给截图。前后表不填预测收益；任何交互、权限或内容缺失都不能因跑分快被放行。回退对应程序/资源版本，保留当前商品和文章；真实用户指标随后单独观察。

本设计应用 core-web-vitals、performance、既有 React 性能审查原则；具体修改仍须由 trace 支持。[Google 指标定义](https://web.dev/articles/vitals)。
