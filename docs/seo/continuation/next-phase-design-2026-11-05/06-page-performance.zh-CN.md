# 06 页面性能：先看基准，再逐段优化

## 11月19日续测：商品首图复用官网连接

上一轮发布后，代表商品的手机首屏仍需4.86秒。这次查看浏览器怎样取得首图。商品网页由官网提供，初始HTML却让浏览器到腾讯云的另一域名请求主图。两个域名现有的公开图片入口都能返回同一张16,116字节WebP。完整内容摘要相同。两端用不存在的图片编号均返回404，用不支持的宽度均返回400。原入口要求不保存响应，新入口要求每次复用前重新确认，两者均未在这次操作中改动响应规则。

在当前正式商品页做四组交叉对照，每次启动全新的Chrome，手机视口412×823，DPR 1.75，150ms限速延迟、下行200,000字节/秒、四倍CPU减速，并关闭浏览器缓存。测试只转发这张照片的真实GET，网页、图片和其他资源均由各自线上入口响应。用响应的实际服务器地址、缓存头及完整文件摘要核验两组请求。预试发现Chrome的响应事件仍保存改写前的URL，因此未用该字段判断实际连接，对照的八次结果均通过后再汇总。

| 浏览器观测 | 现有图片域名 | 官网图片入口 |
|---|---:|---:|
| 网页首字节，中位数 | 1.63 秒 | 1.63 秒 |
| 主图建连，中位数 | 1.42 秒 | 0.16 秒 |
| 主图请求到读完，中位数 | 3.02 秒 | 1.68 秒 |
| 主图出现，中位数 | 5.61 秒 | 4.56 秒 |
| 主图出现，全部样本 | 5.52、5.52、5.70、5.72 秒 | 3.94、4.47、5.82、4.65 秒 |

官网组一次复用网页连接，另外三次各自建连但较短。四组中三组更快，一组更慢。同一台测试电脑的限速对照解释了这条链的改进依据，外部真实流量的收益要在交付后另测。工具与计时定义见[Chrome网络协议](https://chromedevtools.github.io/devtools-protocol/tot/Network/)和[Playwright请求改写](https://playwright.dev/docs/api/class-route#route-continue)。

另拆开正式网页首字节的等待。两组的建连及TLS中位数分别约0.96秒、0.94秒，从发出HTTP请求至收到响应头约0.67秒、0.68秒。该等待包含网络往返和网站响应，只有这份浏览器时间线无法继续分到网关与应用。上一轮美国24份Lighthouse记录的页面正文也都用HTTP/1.1。本机另用支持HTTP/2的curl访问同一商品、图文文章和独立图片API，三项实际协商结果都是HTTP/1.1。减少首次建连等待是后续可检验的方向，现有证据不代表腾讯所有入口均不支持HTTP/2。

方案只针对已核实官网的独立商品页，把图库主图的地址写成现有官网路径。商品照片编号、结构化数据、缩略图、说明图和有效引用检查保持各自既有行为。浏览器收到官网主图错误时，启用JavaScript的页面用原域名重试同一张图、同一尺寸，之后才用原有失败处理。旧程序仍可使用原入口，恢复无需改内容数据或网关。按项目现有权限和发布门禁固定代码版本；若同源入口返回的内容不一致或正常页面重复请求主图，停止交付或恢复网页程序。验证预算是每次打开一份主图，只有明确失败才多请求一次原路径。

本机从旧行为会失败的SSR断言开始，验证39项相关测试和类型检查。接着用3件商品构建初始HTML，22份HTML与13个可收录地址通过SEO检查。本地构建的实际商品页在Chrome有脚本及无脚本时均只向官网请求一次640档图片。注入一次官网503后，只向原地址重试一次，取得同一内容。页面和脚本来自候选产物，成功图片请求走真实网站服务。[网页程序归档44360965463](https://github.com/vibelingan/channel/actions/runs/44360965463)完整读回。正式交付[44361401013](https://github.com/vibelingan/channel/actions/runs/44361401013)耗时28分钟，登记为`site-44361401013-1`，使用528件现行商品，商品自动更新读回相同的`baed17b0`网页程序。发布回执中的初始HTML、最新商品数据、分类分页和询盘检查均通过，业务写入为零，两只临时函数也已独立查询确认不存在。

从正式网址直接读回的商品初始HTML中，主图和三个尺寸均使用官网路径。新的无脚本Chrome只请求一次640档，16,116字节和内容摘要均与原入口一致。另在启用脚本的浏览器里只模拟一次官网图片503，程序确实向原入口重试了同一尺寸，原入口200后图片成功绘制。用户页面实测正常，模拟的失败仅存在于测试浏览器。真实整页速度由[美国复测44366803040](https://github.com/vibelingan/channel/actions/runs/44366803040)另行核对。

## 11月19日复盘：17.31秒降到4.54秒是怎么测到的

这项工作让读者在手机上较早看到文章首屏大图。原来，文章服务器把首图的2,209,843字节PNG交给浏览器，首图还要等浏览器判断它位于可见区域附近才开始加载。上线时把它换成91,902字节WebP，在最初HTML里标为立即加载、优先请求；第二张图从714,791降到67,836字节，仍按需加载。两张公开图合计2,924,634→159,738字节。原件保留供后台使用。这里没有靠新增CDN、扩大缓存或拆JavaScript包取得这次收益。具体渲染规则见仓库的 `packages/articles/src/render.ts`。

**历史线上测量。** [原版](https://github.com/vibelingan/channel/actions/runs/43741817103)与[改版](https://github.com/vibelingan/channel/actions/runs/43779782125)各取三次同一手机页面。Lighthouse按相同手机参数模拟的LCP中位数为17.306→4.539秒，三次分别为17.345/17.306/17.073和4.539/4.487/4.871。两轮美国网络出口由ORD换到MSP，不能把全差额归给代码。下面四段来自浏览器原始时间线，按各段三次分别计算中位数，与Lighthouse的模拟数值口径不同。

### 文章图片直达接口与耗时记录（11月17日上线验收）

这一步只改变图片怎样送到读者浏览器。文章服务器照常先返回文章HTML；浏览器随后直接向网站的公开图片接口取图，文章服务器不再代转图片。图片是否已发布、是否已撤回，仍由同一个接口检查。

正文接口的 `getRender` 依次读取文章地址登记、已发布正文和网页图片登记，共三条文档读取，旧 `get` 为前两条。它们在同一个CloudBase事务内。仓库[同事务真实并发对照](../../../catalog-single-source-of-truth/P7a1_NATIVE_TRANSACTION_READS.zh-CN.md)已有并发读2/3次出现 `TransactionBusy`、串行读通过的记录，所以不能直接把后两条改为 `Promise.all`。事务外并行又会改变共同快照和撤回检查，需要另做一致性设计，当前不采用。

当前代码给文章服务器增加两项 `Server-Timing`：`article-read` 是文章API往返、正文读取和解析的合计；`blog-handler` 是中间件等待页面处理器产生响应的时间。两者重叠，不能相加，也不等于全部HTML流传输时间；尚未分别测量API内部三条数据库读取。数字之外不输出数据库名、凭据或用户资料。[响应头说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Server-Timing)。11月17日切换前，浏览器先请求 `/blog/media/articles/...`，文章服务再调用 `/api/articles/media/...`；后者负责核对公开引用、读取存储并返回字节。新程序在 `BLOG_MEDIA_DELIVERY=api` 时，HTML和结构化数据统一使用同域现有API地址，应用HTTP层数由两层降到一层；未设置时仍走 `proxy`，无须立即切换。正常成功、无事务冲突重试时，每图仍是6条文档读取、2次事务、1次临时下载地址查询和1次对象GET，不能宣称减少了授权检查或所有数据库调用。

直达前须精确放行 robots 的 `/api/articles/media/`，保留其他私有/JSON接口的屏蔽；旧 `/blog/media/...` 持续兼容，公开/撤回/换源核对不减少。完成同一篇文章、相同美国条件下三次对照后，再决定是否处理正文读取。26项定向测试和两种地址的实际打包服务器联测已通过，其中直达模式还运行真实浏览器旅程；另通过Astro检查、测试类型检查和CloudBase SDK门禁。上述本地检查、三项远端工作流以及本次真实部署和新旧方式切换分别通过；实际数据见本页11月17日记录。数据库并发方式没有改动。

本次已执行的顺序：保留当前公开文章与配置 → 美国手机/桌面各三次Before → 更新文章程序但保持proxy → 正常部署robots的精确Allow → 读回确认 → 切换api → 新旧图片地址和内容摘要验收 → 切回proxy验收 → 再启用api测After → 因未证明收益，切回proxy做一次对照并保留。美国结果见本页最新记录。恢复时把模式切回proxy，保留新兼容程序、正文和图片；若程序本身异常则用已归档的上一镜像恢复。公开图片非200、摘要不同、文章内容/日期变化或其他环境变量变化时立即停止后续切换并恢复。既有部署工具不改，CDN与发布提速继续后置。

沿用 Astro 初始 HTML 和 React 交互；不为了性能把商品功能删掉、换站点框架或重构其他业务。按资源发现、下载、服务响应、主线程处理四段分别定位：

| 分段 | 方案 | 验收关注 |
|---|---|---|
| 6A 首屏图片 | 使用模块 01 的合适版本、准确宽高和 `sizes`；真正的首屏图优先 | 字节、请求发起时间、完成时间、LCP 元素；文字图和透明图质量 |

## 指标与采集约定

真实用户目标按第 75 百分位分别看手机与桌面：LCP ≤2.5 秒、INP ≤200ms、CLS ≤0.1。实验室同时保留 FP/FCP、LCP、CLS、TBT、Speed Index、TTFB、传输字节、请求数、LCP 元素及失败；FCP 1.8 秒、TTFB 800ms 只作诊断参考，不冒充三项 CWV。

优化后使用同一工具版本、页面状态、设备、CPU/网络与冷缓存条件，每页各三次，给中位数和范围。记录运行版本、出口地域、实际入口、资源版本及失败。主域 DNS 或公开内容已经变化时补一个同条件当日对照，不把所有差异都归给代码。

现有 9 页保留可比性；补按图片量和变体量分层的商品、空分类和视频页，不需测 500 多页。后台私有编辑作为功能验收，不与公开页面的 SEO 分数混报。美国测试必须验证网络出口；改浏览器定位不能模拟跨境线路。

真实用户采集如需新增，复用或引入有维护的 `web-vitals`，仅记路由类别、版本、设备、粗粒度地域和指标，不收询盘内容、token、全文 URL。先确认现有统计和隐私要求；不能擅自上线第三方跟踪。样本不足就报告不足，不用三次实验宣称真实用户达标。
