### PERF-3：图片接口分段测量（本地完成，待远端与线上验收）

这一小段只回答“同一张已公开图片，到底在哪一步等待”。属于Channel现有公开API、文章读取库和存储适配器，运行在现有CloudBase函数内，不调用模型、不增加常驻资源，也不保存新的业务记录。浏览器请求、正文、图片、存储权限和缓存策略不改。沿用已有的公开图片HTTP、文章SDK离线事务、受限存储读取三处测试边界。

公开API调用 `articles.media(id,file,{measure:true})`，文章读取库才附带本次请求的数值；旧调用不请求测量时仍只有原来的图片正文和类型。存储适配器同样按请求返回取址/完整下载耗时。返回成功后，HTTP处理器只把下表固定字段写入 `Server-Timing`；忽略未知字段、非数值、非有限数、负数和超过120秒的值。404/503不输出分段，不放行额外跨域读取，不输出对象地址、签名、客户编号、数据库名或异常内容。

| 响应头名称 | 测量范围 |
|---|---|
| am-ref1 | 第一次事务与公开引用、来源和登记检查 |
| am-storage | 存储适配器整体读取，含下面两段及Base64转换等开销 |
| am-url | 现有SDK获取临时地址的往返 |
| am-download | 发起原有GET至读完、合并全部正文 |
| am-check | Base64、长度和SHA-256核对 |
| am-ref2 | 第二次事务与当前公开授权对照 |
| am-total | 文章图片读取库的总耗时 |

这些数值嵌套，不能全部相加。总耗时不包括函数启动前、网关、用户连接或完整HTTP传输；也不能把浏览器往返减去另一次请求的服务器耗时就称为网络耗时。当前页面最终仍走旧图片地址；排查时读取同图的 `/api/articles/media/...` 响应才能取得这些API分段，前端不会为测量多发请求。正常每图的数据库/存储调用预算与未测量请求相同，读取期间撤回和换源检查保留，不新增远端查询。

### 静态CSS压缩：已确认缺口，尚未改交付方式

11月16日的中间态另用5次公开GET核对压缩：首页、当时主CSS的identity/gzip对照、Blog列表和其CSS。当时主CSS为 `/_astro/BaseLayout.CFSYkLYb.css`，两次均传输129,559字节，没有 `Content-Encoding` 和 `Vary`，完整正文SHA-256一致。它与美国Before中101,854字节的CSS不是同一版本，不能直接比较增减。Blog当时的 `/blog/_astro/404.CVlv8pxx.css` 则返回 `Content-Encoding: gzip` 和 `Vary: Accept-Encoding`，传输17,314字节、解压后99,868字节。这两份CSS也不是同一文件，不能据此声称主站已取得相同压缩收益。

正常部署后又对当前两份CSS各做一次带 `Accept-Encoding: gzip` 的GET：主站 `BaseLayout.BwkNjP1T.css` 仍无编码头，正文及HTTP正文传输均101,912字节；Blog的 `404.CqKyFG8Y.css` 返回gzip，传输18,107字节、解压后103,629字节。上方Lighthouse的102,459/18,825字节是浏览器网络记录口径，包含响应开销，不能与这两次GET的HTTP正文长度混为同一指标。两次读回均200，没有云端写入。

上述中间态的5次请求来自Mac当时的网络/VPN，不是美国After，也不是新的CWV成绩。那份主CSS单次首字节约1.55至1.72秒，总耗时2.76至2.92秒；压缩主要减少正文传输，不能据此承诺消除首字节等待。安全回执保存在忽略目录 `output/blog-direct-publication-20261116/static-css-compression/`，不包含完整响应正文或全部响应头。

当前已安装Manager SDK为5.9.1。对照其域名/托管接口及官方文档，尚未找到普通网关可验证的免费压缩开关；扩展字段允许未知键，不代表服务端支持任意压缩设置。[官方智能压缩](https://docs.cloudbase.net/service/custom-domain#acceleration-features)属于开启边缘加速后的能力，需要标准版及以上、资源点计费，并产生加速流量和请求费用，还涉及域名验证及CNAME。用户已把CDN后置，本轮不为压缩擅自开启这些资源或改变计费。

### 文章图片直达接口与耗时记录（11月17日上线验收）

这一步只改变图片怎样送到读者浏览器。文章服务器照常先返回文章HTML；浏览器随后直接向网站的公开图片接口取图，文章服务器不再代转图片。图片是否已发布、是否已撤回，仍由同一个接口检查。

正文接口的 `getRender` 依次读取文章地址登记、已发布正文和网页图片登记，共三条文档读取，旧 `get` 为前两条。它们在同一个CloudBase事务内。仓库[同事务真实并发对照](../../../catalog-single-source-of-truth/P7a1_NATIVE_TRANSACTION_READS.zh-CN.md)已有并发读2/3次出现 `TransactionBusy`、串行读通过的记录，所以不能直接把后两条改为 `Promise.all`。事务外并行又会改变共同快照和撤回检查，需要另做一致性设计，当前不采用。

当前代码给文章服务器增加两项 `Server-Timing`：`article-read` 是文章API往返、正文读取和解析的合计；`blog-handler` 是中间件等待页面处理器产生响应的时间。两者重叠，不能相加，也不等于全部HTML流传输时间；尚未分别测量API内部三条数据库读取。数字之外不输出数据库名、凭据或用户资料。[响应头说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Server-Timing)。11月17日切换前，浏览器先请求 `/blog/media/articles/...`，文章服务再调用 `/api/articles/media/...`；后者负责核对公开引用、读取存储并返回字节。新程序在 `BLOG_MEDIA_DELIVERY=api` 时，HTML和结构化数据统一使用同域现有API地址，应用HTTP层数由两层降到一层；未设置时仍走 `proxy`，无须立即切换。正常成功、无事务冲突重试时，每图仍是6条文档读取、2次事务、1次临时下载地址查询和1次对象GET，不能宣称减少了授权检查或所有数据库调用。

直达前须精确放行 robots 的 `/api/articles/media/`，保留其他私有/JSON接口的屏蔽；旧 `/blog/media/...` 持续兼容，公开/撤回/换源核对不减少。完成同一篇文章、相同美国条件下三次对照后，再决定是否处理正文读取。26项定向测试和两种地址的实际打包服务器联测已通过，其中直达模式还运行真实浏览器旅程；另通过Astro检查、测试类型检查和CloudBase SDK门禁。上述本地检查、三项远端工作流以及本次真实部署和新旧方式切换分别通过；实际数据见本页11月17日记录。数据库并发方式没有改动。

本次已执行的顺序：保留当前公开文章与配置 → 美国手机/桌面各三次Before → 更新文章程序但保持proxy → 正常部署robots的精确Allow → 读回确认 → 切换api → 新旧图片地址和内容摘要验收 → 切回proxy验收 → 再启用api测After → 因未证明收益，切回proxy做一次对照并保留。美国结果见本页最新记录。恢复时把模式切回proxy，保留新兼容程序、正文和图片；若程序本身异常则用已归档的上一镜像恢复。公开图片非200、摘要不同、文章内容/日期变化或其他环境变量变化时立即停止后续切换并恢复。既有部署工具不改，CDN与发布提速继续后置。

后端先提供兼容读取，再准备副本，最后部署并启用新文章渲染；旧GET和旧图片地址须一直工作。正常文章HTML请求仍只有一次文章API往返，最多额外读取一份每篇文章的旁表，不在渲染过程中读图片字节或为每张图发请求。图片GET复用当前引用检查，副本读取前后各核对一次登记；这些额外数据库读取单独计数，不声称整条调用只有一次读库。图片转换只在受控准备中发生，不在读者请求内执行Sharp。

缺少ready副本时，生成HTML继续选原件；已经选定产物SHA的地址则必须返回对应产物，不能用原件冒充。新展示停用时保留文章发布状态、原件、人工修改和旁表；已交付媒体地址的兼容读取不能随便回滚掉。后台私有预览仍用带登录检查的字节接口和Blob，不引入COS直链；本段不改缓存期限、CDN、实例数量、模型或网站助手。

| 6B 脚本与样式 | 找出公开页面引入的非必要后台/同步逻辑，按边界拆包；核对 GET 实际压缩 | 真实压缩字节、执行与长任务、完整变体/询盘交互；不能只看文件名 |
| 6C 字体与布局 | trace 证实字体延迟后，再选择授权允许的自托管、必要字重及加载策略 | FCP、字体切换、CLS；桌面手机截图不突变 |
| 6D Blog 响应 | 分开常驻服务响应、文章 API、数据库与渲染耗时 | 首次/连续/空闲后读取；不把所有慢响应归咎冷启动 |
| 6E 真实交互 | 对导航、筛选、商品图库/变体、询盘做点击与输入 trace | 事件等待、处理与绘制耗时；保留反馈和键盘操作 |

这些段有各自前后数据，实施按诊断优先级推进。不要盲目给所有图片 preload、给全部组件 memo，或添加 service worker、全站预渲染来掩盖实际瓶颈。

## 指标与采集约定

真实用户目标按第 75 百分位分别看手机与桌面：LCP ≤2.5 秒、INP ≤200ms、CLS ≤0.1。实验室同时保留 FP/FCP、LCP、CLS、TBT、Speed Index、TTFB、传输字节、请求数、LCP 元素及失败；FCP 1.8 秒、TTFB 800ms 只作诊断参考，不冒充三项 CWV。

优化后使用同一工具版本、页面状态、设备、CPU/网络与冷缓存条件，每页各三次，给中位数和范围。记录运行版本、出口地域、实际入口、资源版本及失败。主域 DNS 或公开内容已经变化时补一个同条件当日对照，不把所有差异都归给代码。

现有 9 页保留可比性；补按图片量和变体量分层的商品、空分类和视频页，不需测 500 多页。后台私有编辑作为功能验收，不与公开页面的 SEO 分数混报。美国测试必须验证网络出口；改浏览器定位不能模拟跨境线路。

真实用户采集如需新增，复用或引入有维护的 `web-vitals`，仅记路由类别、版本、设备、粗粒度地域和指标，不收询盘内容、token、全文 URL。先确认现有统计和隐私要求；不能擅自上线第三方跟踪。样本不足就报告不足，不用三次实验宣称真实用户达标。

## 发布与恢复

先评审本设计，实施时每段小范围验收，UI 变化先给截图。前后表不填预测收益；任何交互、权限或内容缺失都不能因跑分快被放行。回退对应程序/资源版本，保留当前商品和文章；真实用户指标随后单独观察。

本设计应用 core-web-vitals、performance、既有 React 性能审查原则；具体修改仍须由 trace 支持。[Google 指标定义](https://web.dev/articles/vitals)。

## 底层设计：先把测量条件固定

扩展现有 `scripts/performance/`，保留9个已有URL便于比较，再补实际图片较多/变体较多商品及空分类、视频页。每份样本记录源码或部署版本、页面内容revision、测试工具与浏览器版本、CPU/网络条件、缓存、出口country、请求/最终URL、错误和LCP元素。分类网址仅保留允许的family/page等参数；诊断时不能再次删除参数后误判400。

载入测试使用现有美国运行入口，各类手机/桌面各三次；地区、网络、页面版本变化时单列，不硬拼前后平均值。历史11月4日共54次美国样本不重写。新的优化前与优化后共用清单和参数，输出逐页中位数、范围、失败次数、FP/FCP/LCP、TBT、CLS、Speed Index、TTFB及字节与请求数。失败保留，不以增加重跑次数挑出好看的三个值。

另加真实交互旅程：打开商品→切图→选变体→填写并打开询盘；分类筛选→翻页→前进后退；Blog列表→文章。保留事件等待、处理及绘制分段和长任务归因。实验得到的是这些操作的响应时延；用web-vitals收集到一次会话INP时也只标实验室会话，不宣称达到真实访客p75。

## 底层设计：按因果逐段改

| 位置 | 具体方案 | 不允许的取巧 |
|---|---|---|
| 商品/文章图片 | 复用IMG-4的尺寸描述；renderArticle和ProductMedia显式选择宽度；LCP图在初始HTML可发现 | 把所有图片高优先级，或压到字看不清 |

## 调用预算、门槛与数据保存

测量页面只读，不提交真实询盘或后台批量操作。加载基准不产生模型调用；若现有助手启动本身发请求，分别计入并标明，不自动打开聊天触发回答。每个变更只跑受影响代表页的三次对照，整合交付再跑一次完整清单。没有改动/新假设不反复全量回归。

最小验收包含：主要商品和图文LCP有可复核改善、CLS无明显退化、真实业务操作正常、没有新增失败请求，实际目标仍为LCP≤2.5秒、INP≤200ms、CLS≤0.1的真实用户p75。某类尚未达标就报告剩余资源与耗时，不能以总分提高宣称CWV全过。

首期采用CrUX/GSC加可复现的实验，不另开RUM数据库和第三方服务。若访问样本持续不足，再提交基于web-vitals的第一方采集：路由类别、发布版本、设备类型、指标值，去掉用户输入和token；采样率、保留期和请求费用另审。没有这些现场数据就把真实用户INP标为未知。
