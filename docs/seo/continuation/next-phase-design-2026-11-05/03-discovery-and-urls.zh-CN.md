# 03 商品发现、分类分页与网址入口

## 现状与目标

商品详情已有独立 URL 和初始 HTML。缺口在分类：最初返回的页面没有商品详情链接，列表依赖 React；分页主要是按钮。Google 能运行脚本，但通常不会点击按钮发现下一页。目标是在保留现有筛选、图库、详情展开和询盘操作的同时，用普通链接找到所有公开商品。

## 高层结构

`当前公开商品快照 → 同版分类清单 → 分类首屏 / 分页 HTML + 真实链接 → React 接管并读取当前公开 API`。

分类首屏继续用现有页面和卡片，不另建一套 SEO 专用页面。后续页建议使用 `/headphones/page/2/` 这类可生成的路径，其他大类采用同一规则。每页有对应商品及自己的 canonical；第一页保持现有 `/headphones/`。新路径是待实现方案，不是现有线上地址。

快照按现有公开排序加唯一稳定键分页。同一次交付中的商品、分类和 sitemap 使用同版内容；既有自动交付增加受影响分类集合，不新增一套商品保存机制。创建、移类、撤回及排序变化须重新计算相关页码；过界页返回真实 404，不继续展示旧商品。

浏览器打开这些 HTML 后仍能刷新 API。快照较旧时，真实列表可以更新；不得把新旧版本的分页结果拼在一起。原有分类内展开交互保留，商品卡片仍有稳定独立详情链接；鼠标、键盘、新标签、刷新与前进后退都要正常。

## 网址规则统一管理

| 地址 | 处理 |
|---|---|
| 正式商品、分类、文章 | 200，独立标题、正确 canonical，按公开状态入地图 |
| 第一页参数副本 | 合并到正式第一页；内链不再制造多份地址 |
| 真正的第二页及后续页 | 各页正文不同、canonical 指向自己，前后页用 `<a href>` |
| 排序、临时搜索和任意筛选 | 不批量放进 sitemap；仅内容等价时合并，否则按明确索引策略处理 |
| 草稿、预览、后台、登录、缺失页 | 保留现有权限及不收录规则；真实缺失为 404 |
| www 和 HTTP | 保留路径、查询参数并统一到正式 HTTPS 主域；禁止跳转循环 |

www 301 已验收，不重复做。主域 HTTP 301 仍未完成：CloudBase 原生强制 HTTPS 曾实测返回 307，已恢复；实施先核对官方及现场入口能力，再选择最小范围的永久跳转入口。若必须让根域经过新边缘服务，单独列 DNS、TLS、费用和回退方案，不能借静态子域试验悄悄接管根域。现有 API 和第三方回调列入兼容核对，不笼统用 301 改写所有 POST。

补一个真实可用的 `/favicon.ico`，保留 SVG；不把其他未知路径转首页。OEM、Toys 的待收录需要核对真实内容和相关内链，不能断言分页就是它们未收录的唯一原因。

## 分段验收与恢复

3A 分类首屏、3B 真实分页及自动变化、3C HTTP 入口与图标，分别验收。无脚本检查首屏和有限链接遍历；对比页 1/2 商品集合；覆盖新增、移类、撤回、最后一页缩减及迟到交付；浏览器保留全部业务操作。页面变化先给同视口截图。

线上检查真实响应、标题、canonical、地图和当前 API；Google 实时可读与后续实际收录分开记录。程序恢复用当前商品内容重建相容产物，不恢复旧商品库。DNS 恢复不是瞬时操作，须在切换前留好源站与证书通路。

依据：[Google 分页规范](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading)、[JavaScript SEO](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)。
