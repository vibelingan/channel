网站明显多占空间的是**旧版本网页资源**。从 11 月 18 日真实发布归档到本次归档，JS 从 1,198 个增加到 1,328，CSS 从 65 个增加到 70，HTML 仍是 589 个。两份公开清单中有 56.85 MB 的 JS/CSS 路径和摘要完全相同。发布程序会保留上一版的非 HTML 文件，让浏览器已打开的网页继续加载脚本，也为恢复留出空间。这个做法每轮叠加，但没有给旧资源设保留期限。以 589 个本期 HTML 为入口，跟踪其中直接写出的路径，再递归跟踪 JS/CSS 写出的文件名，只能连到 48 个文件，约 2.07 MB。剩下 1,350 个约 65.46 MB（在该 ZIP 中压缩后约 18.85 MB，占压缩包约 22%）没有在这条静态引用链上出现；运行时拼出的网址可能漏掉，所以它们是排查范围，而非删除名单。[现有保留程序](../../../../scripts/release/site-files.mjs)

CSS 那次是 Tailwind 在生成样式时扫描了不该看的目录，修复是在输入端排除依赖、框架生成文件和构建输出。归档中找到的旧 JS/CSS 则是发布程序主动继承的资源。按浏览器记录溯源也很重要。HX10 商品页曾下载一个名称含 Alibaba 同步的约 106 kB 脚本；本地同版本构建清单显示，主要是共用的字段定义和校验库，Alibaba 工作流源码在压缩前只约 877 字节。当前优先减少更大的图片流量，后续若脚本执行占主要时间再拆这部分依赖。

建议让发布提速负责人用同一候选版本离线比较：一份保留全部旧文件，一份保留当前版本、允许立即恢复的版本及尚在缓存期的引用。记录压缩包字节、需要上传的对象数和同条件计时，用旧 HTML 打开商品图库、后台、动态资源以及恢复旧程序，确认 JS/CSS 无 404，当前商品和 Blog 仍可读。通过后再审生产公开文件保留期；完整恢复包继续保存在私有存储。当前归档大小和单个买家下载的数据不是同一个指标。18.85 MB 是待核对范围的实测压缩体积，不能直接当作能节省的空间或时间。

## 4. Alibaba 实际怎么交付图片

Alibaba 国际站的一个耳机列表页原始 HTML 中，将完整 HTTPS 地址和省略协议的写法合并去重后，找到 285 个带 `300x300` 的不同图片地址、47 个带 `200x200`、10 个带 `100x100`。其中 45 个商品列表图片标签直接在 `src` 使用了 `300x300` 地址。其余出现的地址还包括预加载和页面数据，实际请求数量需另用浏览器记录。同一耳机详情页的一张图，用同一个文件名公布了无尺寸后缀和 `50x50`、`120x120`、`350x350` 等版本。用正常 GET 单独读取四个文件时收到 429，未拿到图片文件大小。再次实测时，这些公开列表及详情图变体仍返回 429，但此前同步来源中的 SH1 原地址本次完整返回 200，PNG 为 3000 × 3000、5,021,685 字节，摘要与此前本站来源记录一致。这证实了页面提供多档图，已同步商品的高分辨率来源也确实可以取得。Alibaba 私有库存放方式、所测试列表和详情的实际下载体积暂未证实。[Alibaba 列表](https://www.alibaba.com/wholesale/gaming-usb-headset-7.1.html) · [Alibaba 耳机详情](https://www.alibaba.com/product-introduction/REDRAGON-ZEUS-X-H510-RGB-Gaming_1600827712403.html)

我们的具体问题是 Alibaba 同步取得大图后，早先网站对缩略图也可能请求大文件。还有部分原图由云函数编码为响应，体积超过平台响应上限，导致原图正常、官网却返回 400。网站保留原图作为来源和恢复依据，列表、商品图库和放大图各自使用合适尺寸。HX10 样本的页面缩略图显示约 80×80 像素，却读取 1,996,048 字节；本地从同一原图生成的 160、640、1280 像素 WebP 分别为 6,570、34,014、80,626 字节。Google 新导出的那一个图片地址正是 HX10 此图，记录的抓取日为 11 月 17 日，发布前官网取回原 PNG 为 HTTP 200。[本站测量](PERFORMANCE-2026-11-20-HEADPHONES.json) · [阿里云 OSS 图片处理](https://www.alibabacloud.com/help/en/oss/user-guide/overview-17)

11 月 20 日针对同一张 HX10 图片的准备任务已通过。线上三个网址均用完整 GET 核对字节和 SHA-256：默认 1280×1280 WebP 为 80,590 字节，`?w=160` 为 6,570 字节，`?w=640` 为 34,014 字节。原件记录的文件、字节和 SHA-256 未变。再打开实际 [HX10 商品页](https://supplychainsai.com/products/p-f5e72d34-1c75-40a5-a7a0-4208e7c6477a/)，原始 HTML 里的 80×80 缩略图仍请求默认地址，取回已是 80,590 字节，比之前少约 96%。两个小尺寸已经可以从网站取到，商品页初始 HTML 尚未选择它们，本次也未重新发布整站或测页面 LCP。 [线上准备任务](https://github.com/vibelingan/channel/actions/runs/44721109221)

## 5. 下次如何用这些经验

[Dev Pipeline 草稿 PR #16](https://github.com/orocsy/dev-pipeline/pull/16)负责规定在哪一步看证据、决定修复和验证结果。[Engineering Craft 草稿 PR #11](https://github.com/orocsy/engineering-craft/pull/11)负责告诉 Agent 怎样查生产包、区分图像与网页索引、拆发布各段时间，并保留现场案例。

先扫对当前问题有用的标准和开源技能，再从各处挑最合适的检查。例如 Google 文档用来判读 989 个网址，Chrome 和 Web Quality Skills 用来查买家实际下载了哪个文件，Vercel 的 React 建议留给浏览器记录显示脚本或交互慢的情况。若两种做法都讲得通，固定页面、代码、网络、缓存状态，交替测两种做法，并一起记录更快和更慢的结果。重复出现且验证过的技术做法归 Engineering Craft，发布前后做这些动作的顺序归 Dev Pipeline。仓库热度只能帮助筛选资料。
