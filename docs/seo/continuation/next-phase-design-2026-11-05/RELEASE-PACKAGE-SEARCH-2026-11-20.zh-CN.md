## 2. 生产归档里实际有什么

从已验收的网站交付下载实际 ZIP，先校验 ZIP，再用清单逐个校验 SHA-256 和字节大小。网站压缩包 85,986,135 字节，公开清单 2,078 个文件，共 175,769,425 字节。压缩包 SHA-256 为 `df2852c13ddb19616aa76095d38c0a9f85bb7034856dea1e4aebcba3f8effadc`。从文件路径及 JS/CSS 实际文本检查测试文件、示例、fixture、源码映射、Vite 开发服务、热更新脚本、React 开发构建与开发工具标记。检查是针对这些可见特征，无法凭关键词扫描证明所有生成内容都没有问题。[已验收的生产归档](https://github.com/vibelingan/channel/actions/runs/44653668498/artifacts/14592511687)

| 交付物 | 扫描结果 |
|---|---|

Blog 这项宜先在本地用同一份源码对比现有包和只包含生产依赖的候选，核对文章首页、正文、首屏 CSS、公开状态和 404，再比较压缩传输体积、冷启动及服务端响应。没有数据时，不把服务端包变小直接折算成访客速度。

网站明显多占空间的是**旧版本网页资源**。从 11 月 18 日真实发布归档到本次归档，JS 从 1,198 个增加到 1,328，CSS 从 65 个增加到 70，HTML 仍是 589 个。两份公开清单中有 56.85 MB 的 JS/CSS 路径和摘要完全相同。发布程序会保留上一版的非 HTML 文件，让浏览器已打开的网页继续加载脚本，也为恢复留出空间。这个做法每轮叠加，但没有给旧资源设保留期限。以 589 个本期 HTML 为入口，跟踪其中直接写出的路径，再递归跟踪 JS/CSS 写出的文件名，只能连到 48 个文件，约 2.07 MB。剩下 1,350 个约 65.46 MB（在该 ZIP 中压缩后约 18.85 MB，占压缩包约 22%）没有在这条静态引用链上出现；运行时拼出的网址可能漏掉，所以它们是排查范围，而非删除名单。[现有保留程序](../../../../scripts/release/site-files.mjs)

建议让发布提速负责人用同一候选版本离线比较：一份保留全部旧文件，一份保留当前版本、允许立即恢复的版本及尚在缓存期的引用。记录压缩包字节、需要上传的对象数和同条件计时，用旧 HTML 打开商品图库、后台、动态资源以及恢复旧程序，确认 JS/CSS 无 404，当前商品和 Blog 仍可读。通过后再审生产公开文件保留期；完整恢复包继续保存在私有存储。当前归档大小和单个买家下载的数据不是同一个指标。18.85 MB 是待核对范围的实测压缩体积，不能直接当作能节省的空间或时间。

## 3. Google 的 988 个未收录是什么

| 报表所写的数据日期 | 已收录 | 未收录 | 完整导出的「已抓取未收录」 |
|---|---:|---:|---|
| 11 月 13 日 | 528 | 988 | 959 个，逐条都是 `/api/images/…` |
| 11 月 16 日，11 月 20 日线上读取 | 529 | 989 | 960 个，逐条都是图片；较上次只新增一个该类别的网址 |

其余 29 个的分类数量合计为 12 个已发现未收录、4 个历史跳转、5 个已声明正式网址的替代版本、5 个历史 4xx、1 个历史 404、1 个历史 noindex、1 个被 robots 规则排除。12 个已发现未收录的明细包括 10 件商品、Toys 分类和隐私页。今天记录中它们直接返回 200、允许索引、列在地图中，并声明自身为正式网址。5 个历史 4xx 和旧 404 也都是图片。官网已实际取回五张旧 4xx 图片及核对完整字节；Google 仍是待复查 5、失败 0。网站本身的 528 件公开商品与 Google 当时报的 528 个已收录地址来源不同，不能把它们一一对应。[此次 Search Console 逐网址记录](SEARCH-2026-11-20.json) · [旧报表与网址核对](08-search-and-outcomes.zh-CN.md)

正常图片没有成为普通网页搜索结果，不会因为数量多就给商品页扣分。需要修的是访客和爬虫实际打不开的图、浏览器下载过大的首图以及正式商品页发现和抓取的问题。图片可用性关系到 Google 图片搜索、商品页面展示和加载体验。单独的图片域名也可以收录，但为了改变报表数字搬域名没有收益依据。若后续实测证明 CDN 可以让图片更快、更稳定，再比较两个路径的真实读取时间和缓存命中，保留旧地址和图片权限，复查页面链接及图片地图；Google 建议图片地图使用独立 CDN 域名时也验证该域名。[Google 图片最佳实践](https://developers.google.com/search/docs/appearance/google-images) · [图片地图](https://developers.google.com/search/docs/crawling-indexing/sitemaps/image-sitemaps) · [报告口径](https://support.google.com/webmasters/answer/7440203)

## 4. Alibaba 实际怎么交付图片

Alibaba 国际站的一个耳机列表页原始 HTML 中，将完整 HTTPS 地址和省略协议的写法合并去重后，找到 285 个带 `300x300` 的不同图片地址、47 个带 `200x200`、10 个带 `100x100`。这些是 HTML 中出现的地址，范围包括预加载和页面数据；它们不一定都会被浏览器请求。同一耳机详情页的一张图，用同一个文件名公布了无尺寸后缀和 `50x50`、`120x120`、`350x350` 等版本。用正常 GET 单独读取四个文件时收到 429，未拿到图片文件大小。可确认的是 Alibaba 页面提供多档交付地址，无法据此判断它内部如何保存原图或断言无后缀版本一定是原片。[Alibaba 列表](https://www.alibaba.com/wholesale/gaming-usb-headset-7.1.html) · [Alibaba 耳机详情](https://www.alibaba.com/product-introduction/REDRAGON-ZEUS-X-H510-RGB-Gaming_1600827712403.html)

我们的具体问题是 Alibaba 同步取得大图后，早先网站对缩略图也可能请求大文件。还有部分原图由云函数编码为响应，体积超过平台响应上限，导致原图正常、官网却返回 400。网站保留原图作为来源和恢复依据，列表、商品图库和放大图各自使用合适尺寸。HX10 样本的页面缩略图显示约 80×80 像素，却读取 1,996,048 字节；本地从同一原图生成的 160、640、1280 像素 WebP 分别为 6,570、34,014、80,626 字节。能确定的是这三份文件确实生成并且字节减少。Google 新导出的那一个图片地址正是 HX10 此图，记录的抓取日为 11 月 17 日，官网取回原 PNG 为 HTTP 200。线上还须核对手机、桌面、放大图分别选哪一份、响应和画质怎样，以及未公开图片仍取不到。这个样本的线上结果随后续受控发布回执记录。[本站测量](PERFORMANCE-2026-11-20-HEADPHONES.json) · [阿里云 OSS 图片处理](https://www.alibabacloud.com/help/en/oss/user-guide/overview-17)

## 5. 下次如何用这些经验

[Dev Pipeline 草稿 PR #16](https://github.com/orocsy/dev-pipeline/pull/16)负责规定在哪一步看证据、决定修复和验证结果。[Engineering Craft 草稿 PR #11](https://github.com/orocsy/engineering-craft/pull/11)负责告诉 Agent 怎样查生产包、区分图像与网页索引、拆发布各段时间，并保留现场案例。

先扫对当前问题有用的标准和开源技能，再从各处挑最合适的检查。例如 Google 文档用来判读 989 个网址，Chrome 和 Web Quality Skills 用来查买家实际下载了哪个文件，Vercel 的 React 建议留给浏览器记录显示脚本或交互慢的情况。若两种做法都讲得通，固定页面、代码、网络、缓存状态，交替测两种做法，并一起记录更快和更慢的结果。重复出现且验证过的技术做法归 Engineering Craft，发布前后做这些动作的顺序归 Dev Pipeline。仓库热度只能帮助筛选资料。
