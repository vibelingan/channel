## 现有改动用了哪些办法

| 位置 | 读者遇到的问题 | 改动及已核验的结果 |
|---|---|---|
| 文章图片 | 手机一打开就被要求下载很大的图 | 把原件保留在后台，网页用 WebP，首图在初始 HTML 中立即请求。后来单篇为小屏增加 768 像素版本，手机首图由约 92 KB 减到 33 KB |
| 商品图片与布局 | 小按钮有时在读原图，图到达后也可能撑开页面 | 根据显示尺寸提供实际像素的文件，带上宽高让浏览器提前留出位置。图库、切换规格和询盘用官网操作验收。这些动作证明正常业务仍可用，宽高本身解决画面跳动风险 |
| 页面 CSS | 每页首访都要等站内通用样式，归档构建还曾把依赖示例扫入 CSS | 精确限定扫描范围，通用样式 129,705→102,058 字节。首页、耳机分类、OEM、案例和视频页再各取所需样式。官网和受控试验均保留完整数据 |
| 商品详情启动数据 | 主图标签前出现重复的商品资料 | HTML 只发商品详情操作所需的数据，三页少发约 8–9 KB。实际验证商品内容、规范地址和结构数据保持一致，浏览器验证商品操作 |
| 服务端图片缓存 | 每次重复取同一个网页图都可能读腾讯对象存储 | 已上线给有内容版本号的文章图保留短时内存副本。每次仍按当前发布状态核对用途及字节。新一轮六对样本中，取图开始到首字节的中位数仍为 2.68/3.38 秒，主要等待没有随应用内部耗时消失 |
| 浏览器缓存与传输压缩 | 换页会重复下载已读的样式，冷访问还收到未压缩的文件 | 同内容的临时官网路径可让第二次传输为零字节，实测它也给 404 加缓存头，已撤掉试验路径。本机 gzip 对照验证少传字节可更早绘制，正式静态入口仍未启用此项压缩 |
| Blog 发布包 | 云服务每次发布都重复传同一个工厂视频，曾等约五分钟收到拒绝 | 视频相同时由构建云端取现有文件、校验完整摘要后装入新镜像。压缩传输包 8.05 MB→0.89 MB，下一次约 41 秒获腾讯接收。这节省发布等待，访客读的是同一份视频 |

服务端计时在实际成功的图片请求上提供额外证据。腾讯图片程序先检查图片是否仍属于已公开文章，然后读取云存储或校验内存里的那份图。远程下载后会再检查一次，以处理下载时恰好有编辑撤稿的情况。上述六对实验的两组各有 4 次存储耗时记为零，源码确认这种模式使用了内存文件，但仍做发布状态检查。浏览器建立 HTTPS 连接的中位数约 1.21/1.31 秒，应用处理不计这段时间。官网上正常取页面的网关和网络等待仍按同一个请求编号核对。目前首屏的证据先指向网络与服务响应，React 运行或 Node 计算需要独立的长任务或 CPU 采样才能判断是否值得改。 [文章图片计时](06-page-performance.zh-CN.md#11-月-19-日接着查-blog-首图的等待) · [缓存与压缩验证](06-page-performance.zh-CN.md#11-月-19-日补验首页样式压缩与浏览器缓存)

**这轮新上线的收益。** 代表商品的四张小图原来合计用 819 KB。改用真正的小尺寸后，手机和电脑均实收 9.75 KB，点击仍会请求清楚的大图，规格与询盘照常打开。新一轮三次手机慢网 LCP 为 12.96、4.92、4.56 秒，其中第一次的 16 KB 主图单在腾讯对象存储读取就用了 5.17 秒。随后同图与对照各取六次，读取只用 75–181 毫秒，未复现这次长等待。官网实际节省了图片字节，整页改善仍需再用同口径验证。528 件商品、三篇公开文章和五张历史故障图逐项读回，两只辅助发布函数已独立确认清理。 [官网交付](https://github.com/vibelingan/channel/actions/runs/44564948867) · [全部测量与慢样本](06-page-performance.zh-CN.md#少传图片后整页速度有没有提高)

### 从四秒继续往下，按哪段耗时决定改法

1. **网页到浏览器。** 用同一请求的编号对照 Chrome 和腾讯网关，记录 DNS 查询、TCP 建连、HTTPS 握手、等待回应、实际传输。首页最大元素是一个文字段落，当前中位数收到第一个字节要 2.34 秒。这一段本身就接近 2.5 秒目标。检查样式、字体和脚本是否在等这个请求，以及页面与资源是否能复用连接。
2. **首图何时请求、何时收到。** 保留原图摘要和访问规则。对于首页样式与商品照片的连接竞争，先量同一条链路的 HTTP 协议、样式等待和首图时间，再尝试一个改动。对于文章小图，拿到实际服务计时后再决定是否减少应用内工作。若需改善海外连接或打开官网压缩，先在获准的独立入口试验，验收失败时不影响官网。
3. **页面何时能操作。** 对商品切规格、图库、打开询盘、菜单与 Blog 跳转录制真实交互。页面慢且主线程出现长任务时，才按浏览器火焰图查看脚本和组件。上述 12 次慢网测试，文章、三次商品页都没有记录长任务；首页两次记录到合计 122 和 294 毫秒，耳机分类两次分别有 77 和 51 毫秒。导航样本只能筛查加载，后续仍要测用户点击后的交互耗时。
4. **怎样算改进。** 首次看到内容的时间（FCP）、主要内容显示（LCP）、布局跳动（CLS）和具体操作的交互延迟分别比较。用同一出口做交替对照，保留原始结果和失败。发布后验证命中正确资源、业务仍可用，再复测。同一地区、设备和页面类型都满足真实访客第 75 百分位 LCP ≤2.5 秒、INP ≤200 毫秒、CLS ≤0.1，才报告该范围达标。目前无足够真实访问数据。 [Chrome 性能面板](https://developer.chrome.com/docs/devtools/performance/reference/) · [Google Core Web Vitals](https://web.dev/articles/vitals)

## 把这次经验接到下一个网站

新站用 Dev Pipeline 串起需求、设计、开发、验证、评审和发布。第一个版本能打开时运行 SEO 与性能审计，发布后从正式网址再查。修故障先复现，重构先保留原来操作的验证，再比较新的实现，需求迭代只重验受影响部分。现有 Codex 或 Claude Code 会话可以按路线加载技能。Engineering Craft 提供分别可调用的技术 SEO 和性能技能。Channel 放具体网址、样本和回执。已经有发布后的站点，也可以直接从 `seo` 或 `perf` 入口开始。 [路线及复用步骤](https://github.com/orocsy/dev-pipeline/blob/5665d3bdb2583f40370b2c30d315d6270f452b22/docs/WORKFLOW_ROUTES.md)

这次在两份技术技能补进“平台日期不动时何时停止重查”和“相同图片直读没有稳定收益时保留现有路径”两条实测做法。Dev Pipeline 的交付说明补进一个接手的人用得上的要求：每次更新要给出用户已经得到的结果、当前任务正在做的动作，以及什么新证据才会触发下一次检查；用两个故障故事做后续回放用例。工程技能的文件结构和引用校验通过，流程插件校验与现有脚本回归通过。插件仍提示根目录的说明不会自动加载，所以路线已接进命令和技能路由。有真实模型执行结果前，只能确认插件能加载、命令能找到规则。 [工程技能评审分支](https://github.com/orocsy/engineering-craft/commit/309bafa683ad43c3119df471827e1f59f6a36109) · [流程插件评审分支](https://github.com/orocsy/dev-pipeline/commit/5665d3bdb2583f40370b2c30d315d6270f452b22)

改进优先级由实测决定。上线前保留一个最慢的代表场景、一个未改的对照场景、实际生效版本和可回退版本。将测试数据、变更、现场结果、时间和待办记在同一条记录。报告里的数字要能回答“谁受益、怎么测到、什么时候能读到”。遇到平台等待继续做独立工作。出现真实失败时在同一条记录跟到底。旧报告日期不变时只保留外部待办。GitHub 工序与作者实际工作时间分开，缺记录的时段保留未知。

## 文章为什么从 17.31 秒降到 4.54 秒

LCP 是访客初次打开页面后，首屏最大一块文字或图片真正出现的时间。Chrome 在这篇文章里把首图识别为最大内容。原站给手机下载 1536×1024、约 2.21 MB 的 PNG，实际显示只需约 380×253 像素。浏览器还要先判断该图靠近可见位置再开始加载。我们保留后台原件，把首图改成约 92 KB 的 WebP，并在最初的网页里让浏览器立即、优先请求。下一张图也减重，仍按需加载。两张图共由 2.92 MB 降到约 160 KB。这个改动直接减少读者下载的字节和等待开始下载的时间。

线上两轮美国 Lighthouse 手机中位数为 17.306→4.539 秒，每轮三次，原版三次都超过 17 秒，网络出口由 ORD 换到 MSP。公开记录中首图传输约 4.21→2.16 秒，发起前等待约 588→61 毫秒，读完至绘制约 20→22 毫秒。改版那轮 HTML 首字节反而由约 1.45 变为 1.65 秒。Lighthouse 模拟值与浏览器原始时间不能相加。为排除网络出口变化，用同一台 Chrome、同样限速和实际图片字节，分别测试文件大小和加载优先级。只换 PNG 为 WebP 的中位数从 11.64 降到 0.896 秒。换完再加首图优先为 0.836 秒。这个实验锁定了大图传输为主要瓶颈，也显示提前发起有额外收益。[两轮线上报告、同条件复现和 DevTools 记录](06-page-performance.zh-CN.md#11月19日复盘1731秒降到454秒是怎么测到的)

这次进一步用 Chrome 直接测官网。最慢的一次主要画面 9.32 秒才出现，浏览器在发出 HTML 请求前已经等了 4.59 秒。收到图片后绘制只用约 13 毫秒。已发布一项小改动，让文章访客只有打开商品菜单时才请求子分类。浏览器证实每次首访少了四个请求。新版主要画面的中位数仍约 5.57 秒，高于该轮旧版的 5.33 秒。两组范围重叠，当前没有证据表明这项改动提升了 LCP。手机、桌面实际打开菜单，首项约 1.29 秒和 0.80 秒出现。 [最新浏览器读数与正式回执](06-page-performance.zh-CN.md#文章首访只加载当前需要的内容)

接着把这篇文章的手机首图从 92 KB 降到 33 KB，让桌面继续使用宽图。官网同条件前后各五次，手机 LCP 中位数 6.37→5.54 秒，首次显示内容 4.30→3.72 秒。旧版 5.44–7.42 秒，新版 4.34–6.34 秒，现场结果仍有重叠。小图在固定网络的交替试验少等约 0.25–0.45 秒，手机每次只下载一种尺寸。官网首图在下载前仍等约 1.57 秒才收到第一个字节。进一步加速得先处理这个等待和网页首次响应。 [单篇试点的上线与逐次读数](06-page-performance.zh-CN.md#一篇文章的手机版首图已上线)

## 其他前端、后端与发布修补各自解决什么

- **浏览器少下载、布局更稳。** 商品图库的两张小按钮图与四张详情图，实际手机下载从约 1.72 MB 降到 170 KB。给配置专属照片的 HTML 加宽高，浏览器在图到达前就能留出正确比例的位置，避免切换规格时图像撑开页面。这一条对应布局稳定性，图库、规格和询盘是防止提速破坏现有操作的回归检查。后续还修过同一张图在主图和缩略图走两个网址导致重复下载的问题，浏览器已确认只请求一次。[图片交付与浏览器验证](01-images.zh-CN.md) · [去重线上回执](https://github.com/vibelingan/channel/actions/runs/44370243955)
- **首屏少等一次连接或一份过大的样式。** 耳机分类桌面版把首图接到官网现有的同站图片入口，浏览器能复用取网页时建立的连接。上线后的六对同条件实验中位数 5.78→4.04 秒。手机的最大元素是标题，结果基本持平。构建归档曾把依赖包扫进 Tailwind 规则，修回后共用 CSS 从 129,705 降为 102,058 字节。首页已发布独立样式，首次读取从 102,058 降到 63,992 字节。官网同机六对慢网实验中，首次绘制约 3.14→2.86 秒，最大内容显示约 3.21→2.93 秒。[分类正式交付](https://github.com/vibelingan/channel/actions/runs/44396811581) · [样式完整测量](06-page-performance.zh-CN.md)
- **弄清 16 KB 图片为何还能卡秒。** 美国独立冷连接的三个样本里，官网完整读取 1.159–1.225 秒，图片程序业务处理 192–246 毫秒，其中数据库读记录约 41–54 毫秒。较早样本曾接近 2–3 秒。小文件仍会等待网络建连、平台接入及原文件读取。目前没有证据支持先删数据库查询或图片权限检查。页面交互测试偶尔快过事件采样门槛，现有数据不足以写真实访客 INP。[美国分段记录](https://github.com/vibelingan/channel/actions/runs/44335663143)
- **后台大图上传与 Alibaba 同步各有不同入口。** 管理员从后台上传 4.8 MB PNG，Chrome 直接把原件传到腾讯对象存储，完成后后端才生成网页副本。那一次 155 秒中约 139 秒在发字节，约 15 秒在等存储回复。原件及常用尺寸都读回验证，且没有把私有图公开。上传速度和实际传到一半断线的重试仍有独立验收缺口。另一次试验查 Alibaba 商品同步拿到图片之后怎样处理。输入是一张程序画的 PNG，模拟供应商交来的文件。处理程序在腾讯正式环境写入测试图片登记，把原件和网页版本存进专用目录。把同一个来源地址送两次，仍只登记一张图。图片未被任何公开商品引用，匿名访客得到 404。结束后删除这次的测试文件、登记和临时函数，比对客户公开商品及文章，确认这些内容未受到影响。供应商实际下载及其耗时还没有在这一条试验里测。[两类入口的独立验收与时钟](01-images.zh-CN.md)
- **Blog 部署和内容互不覆盖。** 已用实际新旧程序复现浏览器能取到文章却取不到样式。发布工具现在先确认旧网页引用和新网页引用的资源都可读，再更换文章程序，保留可回退的旧镜像。正式官网已验收资源齐备时的一轮切换。恢复只换程序及其文件，现有已发布文章与商品状态继续由业务系统决定。[Blog 发布与资源读回](https://github.com/vibelingan/channel/actions/runs/44393810050)

## 根据数据继续从四秒往下压

本轮九类页面各测三次手机和桌面，共 54 份新报告，历史基准也有 54 份。三件商品和文章都早于最初基准。首页、耳机分类、Blog 列表也有变慢记录，原始整页测试的美国出口有变化。同机试验能解释某个改动带来的变化。目前的整页数据不足以判断所有慢项是偶发波动还是回归。手机各页的实验室 LCP 仍高于 2.5 秒。完整指标和个体样本在[性能模块](06-page-performance.zh-CN.md)与[108 次读数](PERFORMANCE-2026-11-19.json)。[Google 指标定义](https://web.dev/articles/vitals)

1. 先用同一出口、浏览器、设备、网络限速、缓存状态和 URL 重复测首页、分类、带图商品、Blog 列表与文章，保留每个样本和失败。若小收益与波动重叠，增加交替对照次数，再决定是否发布。
2. 在 DevTools 的 Network 和 Performance 里找到首屏元素，把等待拆为 HTML 首字节、发起图片、收到图片、绘制。当前证据仍指向文章 HTML、图片首字节和首访样式。要判断 Node.js 是否算得慢，用服务分段计时或 CPU 采样。要判断 React 或 JS 包是否挡住用户，用长任务和实际交互记录。只在数据指向该层时安排对应改动。
3. 每次挑一个有明确瓶颈的改动，固定条件前后对照，复测正常买家操作，发布后从官网拿版本和实际资源，再复测相同样本。正式性能目标按设备看真实用户第 75 百分位，LCP ≤2.5 秒、INP ≤200 毫秒、CLS ≤0.1。Search Console 目前缺数据。现有公开模板及隐私测试都核对过，未发现可直接复用的常见分析脚本，页面也声明不使用分析 Cookie。若继续缺样本，可另审不使用 Cookie 的站内采集，只记录页面类别、设备、版本和性能数值。访问内容、询盘及后台不纳入。
4. 管理员上传走单独测试。用同一张试验图在可用的两条上行线路记录发送、存储回复、转换，验证一次受控中断及重试后的对象数量。只有证据显示网络上行或重传是持续主要损失，再选择跨境传输加速或断点续传。海外静态 CDN 延后，发布提速由原负责工作流处理。

## 下次建站怎么复用

Dev Pipeline 管顺序。新建站按需求、设计、实施、检查、发布推进，第一个页面能跑时做 SEO 和性能检查。修问题走复现、修复、验证。重构先记原有行为，再验等价。需求迭代只重验受影响部分。同一会话可以执行这些路线。已有后台经常给出路径级别的异常时，按问题一直跟到官网回读和平台结果。

Engineering Craft 保存两份各自可独立调用的技术技能。技术 SEO 管收录、网址、网页结构、外部报告。网站性能管浏览器、网络、服务和上传，收到 SEO 性能问题时可接手诊断。两份技能都引用上游标准，以项目中可复现的例子补充条件。项目本身保存日期、发布回执、路线、前后原始证据。更新上游时先看版本和适用性，拿一个旧例回放再更新做法。[Google Search Central](https://developers.google.com/search/docs) · [Web Quality Skills](https://github.com/addyosmani/web-quality-skills) · [Marketing Skills](https://github.com/coreyhaines31/marketingskills) · [Vercel React 指南](https://github.com/vercel-labs/agent-skills) · [Node.js 性能诊断](https://nodejs.org/en/learn/diagnostics/poor-performance)

本机已经放入可查的技能和路线，检查通过。Dev Pipeline 的插件通用校验确认，仓库根目录的 `CLAUDE.md` 不会自动作为项目指令。因此把网站流程写入实际可发现的 `skill-router`，并保留 `seo`、`perf` 两个明确入口。本次从临时项目加载本地插件，Claude Code 实际列出了 `seo`、`perf`、`skill-router` 及两份技术技能。模型调用因为 Claude 登录已过期而返回 401，只确认了发现和命令加载。插件市场、云端安装及独立任务验证仍待验。两个通用仓库的安装复验和 Channel 生产发布各有单独结果。

接手时，每个问题用一条记录写清谁遇到、打开哪个地方、看到了什么、什么证据说明根因、改了哪一步、现场现在能做什么、还等谁处理。记录真实测试和发布的运行时间。一个通过的旧实验只在发现新问题或代码发生变化时才重跑。以此模板检查汇报正文，防止把“一项测试通过”写成“这个功能或 SEO 已经做完”。

## 同日官网试发，为什么这项改动被撤回

商品主图的提前请求在本地实验有效。正式网站同一出口的三次手机测量中，浏览器在收到网页后等 **803→20 毫秒**就发出主图请求，但首次显示内容由 **3.37→4.24 秒**，首屏主图由 **3.67→4.30 秒**。对照商品的首屏由 **4.20→4.23 秒**。Chrome 在这里使用 HTTP/1.1，提前发出的图用了原本可供样式表复用的连接。三次样式都另建连接，约花 0.89 秒，样式首字节由约 0.64 变为 1.53 秒。样式到齐才能画出页面。本地的 HTTP 重放保留了文件和下载速度，但没反映官网这次发生的连接竞争。[逐次数据](SEO-RETEST-2026-11-19.json)

图库、规格、询盘和原接口回退都实际过了。它们证明正常操作可用，页面变慢仍足以撤回这项改动。此后的资源优先级实验要报告样式、字体等同站请求的连接复用、协议和排队变化，并看 FCP 和 LCP 是否一起变好。文件字节或单张图的请求提前只能作为过程指标。运营侧继续使用当前商品和 Blog 内容，回退只切网页程序。

官网已用前一版渲染程序恢复，528 件当前商品的公开版本和三篇公开文章正文逐项核对一致。五张历史 4xx 图片仍能按原字节打开，两只本轮临时函数已独立确认删除。恢复后目标商品样式两次复用连接、一次新建约 0.19 秒，样式首字节中位数由试发时 1.53 秒回到 0.66 秒。整页 LCP 仍慢，目标商品约 5.72 秒，始终未使用提示的对照商品约 7.53 秒。这轮网页和图像首字节都比第一轮晚，剩余等待仍需按请求排查。[恢复任务](https://github.com/vibelingan/channel/actions/runs/44429020643) · [三阶段对照](06-page-performance.zh-CN.md#官网试发后的性能回退)

## Blog 首图剩余等待查到哪里

从公开图片接口取同一张约 92 KB 的首图，三次测得前后两次文章公开状态检查合计约 0.53–0.65 秒，存储读图约 0.20–0.56 秒。检查两次是为了确保取图途中刚撤下的文章不会把图片交给访客。官网 Blog 图片地址目前只能看到外层总时间。新代码让浏览器从同一次真实响应看到这几段，但两次发布都卡在等腾讯工具回执。腾讯未登记新版，官网仍用旧程序。三篇公开文章、528 件商品的公开修订、五张旧故障图和地图均已独立读回。上次带同一视频的包能在约 26 秒内收到回执，因此这次仍需查清 GitHub 上传和云端登记各花了多久。 [完整验证与发布记录](06-page-performance.zh-CN.md#11-月-19-日接着查-blog-首图的等待)
