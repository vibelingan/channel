## 文章为什么从 17.31 秒降到 4.54 秒

LCP 是访客初次打开页面后，首屏最大一块文字或图片真正出现的时间。Chrome 在这篇文章里把首图识别为最大内容。原站给手机下载 1536×1024、约 2.21 MB 的 PNG，实际显示只需约 380×253 像素。浏览器还要先判断该图靠近可见位置再开始加载。我们保留后台原件，把首图改成约 92 KB 的 WebP，并在最初的网页里让浏览器立即、优先请求。下一张图也减重，仍按需加载。两张图共由 2.92 MB 降到约 160 KB。这个改动直接减少读者下载的字节和等待开始下载的时间。

线上两轮美国 Lighthouse 手机中位数为 17.306→4.539 秒，每轮三次，原版三次都超过 17 秒，网络出口由 ORD 换到 MSP。公开记录中首图传输约 4.21→2.16 秒，发起前等待约 588→61 毫秒，读完至绘制约 20→22 毫秒。改版那轮 HTML 首字节反而由约 1.45 变为 1.65 秒。Lighthouse 模拟值与浏览器原始时间不能相加。为排除网络出口变化，用同一台 Chrome、同样限速和实际图片字节，分别测试文件大小和加载优先级。只换 PNG 为 WebP 的中位数从 11.64 降到 0.896 秒。换完再加首图优先为 0.836 秒。这个实验锁定了大图传输为主要瓶颈，也显示提前发起有额外收益。[两轮线上报告、同条件复现和 DevTools 记录](06-page-performance.zh-CN.md#11月19日复盘1731秒降到454秒是怎么测到的)

## 其他前端、后端与发布修补各自解决什么

- **浏览器少下载、布局更稳。** 商品图库的两张小按钮图与四张详情图，实际手机下载从约 1.72 MB 降到 170 KB。给配置专属照片的 HTML 加宽高，浏览器在图到达前就能留出正确比例的位置，避免切换规格时图像撑开页面。这一条对应布局稳定性，图库、规格和询盘是防止提速破坏现有操作的回归检查。后续还修过同一张图在主图和缩略图走两个网址导致重复下载的问题，浏览器已确认只请求一次。[图片交付与浏览器验证](01-images.zh-CN.md) · [去重线上回执](https://github.com/vibelingan/channel/actions/runs/44370243955)
- **首屏少等一次连接或一份过大的样式。** 耳机分类桌面版把首图接到官网现有的同站图片入口，浏览器能复用取网页时建立的连接。上线后的六对同条件实验中位数 5.78→4.04 秒。手机的最大元素是标题，结果基本持平。构建归档曾把依赖包扫进 Tailwind 规则，修回后共用 CSS 从 129,705 降为 102,058 字节。首页已发布独立样式，首次读取从 102,058 降到 63,992 字节。官网同机六对慢网实验中，首次绘制约 3.14→2.86 秒，最大内容显示约 3.21→2.93 秒。[分类正式交付](https://github.com/vibelingan/channel/actions/runs/44396811581) · [样式完整测量](06-page-performance.zh-CN.md)
- **弄清 16 KB 图片为何还能卡秒。** 美国独立冷连接的三个样本里，官网完整读取 1.159–1.225 秒，图片程序业务处理 192–246 毫秒，其中数据库读记录约 41–54 毫秒。较早样本曾接近 2–3 秒。小文件仍会等待网络建连、平台接入及原文件读取。目前没有证据支持先删数据库查询或图片权限检查。页面交互测试偶尔快过事件采样门槛，现有数据不足以写真实访客 INP。[美国分段记录](https://github.com/vibelingan/channel/actions/runs/44335663143)
- **后台大图上传与 Alibaba 同步各有不同入口。** 管理员从后台上传 4.8 MB PNG，Chrome 直接把原件传到腾讯对象存储，完成后后端才生成网页副本。那一次 155 秒中约 139 秒在发字节，约 15 秒在等存储回复。原件及常用尺寸都读回验证，且没有把私有图公开。上传速度和实际传到一半断线的重试仍有独立验收缺口。另一次测 Alibaba 同步的图片处理时，用程序画的测试 PNG 代替供应商下载结果，实际走正式云的数据库及对象存储，验证原图、网页副本、同地址重复同步和私有访问。该试验没有测供应商下载速度。只清理测试专用的图及临时验证函数。对照现有公开商品和文章，确认没有改到客户内容。[两类入口的独立验收与时钟](01-images.zh-CN.md)
- **Blog 部署和内容互不覆盖。** 已用实际新旧程序复现浏览器能取到文章却取不到样式。发布工具现在先确认旧网页引用和新网页引用的资源都可读，再更换文章程序，保留可回退的旧镜像。正式官网已验收资源齐备时的一轮切换。恢复只换程序及其文件，现有已发布文章与商品状态继续由业务系统决定。[Blog 发布与资源读回](https://github.com/vibelingan/channel/actions/runs/44393810050)

首页源码 `e23c029c` 的[完整检查](https://github.com/vibelingan/channel/actions/runs/44406412393)、两个 Blog 专项、[可恢复程序归档](https://github.com/vibelingan/channel/actions/runs/44407527462)及[官网发布](https://github.com/vibelingan/channel/actions/runs/44407855056)均成功。第一轮 CI 的布局类型导入问题已修正，旧运行里本地测试后台登录连接断开未在修正后的远端回归复现，检查保留。发布以当前 528 件商品生成网页。读回官网资产、两种屏幕的三个入口，以及两只辅助函数的清理状态均已通过。首页速度和现场验收见[完整性能证据](06-page-performance.zh-CN.md#官网发布与实际测速)。

## 根据数据继续从四秒往下压

本轮九类页面各测三次手机和桌面，共 54 份新报告，历史基准也有 54 份。三件商品和文章都早于最初基准。首页、耳机分类、Blog 列表也有变慢记录，原始整页测试的美国出口有变化。同机试验能解释某个改动带来的变化。目前的整页数据不足以判断所有慢项是偶发波动还是回归。手机各页的实验室 LCP 仍高于 2.5 秒。完整指标和个体样本在[性能模块](06-page-performance.zh-CN.md)与[108 次读数](PERFORMANCE-2026-11-19.json)。[Google 指标定义](https://web.dev/articles/vitals)

1. 先用同一出口、浏览器、设备、网络限速、缓存状态和 URL 重复测首页、分类、带图商品、Blog 列表与文章，保留每个样本和失败。若小收益与波动重叠，增加交替对照次数，再决定是否发布。
2. 在 DevTools 的 Network 和 Performance 里找到首屏元素，把等待拆为 HTML 首字节、发起图片、收到图片、绘制。当前证据仍指向文章 HTML、图片首字节和首访样式。要判断 Node.js 是否算得慢，用服务分段计时或 CPU 采样。要判断 React 或 JS 包是否挡住用户，用长任务和实际交互记录。只在数据指向该层时安排对应改动。
3. 每次挑一个有明确瓶颈的改动，固定条件前后对照，复测正常买家操作，发布后从官网拿版本和实际资源，再复测相同样本。正式性能目标按设备看真实用户第 75 百分位，LCP ≤2.5 秒、INP ≤200 毫秒、CLS ≤0.1。Search Console 目前缺数据，真实访问采集若有既有统计入口再评估接入，访问内容及后台不放入采集。
4. 管理员上传走单独测试。用同一张试验图在可用的两条上行线路记录发送、存储回复、转换，验证一次受控中断及重试后的对象数量。只有证据显示网络上行或重传是持续主要损失，再选择跨境传输加速或断点续传。海外静态 CDN 延后，发布提速由原负责工作流处理。

## 下次建站怎么复用

Dev Pipeline 管顺序。新建站按需求、设计、实施、检查、发布推进，第一个页面能跑时做 SEO 和性能检查。修问题走复现、修复、验证。重构先记原有行为，再验等价。需求迭代只重验受影响部分。同一会话可以执行这些路线。已有后台经常给出路径级别的异常时，按问题一直跟到官网回读和平台结果。

Engineering Craft 保存两份各自可独立调用的技术技能。技术 SEO 管收录、网址、网页结构、外部报告。网站性能管浏览器、网络、服务和上传，收到 SEO 性能问题时可接手诊断。两份技能都引用上游标准，以项目中可复现的例子补充条件。项目本身保存日期、发布回执、路线、前后原始证据。更新上游时先看版本和适用性，拿一个旧例回放再更新做法。[Google Search Central](https://developers.google.com/search/docs) · [Web Quality Skills](https://github.com/addyosmani/web-quality-skills) · [Marketing Skills](https://github.com/coreyhaines31/marketingskills) · [Vercel React 指南](https://github.com/vercel-labs/agent-skills) · [Node.js 性能诊断](https://nodejs.org/en/learn/diagnostics/poor-performance)

本机已经放入可查的技能和路线，检查通过。Dev Pipeline 的插件通用校验确认，仓库根目录的 `CLAUDE.md` 不会自动作为项目指令。因此把网站流程写入实际可发现的 `skill-router`，并保留 `seo`、`perf` 两个明确入口。本次从临时项目加载本地插件，Claude Code 实际列出了 `seo`、`perf`、`skill-router` 及两份技术技能。模型调用因为 Claude 登录已过期而返回 401，只确认了发现和命令加载。插件市场、云端安装及独立任务验证仍待验。插件市场、全新环境安装和独立任务验证仍需真实通过后才能称为已发布。两个通用仓库已有本机工作，未把它们与 Channel 一起合并或发布。

接手时，每个问题用一条记录写清谁遇到、打开哪个地方、看到了什么、什么证据说明根因、改了哪一步、现场现在能做什么、还等谁处理。记录真实测试和发布的运行时间。一个通过的旧实验只在发现新问题或代码发生变化时才重跑。以此模板检查汇报正文，防止把“一项测试通过”写成“这个功能或 SEO 已经做完”。
