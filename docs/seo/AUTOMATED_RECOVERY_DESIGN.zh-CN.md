# 发布、自动恢复与数据兼容：实现设计

2026-10-20，第二轮设计收口。适用分支 `feat/seo-foundation`，审阅代码基线 `b3c5f3a89b44b6ff6f99e62a24fbfa413bfd9e8c`。本文规定下一步要实现的行为，不表示这些能力已接通云端。pricing、Blog、Hermes 和公共请求层本轮均不改。

## 1. 已确定的方向与实际边界

采用有条件的自动恢复，同时保留 GitHub Actions 的手动恢复入口。恢复属于技术交付平台，不放进客户应用后台。自动恢复在本次发布协调器内执行；人工或经授权的 agent 触发的恢复也必须使用同一个协调器、同一目标锁和相同兼容检查。

lint、测试、采集、构建或备份失败，且尚未改变线上交付状态时，只停止发布。需要修复的是失败原因，此时恢复旧站没有作用。只有发生了线上写入，才进入恢复判断。恢复成功也不把原发布变成成功：原运行记录为发布失败、已恢复，后续仍须修复代码或发布链路。

不能承诺所有故障下都能自动恢复。凭证失效、运行器被强制结束、云端写入结果未知、目标已被其他发布占用，都可能使自动流程无法安全继续。对这些情况，正确行为是停止写入并留下可接手的证据，而不是猜测一个旧版本覆盖过去。

当前已有静态备份、只读恢复计划与执行内核；尚无完整云端恢复适配器、自动恢复工作流、函数恢复包、可信发布日志或数据库兼容合同。现有脚本会先更新函数/网关/触发器，再上传静态文件。因此只恢复前端，不能称为恢复整次发布。

## 2. 失败分类与状态转换

| 观察到的结果 | 协调器动作 | 是否恢复 |
| --- | --- | --- |
| lint/test/采集/build/备份失败，无线上交付写入 | `FAILED_PREWRITE`，保留日志和失败原因 | 不恢复 |
| 已完成某些明确的线上写入，读回可确认，兼容检查全部通过 | `FAILED_LIVE` → `RECOVERING`，最多一次恢复 | 自动恢复本次允许的组件 |
| 部分写入失败，但读回能确定实际状态 | 先记录真实状态，再执行相同资格检查 | 有条件恢复 |
| 调用超时、取消或断线，无法确定实际写入结果 | `STATE_UNKNOWN`，尝试只读核对；核对不清则停止 | 不盲目恢复 |
| 新版本已经占用目标、内容世代变化或发布凭据失效 | `SUPERSEDED` 或 `MANUAL_REQUIRED` | 不覆盖后来的版本 |
| 旧代码与当前数据库/API 不兼容，或缺少可信恢复产物 | `MANUAL_REQUIRED`，安排兼容修复 | 不自动恢复 |
| 恢复上传完成但验收失败 | `RECOVERY_FAILED`，保留步骤结果和当前读回 | 不递归恢复、不反复重试 |
| 恢复并验收成功 | `FAILED_RECOVERED`，登记实际恢复身份 | 原发布仍失败 |
| 发布已经验收并提交成功，后续通知/统计失败 | 保留成功发布；单独重试对应事件并报告 | 不因通知或统计失败恢复站点 |

“线上交付写入”包括函数代码、网关/触发器、托管文件、影响服务的配置及数据库迁移。写入协调日志不等于已经改变业务站点；但日志写入失败时，禁止开始下一步业务写入。

正常发布只有在全部验收通过后才能成为新的成功基线。失败、取消、部分成功的构建均不得被后续运行当成 last-successful。

提交顺序必须明确：验收通过后先封存已验收候选恢复包，确认固定 artifact 可用；再在同一条件事务中更新 active release 与 last-successful 指针。封存失败不能先移动成功指针。封存后条件提交失败的包属于未激活候选，不能按最新产物自动选用；提交结果未知时先读回，不猜测成功或立即覆盖。

## 3. 统一协调器、产物和写入日志

### 3.1 目标身份与并发

目标身份至少包括仓库、CloudBase 环境、实际域名和交付器范围；现有 `cloudbase-deploy-test` 只对应当前目标，名字中的 test 不代表另有隔离环境。正常部署、手动恢复和自动恢复共享该目标锁。自动恢复留在当前持锁执行中，不另起一个可能排队到新发布之后的恢复任务。

GitHub 并发控制不是业务发布事务，也不是持久任务队列。恢复开始前必须重新读取运行状态与 active release。进程内变量和排队前的状态不足以证明当前归属。

需要一个最小的服务器端发布合同：目标发布租约、递增 fencing token、公开内容 generation，以及对当前 release 的条件更新。发布器在首次业务写入前验证这些值，关键阶段和完成提交时再验证。日志和租约可放在独立、仅服务端可写的 CloudBase 文档集合；具体事务/条件写接口须按现有 SDK 合同验证后实现。

商品发布、撤回等影响公开集合的写入方必须遵守同一短期发布租约或等价的事务条件。构建期间可以只读取 generation，进入实际交付时重新比对；不要为了长时间构建冻结整个业务数据库。询盘、用户和其他不影响这次公开集合的写入继续运行。

仅有“发布前后各读一次 generation”仍有竞争窗口。所有相关公开内容写入方尚未接入协调前，自动恢复不能声称已防止撤回商品复活。本分支先定义最小合同；pricing 的写入实现由其工作流整合，不在这里改写。

### 3.2 恢复包必须可追溯

为每个已验收版本封存固定恢复包，至少包含：

- `releaseId`、代码 SHA、生成它的仓库/workflow/run/artifact ID、目标环境/origin、产物格式版本和有效期。
- 静态路径清单、字节数和 hash，商品快照、HTML/SEO/商品 manifest 与全部 sitemap 分片。
- 本次涉及函数的固定包、函数名称、代码 hash、运行时、必要的公开 API 合同，以及可验证的配置引用。
- 数据 schema/migration 范围、公开数据格式版本、前后端兼容范围、写入兼容检查结果及审核来源。
- 发布器拥有的路径/组件清单、受保护路径、可执行的配置反向补丁，以及验收记录。

hash 检查完整性；来源检查证明这些字节来自允许的成功发布，两者都要有。下载固定 artifact ID，禁止使用会移动的 latest 链接。产物过期或缺失就停止，不能临时重构建并冒充原版本。

配置只保存允许公开归档的值及安全的版本引用。凭证不进交付包；GitHub Secret 本身也不能当作可回到历史值的版本库。拿不到旧配置或旧 secret 引用的组件，不具备自动恢复资格。

当前 `site-recovery-*` 的 dist+快照还不是上述封装；现有 `hosting-backup-before-*` 也不能自动提供函数恢复能力。首次启用前需要建立并验收真实可用的基线。

### 3.3 每一步先记录意图，再调用，再读回

持久日志记录 `runId/releaseId/fence/step/component`、预期旧状态、新产物 hash、意图时间、调用结果和读回结果。调用前先提交意图；调用返回不等于云端已经完成。读回确认后才能记该步骤成功。未知结果保留为未知，不能把它当成“肯定没改”。

恢复计划按这份日志计算本次改动的组件集合；不恢复未涉及的函数，不全量覆盖未知网关设置，不处理其他发布器的文件。所有写适配器失败必须抛异常或返回被内核严格断言的结构化失败。`accept: async () => false` 不能被当成恢复成功。

即使 GitHub 任务结束，日志也应可读；硬取消时不能依赖 finally 一定运行。人工接手先读回目标，再决定继续恢复或修复。需要一个有明确权限的人工入口，不配置“看见失败就无限重启恢复”的监控。

## 4. 数据库如何兼容旧代码

### 4.1 当前仓库事实

商品主库通过 `packages/db` 使用 CloudBase 文档数据库。AI 模块的 `packages/ai-store` 使用 `pg` 与自写 SQL 迁移，本次检索未发现 Prisma schema 或依赖。两者不能被当成同一个数据库，也不能假定 SEO 发布自然需要执行 AI 数据库迁移。

`packages/ai-store/src/migrations.ts` 的 `migrateDown` 会逆序执行全部 down 文件；`001_ai_assistant.down.sql` 包含删表。`002_engine_provenance.up.sql` 既增加 provenance 字段，也删除旧 `image_digest`。这些是实际存在的破坏性迁移例子，禁止把现有 migrateDown 接入发布自动恢复。migrateUp 的单个 SQL 文件自行管理事务，整批文件不是一个总事务；后续迁移失败，前面已完成的迁移可能仍然存在。

### 4.2 多一个字段通常可以保留，但不等于一定兼容

| 数据变化 | 旧版本可能遇到的问题 | 发布要求 |
| --- | --- | --- |
| 新增可空字段、旧写入可使用的默认值 | 旧代码通常可以不读取；全量覆盖文档仍可能删掉新字段 | 验证读和写，保留未知持久字段 |
| 新增 NOT NULL 且旧写入无值/无默认值 | 旧版本新增记录失败 | 先扩展为可空或给兼容默认值，再分阶段收紧 |
| 新增 UNIQUE/CHECK/FK 约束 | 旧代码原本合法的写入被拒绝 | 检查旧写路径及现有数据，不能只跑 SELECT |
| 新 enum 值、新 JSON 分支、计价含义/单位变化 | 旧解析器拒绝；同字段也可能被误读 | 版本化数据格式，兼容读取或双写过渡 |
| 删除、重命名、改类型/语义 | 旧查询找不到列，或按错误语义运行 | 延迟删除，经过兼容窗口后单独实施 |
| 批量回填或覆盖业务数据 | 旧代码不能反推原值；并发新写入可能被覆盖 | 幂等、有条件更新，记录可核对的修复输入 |

公开 API 为避免暴露内部字段而剔除未知字段，是正常的响应投影；数据库写入把未知字段整份丢弃，则可能损坏新版本数据。仓库中既有 patch 更新，也有 `.set` 或嵌套对象替换，必须逐个核对涉及的旧写入路径。

### 4.3 默认采用扩展后收缩

1. 先增加旧版本也能继续读写的字段/表/API，不移除旧结构。
2. 新代码兼容旧记录与新记录；必要时暂时双读或双写。明确缺省值和冲突处理。
3. 独立执行可重入回填，按记录版本/条件写防止覆盖新业务数据，记录完成进度。
4. 新版本上线后验证新旧写入兼容，保留约定恢复窗口和对应产物。
5. 窗口结束且旧版本不再是恢复候选后，另一次变更才收缩旧字段/约束；更新最低可恢复版本。

若新代码发布失败，通常恢复兼容的旧代码，保留已经扩展的 schema 和期间的业务数据。恢复目标不必与数据库的历史快照一模一样。Prisma 等工具能执行/记录迁移，不能自动判断数据的业务含义或补偿客户操作；Prisma 的迁移 resolve 也不等于撤销 SQL。[Prisma 扩展与收缩](https://www.prisma.io/docs/guides/v7/database/data-migration)、[迁移故障处理](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/patching-and-hotfixing)、[PostgreSQL ALTER TABLE 行为](https://www.postgresql.org/docs/17/ddl-alter.html)。这些资料用于模式核验，不表示当前项目使用 Prisma 或已确认生产 PG 版本。

### 4.4 数据修复与灾难恢复独立处理

自动恢复不执行数据库 down、全库快照覆盖或任意回填的逆运算。需要修复错误数据时，先确定受影响记录，使用预期版本/hash 的条件补偿；记录已经被客户更新时停止该记录，避免覆盖合法新值。

全库备份/PITR 用于独立的数据保护。若需要恢复，应优先恢复到另一份数据库，核对后选择合并或安排明确的切换；不能为了回退代码丢掉期间新增的询盘、用户和订单。实际备份能力、保留期、恢复粒度和费用尚未核验，不能据此承诺数据库已受保护。

## 5. 哪些组件可以自动恢复

所有条件同时成立才允许：当前 run 仍有目标归属和有效发布凭据；没有新版本接管；当前公开内容 generation 与恢复计划相符；恢复包来源/环境/有效期通过；旧代码能读写当前数据并兼容当前 API；所需配置可恢复；本次所有相关改动均有明确处理计划。

| 组件 | 自动恢复的目标 | 不满足条件时 |
| --- | --- | --- |
| 静态 HTML、hash 资源、发现文件 | 固定且兼容的成功产物；保留旧依赖资源 | 停止，不能现场重建代替恢复 |
| Cloud Function 代码 | 已封存包和运行时，且当前数据库/API 可兼容 | 修复向前；不把静态恢复称为全恢复 |
| 网关、触发器、托管配置 | 本次实际修改字段的允许反向补丁 | 不整份回放，缺值则转人工 |
| 数据 schema 与业务数据 | 保留当前兼容扩展及客户写入 | 单独迁移/补偿/灾难恢复 |
| 外部图片/视频/AI 服务 | 不因代码回退改变它们的业务状态 | 各自独立的资源生命周期 |

恢复顺序由依赖合同决定：先使后端同时兼容已暴露的新旧客户端，再恢复前端，最后收口允许回退的后端/配置。若旧后端不能兼容浏览器里已经加载的新前端，就不能直接降级函数。不存在一条适用于所有组件的“全部逆序”规则；恢复计划必须在交付前明确保留哪些兼容层。

兼容证据至少包含旧代码对当前格式的读取、插入和更新，以及已暴露新客户端调用候选旧 API 的结果；不能仅比较 migration 编号或列名。商品旧快照即使暂时可恢复，也必须先排除当前撤回和路径归属冲突，并标明其内容时点。旧 HTML 可以短时落后于保留当前状态的 API，恢复验收不能把它冒称为当前数据库的完整快照；随后安排兼容版本重新交付，恢复通知差异以实际公开 HTML 为准。

静态交付沿用资源、HTML、发现文件的顺序，逐项读回；删除只限本发布器拥有且确认应删除的路径。保护平台路径和 Google/Bing 验证文件。真实撤回的商品不可因恢复重现。恢复必须联合解析 HTML、所有 sitemap 分片、商品 manifest 和 SEO manifest，并与当前公开集合核对，不能只检查 HTML 文件名。

当前托管未证明有原子切换，分阶段上传仍会出现短暂混合版本。短期依靠兼容 API、保留旧资源和一致性验收缩小风险；若业务要求严格原子发布，须另验证平台路由能力，不能用文档消除这个窗口。

HTML/sitemap/可变 manifest 复用前需要校验；hash 资源可以长缓存。CDN 清理不能清掉浏览器内存或 bfcache。恢复后需同时验证普通 URL、重校验请求、旧 context 和 API 当前数据；客户端恢复/联网/聚焦刷新仍按公共请求层方案后续实现。

## 6. sitemap、恢复与搜索通知

### 6.1 文件更新与提交是两件事

sitemap 是站点上供爬虫读取的文件。Google/Bing 已登记的稳定 sitemap 地址继续沿用；普通 CI 发布或恢复不需要反复登记。sitemap 的 URL 集合必须与实际可访问的公开页面一致，不能为了减少通知而故意保留不存在页面的链接。

Google 将 sitemap 视为发现提示，不保证抓取或收录；旧式匿名 sitemap ping 已废弃。`lastmod` 只在可靠记录了显著公开内容变化时更新，不使用每次构建时间或回退时间冒充内容更新时间。[Google sitemap 指南](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)、[ping 废弃说明](https://developers.google.com/search/blog/2023/06/sitemaps-lastmod-ping)。

当前不要求接入新的 Google 通知 API，也不把 IndexNow 当作已经存在的能力。未来如果启用 IndexNow，只推送实际新增、更新、删除的 URL，避免同一未变 URL 重复发送；收到成功响应也不等于收录。[IndexNow FAQ](https://www.indexnow.org/faq)。

### 6.2 主动通知采用合并策略

只在公开验收通过后记录内容事件。比较 URL 的公开语义 hash：正文、重要元数据、canonical/schema、存在/撤回状态；JS 包 hash 或代码 SHA 变化本身不产生搜索事件。

为待发送事件保存 `URL + activeReleaseId + contentGeneration + semanticHash`，使用约 30 分钟稳定窗作为本项目初始可调参数，非搜索平台规定。相同 URL 的后续变化替换旧事件；发送前重新确认当前 active release、generation 与页面状态仍一致。按 URL+hash 幂等记录发送结果，重试不得无限推送。

外部通知与站点发布无法组成一个跨平台原子事务。最终检查后若又发生新发布，仍可能送出一条很快过期的变化；保留发送 attempt 与实际 hash，后续对账合并，不能承诺绝对零过期通知。通知失败不撤销已提交的成功发布。

例子：A 已稳定 → B 上线后故障 → 恢复 A → 几小时后修好 B。

- 若稳定窗内 B 尚未推送，恢复后的 A 与最后通知的 A 相同，合并后不推送；真正稳定的 B 再形成一次变化事件。
- 若 B 根本没进入线上，或只是在构建阶段失败，就没有 B 的公开事件。
- 若 B 已经被通知或抓取，无法撤销那次访问。恢复后仍如实提供 A 和对应 sitemap，后续稳定的 B 再正常更新。无需因为恢复调用紧急移除、noindex 或 robots 屏蔽。

爬虫随时可能自行访问。延迟主动通知不能阻止抓取，也不能承诺没有短期索引波动。综合时序图中通知与访问的排列用于讲解，不代表访问受通知步骤控制。

### 6.3 技术故障与真实撤回分开

真实业务撤回及时移除入口/sitemap，返回恰当的 404/410，不为通知稳定窗继续曝光。临时技术故障优先保留能兼容服务的旧页面；确需短暂停用已存在 URL 时，可考虑真实 503，但当前静态托管能否逐路径提供该行为仍待合同和实测验证，不能先写成已支持。

不要用首页 200、永久重定向或永久删除信号掩盖短暂部署问题。Google 对 4xx 和 5xx 的处理不同，但长期 5xx 也会影响索引；503 不是无限期保护。[Google HTTP 状态说明](https://developers.google.com/crawling/docs/troubleshooting/http-status-codes)。

## 8. 实施顺序与验收尺度

继续在原分支实施，不复制部署系统：先修恢复内核的确定性缺口和可信产物封装；再实现持久写入日志、目标归属、组件恢复适配及人工入口；随后接同一次发布内的有条件自动恢复；在相关内容发布方遵守合同后启用内容恢复能力。函数/数据库超出当前可恢复范围的发布，先明确标记为不可自动恢复，不能靠全局开关强行放行。

正常发布、备份、手动恢复 happy path 先通过，再做一次范围受控的自动恢复演练。保留少量本地负向检查防止错误恢复，不扩成大规模线上故障注入。具体步骤和清理条件见 [恢复演练计划](RECOVERY_DRILL_PLAN.zh-CN.md)。

本次仅更新设计、流程图和计划；没有执行生产变更、迁移、备份恢复或演练。上述启用证据缺失时，能力状态保持“待实现/待验证”。
