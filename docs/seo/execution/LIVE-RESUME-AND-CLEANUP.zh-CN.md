## 真正要跑的 API 和数据检查

| 检查 | 实际动作 | 应保存的证据 |
| --- | --- | --- |
| 管理 API | 创建假函数 A、等待就绪、查询配置、下载运行包、调用，再更新 B 和恢复 A | 原始包 hash、实际云端包 hash、runtime/handler、函数身份、调用结果与时间；只保存脱敏结果 |
| 函数执行 | 用真实调用 API 执行云端 A/B；函数内部初始化服务端 SDK，在固定测试集合完成实际读写，不调用业务服务 | 真实调用编号、返回版本、函数内部数据库执行结果；不能用本地直接调用 handler 代替 |
| 数据 API | 由假函数内部创建/读取测试记录并以事务/CAS 更新；并发调用两次相同 revision。Actions 执行器另行直接读取专用集合核对结果 | 只有一次成功，另一条冲突；实际数据库前后值、revision、新字段保留；证明函数运行权限可用而非只证明执行器可写 |
| 查询/停用 | 有界分页读取本次记录；停用 D 使用 deleted 标记，仍能管理读回 | 不读取整站集合；D 不被旧程序复活；C 仍存在 |
| 私有权限 | 以非管理身份尝试直读测试集合，并核对权限设置 | 明确拒绝；管理入口可读。无法取得低权限测试身份时，这一项记未验证 |
| 静态和浏览器 | 普通 URL、重校验请求、先缓存 A 的浏览器分别经过 B→A | HTTP 状态、正文 hash、Cache-Control/ETag、实际显示版本；不能只测 cache-busting URL |
| 清理 API | 演练通过并归档后删除自建假函数/精确对象/测试记录，复查不存在 | 删除范围、响应、再次查询结果；不把删除请求成功当已清干净 |

复用现有 A/B 的纯业务规则，但在云端包外加受限存储层：`Actions → 腾讯云函数调用 → 假函数内服务端 SDK → 专用集合事务`。数据库结果再由 Actions 独立读回。原本“执行器读写库、假函数只返回补丁”的设计不足以验证函数运行时的 SDK、权限和事务，现场以这条真实链路为准；原本地假程序测试仍只证明纯规则。

函数包固定集合名和允许操作，校验 runId/精确记录主键及 expectedRevision；不接受任意集合名、查询条件或数据库命令。调用入口仅限授权管理调用，不加公开网关；函数需要的环境、凭证取得方式、SDK 版本及权限在创建前核对，只使用满足演练的权限，不放入代码/日志。A、B 都包含这一存储层，备份和兼容测试面向完整云端 ZIP，而不是拿本地纯 handler 包冒充云端可恢复包。

恢复 A 后再次通过函数读取和修改 B 留下的数据，再由独立读回确认新字段、C 和 D 的停用状态。失败回滚事务、同 revision 冲突以及重试不重复新增也要通过真实函数调用验证。这证明的是该受控场景，不扩大成所有业务函数或全库恢复都安全。

## A→B→A：先证明手动恢复，再测一次自动恢复

1. **只读基线。** 核对队列、锁、目标、假资源占用和额度；保存首页/分类/商品/API/404/缓存的普通请求结果。出现现有业务异常就不开演练。
2. **建立真正可用的 A。** 创建假函数 A、假页面 A、记录 X 和 D。调用、读回、下载包并核对 hash，保存原 ZIP、固定运行编号和成功记录。不可只保存 Git SHA。未证明 A 可用就不发 B。
3. **核对恢复入口确实选择 A。** 当前仍为 A，预览恢复计划，检查选中的就是第 2 步包和清单，必要时对同一 A 做一次无业务影响的恢复。它能证明入口和备份可读，不能替代下一步真正 B→A。
4. **发无害的 B。** 假页面改文字，函数增加可选 note；修改 X、增加记录 C、停用 D。真实数据库读回 X 的新字段、C 和 D 的停用状态；普通业务基线仍正常。
5. **明确指定恢复 A。** 针对保存的旧 A 运行专项兼容检查，锁内再读当前版本；只恢复假页面和假函数包。完成后下载包及实际调用均为 A。X 的 note、C 和 D 的停用状态必须仍在；不做数据库整体倒退。
6. **单独验证数据补偿。** 仅对精确 X，在 revision 仍为预期 B 时补偿允许的 value 字段；C 和 D 不动。有并发变化就拒绝补偿，不覆盖整条记录，不删除 B 新字段。
7. **只在人工恢复通过后测自动恢复。** 再发无害 B，让假页面专用验收失败一次；仅在本次确已写云端、A 已验收、仍持有锁且无新版本时恢复 A 一次。原 B 任务仍为失败。恢复失败停止，不递归恢复。
8. **确认无写入的失败不恢复。** lint/test/build/采集/备份在云端写入前失败只停发；这项离线检查必须已有，现场无需故意让客户构建失败。网络提交结果不明时先查询，不能盲目上传或自动改旧版。

备份、运行包、关键步骤和兼容结果都有固定来源。若线上 B 与预期不符、包 hash 不符或记录身份变化，不尝试猜测一个“差不多”的 A。

## 假业务通过以后才做商品 SSG 交付

仍需完成前表待接线能力，再在现有 test 交付目标部署整合后的 SEO 版本。发布前保存完整已成功静态产物、函数是否变化的清单、配置反向参数及精确恢复入口。不得为了验证 SSG 顺便发布未完成的 Blog 或恢复业务数据库。

现场主路径：分类点击详情、直接打开商品 URL、禁用 JS 看初始正文、启用 JS 后 API 刷新、刷新页面读实时数据、图库/变体/询盘流程、独立 canonical、sitemap、未知路径真实 404。新增/修改/撤回商品用明确的无害测试记录验证，不能误动客户在售商品。无 JS 和 API 失败时的旧正文/下架状态分别检查，不把陈旧 HTML 标为最新。

浏览器已有缓存、窗口恢复、重新联网，以及正常刷新必须与设计的新鲜度策略一致；商品 API 的版本错误不能把新旧分页变体拼在一起。错误快照或采集失败不得覆盖当前成功网站。若紧急 skip 只能保留旧公开快照，必须在运行结果明确标记其版本与局限；撤回不能靠 skip 拖延处理。

本地针对实际差异回归；线上保留完整主路径和关键保护检查，不制造大面积故障。实测后再填恢复耗时，不承诺未经测量的“一键几秒恢复”。

## 停止和恢复边界

发生以下任一情况立即停止新增写入：目标/资源归属不符、另一发布正在运行、锁丢失、当前版本在检查后变化、备份/兼容不通过、权限不符、提交结果未知、真实业务异常或恢复验收失败。

已确认 B 写入且 A 仍可信时，只恢复本次假范围；提交不明先只读查证。无法确认时保留现场和精确人工接手步骤，不上传整站旧包、不自动更改业务集合。搜索通知计数为零，不临时屏蔽正常网站，也不向 Google/Bing发送 canary。

## 演练后删除什么、保留什么

用户已明确要求临时假资源和专用用例在真实验收后清理。**本轮不提前删除它们。**清理作为单独人工触发步骤，在证据归档、A 已恢复和业务基线正常后执行，不挂到失败任务的无条件 finally 中。

1. 导出脱敏的 A/B/恢复记录、包 hash、请求结果、数据前后值和耗时；确认所有上传清单和资源身份。
2. 删除本次创建的 `seo-release-dummy`，前提是资源身份、创建归属、版本及无附加触发器/路由均匹配。再次查询为不存在；不接受任意函数名作为删除参数。
3. 仅删除 manifest 列出的假静态对象，保留普通网站和平台验证文件。查对象确实不存在，普通假 URL 返回缺失状态，CDN 不再展示演练文字。
4. 按本次 runId 和精确主键删除假数据。五个独立演练集合只有在确由本演练创建、已导出、清空后无其他记录时才可删除；发现外来记录则停止删集合，保留清单，不为“清干净”扩大删除。
5. 云端演练证据齐全后，移除仅供本次假业务使用的 `dummy-recovery-fixture.mjs`、`recovery-dummy.test.mjs`、`release-dummy-recovery.test.mjs` 及那 12 项专用用例；辅助 fixture 的变更先检查是否已有其他使用者。保留通用恢复测试、限制越界测试、测试标准、场景说明和验收记录。不整提交 revert，以免一起删掉设计与证据。
6. 重跑本地和远端 CI，确认无引用残留、没有未清理的网关/触发器/测试通知，业务恢复开关仍关闭。报告清理后的线上只读核对结果。

“默认不删客户数据”继续有效；本次例外只针对明确归属于本演练的临时资源。不能把清理授权扩大成删业务 schema 或旧字段。
