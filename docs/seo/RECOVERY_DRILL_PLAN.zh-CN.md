# 受控发布与恢复演练计划

2026-10-22 更新。本文为待执行计划，适用现有真实交付目标。`Deploy Test` 的命名不代表隔离测试环境。不搭 Tunnel；按最新要求先用假函数、假页面和测试数据验证。已完成的本地程序联测、精确云端范围和实际执行顺序见[假业务演练](execution/module-06-dummy-rehearsal.zh-CN.md)，云端创建和恢复尚未执行。

## 1. 要证明什么

先证明一次正常发布、备份、人工恢复能闭环，再验证一次条件明确的自动恢复。恢复结果包含：静态文件和允许恢复的接口代码回到 A，当前合法业务数据继续保留，受控测试记录可以按条件补偿回 A。

这不是把整个网站和数据库恢复到过去某一秒。新增 schema 可以留着；期间新增的真实询盘、用户和客户编辑不能消失。全库恢复另需独立目标及切换计划，不在生产原库上为演练覆盖历史快照。

## 2. 开始前准备

1. 核对实际环境、域名、API 和当前 release；确认同目标没有发布/恢复在运行，产物、函数包、配置反向补丁和有效凭据齐备。没有可信基线则先建立基线，不进入故障演练。
2. 生成唯一 `drillRunId`，固定 A/B 两份代码与文件 hash，写明允许修改/删除的精确路径、函数和 fixture 记录 ID。自动脚本拒绝超出该清单的动作。
3. 选未被页面链接、未进 sitemap 的静态 canary，显式 noindex，仅显示无业务含义的 A/B 标记。不改首页、商品价格、登录或询盘逻辑。页面不包含秘密，即使偶然被访问也无害。
4. 使用独立 `seo-release-dummy` 假函数提供 A/B 标记和假数据处理，不改业务函数，不增加公开网关。先保存并验证 A、证明能够指定恢复，再发布增量 B。整套假业务演练通过以后，才考虑真实业务函数的受控恢复。
5. 商品主库使用专用、与商品/询盘集合隔离的 fixture 记录。若本次确实验证独立 PG 适配器，再使用专用 fixture 表；不为 SEO 演练顺便部署 AI 数据库迁移。
6. 暂停该 canary 的主动搜索通知，确认不发送邮件、企业微信或客户询盘通知。捕获已有普通页面与已有缓存的浏览器基线。

只有已有可用的补偿路径和操作窗口，才开始写入。具体执行时核对以上清单即可，不要求用户逐条审阅内部检查。

## 3. 主要 happy path

| 步骤 | 操作 | 应看到的结果与保留证据 |
| --- | --- | --- |
| A 基线 | 正常交付 canary A 与 API A，创建 fixture A，完成验收并封存 | 固定成功 release、artifact ID、文件/函数 hash、配置摘要和 fixture 版本 |
| B 发布 | 同一协调器发布 canary B/API B；按预期版本把 fixture A 更新为 B | 普通 URL 与旧/新 context 读到 B；API 返回 B；日志先有写入意图再有读回 |
| 新写入保护 | 在 A 基线之后创建第二条 fixture C，模拟期间新增业务数据 | C 与 A/B 标记记录分开，记录其版本和内容 hash |
| 人工恢复 | 从 Actions/授权 CLI 显式选择 A，进入同锁并执行兼容检查 | 恢复精确静态/API 范围；schema 不 down；业务数据不自动覆盖 |
| 恢复读回 | 用普通 URL、重校验请求、旧浏览器 context 读取；检查函数实际运行 hash/版本 | 页面/API 为 A；正常商品、导航、图库和只读业务路径仍可用；真实 404 正确 |
| 数据核对 | 读取 fixture B、C 及迁移状态 | 默认仍保留 B 和 C，已增加的兼容 schema 仍在；证明代码恢复未倒退业务库 |
| 受控补偿 | 仅当标记记录仍等于预期 B 时，将该 fixture B 条件更新回 A | 测试记录回 A，C 保持原值；并发变化则拒绝补偿并报告 |
| 停用与归档 | 按 drillRunId 停用测试记录并保留演练文件和历史；删除另行说明 | 正常 URL 验收；当前成功身份正确；无测试通知、无 sitemap canary，留下来源与耗时报告 |

记录恢复开始、首次正确 HTML、首次正确 API、普通缓存路径验收完成的实际时间。先测量再给恢复耗时目标；一次成功不证明所有网络和凭证故障都能恢复。

如要证明数据库备份能读出 A，可另外恢复到隔离副本，核对 fixture A 和 schema；不把副本直接覆盖生产，也不把这一步写成整库生产恢复已经演练通过。实际平台能力未确认前，此项标为未验证。

## 4. 一次自动恢复演练

人工恢复闭环通过后，再发布同样无业务影响的 B canary，让“只针对 canary 的交付验收”返回一个可辨认的失败。客户正常路由保持可用，不通过破坏数据库、鉴权或商品 API 制造故障。

协调器应确认已发生本次线上写入、当前仍持有目标、没有新 active、恢复包和数据合同兼容，然后在原锁内恢复 A 一次。恢复验收通过后记录 `FAILED_RECOVERED`；原 B 发布仍显示失败，后续需修复造成探针失败的原因。恢复过程最多一次，失败则停止并输出人工接手证据。

验收只接受精确的 canary/API/fixture 结果，不接受“workflow 绿色”代替实际读回。如果函数恢复适配还没完成，就只能报告静态恢复通过，API 未演练，不能扩大结论。

## 5. 三组低成本本地负向检查

这些检查避免错误覆盖，在线上演练前完成，不额外建设大规模故障矩阵。

- 未写入：模拟 lint/build/备份失败，断言恢复调用数为 0。发布错误仍按原原因报告。
- 不具备资格：表驱动检查错环境/来源或过期产物、新 active/租约丢失、撤回商品仅残留在 sitemap、旧代码不兼容新约束。所有情况断言业务云写入数为 0。
- 恢复未成功：模拟上传/读回抛错或 `accept=false`，断言不登记成功，不开始第二轮恢复，保留已完成步骤。

缓存只保留一条主路径：已有 A 缓存的浏览器经过 B 和恢复 A，API 成功后内容与当前服务相符；网络失败时不把旧内容标为最新。更多浏览器/网络组合遇到具体问题后再补。

## 6. 停止条件和最终记录

目标身份变化、无法确定写入状态、artifact 不可信、数据合同不兼容、真实业务出现异常或配置反向失败时立即停止演练；先保留当前读回，不盲目执行“全量恢复”。人工仍需使用同一检查，不能绕过兼容要求。

最终记录包含 runId、环境/域名、A/B SHA、artifact ID、执行者、写入日志、普通 URL/HTTP/cache/hash、API 运行版本、fixture 前后值、C 保留证据、配置差异、搜索通知数、清理结果、实测恢复时间及未覆盖范围。凭证和真实客户内容不进报告。
