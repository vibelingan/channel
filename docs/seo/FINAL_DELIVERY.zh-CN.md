## 恢复入口和触发方式

建议在 GitHub Actions 提供独立的 `Recover Static Site` 手动工作流，使用 `workflow_dispatch`。名称是拟定名称，目前仓库还没有这个可执行入口。运维人员在 Actions 选择固定产物和目标；经授权的 agent 可以通过 GitHub CLI/API 发起同一任务。Git 是代码记录，GitHub Actions 是执行与审计入口，文件实际恢复到 CloudBase 托管。

不放进客户应用后台：后台本身也可能在故障中不可用；网站编辑权限不应自然获得站点恢复和云端配置权限。后台以后可以显示只读发布状态，不因此增加一个能绕过部署锁的上传入口。

常规发布自动完成快照、构建、备份和验收。恢复由人工或经授权的 agent 显式发起，不由 `push`、商品编辑、定时器、监控告警或 `if: failure()` 自动发起。发起后，下载、检查、上传和验收由任务自动执行；“人工触发”不代表每个文件都要手工恢复。未来若要自动恢复，需另定触发条件、兼容检查和授权，本期没有这个策略。

GitHub 官方支持从网页、CLI、REST API 触发手动工作流；工作流需要先存在于默认分支，网页操作需要仓库写权限。因此当前 SEO 分支上的设计不等于 Actions 中已经有按钮。[手动工作流说明](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)。

## 发布、备份、恢复的范围

| 对象 | 当前正常发布 | 当前备份与恢复能力 |
| --- | --- | --- |
| 公开页面和管理后台前端 | 同一个 Astro `dist` 上传，包含 HTML、JS/CSS 和构建内的静态文件 | 线上备份覆盖托管文件；恢复内核恢复静态文件，保护平台及搜索验证文件 |
| 商品 SSG 与 SEO 文件 | 商品 HTML、canonical、结构化数据、sitemap 和 manifest 随构建交付 | 静态范围内；恢复须额外检查当前公开状态及发现文件一致性 |
| 托管/域名路由配置 | 发布会设置首页与专用 404；缓存补丁仍待执行 | 已读回保存配置；恢复时只执行审核过的配置动作，不能整份盲目回放 |
| Cloud Functions、网关、触发器 | 现有 Deploy Test 会先处理这些，再交付静态站 | 本次静态备份不包含函数包、运行配置和触发器的完整恢复输入；静态恢复不会撤销它们 |
| 数据库、商品编辑、询盘、用户 | 正常业务仍使用现有后端；部署脚本还会确保所需资源 | 本次不备份业务数据库，不回滚业务数据；需独立的数据保护方案 |
| 外部/COS 商品图片、视频、AI 服务 | 沿用各自现有交付链路 | 只有实际位于静态托管内的文件在本次备份内；外部存储和服务不在内 |

因此，不能把这套能力叫作“全站一键回滚”。恢复前必须确认旧前端与当前后端兼容；不兼容时停止静态恢复，安排单独的兼容后端修复或已设计的数据恢复操作。`git revert` 也不同于恢复：它需要重新经过安装、构建和发布，而这里的静态恢复使用固定的已核验字节。

## 正常发布与独立恢复

正常发布沿用现有 Deploy Test：同 SHA 完整 CI → 显式采集公开快照 → Astro 构建及门禁 → 归档新 `dist` 与快照 → 核验并归档旧站备份 → 现网缓存前检 → 函数/网关/触发器 → 静态上传、hash 读回、既有精确清理与 404 配置 → 普通 URL、缓存、SEO 和业务验收。

采集、构建或归档失败发生在业务云写入前，当前线上文件继续服务。函数更新或静态上传开始以后，失败可能留下部分新版本；现有目录上传没有证明按资源、HTML、manifest 分阶段，更没有原子切换或自动恢复保证。不要把恢复内核的有序上传能力写成正常发布已经具备的能力。

独立恢复的目标流程如下，尚未接通云端：

1. 指定目标环境、域名、备份 run/artifact ID、恢复理由与确认的当前版本。运行受信任的恢复工具版本，不能仅因为要恢复旧文件就执行旧提交里的任意脚本。
2. 进入与部署相同的目标锁；重新读当前版本、文件归属、公开状态和配置。排队时看到的状态不能直接用于写入。
3. 下载未过期、来自允许仓库/工作流/环境的固定备份，校验来源、长度、路径、文件 hash、配置 hash。hash 证明完整性，不能代替来源认证。下载失败或过期时停止，不改成“现场重新构建”。
4. 验证旧前端与当前 API 兼容；同时解析商品 HTML、所有 sitemap 分片、商品 manifest 和 SEO manifest，校验它们与当前公开状态的关系。发现已撤回地址时拒绝整份恢复，不能只删 HTML 后继续恢复旧 sitemap。当前内核只覆盖部分检查，见审阅报告。
5. 先备份当前待覆盖状态，确认恢复本身也有可用的退出路径。处理后台发布并发：共享 Actions 锁不会冻结数据库发布；需要版本条件检查及发布协调机制，不能擅自引入未实现的后台“冻结开关”。
6. 依赖资源先上传并逐项读回，然后 HTML，最后发现文件；只删除当前发布器明确拥有的差异页面。保留兼容旧资源、平台路径和搜索验证文件。配置动作单独审核。
7. 用普通 URL 和重新校验请求验证正文、hash、404、元数据及缓存，再验证核心交互/API 兼容；通过后才登记恢复结果。异常和取消需保存已完成步骤及报告，部分执行不登记成功。自动重试只适用于有边界、相同字节的幂等步骤。

当前 `site-recovery-*` 只存新构建和快照，不能直接交给要求 `hosting-recovery` manifest 的内核；当前内核原生接受的是封好的 `hosting-backup-before-*`。后续若要从新构建建立 last-successful，须在全套验收之后另外封装来源、配置、兼容和所有权信息。两种 artifact 都有保留期，14/30 天不是长期容灾承诺。

共享锁仍用现有目标身份 `cloudbase-deploy-test`。`cancel-in-progress: false` 保护正在运行的任务；默认的等待队列仍可能被后来的任务替换，不能当作不丢任务的持久队列。实现手动恢复时须核对运行状态、取消原因和锁内当前版本；是否采用 `queue: max` 应做独立 workflow 合同验证，本轮没有修改队列配置。[并发控制说明](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)。

## 页面访问与商品更新

商品标准 URL 的 HTML 在 Astro 构建时生成，访客和搜索引擎访问同一个文件。分类菜单普通点击沿用原分类页内展开；新标签、复制地址和直接进入标准 URL 使用独立页。打开页面本身不会再执行 SSG。

独立商品页通过 `client:load` 接管已有正文，挂载后用现有 `fetch` transport 读取 API，成功后更新可见数据；当前尚未迁移 React Query。API 成功才意味着本次内容得到校验。网络错误、旧浏览器缓存、bfcache 和打开后未再次校验的标签页都有新鲜度边界。API 更新不会自动改写已交付的 title/schema/sitemap，也不能改变已经返回的 HTML HTTP 状态。

商品编辑后的自动构建触发、全局内容世代、完整商品远端差异清理、客户端恢复/聚焦刷新、有限请求超时和应急旧快照模式，均仍待实施。公共请求层保留现有设计，待与 pricing 的接口整合时统一落地；本轮不修改它。Blog、Hermes 草稿接口、海外部署也仍在后续范围。

## 复核结论与当前状态

方案方向保留：Astro + React + Cloud Functions、SSG 初始正文加 API 更新、单一目标锁、自动备份与独立显式恢复。没有迁移 Next.js，也不需要把恢复做进应用后台。

本轮重新运行的 7 个相关测试文件共 41 项全部通过；额外的合成反例发现“没有旧 HTML，但发现文件仍引用撤回商品”的恢复缺口。该项已记录为云端恢复启用前必须修复的阻断项；41 项通过不能覆盖这个未纳入原测试的场景。详见 [最终流程审阅](FINAL_REVIEW.zh-CN.md)。

下一次实施顺序保持：补齐恢复门禁与锁内云端适配器 → 验证来源/当前状态/兼容与失败路径 → 在共享锁下执行缓存变更及反向参数读回 → 整合目标分支后交付 404 和商品页 → 在现有真实目标做旧缓存、更新、撤回、恢复和业务 E2E，记录恢复耗时。没有额外测试环境，也不搭 Tunnel。定量恢复时间和原子切换仍未证明。
