# 静态网站备份下载：故障、修复与验证

2026-10-25。继续原 `feat/seo-foundation`。本轮只调查和修复备份读取，不部署网站、不改函数和业务数据、不改 main、不启用自动发布。404 继续采用本分支已有页面。

## 调查结论

之前用“网络断开”概括这件事不准确。旧日志只记录 `MCP error -32000: Connection closed`，没有保存子进程最初的错误，因此不能百分之百追溯第一次退出的触发点。

回查旧备份目录发现，云端同时存在一个文件和以它为前缀的其他文件。这是对象存储允许的布局，但本地不能把同一个名称同时建成文件和目录。第一次失败留下的对应路径已经是目录；第二次本地下载则保存成了文件，随后创建子目录时报 `EEXIST`。这两轮都没有形成完整恢复清单，也没有因此开始云端写入。

用安装中的 `@cloudbase/manager-node@5.9.1` 和真实本机 HTTP 服务，已经独立重现：正常网络、两个上述布局的对象，足以让批量下载因写文件流的 `EISDIR` 异常退出进程。这与第一次遗留目录相符，是直接线索；不是从“连接关闭”推断腾讯网络坏了。

同时验证了 SDK 下载的另外三个问题：

| 情况 | 安装中 SDK 的实际结果 | 我们的备份必须做到 |
| --- | --- | --- |
| 正常响应 | 文件写入完成 | 保留这个正常流程，再核对内容 |
| HTTP 响应到一半断开 | 调用没有完成或返回错误；诊断看守在 1 秒后结束子进程 | 总时限内报错，最多重试三次，不保存半截文件 |
| 注入读取流异常 | 异常逃出 Promise，结束进程 | 在当前任务内处理失败，不放行后续发布 |
| 服务器返回 503 错误正文 | 错误正文被保存，SDK 仍报告完成 | 检查 HTTP 状态、长度和内容，不能拿它当备份 |

也下载并对比了 npm 的 5.9.2 发布包：`downloadFile` 仍是 `body.pipe(dest)`，只等目标流 `close`，缺少上述错误和完整性处理。没有直接升级依赖。SDK 声明了目录下载内部并发为 20，但减少并发不会解决文件/目录名称冲突。

## 修复后的读取流程

1. 从已认证的目标环境取得静态托管桶、地域和共享桶前缀。静态托管桶与普通图片存储桶分别识别。
2. 正式交付优先通过已安装的 COS SDK 生成短期签名，在脚本内部直接读取 **COS 源站**。不经过网站网关和缓存；不公开存储桶、不改权限、不把密钥或签名链接写入日志和备份。
3. 网站备份只排除平台单独保存的 `.cloudbase-backup/` 历史备份目录，和原 MCP 列表保持一致；这些历史对象没有被删除。本轮实际 SDK 完整桶列表还发现了 1,078 个这类历史对象，命令入口复测发现后，已把命令和网站发布统一为同一个备份函数，防止递归复制旧备份。最多同时读三个文件。每个请求覆盖响应头和全部正文的总时限为 60 秒；网络异常和 5xx 最多三次，重试前分别等待 250、500 毫秒。权限失败、长度或内容不一致立即停止。
4. HTTP 读取有独立的超时 Promise，并主动取消正文读取。即使底层连接忽略取消信号，也不能一直等下去或接受超时后才到达的内容。
5. 完整字节读取并通过长度、MD5 校验后，才保存文件。分片对象的 ETag 不是整文件 MD5，必须匹配源站响应 ETag，并保存 SHA-256 校验值。
6. 本地文件用原路径的 SHA-256 编号保存；清单另记原路径。这样能同时保留 `X` 和 `X/...`，恢复仍上传到原来网址。没有删掉或跳过冲突文件。
7. 再读一次完整目录和网站配置。前后完全一致，全部文件重新验算通过，才生成 `recovery-manifest.json`。另存 `transfer-summary.json`，记录文件数、完整字节数、请求数、重试数和下载时间。

没有改动旧备份的读取格式，也没有把下载重试规则用到线上写入。线上写入的结果不明确时，仍按现有记录停止、读回，不能盲目再写一次。

## 会影响发布的哪一步

| 流程 | 影响 |
| --- | --- |
| 普通代码部署 | 构建和检查通过后，先完整备份现有网站并保存到 GitHub；这两步失败，网站和函数更新都不能开始 |
| 第一次纳管现有网站 | 需要读取全站形成可恢复版本 A；不完整则不能登记 A 或发布 B |
| 后续文章发布、更新、撤回 | 读取已经验收的版本和候选包，按差异交付；不要求每次重新下载整站所有历史视频 |
| 故障恢复 | 使用经过校验的 A；下载或校验失败时不能拿残缺文件覆盖网站。数据库不跟着回灌 |
| 客户浏览网站 | 不运行备份脚本；不会因降低备份并发而改变页面加载或商品交互 |

正常部署有明确凭据时，命令直接用绑定目标环境的管理 SDK 完成目录/配置读取，不再为每次查询启动 MCP 或修改它的全局环境选择。缺少明确凭据的本地旧调用仍保留 MCP 读取入口。两者校验规则相同。

正常部署的备份和归档步骤都没有 `continue-on-error`；检查还要求它们排在更新云端之前。不能以应急 skip 为由跳过恢复资料。

## 性能：用实际结果判断

本轮保留了失败和慢的结果，没有把“最终下载成功”当成性能已经合格。

- 现有 HTTP 读取完整下载了 **1,239 个文件，88,982,956 字节**，前后目录/配置一致、全部内容重新验算通过；用时 **1,105.04 秒（18 分 25 秒）**，三个并发，1,239 次请求，无重试。单次请求中位数约 979 毫秒，95 分位约 4,962 毫秒；三个视频请求分别达到约 128、187、305 秒。这是本机当时的实测，不能代表 GitHub runner 的速度。
- 第二轮相同网站读取遇到 `UND_ERR_CONNECT_TIMEOUT`，三次后正确停止，没有恢复清单。它证明网站分发路径本身也会不稳定，不能只改路径映射就宣布完成。
- 20 个真实文件的 COS 源站与网站内容全部 SHA-256 一致。源站请求中位数约 **536 毫秒**，网站分发约 **868 毫秒**。请求串行取样、TLS/缓存状态不完全相同，不能把这个差值承诺成整条发布流程的提速比例。
- 既有 GitHub 运行 `40091240391` 完成现有站点备份、归档和 A 登记所在整段为 **5 分 6 秒**；该段还含其他检查，不能当纯下载耗时。该运行随后因读取自己的产物少传运行编号而失败，不是这次备份失败。

源站完整复测已完成：同样 **1,239 个文件、88,982,956 字节**，前后目录/配置一致、全部文件重新验算通过，用时 **346.03 秒（5 分 46 秒）**。和本机前一轮网站分发读取相比，这一轮减少约 12 分 39 秒；两个样本的时间和网络状态不同，不承诺今后固定减少多少。保留了失败的首次域名检查：签名器实际使用 `tencentcos.cn`，最初只允许 `myqcloud.com` 而被本地检查拒绝，未发生 HTTP 内容读取或云写入；核对安装包后兼容两个受限域名。

最终适配只调用公开的 `hosting.getInfo()` 和 COS `getObjectUrl()`。SDK 私有桶解析器和 COS 实例方法用于核对实现，没有留在正式读取路径中；这个版本再次完整复测通过：**1,239 个文件、88,982,956 字节，258.94 秒（4 分 19 秒）**。两轮源站备份与前面的完整网站备份，逐一比较全部原路径、长度和 SHA-256，**1,239 个文件完全相同**。

本轮还发现旧 HTTP 读取只请求取消底层连接，某些长请求实际超过了时限。对已知 Node/Undici 取消信号问题进行了检索，并运行了强制垃圾回收的本机 HTTP 实验；短时和长时实验都正常超时，**没有证据断言这次一定由垃圾回收引起**。采用独立总时限修复可观察的结果，不把类似 issue 当作本次根因。

部署实际调用的 `capture-hosting-backup.mjs` 也已用内存中的临时凭据完整执行通过：**1,239 个文件、88,982,956 字节，276.10 秒（4 分 36 秒）**；其中完整下载为 259.03 秒，1,239 次请求、零重试。它与前三次备份的所有原路径、长度、SHA-256 和配置指纹一致。没有模拟云端文件，没有缩减网站文件范围。

早期 CLI 包装失败只保留了退出码，不能据此归因平台。最终命令的复测已捕获脱敏 stderr，并通过真实临时会话凭据验证；错误和被主动停止的历史目录递归实验都保留在本机证据目录，没有当成通过。

## 什么时候需要腾讯支持

源站完整读取已通过两轮，实际部署调用的命令也已完整通过。若源站也持续失败、合法签名稳定返回服务端错误，或前后未变的对象仍无法取得一致字节，再整理时间、地域、请求编号、脱敏错误、最小重现和已尝试方案，由用户决定提交工单。本轮不提交工单、不发外部消息。

原 SDK 的错误处理可以另作产品缺陷反馈，但存在可验证的替代路径时，不把它当作必须由客户处理的部署阻塞。
