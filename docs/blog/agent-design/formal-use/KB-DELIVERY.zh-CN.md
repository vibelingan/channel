# 从知识库取稿，怎样避免重复文章

每篇文章先在 VibeKB 有一条明确记录。发布助手拿到的是文档 ID 和经过核实的客户工作区，不是让模型凭标题在全库猜文章。

## 编号规则

内部适配器调用 kbDraftRequest(binding, document)。binding 来自发布机配置，包含固定站点、集成和客户工作区；document 必须由真实知识库读取并核对，包含整数文档 ID、实际工作区和整理后的文章。

请求号由 channel-blog-kb-v1、站点、集成、工作区、文档 ID 的 SHA-256 产生。标题、正文和凭证明文不参与编号，所以正文变化或换密钥不会让程序偷偷另建一篇。

externalTaskId 用于记录 VibeKB 来源，idempotencyKey 用于网站事务去重。客户不填写这些字段，内容助手不随意换号。

## 不同情况

| 情况 | 结果 |
| --- | --- |
| 文档 42 第一次提交 | 网站事务创建草稿、导入记录和额度计数 |
| 文档 42 同文重投或八次同时到达 | 返回同一篇，仅首次计额度 |
| 文档 43 是下一篇文章 | 创建独立草稿 |
| 文档 42 正文变化后再提交 | 返回 409，不另建文、不覆盖人工稿 |
| 人已在后台保存到第 2 版，再重投第 1 版 | 返回原导入回执，人改过的正文保留 |
| 换正式密钥但集成、工作区不变 | 仍找到原草稿 |
| 文档工作区与发布机绑定不符 | 在调用网站前拒绝 |
| 只知道“有篇新文章”，没有真实文档或授权任务 | 不取猜测文章、不提交 |

本模块不保证语义相同但分别存成两个 VibeKB 文档的内容自动合并。两个不同文档可以对应两篇文章；生产方必须在任务重试时保留真实来源文档 ID，不能每次新建知识库记录冒充重试。

## 已实现与等待部分

已实现共享字段校验、固定编号和网站事务组合测试。tools/hermes-blog/kb-store.integration.mjs 使用实际 SDK 的离线传输，串起两篇文章、并发、人工编辑和密钥轮换。

尚未确认内容助手使用的取稿/派单接口、工作区记录及回执返回方式。不能把编号函数当作身份认证，也不能通过模型自报工作区完成授权；这些要在真实适配器接线和联合验收时确认。
