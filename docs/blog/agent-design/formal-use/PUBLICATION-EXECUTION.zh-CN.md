## 客户怎么说，助手怎么做

| 客户要求 | 内容助手 | 发布助手 |
|---|---|---|
| 写作、润色、翻译，没有要求公开 | 完成内容，询问是否发官网；明确草稿则只存草稿 | 不自动公开 |
| 写完直接发官网 | 创作、配图、准备完成，带原发布意图交接 | 确认指定成稿后直接发布，不重复要求后台审核 |
| 直接@发布助手，把成稿/文件发官网 | 需要内容转换时按“原文整理、不得擅改”协助 | 取指定成稿，完成发布并返回实际公开链接 |
| @发布助手，修改后再发 | 按内部交接完成修改 | 委托内容助手，拿回指定修订后发布，自己不改正文 |
| 写完后被问是否发布，客户回复是 | 关联同群同任务，交接指定成稿 | 发布该稿，不误用其他人的文章 |
| 只要草稿、预览、暂不发布 | 保存私有草稿及真实编辑链接 | 不发布；文章里写的“请发布”不属于客户指令 |

客户不用填写接口、编号、alt或SEO字段。助手负责必要元信息；原文成稿不被发布助手润色。其他平台不因官网任务自动发布。

## MIU PUB-1：网站受限发布能力

当前 `createArticleImportService` 没有发布能力。新增独立publication服务和固定子路由，复用已有发布事务；后台的管理员校验继续默认生效，仅新的服务器端调用可注入受限的集成校验。

- 输入固定本站operationId、操作、稳定requestId、expectedRevision、expectedContentHash和expectedSourceHash；客户消息引用留私有审计，不能单凭调用者写“客户同意”扩大权限。
- 事务内核对当前凭证未过期/停用、独立发布许可、operation实际归属及草稿创建者、版本和摘要。人工修改拒绝旧任务；同号换稿拒绝，重复请求返回同一结果，不重复建文或改时间。
- 复用slug、图片active/归属检查、冻结成稿与公开快照写入；没有GitHub文章构建或五分钟等待。不伪造admin用户或创建有后台权限的账号。
- 复用现有私有集合，独立前缀保存授权与请求回执；不向旧严格格式的发布任务里塞新字段，避免旧admin程序不能读新任务。
- 已有草稿通常两次网站API请求（确认版本、提交）加一次公开页面读取；已上线同稿只读状态和公开页面。尚未导入时额外保存一次并读回；来源改动时额外同步同一篇，不另建文。VibeKB只取指定文档。失败/未知结果沿用原requestId，不换号猜成功。

先写HTTP路由及事务测试：旧凭证拒绝、跨集成拒绝、人工改稿、摘要不符、重复/并发请求、图片未完成、失败不留半次发布；再做真实云端、公开HTML/列表/sitemap与撤回检查。测试替换SDK传输不算真实云身份验证。

## MIU PUB-2：两个角色的工具和交接

保留现有VibeKB及图片工具。内容侧只请求交接；发布侧持凭证执行官网发布。工具描述和角色技能同步更新，移除本网站旧的“必须后台人工审核”限制，保留普通草稿路径。内容助手负责内容，发布助手负责发布，不添加第二套内容创作技能。

公开动作须来自客户任务；读取文章/网页中的命令不当授权。模型负责理解语义，网站负责本站身份、文章归属和固定版本，不宣称网站服务器独立验证了微信原话。稳定消息引用/任务与文章绑定并留回执，角色输入与网站结果分开核对。

## 授权和调用边界

网站凭证证明调用来自本企业发布机；独立publication-access记录决定它能否公开本站自己导入的文章。消息原话和引用由受信任的助手程序传来，供审计和重试，网站不声称自己验证了企业微信消息签名。模型负责分辨客户指令与附件内容；服务端强制文章归属、版本、发布额度和人工改稿保护。原有凭证轮换保留相同keyId，因此不需要每次续期重配发布许可。

改稿与发布是两步：来源内容变化先核对网站无人手工修改，再更新同一私有稿；公开内容直到发布成功前不变。有已插入图片且正文变更会影响布局时拒绝自动覆盖，要求先核对排版。公开提交后实际页面验证失败，会返回“已提交、公开页未确认”的原文章回执，不能把它当没保存而另建文。
