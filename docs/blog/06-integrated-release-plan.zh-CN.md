## CI 调研与选型

采用 GitHub 官方支持的 `needs`、matrix 和不可变 artifact 传递：检查可以并行，部署必须依赖全部必需检查成功。浏览器重用实际构建包，缓存用来减少依赖下载；缓存命中不代表源码或业务已经验证。源码失败不触发恢复，写后验收失败才进入本次发布受控恢复。

依据：[jobs 与依赖](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-jobs)、[artifact 传递](https://docs.github.com/en/actions/how-tos/writing-workflows/choosing-what-your-workflow-does/storing-and-sharing-data-from-a-workflow)、[依赖缓存](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)。实际改动先核对主线已拆出的 Browser regression，避免把同一整套浏览器检查再串行跑两次。

公开内容继续 Astro 构建时生成 HTML；不迁移 Next.js。依据：[Astro 静态与按需渲染](https://docs.astro.build/en/guides/on-demand-rendering/)、[Google JavaScript SEO](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)、[sitemap](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)。

## 正常文章交付的具体接法

普通代码部署读取正式 articleAccepted，导出公开正文和已经核验的图片，再参与同一次 Astro 构建；不把草稿、用户身份或云存储地址交给静态构建。首次准备7个私有集合后再启用正式文章功能。没有公开文章时，普通 /blog 仍可打开清楚的空状态，但明确 noindex、从 sitemap 排除；输入不存在或读取失败不等同于“没有文章”，必须停止构建。

后台点击发布仍只冻结修订和登记任务，静态交付由技术平台执行。内容发布复用现有发布锁、控制记录、固定构建包、逐步上传与验收，并在完成后更新 articleAccepted。内容更新无需重新发布商品同步函数；代码检查已经通过的同一提交可用于后续内容构建，不能用不同提交的绿灯放行。

GitHub 定时任务只能从默认分支启动。正式自动扫描队列需要在 main 安装受控调度入口；实现和验收继续沿用原分支，在既有 test 目标通过人工触发同一个执行器先验收。这个默认分支要求是平台限制，不能用本地 agent 常驻或向云函数复制个人 gh 登录令牌来掩盖。自动触发实际启用前必须单独记录结果，不能把一次人工跑通写成已经自动运行。

## 上线前先建立兼容的后端恢复版本

先准备7个文章私有集合及队列索引，只更新现有 admin 函数的文章API，保留网站当前界面和所有商品流程。通过真实账号、真实数据库和真实图片保存/重开后，把这份同时支持旧后台和新文章页的程序登记为可恢复版本A。此前不支持文章的旧程序仍保存原包，但不能作为新文章界面上线后的自动恢复目标。

后续程序B和网站上线后，恢复程序只能选已经验收的A，并继续使用当前数据库；不回灌数据库，不清空草稿，不执行删除字段。实际恢复后再从新文章页面保存和重开，证明已经打开的新网页也能继续工作。这样检验的是实际接口和程序，而不是只对比Git编号。
