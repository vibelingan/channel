# 发布、更新和撤回：执行与验收计划

> 当前实现以“第二段接线的具体做法”和共同进度表为准。“第一段初始记录”保留当时的边界，不代表本轮仍未接线。实际成功与失败均记入同日 worklog。

本轮继续原 SEO 分支，起点 `cd4cd2b9527344799732d819b3306ee51e6e6c98`；开始时读回 main 仍为 `404d1a257722175dcd70916e3f92ec6763fa0243`。用户本轮明确要求细分实施、完整前后端验证，并部署隔离 dummy。该授权覆盖本任务必要的隔离测试资源，取代原交接中“只做离线”的限制；不授权发布正式 Blog、改业务数据、正常部署入口或 pricing。

## 按可以检查的结果分段

| 顺序 | 实现与边界 | 通过标准 |
| --- | --- | --- |
| 1，后端发布任务 | 管理员请求指定修订；在同一数据库事务内查权限、冻结正文与图片、占用 slug、登记任务。状态查询只返回页面需要的字段 | 双击/响应丢失不重复建任务；旧修订、非管理员、停用账号、缺图、占用 slug 被拒绝；保存新草稿不影响冻结内容 |
| 2，构建输入 | 从服务器保存的任务生成专用内部候选输入，合并其他已公开文章；图片按固定清单读取并验字节。正式公开导出仍只读已验收记录 | 不伪造 accepted；缺文件、hash 不符、草稿泄漏或媒体归属不符时，构建失败且当前公开状态不变；重试沿用原候选 |
| 3，交付和恢复 | 接现有发布锁、写入前备份、逐步记录、普通 URL 读回和恢复。只有已确认的结果才能更新文章公开引用 | 未写线上时失败不恢复；写入结果不确定时停止并读回；恢复只选已验收的旧包；恢复失败不递归；旧任务不能盖掉新状态 |
| 4，后台完整操作 | 在现有编辑页增加发布、更新、撤回、进度与失败重试。保存/预览继续沿用已有行为，网络请求用公共请求层和 React Query | 页面操作确实创建后端任务，重新打开仍能读到进度；未保存内容处理清楚；失败保留输入；撤回有明确确认，普通保存不加确认步骤 |
| 5，真实 dummy 准备 | 读回实际目标、凭证和资源占用；明确独立函数/集合/对象/页面前缀，形成精确清单。部署同一业务实现，不另写假成功接口 | 云端运行代码身份可核对；测试集合 ADMINONLY；测试身份及凭证不入库、不进静态文件；所有写入口拒绝业务资源 |
| 6，从浏览器实际验收 | 通过真实页面、云函数、数据库和存储执行下表场景，独立读回数据、页面和字节 | 不能用接口拦截返回成功，也不能把离线 SDK 结果当云端结果。保留时间、版本、截图及读回记录；完成后按清单停用测试入口，删除另行核对范围 |

每一段的结果更新同一份 `NEXT-STEPS.zh-CN.md`；细节和执行证据记在本模块 worklog。云端登录等待期间继续前四段，不把授权尚未完成写成程序错误。

## 状态与允许的转移

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| QUEUED | 后端已保存指定内容，尚未开始执行 | 工作进程领取后到 BUILDING |
| BUILDING | 正在生成和检查产物，尚未写线上 | 检查成功到 DEPLOYING；失败到 FAILED；工作进程租约过期可重新领取 |
| DEPLOYING | 已登记线上写入意图，可能已写一部分 | 所有读回与记录成功到 SUCCEEDED；确认恢复成功或确认未写入才到 FAILED；不能确认到 UNKNOWN |
| SUCCEEDED | 交付已验收，公开引用和任务结果已登记 | 终态；重复完成只读回同一结果 |
| FAILED | 已确认不影响当前公开版本，或已确认恢复完成 | 原候选可创建新的重试任务；不能悄悄换成最新草稿 |
| UNKNOWN | 可能写入，实际结果或恢复结果尚不确定 | 保留占用，先核对现场；禁止自动重发、新任务覆盖和自动再次恢复 |

每篇文章最多一个未结束任务；交付阶段还要持有环境共享锁。任务使用后端递增顺序、工作进程领取次数及有限租约，防止迟到的工作进程写回结果。终态记录和旧候选保留，不通过删除任务来解除异常。

## 并发要怎么处理

| 同时发生 | 应有结果 | 在哪里保证 |
| --- | --- | --- |
| 相同请求重复提交 | 得到同一任务；更换内容/操作重用请求号则冲突 | 数据库事务中的确定性任务编号与请求摘要 |
| 两个不同发布请求 | 只有一个取得这篇文章的占用 | 同一篇文章的发布指针事务 |
| 发布请求与保存草稿 | 冻结请求指定的修订；保存成功后不改候选 | 同一事务读取草稿 revision；候选独立保存 |
| 两篇文章抢同一 slug | 只有一篇成功；撤回后仍保留原归属 | slug 唯一文档与事务 |
| 两个工作进程领取 | 只有当前领取者能推进；过期领取不能写回 | 数据库租约、领取次数及任务顺序 |
| 完成交付与新草稿保存 | 只更新公开引用，不回写/覆盖正文 | 完成事务重新读取当前草稿 |
| 超时工作进程与后续任务 | 拒绝旧回执；已进入写入的超时先核对现场 | 任务顺序、租约和共享交付锁 |
| 撤回与历史恢复 | 恢复文件时仍尊重撤回记录，不能复活旧页 | 文章撤回记录及交付清单检查 |

## 真实 dummy 验收场景

| 场景 | 必须看到的真实结果 |
| --- | --- |
| 首次发布 A | 页面创建任务；云端保存冻结内容；dummy 公开普通 URL 有正文和正确图片；数据库显示同一任务成功 |
| 发布中继续写草稿 B | A 的候选、图片和最终正文不变；B 留在草稿里 |
| 更新到 B | 同一 slug，公开正文变成 B；首次发布日期保留，修改日期只因真实内容变化更新 |
| 重复点击/丢回复 | 不重复建文章、任务或公开引用；页面可以读回真实状态 |
| 两个标签同时发布 | 一个取得占用，另一个收到明确冲突；没有互相覆盖 |
| 旧修订、同名 slug、缺图、非管理员 | 请求真实失败；云端数据和公开页面均不变 |
| 构建失败 | 不上传、不恢复、不登记发布成功，草稿仍能继续编辑 |
| 上传后验收失败 | 只恢复本次保存且已验收的 dummy A；记录原发布失败及恢复结果 |
| 上传结果不确定/租约丢失 | 停止新写入，显示需核对，实际读回后再决定后续操作 |
| 撤回与刷新 | 列表及 sitemap 不含该文；普通 URL 返回实际 404；旧标签页刷新不继续展示旧正文 |
| 手工 A→B→A | 精确指定 A；正文、图片和运行身份可核对；数据库新字段和测试记录保留 |
| 访问与退出 | 未登录/非管理员不能读草稿和私有图片；撤销身份后继续操作也被拒绝；私有 Blob URL 释放 |

## 云端写入前的说明

写入前必须给出实际环境、固定名称/前缀、预计写入与保留的对象、现有站点只读基线、A 的保存位置、逐步恢复动作和停止条件。当前尚未完成现场资源查询，不把历史空闲名称当作当前可用。

停止条件至少包括目标/归属不符、资源重名、权限不符、备份缺失、另一发布正在运行、云端代码身份不符、写入结果未知、普通网站基线变化。停止后保留证据和数据，不自动删除业务对象或重建函数。dummy 不加入菜单、正式 sitemap 或搜索通知。

## 第一段初始记录（历史）

第一段的任务、事务、状态查询和 worker 能力已写代码。真实交付器尚未接线，所以正式入口默认关闭；没有向用户提供点击后永远排队的发布按钮。第 2 至 6 段仍待实施或验收，不能将这份计划当成完成清单。

### 任务数据放在哪里

| 集合 | 负责什么 | 谁能读写 |
| --- | --- | --- |
| articleReleaseTasks | 每次请求、固定修订、媒体清单、处理状态和交付回执 | 服务端专用；页面仅得到明确列出的状态字段 |
| articleReleaseHeads | 每篇文章当前任务及递增顺序、长期保留的地址和公开引用 | 服务端事务 |
| articleSlugs | 地址归属；撤回后保留，防止另一篇占走旧地址 | 服务端事务 |
| articlePublications | 指定修订的不可变正文候选；不代表已公开 | 已有私有管理读取，后续构建进程 |
| articleAccepted | 完成交付后供公开导出使用的版本；撤回记空引用，不删历史候选 | 服务端发布进程 |

浏览器只有请求发布/撤回和查询状态两类操作；不能领取任务、提交交付回执或将状态改成成功。CloudBase 与本地存储复用同一段事务规则，各自负责真正的提交或放弃。发布成功只更新当前草稿的公开引用，不整条替换正文。

### dummy 的隔离方案

`packages/db/src/article-dummy.ts` 固定映射八个逻辑集合到 `blogDummy20261023Users/Drafts/Media/Publications/Slugs/Tasks/Heads/Accepted`，不接受外部前缀或任意集合名，事务仍执行安装包中的实际 SDK。此处只是命名与隔离代码；现场尚未读回，不能承诺这些名字当前无人使用，也没有创建集合。

部署前还须补齐独立函数、图片对象前缀、静态页面前缀和运行代码身份核对。不能把正式 HTML 随便移进子目录就认为隔离完成：页面链接、图片、canonical 和 404 都必须与实际测试网址一致。普通网站与搜索文件作为只读参照，不上传覆盖。图片原件和数据库字段默认保留。

dummy 验收可先由本地浏览器操作页面、实际调用独立云函数及真实数据库/存储，交付任务由受控工作进程执行。报告必须说明后台页面、执行进程和公开页面各自实际运行在哪；不把本地 UI 加云端后端说成“后台也已云端托管”。正式长期任务触发方式还须接既有发布入口，不能把浏览器长请求当构建进程。

### 第一段结束时尚未接上的细节（历史）

- 失败任务的“重试原候选”是独立后续操作，不能用最新草稿重新请求来冒充重试。当前重用同一请求号会读回原任务，不自动重发。
- 已进入交付的未知结果保留占用；确认恢复完成后的状态转换，以及 UNKNOWN 的现场核对入口，必须与共享交付记录一起实现。目前只有构建失败可直接登记失败。
- worker 当前有领取、续期、交付前检查和完成登记代码；这些方法还未接真实文件上传、共享环境锁和普通 URL 读回。测试里的回执只验证事务规则，不证明线上交付成功。
- 请求人的权限变化会阻止领取或开始交付；取消尚未开始的任务及更换处理人的操作，需在页面接线前补上，不能靠删除记录解锁。

## 第二段接线的具体做法（2026-10-23）

构建、后台操作和实际上传分开，后台不用等一条 HTTP 请求持续构建。管理员先提交任务，后台定时读取这条任务的状态；本次 dummy 由操作者指定任务号，启动独立的 GitHub Actions。正式站点自动调度仍保持关闭。

1. `packages/articles/src/build.ts` 校验内部候选：任务号、文章、修订、正文摘要、日期、地址和图片清单都必须匹配。公开快照入口继续只收 `accepted`，内部候选明确标为 `candidate`。
2. `article-release-source.ts` 通过现有 SDK 分页读取已验收文章；`article-build-assets.ts` 取固定的私有图片并核对归属、类型、尺寸和字节摘要。构建期间持有交付锁，避免两次文章发布互相覆盖。
3. 正常 `/blog/` 和 dummy 共用 `BlogView.astro`、正文解析器、页面描述和样式。dummy 另外使用 `astro.blog-dummy.config.ts`，只构建 `__blog-dummy/` 目录的列表、文章、图片及必要资源，不构建商品页，也不上传正式 sitemap。
4. `payload.mjs` 固定本次全部文件；上一版本的图片和脚本保留，撤回只精确删除不再公开的文章 HTML。包先上传 GitHub Artifact，再通过 GitHub 元数据核对来源、代码版本、有效期和 ZIP 摘要；不捏造本地产物编号。
5. `delivery.mjs` 复用已实现的交付记录、租约、逐步写入与普通 URL/ETag 验收。它不能改网站、网关、缓存和正常发布配置。上传的不确定结果保留为 UNKNOWN；只有明确完成的上传和可用的原 A，才允许自动恢复一次。
6. 编辑页的 `ArticlePublication` 使用公共 `call` 和 React Query，支持保存后发布、状态重开、取消排队、重试原候选、更新与撤回。撤回保留草稿、图片和地址归属。正式后端没有启用开关，因此正常后台不显示发布按钮。

### dummy 怎样避免与 pricing 互相影响

- 仅新增函数 `seo-blog-dummy`，不改 `admin`、`public-api`、`alibaba-catalog-sync`，不绑定公开函数网关。
- 八个文章集合使用已约定的 `blogDummy20261023*`；四个交付记录集合另外使用 `blogDummy20261023ReleaseTargets/ReleaseScopes/ReleaseRuns/ReleaseSteps`。函数只能访问八个文章集合；交付进程才能访问另外四个记录集合。
- 这四个测试记录集合复用原来交付工具的代码，与正式记录分开保存。**现有正常部署尚未接同一套数据库锁，故不能只靠数据库锁宣称互斥**；真正的部署入口还使用既有 `cloudbase-deploy-test` GitHub 并发队列，与 Deploy Test、原 canary 排队执行。不会取消其他正在发布的任务。
- 云存储只写 `__blog-dummy/articles/…`；静态托管只写 `__blog-dummy/…`。私有图片不返回存储地址，仍通过鉴权字节生成 Blob 预览；发布后的图片才进入 dummy 静态目录。
- 测试会话密钥和 JWT 只存在机器上的外部私有目录及独立函数配置中，不提交 Git，不放进网页和 GitHub Artifact。函数测试窗口自动到期；到期后拒绝操作，不自动删除数据。

### 一次实际测试怎么走

`provision-dummy.mjs plan` 先只读核对环境、命名占用、现有页面摘要，写出待执行范围。通过本地及远端检查后，以同一代码版本执行 `provision`，创建私有集合和独立函数、读回权限与代码身份，再启动本地页面到真实函数的桥接。

从编辑页创建 A、上传图片、保存、预览并发布。后台排队的任务号传给 `seo-blog-dummy.yml`，Actions 构建、保存候选包、上传并验收，再由页面读回 SUCCEEDED。然后编辑 B，选择仅用于 dummy 的 `after-upload`，在 B 的所有文件上传并验收后制造一次失败，恢复到已经验证过的 A；页面应显示恢复完成且 B 发布失败。B 草稿与新字段保留，再重试同一个 B 候选，最后做撤回与实际 404。

这套真实测试由本地页面、独立云函数、真实 NoSQL、真实私有存储、GitHub 执行进程和网站测试目录组成；不能写成“后台已经部署到云端”。尚未运行的步骤继续列为待验收，不用离线测试替代。

### 收尾与停止

目标、权限、代码版本、原站页面摘要或文件归属发生变化时，停止新的写入并查明原因。原来正常发布正在进行时排队等待。未知上传、租约过期、恢复结果不确定时，不递归恢复，不自动解锁或删除记录。

测试结束先停本地桥接并等待独立函数测试窗口到期。默认保留记录、原件及备份；删除资源需要单独列明精确清单并核对用户要求，不做目录级清理。

## 实际执行命令

```bash

# 完成本地/远端验证并核对 plan 后，构建同一提交的独立函数。

export BLOG_DUMMY_EXPECTED_SHA="$CHANNEL_BUILD_SHA"
node scripts/blog/provision-dummy.mjs provision

# 只为隔离测试身份签发短期会话，不输出密码、密钥或 JWT。

# 通过 queryEnv(domains) 核对 127.0.0.1:58484；未配置时只增加这一条临时来源。
```

### 现场 404 设置被旧部署重写时

2026-10-23 的只读检查发现现有设置又是 `ErrorDocument: index.html`。沿用之前已授权的 F1 修复范围：只将错误正文指向现有 `errors/not-found.html` 并保留原始错误状态；首页文档仍为 index.html，不改业务文件、函数、数据库、域名、路由或缓存策略。

`repair-404.mjs plan` 保存完整配置与首页/分类/sitemap 摘要；`start-lock` 请求原有 F1 维护入口并先把这份原始配置保存为 GitHub Artifact。等待 pricing 的 Deploy Test 结束并取得维护队列后，`apply` 要同时核对执行代码、运行中的维护步骤、已保存备份的实际内容和配置没有漂移，才写一次网站配置。之后用普通请求、重新验证与条件请求核对缺失网址确实返回专用 404，正常页面摘要不变。

如果需要恢复原有行为，使用相同备份和仍在运行的维护任务执行 `restore`，恢复保存的原始参数；不会回滚数据库或函数，也不删除任何文件。上传或配置写入结果不明时先读回，不反复提交。旧的首页兜底本身不是正确的 SEO 错误页，因此恢复原始配置只是故障时恢复原有行为，不能写成通过新的 404 验收。

```bash
node scripts/blog/repair-404.mjs plan
node scripts/blog/repair-404.mjs start-lock
# 从 GitHub 读回本次排队任务，确认它实际进入 maintenance 步骤。
export F1_MAINTENANCE_RUN_ID="本次实际任务编号"
node scripts/blog/repair-404.mjs apply
# 仅在确认需要恢复原设置时，仍持相同队列并执行：
# node scripts/blog/repair-404.mjs restore
```

SDK 使用当前管理连接给出的临时凭证，仅保存在该进程内，不显示、不写文件。此修复不能阻止另一个旧版本 Deploy Test 再次设置 index.html；本分支正式合并并采用新的部署约定前，每次现场验收仍须重新检查。

已有 dummy 资源需要更新代码时，不能删除后重建或绕过命名占用检查：先核对本地 prepared 记录、真实函数代码和集合归属，确认没有正在构建、交付或待核对的任务；仅更新该独立函数的代码及版本配置，保留原测试身份密钥和到期时间，部署后实际调用 health 比对提交号。版本切换期间不运行页面测试。

只验证真实后台而不占用静态发布队列时，设置 `E2E_BLOG_DUMMY_BACKEND_ONLY=1 E2E_BLOG_DUMMY_LIVE=1` 启动同一 runner。该场景有独立测试名称，只执行保存、上传、预览、重开、权限和并发冲突；不触发 Actions，不写网站文件，不能把它记为 A→B→A 通过。

## 网页已通过验收，但文章状态没能登记成功

这类情况要分两件事查：网页是不是真的已经正确发布，以及后台是不是漏了最后一次登记。本轮真实演练发现了这种接线错误，修正后继续保留严格的三字段回执检查，不放宽数据格式。

`confirm-accepted.ts plan` 只读核对：交付记录已成功且仍为当前版本、对应 GitHub 原文件包真实存在并通过摘要检查、包内任务号一致、线上每个文件都与原包一致、没有额外文件、权限和原站页面摘要可确认。核对单存放在仓库之外。

`confirm` 只使用独立 dummy 的数据库锁，再把同一套证据全部重查一次。前一个执行进程已停止、任务仍是该篇文章的当前任务、操作者权限仍有效时，才在一个数据库事务内补齐公开引用和成功状态；保留更新过的草稿。它没有静态上传、删除、配置修改或业务集合访问入口，因此不占用正常网站发布队列。静态发布和恢复本身继续使用共享 GitHub 队列。

此入口只用于有完整成功证据的例外情况，正常发布不会多走一次。未确认的云端写入、失效或不匹配的文件包、出现新版本、内容不一致，都不能靠它改成成功。

```bash
export BLOG_DUMMY_TASK_ID="从实际文章任务读取的任务号"
export BLOG_DUMMY_ACCEPTED_RUN_ID="从已验收交付记录读取的编号"
./apps/site/node_modules/.bin/tsx scripts/blog/confirm-accepted.ts plan
# 当前提交须通过两项远端检查，执行代码须已提交且没有修改。
BLOG_DUMMY_CONFIRM_ACCEPTED=CONFIRM_VERIFIED_BLOG_TASK \
  ./apps/site/node_modules/.bin/tsx scripts/blog/confirm-accepted.ts confirm
```

需要继续已核对的 A 页面时，真实测试可设置 `E2E_BLOG_DUMMY_RESUME_ACCEPTED=1`：读取该次成功确认记录，从后台重新打开同一篇文章，再执行 B、恢复 A、重试 B 和撤回。不会删除 A 或另造一份 A 冒充同一次恢复。

新 dummy CI 对本 SEO 分支的每次 push 都运行只读检查，避免依赖文件或测试文件改动漏掉触发。它不在 push 时获得云端写入入口；正式部署流程不改。

2026-10-23 本轮实际已完成到：首个 A 的真实交付、经证据核对的状态补登记，以及重新打开后台和公开页的复查。按用户最新安排，B→A、重试和撤回暂缓。需要只核对既有 A、避免新建任务时，增加 `E2E_BLOG_DUMMY_VERIFY_ACCEPTED_ONLY=1`，并同时设置 `E2E_BLOG_DUMMY_RESUME_ACCEPTED=1`；该场景有独立名称，会在检查公开页面后结束。普通完整演练不要设置这个只读检查选项。
