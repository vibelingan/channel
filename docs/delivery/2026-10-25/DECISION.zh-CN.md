## 三件事情，发生的时间不同

**代码部署**：开发者改组件、接口、样式，GitHub 检查代码，构建固定版本，再更新网站或函数。这里需要备份、交付和恢复。

**文章发布**：客户在后台点发布，服务器检查这篇内容，决定哪个版本对外可见。客户不应该需要认识 GitHub，也不应该等定时器才开始处理。

**访客访问**：浏览器或搜索引擎请求一个网址，得到 HTML；浏览器随后可能再请求图片、脚本和业务 API。这里不执行备份、CI 或部署。

上次“访客不会执行备份”只是在说明两者没有直接调用关系，并非用户把二者混淆。备份慢会拖延新版本上线；上线后网页快慢由首屏 HTML、网络、缓存和 API 决定。以后不把这句话当作构建性能的解释。

## 文章发布：两种正规做法，当前实现为什么要调整

静态网站收到 CMS 发布通知后重新生成 HTML，是正规的做法，适合更新不频繁、可以等几十秒或几分钟的内容。它的问题不在“用构建生成文章”，而在我们把文章和整站交付绑得太紧，还计划用五分钟轮询启动。

目前的具体路径是：后台创建发布任务 → GitHub 人工入口或尚未启用的定时入口 → 读取已验收整站包 → 生成文章快照 → Astro 整站构建 → 归档候选包 → 上传变化文件 → 对外验收 → 登记文章发布完成。`scripts/run-site-delivery.ts` 和 `seo-site-delivery.yml` 就在做这条链。文章不是在浏览器里单纯拉一次 API 就自动拥有新的静态 HTML。

另一个正规做法是：后台保存已发布版本，前端服务器在收到文章请求时读取这个版本，返回包含正文和 SEO 信息的 HTML。可以只让 Blog 用这种方式，其余页面继续静态生成。[Astro 官方支持同一个项目按页面选择](https://docs.astro.build/en/guides/on-demand-rendering/)。

| 选择 | 发布等待 | 代价 | 本项目判断 |
| --- | --- | --- | --- |
| 静态 Blog，发布即触发 GitHub | 立即启动，但仍要排队、启动环境、构建和交付；不是即时出现 | 可沿用静态托管；必须改即时触发与重复构建 | 可行备选，适合接受发布等待 |
| Astro 服务器返回文章 HTML | 提交已发布版本后，下一次请求即可读取；无文章构建任务 | 增加一个 Node 页面服务；要管同域路由、服务可用性、费用和首字节速度 | **推荐，符合本次发布体验要求** |
| 换 Next.js / Payload 重做后台 | 仍要设计缓存、发布和部署 | 重做已经实现的编辑器、权限与存储接入 | 当前没有必要 |

Payload 是内容管理系统；它提供 API，不代表任何接它的网站都只用浏览器渲染。其[官方网站模板](https://github.com/payloadcms/payload/blob/main/templates/with-vercel-website/README.md)明确包含按需更新缓存；[官方发布 hook](https://github.com/payloadcms/payload/blob/main/templates/website/src/collections/Pages/hooks/revalidatePage.ts)在发布、撤回或删除时更新相应页面和 sitemap 缓存。你以前的项目具体怎么返回 HTML，要看那个前端的实现，不能从“API 已出现文章”推断已经生成 HTML。

### 推荐的 Blog 细节

继续用现有 Tiptap OSS 编辑器、文章 JSON、安全解析器、草稿、修订号、媒体和权限模块。只更换“公开页面如何取得文章”和“发布完成的判定”，不重新造 CMS。

1. 保存草稿不公开。点发布要带已保存的修订号和请求编号。接口核对管理员权限、JSON、slug、SEO 字段、图片归属和可公开状态；冲突返回冲突，不能覆盖别人新改的文章。
2. 一次成功提交切换公开修订，连同媒体引用和必要的后续事件保存。请求重试要返回同一个结果。数据库具体事务边界必须沿用、核实当前 CloudBase 文章存储实现，不能只在内存里改状态后就报成功。
3. `/blog/`、分页、文章详情及文章 sitemap 从同一份公开内容读取。初期动态 HTML 使用 `Cache-Control: no-store`，避免先把缓存更新复杂度引进来。正文可以按“文章修订号 + 渲染器版本”缓存，但每次先核对最新公开状态；撤回不能命中旧正文。
4. 接口提交成功后返回 URL 和修订号。页面显示“已发布”；如提交后的确认响应丢失，按请求编号查询结果，不能猜成功，也不能重新创建另一篇文章。公开 GET 自己能从数据库取得新版本，不依靠后台另一个 HTTP 请求来“激活”。
5. 文章更新、撤回和列表使用同一规则。撤回返回真实 HTTP 404，正文用本分支既有错误页；不是返回一张写着 404 的 200 页面。保留修订记录，不删除历史内容。
6. 五分钟任务如以后需要，只负责补做遗漏的非关键工作，例如记录或预热；不控制文章何时可见。搜索引擎自己抓取 sitemap；技术恢复不额外发送“请改回旧版本”的通知。

当前图片路由 `media/articles/[...asset].ts` 也通过 `getStaticPaths()` 输出已构建字节；现有 admin 图片接口是授权预览，不是可直接复用的匿名图片服务。因此新方案必须一起提供只读公开文章投影和发布引用保护的图片交付：按文章当前公开版本确认图片，再从存储取字节，通过同域 `/media/articles/…` 返回；私有预览保持授权与 Blob。不得把 admin 预览改成公开，也不能只切换文章 HTML 后放任新图片 404。缓存和代码恢复都要遵守当前撤回状态。

部署方式建议使用官方 `@astrojs/node` 独立服务，CloudBase 云托管承载；同一个公开域名将 `/blog` 及其子路径转给它，其余路径继续现有静态网站或 API。**不能把 Node 服务文件上传静态托管就算支持 SSR。** [官方 Node adapter](https://v6.docs.astro.build/en/guides/integrations-guide/node/)支持这一运行方式；CloudBase 的[官方 Node 服务部署示例](https://docs.cloudbase.net/recipes/deploy-nextjs-to-cloudbase-run)说明容器需要一致的监听地址和端口。Astro 与 CloudBase 的组合、精确同域路由、成本和海外延迟仍需在现有 test 目标确认；官方支持 Node 不等于本项目现场已通过。

实际依赖为 Astro **6.4.6**。核对 npm 后，`@astrojs/node@10.1.4` 的 peer 为 `astro ^6.3.0`；11.0.0 要求 `^7.0.0-alpha.2`，不能照最新文档直接装 11。没有修改本仓库 lockfile。本轮隔离的本地实验已验证九项：静态商品仍正常、文章初始HTML有正文、不重建更新文章与列表、撤回真实404、撤回正文和列表链接消失、商品静态字节未变、HTML no-store。实验使用本机JSON文件模拟内容存储，没有连接CloudBase；源码未接入产品。结果见 `evidence/astro-mixed-rendering.json`，不能把本机实验时间当成CloudBase发布速度。

## 商品继续 SSG，API 只更新屏幕，不改服务器文件

现在商品独立页的 `getStaticPaths()` 枚举快照，Astro 在构建时输出名称、描述、规格、图片和 SEO。普通访客和爬虫收到相同的初始 HTML；不是识别到 Google 才生成。

页面打开后，`CatalogDetailController` 用同一份构建数据开始显示，挂载后请求公开商品 API。请求配置为 `cache: 'no-store'`。现有取消旧请求、拒绝迟到响应和变体修订号校验继续保留；该组件当前仍是 fetch 加业务状态机，没有改用 React Query。

**浏览器拿到新商品数据，只会更新当前屏幕；不会把托管中的 HTML、canonical、JSON-LD 或 sitemap 改写。** 后四项要通过服务器的内容交付更新。建议商品同步或后台保存完成后，立即记录一条“哪些商品变了”的持久任务；合并短时间内重复修改，再生成并交付页面，不等五分钟定时启动。浏览器不负责触发发布。

还要补齐：浏览器恢复联网、切回页面、前进后退恢复时的刷新；网络失败提示，避免把旧内容标为最新；同步后 HTML / sitemap 更新的时限；新商品在静态地址准备前仍能通过已有详情入口查看，不发出会 404 的新链接，不把商品隐藏。Astro 静态动态路由不会自动为构建后新增的 ID 提供 SSR，不能口头承诺已有这种兜底。

商品接口与 pricing 共用：只通过现有公开投影读取，不新增价格字段，不修改同步写入结构。公共请求层和业务查询 hook 的整理另按原方案接入，不在本轮临时再造一套通用请求器。

## 备份、正常部署和恢复怎么简化

已有上传步骤 `hosting-delta.mjs` **会跳过有一致内容依据的未变化文件**。不能把“开始做增量上传”当作下一轮的新成果。仍需改的是：正常代码部署每轮整站下载，以及完整旧包 / 候选包反复复制历史资源。

推荐的下一版：首次接管保留完整 A；每次正常发布保存固定 B 和文件清单，复用已验收 A 的完整恢复资料。持锁对比现场目录、文件身份和配置，发现未知改动先停止或补齐所需文件，不拿过期清单直接覆盖现场。归档对象只保存一次，历史清单引用已有内容；独立保存可恢复资料，不能只靠可被覆盖的线上文件。候选 B 本身完整性必须校验，归档缺对象就不能写线上。

恢复入口放 GitHub，选择具体的 A、目标环境和本轮操作记录。lint / 单测 / 构建失败时没有更新网站，结束即可；**已经写入 B 后，真实验收失败才需要恢复**。自动恢复只能恢复本轮认领且仍由自己控制的目标；如果版本已被别人更新、旧程序不兼容当前数据或状态不明，就停止自动写入并保留可操作的人工方案。

前端恢复恢复页面和引用资源；函数恢复恢复指定函数包和允许恢复的配置。**不随代码恢复整库**，不删新增字段，不把已撤回文章恢复成公开。旧程序是否会错误整行覆盖新字段、当前新网页是否还能调用旧接口，属于恢复旧函数时的检查；正常部署只校验本次变更需要的向前兼容性，不反复跑所有历史版本。

静态托管逐文件上传不等于全站原子切换。当前方案只能通过先上资源、再页面、保持旧资源、检查版本及失败恢复缩小混合版本窗口；不能承诺所有 URL 在同一瞬间从 A 变成 B。若要求整个网站原子 A/B，需另验可按版本路由的网关 / 托管能力，不能靠给目录改名冒充。文章公开修订可在数据库内原子切换，和整站原子性不同。

COS 服务端复制是值得试验的备份加速路径，但需要真实验证源和目标权限、条件复制、配置以及独立副本读回。它**不自动提供整站快照、数据一致性或原子恢复**，本轮不将它列为已经落地的能力。

### 上次那句 SDK / MCP 话，实际只想表达什么

GitHub 发布程序有专门的发布账号，就使用这个账号读取**明确指定的网站环境**。本机手工检查则可以使用已经登录的 CloudBase 工具。它们最后调用同一个备份校验函数；不会为了查一次文件列表，把其他会话正在使用的环境切来切去。

这里没有额外的 AI、动态决策或新业务功能。SDK 是脚本直接调用腾讯接口用的程序包；MCP 是 Agent 调用腾讯工具的一种入口。用户无需在两种入口之间手动做选择。

## 八分钟：目标保留，先修真正的慢处

八分钟从提交进入发布流程（包括队列）计到目标 URL 验收成功。另报告纯检查、构建、归档、云写入、验收时间，不能把花费移到另一条 workflow 就说达标。已有同一提交、同一配置且仍有效的检查和构建结果可以复用，但必须核对提交、输入、文件哈希和有效性，不能使用“最近一次绿灯”。

事实：

- 已有 509 商品本地构建日志：526 个路由，SEO 检查扫描 527 份 HTML，含 SEO gate 共 **47.55 秒**。不是 GitHub 或线上用时。
- 完整 CI `40116681076` 的首个 job 启动至最终结果为 **12 分 11 秒**。site 单测一组 8 分 48 秒；正式后台浏览器组 10 分 18 秒。构建还在单测之后串行约 3 分 16 秒。详见 `evidence/ci-timing.json`。
- 完整源站备份有 5:46、4:19 和实际 CLI 4:36 的样本；五分钟硬指标还没有稳定达成。

下一步优先拆分 site 单测和耗时后台浏览器组；构建与测试并行，最后统一等全部必需项；同一提交构建一次、交付复用；静态交付只传变化文件；已验收恢复材料只保存一次。不能删除测试、跳过价格 / 图片 / SEO 功能来换速度。

规划预算为：排队 45 秒；并行检查与构建 240 秒；版本核对及归档 45 秒；云端差异交付 90 秒；真实验收 60 秒，共 480 秒。**这是验收预算，不是实测承诺。** 超时算性能未通过；如果已经开始写线上，要先完成或安全恢复，不能在八分钟处强杀留下半站。

新的 Blog 发布不走代码 CI。初步目标是点发布后立即处理，公开状态切换后下一次 GET 读到新版本；页面发布操作到公开 URL 确认可见先定为 10 秒内的验收目标，包含服务冷启动和存储访问，不引用本机实验毫秒值作保证。海外读首字节另外测量。
