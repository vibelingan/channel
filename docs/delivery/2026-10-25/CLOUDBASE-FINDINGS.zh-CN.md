## 已经重现的五种结果

诊断程序调用**实际安装的 SDK**，HTTP 服务只在本机监听，不需要密钥或客户资源。

| 场景 | Manager 5.9.1 实际结果 | 正确要求 / 已有修复 |
| --- | --- | --- |
| 正常完整正文 | 成功写文件 | 正常路径继续通过，并复算长度和校验值 |
| 云对象 `X` 和 `X/a.html` 同时存在 | 本地将 X 同时当成文件与目录，写入流 `EISDIR` 未处理，子进程退出 | 每个原始路径映射为独立编号文件；清单保留原路径，恢复到原地址 |
| HTTP 正文中途断开 | Promise 未完成，诊断看守一秒后报告挂住 | 响应头和整个正文有独立总时限，取消读取，有限重试；半截文件不验收 |
| 注入读取流错误 | 异常逃出 Promise，未处理的流错误结束进程 | 错误归属当前读取任务，不把子进程退出当成功 |
| HTTP 503 正文 | SDK 保存错误文字后报告完成 | 检查状态码、长度、内容摘要；503 不能成为网站备份 |

5.9.2 包中下载器仍采用 `body.pipe(dest)` 并以目标流 `close` 完成，目录任务的失败处理也没有形成完整内容保证。因此**没有依据认为只升级到 5.9.2 就能解决本次问题**；这不是说以后任何版本都不能修好。SDK 即使修好下载，完整备份仍需要清单、内容一致性和配置验证。

第一次旧 MCP 日志只保存了 `-32000 Connection closed`，未保留最初 stderr。遗留目录与路径冲突相符，但不能倒推出第一轮唯一根因。Node / Undici 已知取消问题作为线索查过，本机强制 GC 实验没有复现，因此没有将它写成已证实原因。

node --test scripts/hosting-backup-download.test.mjs scripts/hosting-object-reader.test.mjs scripts/smoke-http.test.mjs

本轮重跑上述合计 **31 项通过**。它们包括对旧下载器的缺陷重现和对新适配的保护测试；“测试通过”并不是“旧 SDK 已修好”。升级后旧缺陷断言变化应触发人工复核，不能为绿灯强迫新 SDK 继续表现成旧缺陷。

## 直接读 COS 是正常的授权读取

原来备份经网站域名取文件，相当于像访客一样经过分发层。现在发布程序使用已授权的管理凭据，通过腾讯官方 COS SDK 对指定托管桶的对象生成五分钟有效的 GET 签名，再下载同一个文件。

这是腾讯提供的[预签名访问能力](https://cloud.tencent.com/document/product/436/36121)和[对象 URL 接口](https://cloud.tencent.com/document/product/436/57421)。授权不足仍会拒绝；我们没有修改桶的公开权限、破解鉴权或隐藏访问。更准确的说法是“**由已授权的发布程序直接读取源文件**”。不需要为每个小文件走网站缓存，主要是减少分发状态对恢复资料的影响。

范围仍须严格限制：环境、桶、地域、共享桶前缀必须从已认证的托管信息取得；不混用普通图片桶；只允许 GET 到该桶的腾讯域名；签名仅在进程中使用，不写日志、仓库、页面或备份。签名 URL 本身可授予短期读取能力，所以不能随手复制给其他人。

“官方接口支持”不代替本项目账号授权；本轮已有目标范围内的完整只读复测。后续换桶、跨账号或做服务端复制，仍须重新核对具体权限，不能沿用本轮结果。

## 官方 skills 有没有提到

对本机 CloudBase 技能树搜索 `EISDIR`、`downloadDirectory`、`ETag`、`multipart`、`AbortSignal`，再阅读 CLI hosting 参考、平台及 CloudRun 入口；并读回官方 Toolkit 当前 hosting 源文件。发现：

| 已有内容 | 本次仍缺的部分 |
| --- | --- |
| 构建后部署、下载整个托管目录、指定环境 | `X` / `X/...` 布局无法直接映射成本地目录；下载器异常可能只表现为 MCP 关闭 |
| SDK / CLI 操作说明 | 完整响应体时限、HTTP 503 不能当成功、内容与目录前后核对 |
| 文件覆盖和 CDN 缓存注意事项 | 恢复版本须完整且可读；增量归档不能递归纳入 `.cloudbase-backup/` |
| 泛化的部署流程 | 历史资源保留与每轮重复复制要分开；不能把逐文件上传写成原子切换 |

它们提供了常用操作，但**本轮核对范围内没有这些具体保护规则**。不能据此说“所有官方文档都没讲过”或认定新版 CLI 的实现一定与本次 Manager 完全相同。

官方 hosting 参考还有先删全站再重新上传的示例。这个操作不适用于本项目：会破坏旧标签页所用资源和恢复能力。我们保留历史资源，不照搬示例去删文件。

## 经验怎么保存，避免以后变成过时补丁

分两层保存：

1. **长期规则**放 `docs/ENGINEERING_CRAFT.md` 的 CloudBase Hosting & Recovery 分类：授权读取、完整性检查、可恢复版本、路径映射、差异交付、失败停止。这些不依赖某个 SDK 一直有 bug。
2. **版本故障**放本文件、现有诊断脚本及验收 JSON。每条写明实际运行或仅源码检查，保留触发版本和上次验证日期。升级 SDK / Node 时重跑；上游已修复就调整“已知缺陷”状态，删除不再需要的兼容分支前仍验证自己的备份要求。

不建议现在新开一个 fork 仓库，复制整套官方技能再自行长期维护。优先在仓库内保留这份补充，并由项目已有 SDK 验证规则链接进来；以后若多个项目实际复用，再做一个很薄的 skill 包装：先读官方原技能，再加载这些带版本与验证命令的补充，不覆盖官方安全和权限规则。

上游可分别贡献：Toolkit 的操作文档补充 PR；Manager 的最小缺陷报告或代码修复。已按 [CONTRIBUTING](https://github.com/TencentCloudBase/CloudBase-AI-Toolkit/blob/4f68e9060c94327c1a39aa282ad17a03a4d7dfe5/CONTRIBUTING.md)核对源目录和提交规范，草稿见同目录 `UPSTREAM-DRAFT.zh-CN.md`。Manager 包声明的 GitHub 仓库本轮返回 404，不能假定有可直接提交的公开源码。当前不新建远端仓库、不发送工单、issue 或 PR。

## 哪些性能问题尚未解决

读取方式已改善：网站分发路径18:25；认证源站样本5:46、4:19；实际命令4:36，内容全部一致。但样本不能证明每次都小于五分钟。

89 MB 主要包括44.66 MB媒体和42.81 MB构建资源；127份AdminApp不同哈希资源说明历史版本占用明显。正常上传已有差异判断；下一步减少的是每次整站备份和完整包反复携带历史资源，不以删历史资源、降低一致性检查或增加不受控并发来凑时间。

数据与脚本来自已校验备份，不对云端再次写入。脚本成功不代表整条部署已达到八分钟，真实 test 的 A→B→A 和端到端计时仍待实施。
