## 模块：代码部署和恢复提速

**要交付的结果**：同一提交构建一次，A、B 可选择且恢复资料完整；正常发布不反复下载全部历史文件；完整流程目标八分钟，不减功能或检查。

改动面：现有 `ci.yml`、复用检查 workflow、`deploy-test.yml`、`run-site-delivery.ts`、归档读取与 `retainSiteAssets` 的版本清单组织。先证明所有权和读取格式，再改调用者；不把文档中的新存储设计直接当成旧包兼容实现。

实施顺序：

1. 导出当前 job / step 耗时。把 site 测试的类型检查、普通测试和真实浏览器测试分别计时；按稳定文件清单拆 shard，核对覆盖文件集合的并集恰好等于原集合，既不遗漏也不重复算通过。对长后台浏览器组做同样拆分。
2. 构建与独立单测并行；最终门槛必须同时等待所有必需项。构建只保存产物，检查未通过不得接触云端。不因为提前构建就提前部署。现有 `deploy-ci-gate.test.mjs` 明确检查 `checks.needs=unit`；并行改造必须同时重写为“最终部署等待全部检查”的有效门槛并保留失败注入用例，不能仅删 `needs` 或放宽断言。
3. 交付复用同一 SHA、同一公开地址及功能配置的产物。fixture 构建不能替代真实商品快照；公开环境输入不同则必须重建对应站点，不能把错误域名的产物当相同版本。
4. 版本档案保存本版本页面和需要的资源，另保留旧资源。历史对象以内容摘要引用，固定清单引用的对象必须完整可读，不能依赖上一轮 GitHub 临时 runner 的缓存。归档与缓存分开；缓存失效允许重建，归档缺失必须停止。
5. 首次导入 A 完整备份；正常交付持锁核对现场目录 / 身份 / 配置与已验收 A。漂移即停止，或只补齐需要备份的变化内容并重新验证。没有版本身份或可信摘要的文件不能只凭长度跳过。恢复缺少任一必需对象就不能写入。
6. 同一个执行器负责差异上传、读回和恢复；先资源再 HTML，保留旧资源。写入失败与写入结果未知分开；后者先读回，不盲目重试。旧包读取保留兼容性。

验收：未变资源无正文下载 / 上传（必要元数据查询另计）；篡改或缺失档案文件拒绝；未知现场修改拒绝覆盖；构建失败没有恢复动作；B 验收失败才尝试恢复自己保存的 A；其他人更新后的版本不被旧任务覆盖。保留全部既有商品、后台、价格、图片、SEO 和函数检查。

计时：同一提交全流程计队列，不靠拆 workflow 藏耗时。目标预算见 DECISION。至少保留冷启动和重复运行结果，报告所有样本、重试和失败，不只挑最快一次。八分钟尚未实测通过；一次全站备份小于五分钟不等于整条流水线达标。超时后优先安全结束或恢复，不按秒强杀正在写线上过程。

## 模块：文章发布即时可见

**要交付的结果**：后台提交公开版本后，文章详情、列表、分页和 sitemap 使用同一份已发布内容，正常发布不经过 GitHub 构建。

保留：现有 Tiptap OSS、文章结构化 JSON、安全 renderer、草稿和媒体权限。新增：Astro 官方 Node adapter 和只负责公开页面的服务；不把管理员凭据发给浏览器，不引入 Hermes。

改动面：Blog 路由从 `getStaticPaths()` 读取构建快照，改为按请求读取公开文章；共享 layout、SEO helper、正文 renderer 和既有视觉样式继续复用。文章接口在事务完成后返回公开版本；退役“只有静态交付成功才能切公开状态”的耦合，但保留必要的权限、媒体、修订和幂等规则。旧任务必须明确停用或迁移，不让旧静态 worker 又把旧文章写回来。

实施顺序：

1. 核对并固定 Astro 6.4.6 对应的 adapter 版本；单独证明静态商品路由与动态文章路由并存。证明不重新构建即可更新和撤回，返回真实 HTTP 状态。框架实验不等于真实 CloudBase 接入验收。
2. 公开读取返回一个完整修订，包括标题、正文、canonical、时间和媒体；列表用相同公开规则。草稿和管理字段不能混入。未发布、无权限、已撤回、错误的 slug 均不得泄露正文。
3. 修改发布服务和预览分界：带版本提交，冲突拒绝；事务里切公开版本、媒体引用与持久事件；请求编号去重。保存草稿、预览与发布相互独立，预览仍需授权。
4. HTML 初期 no-store；正文缓存只能以修订和 renderer 版本为键，先查当前公开状态。现有图片还是构建时静态输出，必须新增受发布引用保护的公开图片读取；授权 admin 预览不能直接公开。新服务覆盖同域 `/media/articles/…`，检查当前公开状态后返回字节，不把私有存储地址塞入页面。文章 sitemap 按请求读公开记录，静态 sitemap-index 指向它。
5. 本地界面继续连接真实 CloudBase，以真实存储验证发布、并发、回读和撤回。页面返回之前先保证正文是服务端产生，不依赖客户端 API 来“补齐 SEO”。
6. 本轮已只读确认云托管开通、现有域名可复用，但还没有Blog服务。test先部署独立页面服务并验证，不切公开域名；确认端口、网络、身份、费用上限和运行版本后，才切 `/blog` 和必要的文章媒体路由。必须对 `/blog`、`/blog/`、文章、分页、sitemap 的精确匹配及优先级做真实请求验收，确认不会吞掉 `/products`、`/api` 或静态资源。主域名现有域名级规则强制no-cache，要读回最终HTTP头，不能只测试服务自己的no-store。当前为DIRECT接入，不把CDN清理当作默认修复；路由/响应头只改经说明的范围，不覆盖全站。

验收：从后台发布一篇普通文章 → 拿真实 URL → 禁用 JS / 原始 HTTP 也有正文与 SEO；更新后新请求见新修订；撤回是 404 且列表 / sitemap 同步消失；双窗口冲突、重复点击、响应丢失、服务重启和代码回退都不复活旧内容。发布成功不是“已入队”。十秒为初始目标，CloudBase 冷启动与海外首字节均需实测。

页面有 UI 变化先截图。这里应主要改变按钮状态含义与可见速度，沿用现有清爽 Blog 视觉；不借架构调整重做一套样式。

## 模块：商品静态正文与实时数据保持一致

**要交付的结果**：独立 URL 首次有正文，用户刷新能拿最新 API；同步或修改后服务器 HTML 也按明确时限更新，不能说 API 请求已经改了静态快照。

改动面：现有公开商品读取和快照采集、内容任务与页面发布。pricing 同步不在本模块重写；接现有公共接口，先核对已合入 main 的投影。公共请求整理沿用现有库，不自创平行协议。

实施顺序：保存 / 同步成功后记录变更 → 幂等任务合并重复商品 → 构建当前公开快照 → 对比版本，过期构建拒绝交付 → 上传变化页面和 sitemap → 验收。新商品静态 URL 未就绪前，现有详情入口可看内容；不要隐藏商品，也不要让分类页输出死链。撤回先保证公开 API 不再返回，再协调静态页移除、真实 404 和缓存清理。

浏览器刷新、切回前台、重新联网和历史恢复触发业务查询；取消旧请求、变体修订一致性继续由现有业务状态规则保护。网络错误显示状态，不能把旧快照称为实时数据。HTML 与 API 修订分开显示于诊断证据，不在客户页面堆实现细节。

验收：已有、刚新增、修改、撤回商品；发布期间连续两次修改；旧慢请求迟到；部分变体分页换版本；离线恢复；旧 HTML 打开后 API 更新；API 失败与重试。以原始 HTML、JS 页面和 API 三路版本对照，不仅看页面截图。
