# 真实 CloudBase 的无害恢复演练

## 要证明什么

先确认保存下来的旧程序 A 确实能恢复，再发布 B，最后明确选择 A 恢复。恢复只换程序和测试网页；B 新增的数据、备注字段和撤回记录都必须保留。最后再让 A 修改原有字段，确认它不会把 B 的备注丢掉。

本页是执行方案。代码写完、离线通过、远端 CI 通过和真实执行结果分别记录，不能把前三项当作演练成功。

## 只动哪些东西

| 资源 | 范围 |
| --- | --- |
| 临时函数 | `seo-release-dummy`，Node 20.19；不接公开 HTTP 路由；每次调用还校验本次演练凭证 |
| 测试数据 | `seoReleaseDrillFixtures` 中本次 `seo-drill-<初始运行号>-…` 的三条记录 |
| 演练记录 | `seoReleaseDrillTargets / Scopes / Runs / Steps` 四个私有集合，与真实发布记录分开 |
| 临时网页 | `__release-canary/index.html`，一份不进站内链接和 sitemap、明确禁止收录的测试页 |
| 归档 | GitHub Actions 保存实际函数 ZIP、测试网页、校验结果与恢复记录；不保存凭证明文 |

这些集合全部要求 ADMINONLY。只创建缺失的固定集合；已有集合权限不符合要求时停止，不重置其权限或内容。临时函数同名资源已存在时停止核对，不能强行覆盖。临时网页路径必须确认为空，或者已经由本轮演练验收。

商品、价格、商品同步、文章数据、AI 数据库和普通网页都不在写入范围内。演练前后读回首页、分类页和两份原站地图，并对比真实发布记录。这里新增的是 NoSQL 测试记录上的可选字段，不是在 AI 的 PostgreSQL 表上做 DDL 迁移。

## 四次人工操作

沿用 `SEO static canary (manual)`，选择 `dummy-recovery`。父入口继续使用现有 `cloudbase-deploy-test` 队列，不与正式发布或 pricing 并行写入。每次运行先要求当前提交完整 CI 成功。

| 次序 | action | 做什么 | 必须看到的结果 |
| --- | --- | --- | --- |
| 1 | initialize | 创建 A，真实调用函数创建和修改测试记录；下载实际运行的包，归档后再登记为可恢复 A；交付临时网页 A | A 的实际包、健康身份、真实数据写入和网页读回均通过，得到 `acceptedRunId` 和 `activationId` |
| 2 | restore | 明确选择第 1 次的 `acceptedRunId`，先执行 A→A；临时网页也恢复 A | 实际使用归档中的字节，恢复后还能读写测试数据，普通网站保持原样 |
| 3 | publish | 发布 B；用真实函数给旧记录加备注、新建一条记录、再新建并撤回另一条；临时网页换成 B | 函数和网页确实为 B，数据确实写在 CloudBase，不能只有本地模拟结果 |
| 4 | restore | 再明确选择第 1 次的 A，执行 B→A | 函数与网页恢复 A；B 的新记录、备注和撤回标记仍在；A 修改旧字段不丢备注；重复请求不重复写入 |

第 2～4 次的 `expected_activation_id` 必须使用上一次返回的函数生效号。`restore_run_id` 始终明确填第 1 次的 A，不接受“上一个版本”这样的模糊选择。网页 A 的运行号由已核对的初始演练号确定，不能由调用方指定任意路径。

A 和 B 的函数包都通过已安装 SDK 真正打包。在任何云端写入前，Linux CI 和人工入口会用云端同版本 Node 20.19 检查包能否独立启动。每次恢复还会实际执行保存的 A 包的兼容测试；此项不加入正常网站发布的每次运行。

兼容范围也要说清楚：A 能读取可选备注，并在修改原有字段时保留它；B 专有的“编辑备注”不属于 A 的功能。这个演练不能证明任意新界面都能配任意旧程序。真实功能若有新增操作，还要检查相应客户端，或者在恢复时关闭那项新操作，不能用本次无害演练替代。

## 怎样恢复，怎样停止

恢复使用已有 C2 函数适配器及 C1 静态文件适配器。二者继续按“记录本次要写什么 → 写入 → 从云端读回 → 确认版本”的顺序工作，演练仅改用独立的发布记录集合。函数包有自己的归档格式，不为通过检查而伪造首页或数据库快照；记录中保留的普通网站部分引用来自实际已验收网站。

恢复前核对当前函数包、运行配置、数据版本与兼容测试。只替换明确选择的函数和一份测试 HTML，不改角色、环境变量、触发器或路由，不回灌数据库。新字段不能读取时明确失败，不能默默把记录整条覆盖掉。

未写入前失败，无需恢复线上。写入结果不明、包不认识、配置变化、权限不明确、网站普通地址变化或上次操作尚未查清时停止后续写入，并保留已记录的具体阶段和请求身份。不能重复提交部署来猜测结果。

实际函数调用记录平台请求号、函数执行号、动作和耗时，便于定位腾讯端日志；不记录调用凭证、完整请求或函数日志正文。

完整演练通过后，先保留操作记录和归档，再核对归属并移除本次临时函数、测试网页及测试记录。清理必须单独确认实际资源和范围；不删除原有资源、业务数据或历史备份。清理的实际结果也需登记，不能只删除本地测试源码就算云端清理完成。

## 代码对应

- `scripts/release-drill/run.mjs`：四个步骤的受控调用与实际结果保存。
- `runtime.mjs / handler.mjs`：固定身份、真实函数调用及三条测试记录的读写。
- `journal.mjs / static.mjs`：复用发布记录协议、C1 和 C2，保留普通网站。
- `scripts/release/function-baseline.mjs`：实际函数包的归档与来源校验。
- `.github/workflows/seo-dummy-recovery.yml`：人工执行；源码仍是原 SEO 分支，不改变默认部署入口。

SDK 核对依据：已安装的 Manager 5.9.1、Node SDK 3.17.2 源码及类型，并核对腾讯官方的[函数管理](https://docs.cloudbase.net/api-reference/manager/node/function)、[数据库管理](https://docs.cloudbase.net/api-reference/manager/node/database)和[权限管理](https://docs.cloudbase.net/api-reference/manager/node/permission)。SDK Invoke 的成功回执与应用返回内容分别检查；只有平台请求号不能算业务成功。
