# 这次实际验收发现的问题与处理

## 当前网站是什么状态

静态发布 `40245662658` 已完成 47 个文件批次，最后检查一个商品地址时，15 秒内没有读完响应。系统因此保留“尚未验收”的记录，没有把这次发布登记成可恢复的正常版本。站点已经有新文件，不能把这个状态说成“发布成功”，也不能直接再上传一次。

新增 `site-readback` 人工入口，只继续最后的读取验收：

1. 从 GitHub 下载原运行归档的完整候选包，核对原提交的 CI、包身份和 47 步写入凭据。
2. 确认原 GitHub 任务已经结束、旧锁已过期，并且未确认的那一步确实只是读取。存在未确认上传、删除或配置操作时，此入口拒绝运行。
3. 取得新的操作锁；重新读取全部文件目录和配置，用源站对象证据核对全部候选文件，检查全部变更网址及明确撤回网址。保留发布器原本不管理的对象，不把文件后缀当作本次发布的所有权。
4. 用当前公开商品列表排除已经撤回的商品，再运行实际公开浏览器检查。检查前后目录、配置和公开商品列表必须一致。
5. 全部通过才登记原候选版本为成功。失败继续保留未验收状态，没有网站写入，没有重新上传，没有自动擦掉问题。

`site-readback` 会写发布记录和操作锁；不会上传/删除网站文件，不改网站配置、函数或业务数据。原来的上传记录保留，换锁也会留下原因和原任务的结束证据。

网络超时、连接中断和 502/503/504 的只读检查最多重试三次，等待 250/500 毫秒。每次仍限制响应头和完整正文的读取时间；字节、摘要、MIME、ETag、权限和配置不符立即失败。该重试不用于云端写入。

## 为什么文章能打开，图片却不显示

实际运行 `40249243887` 已经从后台保存草稿、上传图片、私有预览并发布成功。公开文章返回 200，但图片没有加载。独立 HTTP 检查确认：同一个 `.webp` 地址没有尾部 `/` 返回 404，带 `/` 返回正确的 96,776 字节，SHA-256 与原图一致。不是图片上传丢失，也不能靠多等几秒解决。

Astro 6.4.6 实际生成的动态文件路由沿用了 `trailingSlash: always`。即使把动态文件名写成 `[hash].webp.ts`，生成规则仍要求 `/`，而静态的 `health.json.ts` 不要求。

修复只调整独立 Blog 服务：使用 Astro 支持的 `trailingSlash: ignore`，由现有中间件将没有扩展名的 HTML 页面统一 308 跳转到带 `/` 的地址，保留查询参数。图片和 JSON/XML 用正常文件地址。原静态站点配置、商品网址和业务交互不变。

已在真正构建出来的 Node 服务器上验证图片原地址的状态、类型和完整字节，并完成无重建发布、更新、撤回及桌面/手机浏览器检查。这是本地结果。现有线上服务尚需更新到该修复版本，再从真实后台重发同一篇验收文章。

失败后的验收文章已通过 `40250309491` 撤回；草稿和图片保留。再次验收沿用原文章 ID，避免重复创建。

## Blog 服务怎样更新、怎样退回

`blog-server-update` 仍走原 SEO 手工入口和共享部署队列。只接受当前提交对应、通过 HTTP CI 的服务包。写入前确认现有服务正常且只有一个承接全部流量的镜像，保存实际镜像地址、运行任务和资源设置，归档到 GitHub 确认保存成功，再读一次现场确认没有被别人修改，才提交一次更新。

更新时不传 `serverConfig`。已核对本仓库固定的 CloudBase MCP 2.36.1 实现：它先读远端配置再合并，保留环境变量、网络和访问设置。不会把工具显示的 `***` 当成真实环境变量写回。MinNum=1 和现有镜像之外的配置应保持。

恢复用保存的旧镜像直接部署到同一服务，随后核对运行版本与设置；不重新编译旧代码，不回灌数据库。结果不明先查询任务和健康信息，不重复提交或删除服务。函数源码版本与服务版本的原有一致检查继续执行。

## 验收边界

代码或测试失败且尚未写线上时，无须恢复网站。已经写入但状态、图片、正文或配置不符时，停止下一步，使用保存的对应恢复输入。不会因为一个暂时的读取超时就重复发布，也不会直接把数据库标成成功。

海外部署和整体八分钟目标继续留在功能闭环之后。这里改动的是正确性缺口，没有减少任何验收项目。


## 续验发现的历史文件

第一次续验40253109595停在额外文件检查，没有上传或删除网站。现场目录与原候选包对比，59项额外键中有平台认证页、验证文件、旧dummy和目录标记；真正被新增规则拦住的是7份旧的`_astro`脚本。它们全都存在于上一次失败候选包，长度及实际COS对象MD5均一致。上次恢复时为兼容已经打开的网页，按既有规则保留了这些脚本。

错误在本轮新增的验收条件：`isManagedSiteFile`表示文件类型可以被站点管理，不表示它已经归本次发布所有。原发布器只管理候选和明确撤回的旧路径，续验不能突然扩大范围。已按同一个所有权规则修正：全部候选逐一核对，所有明确撤回路径必须不存在；其余键保持原状并列入结果。前后整个目录仍必须一致。没有删除旧脚本，也没有把它们冒充新候选的一部分。后续整理历史资源需单独设计和授权。
