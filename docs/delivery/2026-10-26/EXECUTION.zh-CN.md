# 文章直接发布：实施与验收

2026-10-26。沿用 `feat/seo-foundation` 和原 SEO 工作目录。本文记录这一轮，不把本地检查写成已经上线。

## 本轮顺序

1. 先完成非 Agent 的文章闭环：后台编辑、保存、预览、人工发布，访客看到列表、正文和图片，更新与撤回及时生效。
2. 保存能工作的 A，交付只有无害差异的 B，再明确选择 A 恢复。恢复程序和文章数据分开：不回灌数据库，不删除新字段、文章或媒体。
3. 接本地 Hermes 内容助手：创作后调用网站的受限接口创建草稿，人登录查看、编辑、预览，最后由人点击发布。不给助手发布权限，不连接真实企业微信群，不改 Hermes 生产配置。
4. 再做部署速度和海外方案。八分钟目标保留，当前不改 CI 分片、不改备份算法。阻碍正确发布或恢复的问题仍立即修复。

本顺序替代 2026-10-25 实施页中“先提速”的排序。该页的故障证据和恢复要求仍有效。

## 文章为什么可以不等 GitHub

网站程序仍需构建、部署一次。之后每次发文章，只需管理员将某个保存版本确认为公开版本。Astro 收到访客请求时，读取当前公开版本，生成带正文和 SEO 信息的 HTML。发文章、修改文章和撤回都不触发 GitHub 构建，不设五分钟定时等待。

Google 能读取这种 HTML。SSR 本身不保证排名；仍检查真实 HTTP 状态、独立 canonical、正文、Article/Breadcrumb、图片、站内链接和 sitemap。页面服务故障返回 503 与 Retry-After，不能伪装成内容已删除的 404。撤回才返回本分支现有 404 页面。

商品仍使用构建时输出正文和浏览器 API 更新；没有迁移到 Next.js，也没有改 pricing 或商品同步。

## 模块一：管理员提交公开版本

修改现有 `createArticleReleaseStore`，保留文章版本、媒体校验和权限检查。服务器设置 `ARTICLE_DELIVERY_MODE=server` 时，一次 CloudBase 事务同时完成：冻结修订、预留稳定网址、更新公开记录、同步草稿的已发布引用、记录发布成功。数据库提交失败时以上都不生效。

复用已有七个文章集合。公开记录仍是 `articleAccepted` 的 `{publication, taskId}`，没有伪造 GitHub 产物收据；直接发布任务的 receipt 和 workerId 都为空。保存草稿不改公开记录。撤回将 publication 置空，保留文章、网址预留和媒体。

- 服务模式只能由后台服务器配置选择，浏览器不能指定。
- 默认仍为原静态方式。`ARTICLE_PUBLISHING_ENABLED` 继续控制入口是否启用。
- 旧发布任务尚在执行或结果不明时，拒绝启动新的直接发布；旧任务的重试也不能偷偷重新排入构建队列。
- 同一请求重试返回原结果，人工编辑不会被旧请求覆盖。

## 模块二：访客读取文章和图片

public-api 增加只读的 `/api/articles`、`/api/articles/slug/{slug}` 和 `/api/articles/media/{id}/{file}`。只有 `ARTICLE_PUBLIC_READ_ENABLED=1` 才接通。现有商品、会员价格和询盘路由不变。

列表每页十二项，只投影公开摘要，读取十三项判断下一页；不把正文、存储位置或编辑者资料送进列表。按稳定 ID 分页，当前不承诺按发布时间倒序。文章详情通过已预留 slug 查当前公开记录，从不回退读取草稿。

图片须属于当前公开文章，且类型、长度、尺寸、SHA-256 与公开记录一致。存储读取后再次核对当前公开引用；下载途中文章撤回时拒绝返回字节。API 返回图片本身，页面不出现私有存储地址或签名链接。图片响应 no-store，旧网址也重新检查公开状态。

`articleAccepted` 新增 `publication.status + _id` 索引，仍为 ADMINONLY；浏览器不直接读集合。上线前创建并读回索引，不能只在本地假定查询可执行。

## 模块三：独立的 Astro 文章服务

`apps/site/astro.blog.config.ts` 使用与项目 Astro 6.4.6 相容的官方 Node adapter 10.1.4，独立输出到 `dist-blog`。复用 `BlogView`、BaseLayout、SiteHeader、SiteFooter 和现有安全 JSON renderer；只增加真实分页链接。原站点默认仍输出 `dist`。

文章服务只持有固定 `BLOG_API_ORIGIN`，不带数据库或管理员密钥。接口地址由部署配置决定，文章输入不能改主机。请求限制超时、响应类型和正文大小，拒绝重定向。故障不返回空列表或旧正文。

服务接管 `/blog`、`/blog/*`，自身 JS/CSS 也在此路径下。公开文章图片使用 `/blog/media/articles/...`；品牌图标等根目录资源仍由原静态托管交付，不打包整站媒体。`/blog/health.json` 报告运行代码版本；`/blog/sitemap.xml` 按当前公开记录生成，包含新发布文章，排除撤回文章。

只有实际切换时才启用静态构建的 `BLOG_SERVER_ENABLED=1`：不再生成静态 Blog HTML，sitemap-index 明确增加同域 `/blog/sitemap.xml`。静态检查继续逐页检查其余 HTML，且拒绝遗留静态 Blog 页面；文章服务另用实际 HTTP 检查正文、状态、canonical、结构化数据、链接、资源和 sitemap。不能通过关掉 SEO 检查来上线。

## 部署包与受控切换

`package-server.mjs` 只收集已构建服务，逐文件记录 hash；拒绝复用旧目录、隐藏文件、符号链接、缺少入口或 CSS 的输出。Node 服务打包依赖，验收从项目外的临时目录启动，不依赖开发机 node_modules。容器以非 root 用户运行，监听平台 PORT。产品媒体、凭据、商品快照都不进入镜像。

写入前重新读取：Shanghai 目标环境、站点已验收 A、后台和 public-api 当前包、文章任务、GitHub 部署队列和共享锁。2026-10-26 的只读核对看到站点为 `site-40106835463-1`、状态 idle、没有 dirtyRun；两个函数 Active，文章发布与公开读取开关均未配置。新 Blog 服务尚不存在。这些是当时观察，执行前必须再查。

真实接线分三段：

1. 先部署独立 `blog-pages`，不修改根站点、现有服务或网关。核对运行版本和服务地址；尚未接通公开 API 时不能把健康接口成功当作 Blog 成功。
2. 在共享部署锁下备份 admin/public-api 的实际包和配置，部署兼容扩展，准备并读回文章索引。先保持发布关闭。用实际后端验证列表、草稿隔离、图片和错误状态，再添加仅指向新服务的 Blog 路由；根路径和商品/API 的原路由不变。
3. HTML、图片、sitemap 和恢复输入都验证后，启用直接发布。用明确标识的验收文章完成页面操作和独立读回；再交付 B 并恢复已验收的 A。临时测试内容按记录撤回，保留资料，不删业务数据。

切换前的退出：保留原函数包与配置，不动现有根路由；新服务失败不影响现有网站。切换后的退出：优先恢复支持同一公开记录格式的已验收文章服务 A，保留当前文章数据。若必须退回旧静态 Blog，须明确新文章暂不可见，不能误报完整恢复。数据库从不整库回滚。

停止条件：目标或现场版本不同、他人占用部署、无可用恢复包、需要升级付费套餐、修改范围越过 Blog、旧任务未结束、图片/权限泄露、404/503/canonical/sitemap 错误。停止继续写入并按已记录范围恢复；构建或单测失败且尚未写线上时，无须恢复线上。

## 已准备的人工入口

原 `seo-static-canary` 入口增加两个明确动作，仍使用原共享队列，不新增分支，不向 main 放调度器。

- `blog-server-stage`：只创建独立文章服务。使用同一提交已通过 HTTP 检查的 CI 产物，核对每个文件、代码 SHA 和网站域名。临时服务带 `BLOG_PREVIEW_ONLY=1`，禁止收录，0.25 CPU / 0.5 GB，最多一实例，空闲缩到零；不升级现有套餐。响应丢失只记录结果待查，不再次创建。若服务已经存在，先停下来保存旧版本，不能覆盖。
- `blog-server-apis`：只扩展 admin 和 public-api 的程序。先从线上下载两份实际函数包并上传恢复资料，保留全部原配置；实际包和运行版本核对通过后再继续。既有恢复逻辑复用到两份程序，允许恢复本次刚写入且配置未改变的候选包，遇到未知包或配置变化则停止。文章发布/读取开关、网站路由、商品、同步、价格和业务记录都不改。

后面的开关切换、实际后台验收、Blog 路由接管和 A→B→A 不在上述两个入口中自动执行。各段必须先有真实检查结果，不能把“已提交服务创建”写成“网站已经接通”。包与运行健康接口都包含网站域名和版本，避免将 localhost 验收包送到正式入口。


后续开关入口 `blog-server-switch` 逐项修改允许的三个文章设置，其他环境变量、日志、runtime和程序包保持不动。initialize先暂停发布、选择直接发布方式、接通只读公开文章；publish仅在实际Blog域名和两个API运行版本都确认后开放人工发布；restore在这个入口中特指暂停新增发布，不撤回已有文章、不恢复数据库。真正恢复代码和网站仍走版本恢复流程。程序健康接口增加可公开的生效状态，避免只凭控制台显示的配置就判断已切换。

历史导航也有检查：普通HTTP刷新从当前公开记录读；浏览器恢复整页内存快照时重新请求。已验证正常加载不会循环刷新，模拟恢复事件会重新获取实际HTML。自动浏览器没有稳定命中真实BFCache，不能登记为该浏览器真实命中已验收。[Chrome说明](https://developer.chrome.com/docs/web-platform/bfcache-ccns)、[Web.dev说明](https://web.dev/articles/bfcache)。
