# 企微任务控制：源码与官方能力核对

2026-10-28。只读审计；没有修改 Hermes、Channel 或企微运行配置，没有向群发消息。本文件讨论的是销售业务任务控制，不是官网当前回答的停止按钮。

## 结论

建议采用“群里只看关键待办和异常，点卡片操作具体任务；详细讨论按需转机器人单聊”的交互。平时运行静默，查询时返回当前真实状态。无需每个阶段发一条群消息，也无需强迫销售每次进入网页。单独的播报身份可以有，但不需要再运行一个模型 Agent。

普通 `@机器人` 不能作为业务任务的暂停。现有网关的“中断当前任务”是会话中一轮模型执行的中断；Sales 任务的暂停、接管、恢复需要持久状态和专门的系统接口。两者不能混用。

引用消息可以帮助人选中任务，但当前协议与适配代码都不能保证提供“原被引用消息的 ID”。推荐按钮回调携带服务器登记的任务引用；引用标准通知正文中的服务器短引用作为备选，再校验客户、群、人员和任务。模型不能凭文字猜测后执行控制。

## 1. 为什么再 @ 一次会出现“正在中断”

已观察到 `deploy/patches/wa-gateway/run.py:5347` 默认选择 `busy_input_mode=interrupt`，可通过配置切换为 `queue` 或 `steer`。`5360` 起有旧 `busy_text_mode` 的兼容逻辑。`5880–5994` 在同一会话已有运行时决定如何处理新输入：

- interrupt：把新输入排入后续轮次，并调用当前模型实例的 `interrupt()`；通常在模型或工具的检查点退出。
- queue：原执行继续，新输入排队。
- steer：尝试把补充信息加入当前执行；无法接受时转排队。
- 正在驱动子 Agent 或压缩上下文时，普通输入的 interrupt 会降为排队。专门的 `/stop` 与 `/new` 另走处理路径。

`run.py:6062–6092` 生成 `Interrupting current task`、`Queued for the next turn` 等回执。这里的 “task” 是网关措辞，不能据此认定已更新销售任务表。`run.py:21315` 起监控的键是完整 `session_key`，不是 Sales 的 `task_id`。

会话键由 `run.py:3856–3884` 和 WeCom adapter `:575–582` 使用 `build_session_key` 生成，输入包括来源和配置；默认传入 `group_sessions_per_user=True`。本仓库没有所导入的完整 gateway/session 实现，不能进一步声称线上一定按哪个具体字符串格式切会话。能确认的是中断作用域按会话键管理，不按上百条业务任务逐一定位。

因此，即使销售只在群里问一句“做到哪里了”，现有 interrupt 模式也可能打断当前会话轮次。对于销售任务控制，应先由确定性的控制路由处理按钮或明确任务引用，和模型讨论通道分开；普通询问不取消后台业务任务。这是建议，尚未改代码。

## 2. 引用是否等于精准 task ID

目前不等于。

`deploy/patches/wecom_adapter_patched.py:499` 取的 `body.msgid` 是本次入站消息 ID，用于排重。`:550–559` 构造事件时，`reply_to_message_id` 被写成 `quote:{本次入站msgid}`；`:693–700` 只提取引用正文。`:952` 还明确不把这个 `quote:` 值当真正的回复目标。

官方 SDK 的 [QuoteContent 类型](https://github.com/WecomTeam/aibot-node-sdk/blob/main/src/types/message.ts) 也只有引用内容类型和正文/媒体，没有原消息 ID；`BaseMessage.msgid` 的说明是本次回调排重标志。不能设计成“企微一定返回原通知 msgid，所以服务器直接查表”。未来若平台新增字段，应另做实测和适配。

建议的选择顺序：

1. 卡片按钮回调中的 `task_id` 与 `event_key`，查询服务器已有卡片/任务映射。平台的卡片 task_id 是开发者设定的标识，不能直接信任为内部任务主键。
2. 引用标准通知中的不透明短引用，例如 `S-7K2Q`。短引用只负责定位，必须在服务器登记、具备足够随机性并绑定客户/群/任务；不能把短引用当权限凭证。引用正文可以伪造或复制，因此仍要认证操作人和核对任务。
3. 没有引用时允许按客户名、询盘标题等搜索，但只能显示获准候选，要求用户选择；不能默认操作最近一项或让模型在多个任务里猜。

“暂停”可以作用于所选任务的最新状态；“批准并发送”必须再绑定所看的收件人、发件人、正文、附件和版本。已经更改的旧卡片不得沿用旧批准。

## 5. 企业微信的三种接入不要混用

| 接入种类 | 能力与本轮设计边界 |
| --- | --- |
| Webhook 消息推送（旧称群机器人） | 用于程序向已配置群发标准消息。它不是现有双向长连接会话；仅有推送 Webhook 不代表可以收到群引用、按钮操作或机器人私聊。若用作单独播报身份，控制接收仍需另一个已配置的双向通道。官方配置页本轮抓取失败，不据镜像夸大其回调能力 |
| 智能机器人长连接 | [官方 SDK](https://github.com/WecomTeam/aibot-node-sdk) 提供群/单聊消息、模板卡片、按钮事件与主动推送。现有 Hermes adapter 用的就是这个协议方向，但未把卡片事件接进控制服务 |
| 自建应用 | 有独立的应用身份、消息 API 和 OAuth 用户识别流程。其卡片更新接口、接收范围与智能机器人协议不同，不能把自建应用接口直接套给当前机器人 |

官方 SDK 的 [事件类型](https://github.com/WecomTeam/aibot-node-sdk/blob/main/src/types/event.ts) 包含操作人、群与卡片的 task_id/event_key；[client.ts](https://github.com/WecomTeam/aibot-node-sdk/blob/main/src/client.ts) 支持向指定群或单聊发送，并要求收到卡片操作事件后在 5 秒内使用该事件上下文更新卡片。不能推导为“后台每次阶段变化都可以永久随意编辑任意旧卡片”。

当前 adapter `:410` 直接忽略 `aibot_event_callback`，所以就算画出按钮，现在也不会形成 Sales 控制操作。`:521–523` 注释说群无法主动 `APP_CMD_SEND`，而本次官方 SDK 明确描述支持群主动推送；这两个事实冲突，可能涉及适配器历史限制或线上差异。建议实现前用获准测试群做一次最小主动卡片/回调/用户身份/更新测试，不能把旧注释写成平台永久限制，也不能把官方声明写成当前部署已经可用。

- 智能机器人长连接：<https://developer.work.weixin.qq.com/document/path/101463>
- 消息推送配置：<https://developer.work.weixin.qq.com/document/path/99110>

## 6. 低噪音与交互可以同时做到

建议把三层分开：

1. **后台事实**：任务每次重要状态变更都持久记录；包括任务/运行、版本、操作者、原因、结果和时间。状态由系统事务更新，不由模型发一句“已停”代替。
2. **通知规则**：程序订阅持久事件，合并同任务短时间内多次变化，只把需要人处理的节点送进企微。普通读取、模型迭代、工具执行、重试、心跳均留后台日志。批量任务用摘要，异常按任务去重和限频。订阅或通知失败不回滚业务事实，也不重跑发信。
3. **操作回执**：卡片点击或引用命令必须回。先说明“已受理，正在暂停/对账”，最终根据数据库提交后的实际结果显示“已暂停/接管完成/未成功”；错误、无权限、目标不明也给明确答复。回执优先更新该次卡片或发给操作人，不给整个群重复广播所有讨论。

第一期可用一个“销售待办”群和同一服务身份处理标准卡片；不强制增加第二个 worklog 群。若客户必须把展示身份分开，可增设程序播报身份，但仍共用同一个任务服务与控制 API，不另起一套 Agent 状态。告警配置可以用不同接收人或群，不必创建会思考的告警 Agent。

详细沟通可在机器人单聊里完成，顶部明确显示当前任务，例如“正在讨论：Acme｜500套耳机｜S-7K2Q”。切任务须显式选择；个人上下文按用户+客户+任务隔离，有有效期，多任务不共享隐形的“当前任务”。群里点“讨论”后若无法自动打开带上下文单聊，就提示用户在单聊发送短引用，不把一个猜测的深链接当成保证存在的功能。单聊也应只返回请求的说明/改稿结果，不推模型推理或完整工具日志。

群内批准可以保留，但完整 HTML/附件仍需要实际预览。网页只在看完整内容时打开，尽量复用企微身份免重复登录；没有真实身份接线时宁可只读。最终是否可从单聊完成动作取决于用户绑定和权限，不能因为知道短引用就获得发送权。

## 7. 必须保留的边界测试

- 50 项任务并行时，对任务 A 的暂停不能中断 B，普通进度询问不取消 A；不能按“最近任务”默认操作。
- 引用被复制、短引用被猜中、群跨客户、用户无权限、卡片已过期：拒绝控制且有可读回执。
- 旧卡片仍可请求暂停最新同一任务；旧正文批准不能发送新版本；恢复不恢复此前批准。
- 暂停期间禁止新外部动作；模型可能在下个检查点才停止。provider 已接受的发送不能宣称撤回；结果未知时显示对账，接管不立即交出第二条发送通路。
- 重复回调和重复命令返回同一操作结果；通知重发不能导致邮件重发。
- 卡片更新的 5 秒窗口内先做及时响应；长时控制处理要另存受理/完成事实，不能为了赶窗口虚报已完成。
- 单聊权限/目标丢失时重新选择任务；不从此前自然语言猜测目标。
