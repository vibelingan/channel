# 企微销售助手：可完整走通的交互样稿 v2

2026-10-29。仅设计与本地演示，不改官网或 Hermes 产品代码，不连接企业微信、Resend、Apollo、模型或真实邮件。

优先用浏览器打开[单文件交互版](wecom-interactive-v2.html)，它已内嵌样式与脚本，单独保存一个文件也可浏览。维护源入口仍是[index.html](index.html)。页面默认“本期 MVP”，正常任务卡只有查看邮件、改稿/讨论和审阅发送；暂停、恢复、人工接管、终止放在顶部“后续控制 · 仅看设计”模式，第一期不实施。左侧任务 A 是 HTML 邮件加两个附件，任务 B 是纯文字无附件。

## 如何体验

1. **查看邮件**：原任务卡进入企微群内正文预览，显示完整收发件人、主题、正文及附件清单。带 HTML 和附件的邮件明确标为摘要，说明省略了什么。纯文字邮件 B 可直接在此核对后进入发送确认。
2. **查看完整邮件**：切到“邮件工作台 · 页面示意”，模拟 Resend 草稿或已鉴权预览。这里能看示例 HTML、内嵌图片及逐个附件；顶部可返回同一企微任务。它不是 Resend 实机截图，没有编造可访问的草稿直达链接，也不增加另一个发送入口。
3. **改稿/讨论**：卡片按钮先让助手在原群回复“请引用本条并输入意见”。下方查看器的“模拟手动引用”才展示已引用任务的可编辑输入框。真实企微客户端需要用户手动引用并 @助手；不声称机器人能自动填输入框、自动引用或开新群。
4. **提交改稿**：写下意见后，先给同任务的受理回执，再用演示按钮查看新稿 v4。生成结果使用固定样例文案，不是模型真的理解任意输入。旧 v3 保留，v4 必须重新核对。
5. **提出问题**：在输入框选择讨论示例，发送后得到同群建议。邮件仍保持原版本，不把普通问题自动变成改稿或发送。
6. **确认发送**：检查任务、版本、发件人、收件人、主题和附件。带附件的样例要求逐个示意核对；没有完成时明确说明缺哪一项，不开放确认发送。纯文字 B 无需打开外部页面。
7. **看返回结果**：确认后进入提交中。下方“演示后续结果”可分别体验服务受理、结果未知或明确未提交。服务受理不等于送达，送达也不等于对方已读。
8. **失败与重试**：结果未知只允许查询原操作；只有明确未提交才展示重试。重试保留同一邮件操作号，不把重新准备内容当成第二次发信许可。
9. **看旧卡片**：左侧可打开旧版本按钮，点击发送会明确拒绝，提供查看当前版本的路径。
10. **切换任务**：A/B 的意见、稿件版本、核对状态与发送记录独立。输入 A 的意见后切到 B，不会带过去；重新回 A，仍能看到其未发送的输入。

切换 MVP/后续方案或点击“重置示例”会清除样例状态。数据只存在浏览器内存，不是持久任务记录。

## 企业微信的实际能力边界

能力调查见 [WECom-CAPABILITIES.md](WECom-CAPABILITIES.md)。群 Webhook 不能承载任意 HTML/CSS 邮件 UI，也不能作为双向按钮事件接收器。当前接入方向的智能机器人支持原生模板卡片和按钮回调，但按钮样式受平台限制。本页圆角、布局、左侧任务导航和右侧说明属于设计查看器，不是可直接投放企微的 HTML。

顶部提供“原生卡片按钮示意”和“文字引用备选”两种体验。文字模式隐藏聊天里的卡片按钮，由查看器演示用户引用任务通知后说出操作。这是没有合适按钮能力时的退路，不表示单向 Webhook 自动获得了收消息能力；接收引用仍需已有双向通道。

原邮件 HTML、CID 内嵌图片和附件不能原样进入普通企微聊天。第一期可以只发正文摘要和附件清单，完整内容按需去原邮件平台或鉴权预览。图片/文件若单独发送，要另做格式转换、媒体上传、授权和终端效果验证。

完整工作台画面只负责查看与核对，本期同一封邮件默认经企微明确批准后由唯一发送通路执行。它不能隐藏或接管客户真实 Resend 账号的原生发送按钮，也没有验证真实平台的并行手工编辑/发送；发现原生变更或发送时必须使旧批准失效并核对，不继续覆盖或重发。

## 后续控制设计

“后续控制”模式保留完整点击路径：

- 暂停确认 → 暂停已受理 → 停止点已确认 → 明确恢复请求 → 新稿示意。暂停期间不再展示自动改稿/发送入口，旧批准不能继续使用。
- 人工接管 → 核对此前在途操作 → 接管完成 → 明确交回 → 重新准备。发送结果未知时不能点“接管完成”开第二条发送通路。
- 终止确认 → 终止已受理 → 本次运行已退出。终止不撤回已发邮件，也不恢复旧批准；第一期不实现群内入口。

这些状态都是未来设计样例，不是当前 Hermes 已有能力。短任务的一期范围优先依靠运行时限、工具次数、费用和有限重试；安全发送仍必须处理精确版本和未知结果。

## 实际检查

`node validate-prototype.cjs` 使用本机现有 Playwright 和独立临时 HTTP 服务。脚本自动分配回环端口，结束时关闭自己的浏览器和服务，不使用用户登录态。

最终完成 19 条真实点击旅程、36 个检查场景在 320、390、768、1024、1440 五档宽度下的 180 项布局检查，全部通过；0 页面 JS 错误，0 外部请求。结果与原型源码 hash 见 [validation.json](validation.json)。这不是企业微信服务已接收 payload、客户手机显示正确或真实发送验收。

实际查看了任务卡、正文预览、同群引用编辑、外部完整预览和发送确认的截图，未见横向溢出、文字裁切或按钮重叠。长内容允许页面正常纵向滚动。尚未验证真实企业微信终端、输入法、屏幕阅读器、账号身份或 API 回调。

## 设计依据与本轮修正

保留上一版设计作为独立历史稿，本轮只新增 v2。实际读过上一版原型与交付说明、官方能力调查和其消息/卡片限制；使用 UI/UX Pro Max 的 `chat loading error recovery confirmation accessibility` 与 `focus responsive mobile dialog form` 搜索，落实明确恢复路径、就地错误、44px 操作目标及焦点。群内核对用原生按钮或引用文字确认，不把HTML checkbox塞进群消息；网页附件核对才用网页表单。

具体修正：将“改稿按钮自动引用输入”改为“同群提示后由用户手动引用”；将“讨论完成就新建稿”拆成只回答建议与明确改稿；修复“核对发送结果”按钮落回任务页的错误，再跑完整旅程；把“已发送”拆成提交中、服务受理、结果未知、明确未提交和送达事件。按 humanizer 将这些变化写成具体动作与边界，没有把原型检查当成上线结果。

根agent另外对单文件交互版重跑同样19条旅程和180项布局，全部通过，见`validation-standalone.json`。本地预览服务只绑定回环地址，供当前Codex浏览器面板体验；没有对外发布。
