# 企业微信里能做到什么：邮件预览与任务按钮

2026-10-29，只读能力调查。本轮没有读取机器人密钥，没有向任何真实群发送消息，也没有修改 Hermes 或 Channel 产品代码。官方网页和官方 SDK 能证明协议能力，实际客户机器人的显示和回调仍需受控验收。

## 直接结论

企业微信可以显示原生卡片和操作按钮，也能发送图片、文件。上一版 HTML 样稿里的自定义按钮样式却不能原样搬进企微；客户端会按自己的原生模板绘制。群 Webhook 和 Hermes 当前使用的智能机器人长连接是两种接入，能力不能混用。

群 Webhook 没有“发送任意 HTML 邮件界面”的消息类型。它支持有限的 Markdown 等格式。自建应用的图文详情 `mpnews.content` 确实支持 HTML，这是用户记忆可能对应的功能，但它不等于群 Webhook 或当前智能机器人会完整渲染邮件的 HTML、CSS 和内嵌附件。

第一期建议保留“企微文字预览、明确的改稿意见、精确版本发送确认”。群里声明这是预览，显示附件数量和文件名；完整邮件及附件按需去 Resend 或已鉴权的成果预览查看。暂停、恢复和人工接管保留设计，第一期不接运行逻辑。

## 三种接入分别支持什么

| 接入 | 文字、Markdown、HTML | 图片与文件 | 按钮和回调 |
| --- | --- | --- | --- |
| 群消息推送 Webhook | 官方列有 `text`、`markdown`、`markdown_v2`；没有任意 HTML 消息。Markdown 只支持各自规定的语法子集 | 独立 `image`、`file` 消息；`news` 可带封面和链接 | `template_card` 仅文本通知与图文展示两类，支持链接跳转；它本身只发不收，不能把“确认发送”接成可信的业务操作回调 |
| 智能机器人长连接，当前 Hermes 接入方向 | 流式文字/Markdown回复，主动发送 Markdown、模板卡片及媒体；本轮官方 SDK 没有定义 `markdown_v2` 或任意 HTML 外发消息体，不能直接套用 Webhook 的类型 | SDK 有媒体上传、回复和主动推送，支持图片、文件、语音、视频；流式结束还可带图片项 | 有 `button_interaction` 等模板、按钮事件、`task_id`、按钮 `key` 及操作人 `userid`；Hermes 仍需把事件接到自己的服务并校验权限 |
| 企业自建应用 | 应用消息有文字、Markdown、卡片等；`textcard` 仅有限标签/内置样式，`mpnews` 图文正文可用 HTML | 原生图片、文件、图文消息，使用其应用接口与媒体身份 | 有应用自己的交互卡片及回调/更新协议；不是给现有群 Webhook 多加一个字段就能获得的能力 |

Webhook 这一行根据[企业微信消息推送官方文档](https://developer.work.weixin.qq.com/document/path/91770)核对；单向限制也见[腾讯 CloudBase 官方接入说明](https://docs.cloudbase.net/recipes/connect-wecom-webhook-cloud-function)。应用这一行依据[企业微信发送应用消息](https://developer.work.weixin.qq.com/document/path/90236)。长连接依据[企业微信团队官方 SDK](https://github.com/WecomTeam/aibot-node-sdk)。

本轮 `web.open` 对企业微信站点失败，但公开 HTTPS 请求实际返回了官方 SSR 正文；已剔除脚本和导航后读取相关段落。没有使用第三方文档镜像作为能力结论，也没有通过登录态读取后台配置。

## 按钮可以做，但外观与点击结果有边界

官方 SDK 的 `TemplateCardButton` 只有按钮文案、`key` 和有限 `style`。样式是原生枚举，不是任意背景色、CSS、圆角或布局。当前类型注释给出 `style` 为 1 至 4；按钮交互卡片列表最多 6 个，足够容纳“查看正文、改稿、确认发送”这类小操作集。实际尺寸、排列和不同终端的视觉仍由企微决定。[固定版本类型定义](https://github.com/WecomTeam/aibot-node-sdk/blob/80615b987ef69c6028ad764924609247c0725955/src/types/api.ts)

按钮可以触发自己的后端动作；跳外部页面则使用对应卡片跳转字段或链接。不能假设按钮事件会自动替用户填写输入框、自动引用一条群消息、打开任意自定义弹窗，或另建一个带上下文的私聊。

建议的“改稿”实际交互：点按钮后，机器人在同一群回一条带任务短号的提示：“请引用这条通知并 @ 我，说修改意见”。人引用后输入文字，服务从引用中的已登记任务短引用定位任务，再核对权限。原型可以提供“模拟引用”便于体验，但要注明这是演示器动作；真实客户端的引用由人完成。

卡片事件会携带本次事件 ID、机器人、群/会话信息、操作人，以及 `event.task_id`、`event.event_key`。它们适合查服务端已保存的卡片与任务映射；不是单凭收到这些字段就授权发送。当前官方 `QuoteContent` 仍没有可靠的原被引用消息 ID，所以普通引用要保留明确任务短引用或让人选择任务。[事件类型](https://github.com/WecomTeam/aibot-node-sdk/blob/80615b987ef69c6028ad764924609247c0725955/src/types/event.ts)、[消息与引用类型](https://github.com/WecomTeam/aibot-node-sdk/blob/80615b987ef69c6028ad764924609247c0725955/src/types/message.ts)

## 邮件内容和附件怎样预览

可在群里展示同一固定邮件版本的文字正文或安全摘要，清楚标示：

> 邮件预览 · Q-1042 · v3 · 尚未发送  
> 这是企微文字预览，邮件版式、内嵌图片和附件可能未完整展示。  
> 附件 2 个：产品规格.pdf、方案.pdf。  
> 查看完整邮件后，可回到本任务继续修改或确认发送。

纯文字且没有被截断或遗漏的简单邮件，可以在企微核对后确认发送。对于带附件、复杂版式或被截断的邮件，应提示具体未展示内容，并要求完成必要审阅，不能把文字摘要悄悄当作“完整邮件已看过”。批准始终对应确切收件人、发件人、正文、附件和版本。

图片可以单独发到企微，或按当前协议支持的图文方式组合。邮件中的 `cid:` 内嵌图不是公开图片 URL，不能直接拼进 Markdown 就保证显示；需要解析邮件资源、做授权检查后转为企微支持的素材。文件也能通过上传后作为独立文件消息发送，但这是另一份投递，不会自动继承邮件附件的版式、权限或线程关系。第一期仅列附件并提供完整查看入口就能避免这部分转换工程。

完整邮件入口应指向实际存在、已经验证的草稿/邮件路由或鉴权预览。不能按猜测拼一个 Resend 私有草稿地址，也不能把公开分享链接当作私有审批权限。原型展示“将打开 Resend 完整邮件”这一跳转过程即可，使用明确的演示页面，不伪称已登录客户的 Resend。

## 推送和更新不能照搬网页状态刷新

长连接 SDK 支持向指定群或用户主动推送 Markdown、模板卡片及媒体。其卡片更新方法要求使用对应按钮事件的 `req_id`，并在事件收到后 5 秒内响应；这不代表后台每个状态变化都可以无限期修改任意旧卡片。先给及时的受理反馈，长操作完成后另发简短结果通知；需要更新旧卡片的具体方案要按该接入的真实协议验收。[官方 client.ts](https://github.com/WecomTeam/aibot-node-sdk/blob/80615b987ef69c6028ad764924609247c0725955/src/client.ts)

Webhook 官方文档给出单推送每分钟 20 条上限，`markdown` 与 `markdown_v2` 内容各有 4096 字节限制；这些数字只适用于该 Webhook 接口，不能当作当前长连接所有消息的统一限额。相应地，完整长邮件应有截断说明和外部查看入口，不为了显示完整而拆成几十条刷群。不同终端对增强 Markdown 的支持也有版本要求，第一期优先使用基本文字/Markdown与原生卡片。[Webhook 官方限制](https://developer.work.weixin.qq.com/document/path/91770)

## 十来分钟的任务要不要做“终止”

可以先不做面向销售的暂停、恢复、接管和任务终止 UI。它们需要独立身份、任务定位、状态转换、在途动作与恢复语义，容易拖慢首个闭环。

但基础运行仍应有系统限制：总运行时限、模型轮次与工具调用上限、单任务费用/输出预算、客户并发与队列上限、重复步骤检测，以及失败后的有限重试。达到上限后保存失败原因与已有成果，通知负责人，不能无限循环。十来分钟是用户对普通任务的预期，不是当前系统已经具有的硬上限。

单独说“终止这个 task”只是一条指令输入。真正停止需要宿主终止计算、拒绝后续工具动作并保存结果；现有同会话新消息中断和 `/stop` 不等于安全终止指定业务任务。若将来确实需要，做一个最小的、只终止本次准备运行的高权限入口即可，仍不需要同时实现复杂的暂停恢复。当前按用户新范围保留设计，不开发这个控制入口。

“失败就重跑”适用于准备内容，但重跑应有新的运行身份，旧成果保留。已获批准或已提交给邮件平台的发送不能因重跑准备任务而再次执行；发送结果未知必须先对账。缩小控制 UI 不改变防止双发的要求。

## 本轮验证和实施前最小平台试验

本轮用示例数据做了 8 项本地 payload 一致性断言：消息类型、原生按钮字段、按钮数量、卡片与事件 task 引用、事件 key、操作人及 JSON 往返；全部通过。它只说明样例结构彼此一致，不是官方服务已经接收或实际终端已显示。没有向真实 Webhook 或长连接发送测试消息。

落地时由工程在获准的独立测试群完成以下最小验证即可，不把协议细节交给客户决定：

1. 发一条带任务短号的基本 Markdown 预览，检查手机/桌面及超长正文的省略提示。
2. 发一个三按钮原生模板卡片，验证“查看正文、改稿、确认发送”的实际外观与 callback；使用合成任务，发送动作仍走 dummy，不触达邮箱。
3. 核对回调身份、群、任务引用和按钮 key；重复事件不重复执行，旧稿按钮不能批准新稿。
4. 验证改稿提示仍在同一群；引用后意见只应用到那一任务，两个任务交替讨论不串线。
5. 如需文件，再发送一个无敏感内容的示例文件；不把能发文件误写成任意邮件附件已经自动预览。
6. 验证外部完整预览能返回原任务，链接复制不会授予权限；当前 API 不支持的卡片更新用新回执退路，不虚报成功。

当前 Hermes 适配器尚未接入销售卡片事件，旧代码还有群主动推送的历史限制注释，必须以这次受控试验验证真实部署，不能因为最新 SDK 有方法就宣布现有机器人已可用。
